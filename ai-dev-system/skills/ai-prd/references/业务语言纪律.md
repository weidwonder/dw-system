# 业务语言纪律

对话、问题和 PRD 成稿必须使用业务语言。内容只描述用户、业务角色、业务场景、业务流程、业务信息、业务规则、权限边界、经营指标、风险、兜底和可观察结果。

不得要求用户理解任何程序实现后才能回答问题；不得在 PRD 中设计程序组件、代码结构、通信方式、存储方式或技术框架。**唯一例外见 §取证出处豁免**。

## 常用翻译

| 不对用户说 | 改成业务问题 |
|---|---|
| 模块、服务、接口 | 涉及哪些业务能力、参与方和协作环节？ |
| 数据结构、字段、入参、出参 | 业务需要记录哪些信息？每项信息代表什么？用户会得到什么结果？ |
| 并发、幂等、重试 | 多人或多次同时操作时以什么为准？失败后是继续、等待还是转人工？ |
| 鉴权、权限模型 | 谁可以查看、发起、修改、撤销和审批？ |
| 性能、吞吐、延迟 | 高峰期业务量多大？最长可接受等待多久？ |
| 状态机、调度 | 业务会经历哪些阶段？什么条件下进入下一阶段？优先顺序是什么？ |
| 模型、提示词、输出协议 | 智能能力使用哪些业务信息、给出什么结果、如何判断结果可用？ |

## 内部取证与对外表达

内部可以读取 Engineering Context 卡片和代码（取证顺序见 `00-prd生成流程.md` §批 B）核实现状，但写入 PRD 前必须翻译成业务事实。引用可以保留为来源注记，正文不得出现需要业务用户解释的程序名词。

若用户主动提供技术方案，只提取其中的业务意图、限制和可观察结果写入 PRD；技术方案留给后续开发流程处理。

## 取证出处豁免

判据是**出处 vs 方案**：写"这条事实从哪来"是出处，写"用什么实现"是方案。出处准写，方案不准写。

- **MAY 出现**（仅此两处）：
  - UI 原型节的「样式依据」——设计 token / 主题变量的文件名、组件库名（antd、element、shadcn/ui、MUI、Vant 等）、同类现有页面的路径或链接（`UI原型纪律.md` §1 自查到什么就写什么）；
  - 现状节的**来源注记**——cite（`path#anchor @确认时间`）、代码位置、"用户口述"。
- **MUST NOT 出现**：这两处之外的框架名、类名、表名、接口签名、存储与通信方式，以及任何形态的技术选型主张——包括把组件库名写成"本次采用 X 实现"。
- 豁免只覆盖**名字与位置本身**：MUST NOT 就此展开组件库用法、版本要求或改造方案。

这两处是**可核对的取证出处**：删掉它们，下游无从核实现状，`UI原型纪律.md` §1 的自查结论也会失传。

## 成稿检查

- 每个问题是否能由业务负责人只凭业务知识回答？
- 每段正文是否说明“谁、在什么场景、按什么规则、得到什么结果”？
- 是否混入程序组件、数据结构或技术选型？有则删除并改写为业务约束（§取证出处豁免 列出的两处除外，它们 MUST 保留具体来源，MUST NOT 被改写成"沿用现有风格"这类不可核对的说法）。
- 智能能力是否写成业务输入、业务结果、人工兜底和质量标准，而不是模型实现？
