# PRD 生成流程（core）

> 用**批量提问**驱动：每批一次抛出该批全部问题，用户答完起草对应章节；只有对回复有疑问或有缺口时才再批量追问，否则直接进下一批。目标是少轮次成稿。
> 提问的具体问法见 `question-bank.md`；成稿骨架见 `assets/templates/`。

## 分流：先选模板（尽量别问）

先从用户已有材料（描述、Issue、聊天记录、旧文档）自行判定类型，判不准再问：

| 判据 | 模板 |
|---|---|
| 单点小改动 / 一个 Issue / 4 项 Triage 全否 | `assets/templates/lite-issue-prd.md` |
| brownfield 变更 / 在既有系统上加功能（默认） | `assets/templates/change-prd.md` |
| 整品 / 从 0 定义产品 / 需要用户旅程与成功指标 | `assets/templates/product-prd.md` |

> Triage 4 问（沿用 ai-dev-workflow）：①改 AI/LLM 行为？②改鉴权/安全/设备形态？③跨服务/迁移/不可逆？④改指标/业务规则/对外承诺？

## 4 批提问

### 批 A —— 立项（一句话结论 · 背景 · 目标 · 非目标）

一次抛全下列问题（按需增删），产出 PRD 前四节。**非目标是硬产出**。

- 一句话说清这次到底要做什么？做完的标志是什么？
- 为什么现在做？触发它的问题/机会/事故是什么？
- 产品目标有哪些（尽量可衡量）？
- **明确不做什么 / 不改什么？** 每个目标尽量配一条边界。
- （整品追加）目标用户是谁？核心用户旅程一句话？成功指标（量化）？

起草批 A 章节后，若非目标为空或目标不可衡量 → 就这两点再批量追问一次。

### 批 B —— 现状与边界（现状/当前逻辑 · 改动范围 · 不改的线上逻辑）

- 现在这块是怎么运作的？涉及哪些模块/服务/接口？
- 本次**改动范围**：新增什么、改造什么？
- **哪些线上逻辑明确不动？**（brownfield 护栏）

> **团队版**：现状不靠口述。先 `ctx find-scenes <关键词>` 取端到端全景，再 `ctx discover "<意图>"` 收窄，`ctx get-card <repo> [域]` 取权威事实，**预填现状草稿并附 cite**，然后让用户确认/纠偏。**禁止把愿景写成现状**——现状以代码为准。
> **个人版**：让用户口述现状，AI 就模糊处追问；无 ctx 也要显式区分"现状事实"与"我想要的样子"。

### 批 C —— 细节（详细行为/字段/规则 · 边界 case 与冲突）

- 逐条问清关键行为、数据结构/字段、触发条件、排序/优先级规则。鼓励**表格化**。
- 主动穷举**冲突与边界 case**：并发、迟到、依赖不满足、失败、过期、跨轮/跨端……把每个 case 的期望处理逼出来。

> 含 AI/LLM 行为（生成/总结/分类/检索/OCR/ASR/固定 prompt 流程）时，在字段/行为里额外问清：输入输出契约、失败兜底、评测口径——为后续 `ai-dev-workflow` 的 AI overlay 铺垫。

### 批 D —— 准出（验收标准 · 埋点与看板 · 风险与兜底）

- **验收标准**三分，逐条**可判定**：
  - 字段/结构验收（出参形态、兼容口径）；
  - 行为/调度验收（规则是否被正确执行）；
  - 端到端场景验收（给场景 → 给预期）。
- **埋点与看板**（团队版重、个人版可精简）：埋点要能回答哪些问题？关键指标带**公式**与统计粒度。
- **风险与兜底**：每条风险配一条兜底。

## 组稿

1. 按所选模板把四批产出拼装成完整 PRD，补流程图（mermaid）与 changelog。
2. 跑 `prd质量清单.md` 自检；不过则就缺项再批量追问或补写。
3. 写入 `docs/`（命名：变更 PRD → `<name>-PRD-YYYYMMDD.md`；整品 → `docs/REQUIREMENTS.md`）。
4. **团队版**：同步更新 `docs/index.md`（doc 治理要求）。
5. 收尾提示：这份 PRD 可作为 `ai-dev-workflow` Step 1 的输入，接着做 Overview / 技术 Spec。

## PRD 生命周期（两次动笔）

- **开发前**：本流程产出的是**意图**——变更 PRD 或整品 PRD 新章节，先于代码定稿；影响产品范围的变更必须先改 PRD 再动代码。
- **开发后（准出必做）**：需求实现验收后，把变更 PRD 中**改变了口径**的部分归并回整品 PRD（`docs/REQUIREMENTS.md`）：更新 Product Scope 能力状态；若用户旅程 / 成功指标被改变，**同步回填旅程叙事**——不能只翻状态位，否则旅程随迭代漂移成史前文档。归并后变更 PRD 加"已归并"头注原地转归档，不再作为平行真相源维护。
- **膨胀分层**：整品 PRD 过大时，主文档只留骨架（Summary / Success Criteria / Scope 状态 / User Journeys / FR 摘要），FR/NFR 明细与验收基线移入 `REQUIREMENTS-appendix.md`（附录从属主文档，冲突以主文档为准）；主文档永远单一，附录可按域再拆。**实现细节不进 PRD**——怎么做归 spec，代码现状归 card；PRD 的细节边界是"用户可感知的行为契约与验收口径"。

## 个人版 vs 团队版裁剪

| 批 | 个人版 | 团队版 |
|---|---|---|
| 分流 | 默认 lite / change | 认真判类型，跨仓倾向 change |
| A 立项 | 简化，但非目标仍必写 | 完整；整品追加旅程/指标 |
| B 现状边界 | 口述 + 追问 | **ctx 预填带 cite** + 确认 |
| C 细节 | 关键行为 + 主要 case | 全字段 + 穷举 case |
| D 准出 | 验收够勾验即可，埋点精简 | 三类验收 + 埋点公式 + 风险兜底 |
| 组稿 | 写 docs/ | 写 docs/ + 更新 index.md + 评审 |
