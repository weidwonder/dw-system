# PRD 生成流程（core）

> 用**批量提问**驱动：每批一次抛出该批全部问题，用户答完起草对应章节；只有对回复有疑问或有缺口时才再批量追问，否则直接进下一批。目标是少轮次成稿。
> 提问的具体问法见 `question-bank.md`；成稿骨架见 `assets/templates/`。
> 所有提问与成稿遵循 `业务语言纪律.md`，不得把程序实现问题交给用户。
> 涉及用户可见 UI 新增/调整时，额外遵循 `UI原型纪律.md`：先参考现有 UI，再输出独立 HTML 高保真交互原型。

## 提问三纪律（先于任何一批问题）

每批问题在抛出前必须过这三条，缺一不可：

1. **事实/决策分离——事实自己查，只把决策抛给用户。** 凡是能从已有材料（描述、Issue、聊天记录、旧文档）、代码（按 §批 B 的取证顺序：先用 `ctx find-scenes`/`discover`/`get-card` 查卡片并附 cite，卡片没覆盖再读源码并按该节标注）或本 skill 已加载内容查到的**事实**，MUST 先自己查清并写成草稿让用户确认，MUST NOT 拿去当问题问用户。问题清单里只允许出现**决策**：读完材料仍需用户拍板的取舍、偏好、边界。把可查事实混进提问 = 把"AI 偷懒没查"伪装成"需求不清"。
2. **每问尽量带草案，禁止编造推荐。** 有材料/代码依据时 MUST 附推荐答案 + 一句话理由（业务语言），让用户在"改一下推荐"而非"从零作答"上表态；依据不足时给 2–4 个典型候选 + 一个倾向；完全无依据的开放题（如首轮"这次到底要做什么"）MUST NOT 编造推荐，显式写"此题无推荐，需要你的输入"。推荐只是草案，决策权在用户；用户未回复某问时 MUST NOT 把推荐当作已确认。
3. **依赖分层，同层批量。** 组批时先看问题间的依赖：答案互不影响的问题（可并行）归入同一批一次抛全；某问的答案会改变后续问法的（依赖链），拆到下一层，等上一层答完再按答案组下一批。判据：**能并行的绝不串行，有依赖的绝不硬塞进同一批**——同批内出现"如果上一题选 X 则本题……"的分支句式，就说明该拆层。

## 分流：先选模板（尽量别问）

先从用户已有材料（描述、Issue、聊天记录、旧文档）自行判定类型，判不准再问：

| 判据 | 模板 |
|---|---|
| 单点小改动或单个 Issue，**且** 4 项 Triage 全否 | `assets/templates/lite-issue-prd.md` |
| brownfield 变更 / 在既有系统上加功能（默认） | `assets/templates/change-prd.md` |
| 整品 / 从 0 定义产品 / 需要用户旅程与成功指标 | `assets/templates/product-prd.md` |

> Triage 4 问（业务表达）：①是否改变智能能力给用户的结果？②是否改变谁可以做什么或敏感信息保护？③是否影响多个业务环节、历史数据或存在不可逆影响？④是否改变经营指标、业务规则或对外承诺？
>
> **Triage 任一为是 → 升级到 `change-prd.md`**，即便它只是"一个 Issue"、改动看着很小：轻量模板没有现状、改动范围与不改的现有业务三节，扛不住这四类影响面。

> **AI-native / Agent 产品的边界（重要）**：上面三个模板给的是 PRD 的"软件外壳"。若产品的**核心价值来自 AI 行为**（模型自主规划、直接调用工具/接口、跨会话记忆影响决策，或置信度/降级是产品级决策），本 skill 的模板**不足以**承载 AI 产品决策——你**必须额外补一张 AI Capability Card**（见批 C 的 AI 追问），写清自主程度、允许/禁止行为、置信度与降级策略、评测（eval）准出标准（自主程度用批 C 的四档：仅给建议 / 辅助操作 / 受控自动执行 / 高影响自动执行）；**Agent 类产品**还要逐档写明**审批闸门**（哪一档起必须有人把关、什么情况必须停下问人），并列一份**不回答清楚就不上线的问题清单**（如：它最坏能造成什么业务损失？如何一键停用？出错了谁负责向谁交代？）。这些属产品/安全决策，**必须在 PRD 定，不能下沉给工程 spec 补**。你所在团队若有自有的 Agentic 产品 PRD 规范，完整骨架以其为准——本 skill 不随包分发这类重型模板。

> **UI / 交互原型边界（重要）**：只要需求新增或调整用户可见页面、组件、入口、状态、信息层级或交互路径，MUST 补一个 HTML 高保真交互原型（**不改结构与交互的纯文案改动豁免**，在 PRD 写清改动前后文案即可）。样式依据**先自查代码里的设计 token / 组件库 / 同类现有页面**，查不到才向用户要材料。原型 MUST 可离线打开（单文件、零外链），用于体验对齐，不是给 PM 解释设计思路的文档页：屏幕内只放真实用户会看到的内容；设计说明、样式依据、开放问题放画布外。原型与 PRD 一并作为 `ai-dev-workflow` 的输入，下游按它落用户可见行为。若确认不涉及 UI，PRD 写明“不适用 + 原因”。

## 4 批提问

> **每批都有退出条件，写在该批小节末尾**：退出条件全部勾验通过才进下一批；任一不通过 → **只就不通过的那几点再批量追问一次**，MUST NOT 整批重来。
> **追问一次后仍未闭合的点，MUST 转成显式的「开放问题」**（写清问题源自哪里、卡住谁的决策）后进下一批：MUST NOT 无限追问，MUST NOT 静默略过，也 MUST NOT 就此卡住不前——用户说不出可衡量目标、说不清特殊场景处理都是常态。开放问题在成稿前按 `collab/` 的规则闭环（solo 自己逐条拍板，或按下面这条分流落位；team 挂评审）。**落位 MUST 分清两个去处**：本次及可预见的将来都不做 → 写成**非目标**（当前边界）；这次不做、以后想做 → 写进 `docs/TODO.md` 的〈想做的功能〉。**MUST NOT 一律塞进非目标**——那会把「还没做」记成「故意不做」，且随本 PRD 归档一起消失（判据见 `<skills 根>/ai-dev-workflow/references/core/文档治理.md` §TODO 出口），并在 `prd质量清单.md` §质量（对照纪律）的「开放问题清单已按协作面结算」一项上被验收。
> **例外——三项硬产出 MUST NOT 转成开放问题**：批 A 的**一句话结论**、**做完的标志**、**非空且具体的非目标**是"不准成稿"的前置（非目标见 `prd写作纪律.md` §1；一句话结论与做完的标志见 `prd质量清单.md` §完备性（对照骨架）第 1 项），把它们转成开放问题只是把死锁原样搬到组稿（组稿照样过不了质量清单）。这三项追问一次仍闭不上，恰好命中 §盘问模式 的进入条件（"用户只有一个念头/一句话，说不出做完的标志"、"方向性决策（做不做、给谁做、边界在哪）尚未定"）→ **MUST 转入 §盘问模式** 收敛方向，收敛出一句话结论 + 做完标志 + 首批非目标并获用户确认后回批 A 起草，**MUST NOT 带着这三项进批 B**。盘问仍受该节 SHOULD ≤ 5 轮的上限约束，超上限按该节处置（建议用户先做探索，不硬写），**同样不允许改判成开放问题**。
> **缺口判据取并集**：`question-bank.md` §追问触发 是**追问触发**的权威判据（什么情况必须回头再问），四批与组稿共用同一份；该节每条都带批次标签（`[A]` `[B]` `[C]` `[D]` `[组稿]`，另有 `[组稿·复核后]` 是 `[组稿]` 的子类，勾验时机推迟到复核门跑完之后），勾验某批时只看标记为本批的条目，**MUST NOT** 拿别的批次的条目卡本批，也 **MUST NOT** 自行另立追问标准。各批退出条件是**准出**判据（本批交出的东西够不够进下一批）。两者**取并集**：§追问触发 里本批条目命中，**或**本批退出条件任一项不过 → 都 MUST 就该点再批量追问一次；**MUST NOT 因为某个退出条件项在 §追问触发 里没有对应条目，就判定它"不构成缺口"直接放行**。
> **退出条件按所选模板判适用**：三类模板骨架不同，退出条件里指向具体章节的项，适用范围以 `prd质量清单.md` §完备性 的「三类模板 × 必备节」矩阵为准——矩阵标"不适用"的章节，对应退出条件项本批**跳过不勾验**（MUST NOT 因它卡住不前）；标"由 X 承载"的，判据落到 X 节。MUST NOT 为过某一项，把变更 PRD 的重章节硬塞进轻量 / 整品模板。

### 批 A —— 立项（一句话结论 · 背景 · 目标 · 非目标）

一次抛全下列问题（按需增删），产出 PRD 前四节。**非目标是硬产出**。

- 一句话说清这次到底要做什么？做完的标志是什么？
- 为什么现在做？触发它的问题/机会/事故是什么？
- 产品目标有哪些（尽量可衡量）？
- **明确不做什么 / 不改什么？** 每个目标尽量配一条边界。
- （整品追加）目标用户是谁？核心用户旅程一句话？成功指标（北极星，量化）？

**批 A 退出条件**（逐项勾验，全过才进批 B）：

- [ ] 一句话结论与"做完的标志"都已写出，且已被用户确认。
- [ ] 非目标**非空**且具体（不是"不做优化"这类空话）。
- [ ] 非目标里**没有混进「以后想做」的条目**——那些 MUST 改写进 `docs/TODO.md` 的〈想做的功能〉，非目标只留当前边界。
- [ ] 每条产品目标可衡量（有数值、比例或可观察的业务结果）。
- [ ] （整品）目标用户、核心用户旅程一句话、成功指标三项齐。
- [ ] `question-bank.md` §追问触发 里**标记为本批**的条目均未命中（带其它批次标签的条目本批 MUST NOT 勾验）。

任一不过 → 只就不过的那几项再批量追问一次（如非目标为空或目标不可衡量，就只追问这两点）。

### 批 B —— 现状与边界（现状/当前逻辑 · 改动范围 · 不改的线上逻辑）

- 现在这项业务由哪些角色参与，经过哪些环节，各方如何协作？
- 本次**改动范围**：新增什么、改造什么？
- **哪些现有业务流程、规则和职责明确不动？**（既有业务护栏）
- （涉及 UI）样式依据：**先自查**项目里的设计 token（`tailwind.config.*`/`theme.*`/`variables.css`/`*.tokens.json`）、组件库依赖、同类现有页面，把查到的样式基线写成草稿让用户确认；**查不到才问**用户要最接近的现有页面链接或截图，仍没有就按临时视觉假设推进。查得到却拿去问用户 = 违反提问三纪律第 1 条。

#### 现状怎么取证（一条路径：先查卡片，卡片没有就读源码）

**装了本体系的项目一律维护 `engineering-context/` 卡片层**（registry + cards）——它是必备资产，没有分档、没有开关。因此现状取证**只有一条路径**：先查卡片，卡片没覆盖就读源码。本 skill 内「只在此处定义」这条顺序，其余各处一律引用本节。

本节**唯一要探测的是代码图谱**：项目根下 `.codegraph/codegraph.db` 是否存在。它只决定第 2 步"读源码时怎么定位"，**MUST NOT 用它决定要不要查卡片**。探测失败（权限不足 / IO 错误）时按"没有图谱"处理并一句话告知原因，MUST NOT 阻断流程、MUST NOT 反复重试。

**MUST NOT 把下面几件事读成"这个项目没有卡片层、可以直接读代码"**：

- `engineering-context/` 目录还不存在——骨架由姊妹 skill `ai-dev-workflow` 在初始化时建（本 skill 不写文件，见第 3 步），缺目录只意味着还没跑过初始化；照常按第 1 步查，查不到走第 2 步；
- registry 只有 `【】` 占位行 / `ctx list-services` 为空 / `scenes/` 为空 —— 这是**正常起步状态**，MUST NOT 因此告警、提示用户建资产，或判定这一层不可用；
- `ctx` 命令跑不通 —— 见第 1 步的兜底调用方式。

**第 1 步 —— 先查卡片（MUST 先做）**

1. `ctx find-scenes <关键词>` —— 除非任务已限定到单一 repo，先取端到端业务全景，避免漏跨服务链路；
2. `ctx discover "<意图>"` —— 收窄到应加载的权威条目；它给出的 **out-of-scope 提示**（哪些是废弃/中间产物）MUST 抄进 PRD 的现状与非目标节；
3. `ctx get-card <repo> [域]` —— 取该仓权威事实（职责/对外接口/上下游/废弃标记）；
4. `ctx search-semantic "<自然语言>"` —— `discover` 未命中时的兜底；
5. 命中的事实**每条附 cite**（`path#anchor @确认时间`），用它预填现状草稿再请用户确认/纠偏。**无 card 依据的 cite 视为幻觉，MUST NOT 编造。**

命令找不到时 MUST NOT 判定"没有可信事实"，用 `node <skills 根>/ai-dev-workflow/scripts/ctx/src/cli.js <命令>` 兜底。
`<skills 根>` = **本 SKILL.md 所在目录的父目录**——Claude Code 下是 `.claude/skills/`、Codex 下是 `.agents/skills/`，**MUST NOT 写死其中一侧**（写死 `.claude/` 会让 Codex 侧照抄即 ENOENT）。
**`ctx` CLI 随姊妹 skill `ai-dev-workflow` 分发，`ai-prd` 自身不带**——本 skill 的 `scripts/` 下只有原型预览服务 `preview.mjs`（见 `UI原型纪律.md` §7.4），**没有 ctx**，在本 skill 目录里找 ctx 一定落空。
**`ctx` 与 `node` 兜底都执行不了时**（两条都报错，不是"零命中"）：一句话告知用户原因，直接进第 2 步，MUST NOT 阻断流程、MUST NOT 反复重试。

**第 2 步 —— 卡片没覆盖就读源码**

零命中、或卡片没覆盖到本次要用的模块，**只意味着这个模块的卡片还没建**。MUST NOT 据此停下等资产补齐，MUST NOT 凭空写现状。处置：

- 项目根存在 `.codegraph/codegraph.db` → SHOULD 先走**代码图谱**（MCP 工具或 `codegraph` 命令，子命令以工具自身说明为准）查符号、调用链与影响面；
- 没有图谱、或图谱不可用 → 把重探索**外包给子代理**，主会话只收结论；
- 两种情况都 **MUST NOT 裸 grep 全仓**——"裸 grep"指没有收窄目标、没有外包给子代理、命中内容直接灌进主上下文的全仓扫描；**收窄过的定位式检索不受限**；
- 这一步得到的每条事实 MUST 带 `文件:行`。

代码图谱回答的是"**找得到吗**"，卡片回答的是"**信哪个**"，两者正交：MUST NOT 拿图谱结果冒充权威口径，也 MUST NOT 因为没有图谱就跳过读源码。图谱自身的判据与降级见姊妹 skill 的 `<skills 根>/ai-dev-workflow/references/capability/graph.md`；**该文件属姊妹 skill，本流程按上面几句执行即可，不必为此加载它**。本文 MUST NOT 展开成 codegraph 使用手册。

**第 3 步 —— 把"本次现读源码才搞清楚的模块"在 PRD 里标出来（MUST）**

**本 skill 不写文件，因此 MUST NOT 自己补卡片**：不建 `engineering-context/`、不改 `capability-registry.md`、不写 `cards/`，也 MUST NOT 提示用户去建。补卡是下游的动作——`ai-dev-workflow` 在 Step 1 读源码后当场补卡，判据与最小形态见 `<skills 根>/ai-dev-workflow/references/core/代码事实纪律.md` §4。

本 skill 的职责是**把交接面写清楚**：凡本次是现读源码才搞清楚的模块，MUST 在 PRD 现状节列出模块名与取证到的 `文件:行`，并原文照抄下表标注：

| 情形 | 现状节 MUST 出现的标注原文 |
|---|---|
| 有模块是本次现读源码才搞清楚的（卡片尚未覆盖） | `本次现读源码取证：<模块清单>；这些模块尚无 card，待 ai-dev-workflow 按代码事实纪律 §4 补卡` |
| 连代码都无法核实，只有用户口述 | `现状未经代码核实` |

两条标注 MAY 同时出现（不同条目走了不同路子）。带上适用的标注即视为满足 `prd质量清单.md` 的现状取证项——**现读源码的条目不要求带 cite，但 MUST 带 `文件:行`**。

**真相方向铁律（MUST，不因路径合并而放松）**：card 事实 **MUST 以合入后的源码为准，MUST NOT 从 PRD 生成**——PRD 描述意图，意图常与已落地事实背离（典型："PRD 说可复用，查代码发现不可复用"）。PRD 在这条链路上只做两件事：**约束 scope** 与**补业务语境**。下游据第 3 步的标注补卡时 MUST 回到源码核对，MUST NOT 把 PRD 现状节的文字抄成 card。见 `<skills 根>/ai-dev-workflow/references/core/代码事实纪律.md` §9。

**grep 的边界（收窄，不是全面禁止）**：已有 card 覆盖的能力，MUST NOT 用 grep / 全文检索的结果**代替** card 事实——可以用检索辅助定位，写进 PRD 的事实必须回到 card + cite。

**硬线**：

## 盘问模式（需求高度模糊时的前置收敛）

批量提问假设"需求形状已基本清楚，缺的是细节"。若不满足这个前提，先进盘问模式把方向收敛，再回到 4 批流程。

- **进入条件**（任一命中）：用户只有一个念头/一句话，说不出做完的标志；批 A 抛出后过半问题答"不知道/都行"；用户的目标之间互相矛盾；方向性决策（做不做、给谁做、边界在哪）尚未定。
- **行为**：不再整批抛问。每轮只抛**当前最阻塞的一层决策**（1–3 问的小批，仍遵守提问三纪律：附推荐答案、可并行的并在同层），问透一条决策链再开下一条；主动挑战站不住的理由、把用户没说出口的隐含假设摆到明面确认，不接受"应该没问题"这类含糊保证。
- **退出条件**：一句话结论 + 做完标志 + 首批非目标能被用户确认 → 立即退出盘问模式，回到批 A 正常起草。盘问轮次 SHOULD ≤ 5 轮；超过说明需求还不到写 PRD 的时候，建议用户先做探索（原型/调研），不硬写。
- **禁止**：把盘问模式当默认（默认永远是批量）；在盘问中问可自查的事实；一轮只问一个本可并行的问题。

## 案例（一批长什么样）

**案例 1 — 批 A 批量提问（含推荐答案）**。输入：用户说"给作业辅导加错题重练"。一次抛全（每问带推荐）：

> 1. 一句话结论确认：本次是"学生在作业辅导里对错题一键发起重练"？做完的标志 = 学生能从错题入口发起重练并得到新一轮辅导？（推荐：是——依据你的描述与现有辅导流程）
> 2. 为什么现在做？（推荐：错题复练率低的运营反馈——若另有触发请纠正）
> 3. 目标怎么衡量：错题重练使用率 / 重练后正确率要到多少？（此题无推荐，需要你的输入）
> 4. 非目标：本次不改判题逻辑、不动错题本的收藏结构，对吗？（推荐：不改——两者均为既有稳定流程）

用户答完即起草前四节；仅"目标定多少"仍缺 → 只就该点追问一次，不整批重来。

**案例 2 — 盘问模式一轮**。输入：用户只有一句"我想做个学习激励的东西"，说不出做完的标志 → 命中进入条件。第一轮只抛最阻塞的一层（1–3 问）：激励谁（学生/家长/老师）？激励什么行为（完成作业/坚持打卡/成绩提升）？（附倾向：学生完成作业——从产品主线推断）。用户答"学生坚持打卡"后，下一轮再问打卡的定义与边界；收敛出一句话结论 + 首批非目标并获确认 → 退出盘问，回批 A 正常起草。

## 组稿

1. 按所选模板把四批产出拼装成完整 PRD，补流程图（mermaid）与 changelog。
2. 涉及 UI 时，按批 C 的 UI Prototype Brief、`UI原型纪律.md` 与 `assets/templates/ui-prototype.html` 生成独立 HTML 原型（**全流程只在这一步生成，批 C 不生成**）。生成方式 MUST 走 `scripts/preview.mjs` 的 `init` → `screen` → `slot` 三条命令（命令表在 `UI原型纪律.md` §8.1），**MUST NOT 手工复制容器再逐行替换**，更 **MUST NOT 为动手而通读容器**——容器不含任何示例内容，通读只会把它的实现细节带进你的产出（判据在 `UI原型纪律.md` §7.1、§8）；对某个具体元素的说明 MUST 写成该元素上的 `data-anno` 气泡而不是画进屏幕（§7.2），需要用户拍板的那些 MUST 标成 `data-anno-kind="question"`（§7.3）。交给用户之前 MUST 跑 `preview.mjs check <原型文件>` 且无 P0（§6）。PRD 中只链接原型文件并说明覆盖路径、样式依据和关键状态。原型此时仍**只在对话里**，与 PRD 一起等第 6 步的落盘确认门，门过了才随第 7 步一并写入 `docs/spec/`。
3. 跑 `prd质量清单.md` 自检，并在此勾验 `question-bank.md` §追问触发 里标记 `[组稿]` 的条目（4 批不勾验它们；**`[组稿·复核后]` 子类除外——它们描述的是第 5 步复核门的产出，此刻还判不了，勾验时机见 `question-bank.md` §追问触发**）；不过则就缺项再批量追问或补写。
4. **用户过稿门：请用户读稿提意见，用户定稿了才往下走**。把 PRD 全文与（涉及 UI 时）原型摆给用户，用**业务语言**明确请他提修改意见。本门收的是**用户的意图**，**MUST NOT 在此夹带复核结论**（复核门还没跑），也 MUST NOT 把它当成落盘确认门的提前版——两者参照物不同，见第 6 步。**原型此刻仍未落盘**：MUST 以**预览副本**形式交给用户打开（系统临时目录，或用户明确指定的项目外位置），**MUST NOT 写进 `docs/`**；正式文件在第 7 步落盘。

   - 用户提的每条意见 MUST 逐条落进稿子，或明确回"不改 + 一句话理由"，**MUST NOT 默默忽略**——沉默的忽略无法与遗漏区分。
   - **涉及 UI 时 MUST 同时告诉用户可以直接在原型上批注**：顶部工具栏「＋ 加注释」点选元素写意见、「全局反馈」写整体意见。**预览服务由你后台起、也由你停，MUST NOT 交给用户操作**：后台跑 `node <skills 根>/ai-prd/scripts/preview.mjs <预览副本>`，把它打印的 `http://127.0.0.1:<端口>/` 交给用户打开（批注自动写回文件，用户零操作），**MUST NOT 要求用户自己起服务、也 MUST NOT 要求用户按 Ctrl+C 收尾**；只有在服务起不来时才退回让用户手动「保存到文件」，那时 MUST 说清不点就写不回文件、AI 读不到（判据在 `UI原型纪律.md` §7.4）。收回意见时 MUST 跑 `node <skills 根>/ai-prd/scripts/preview.mjs annotations <预览副本>` 取批注（一次给出用户逐元素批注、全局反馈与你自己写的 `data-anno` 说明，每条带所在屏与元素标签；**MUST NOT 为此通读整份 HTML**），把批注与对话里的口头意见**合并成一份清单**逐条处理——批注与口头意见同等对待，**MUST NOT 只处理对话里说过的那些**。
   - 意见改动触碰模板骨架时（增删节、改验收项、改非目标）MUST 重跑第 3 步受影响的勾验项，然后**回到本门**再请用户过，直到用户定稿。
   - **怎样算"定稿了"**：判据与第 6 步落盘确认门的三条判据**是同一套**（逐点回复或整体认可 → 定稿；只回了一部分 → 只就未回的那几项再问一次；**没有回复 → 停在这里等**，一句话告知，MUST NOT 反复追问、更 MUST NOT 自行判定为定稿往下跑），**MUST NOT 另立一套**。

   **为什么这道门排在复核门之前**：复核报告是针对**某一版稿子**的。用户还没读过就派子代理，用户随后的意见会让整份复核结论作废——白跑两个子代理不算最坏，最坏是主会话带着"这稿已复核通过"的印象接受了大改，改出来的那部分从头到尾没有被任何第三方视角看过。先定稿再复核，复核的就是要落盘的那一版。
5. **复核门：派子代理跑双轴复核**（判据与 prompt 模板见 `prd复核纪律.md`，本步不复述）。**起过预览服务的，MUST 在派子代理之前把它停掉**（结束你后台起的那个进程）——用户已在第 4 步定稿，服务再开着，用户之后写的批注会落进一份正在被复核的稿子，报告与文件对不上；停服务之前 MUST 最后跑一次 `annotations` 收干净。`change-prd` / `product-prd` 派 2 个并行子代理（自洽轴 / 冲突轴各一），`lite-issue-prd` 派 1 个跑两轴精简版、报告仍分两节。**这道门夹在用户定稿与落盘确认门之间，两边都不能挪**：挪到用户定稿之前，复核的是一版随时会被推翻的稿子（理由见第 4 步）；挪到落盘确认门之后，则文件已进 `docs/spec/` 与索引、下游可能已开跑，而冲突轴查出的东西几乎全要用户拍板（"系统现在是 A，你要的是 B"），落盘后再摆出来已经晚了。

   复核结论 MUST 逐条走**三个出口**之一（①当场改稿 ②回流到对应那一批 ③并入下一步的回述清单），**MUST NOT 悬空**；每个出口的适用范围与两条 MUST NOT 见 `prd复核纪律.md` §严重度与处置，本步不复述。P0 与 P1 全部处理完才算过门。
6. **落盘确认门：先取得用户确认再落盘**。把关键取舍、非目标、验收口径回述给用户；涉及 UI 时同时回述原型覆盖范围和样式依据，并 MUST 把原型里 `data-anno-kind="question"` 的待拍板项**逐条摆出**（用 `preview.mjs annotations` 取，MUST NOT 让它们跟着原型静默进库）；已被用户回复的待拍板项 MUST 连回复一起摆出供确认，MUST NOT 当成没答过重新问一遍；**上一步复核门标记为「需用户拍板」的每一条 MUST 在此逐条摆出**（与现有系统的冲突、两个选项各自的业务后果、你的推荐）；并 MUST 逐条列出**用户第 4 步定稿之后稿子被改了什么**（复核门带来的当场改稿与回流改写）——用户定的是旧那一版，不列等于让他确认一份自己没读过的稿。**达成共识后才写文件**——不要在用户还没确认的情况下就当成定稿交付。**门管住的是 PRD 与 HTML 原型两个文件**：任一在确认前落到 `docs/spec/` 都算绕门。

   **本门与第 4 步用户过稿门 MUST NOT 互相顶替**：那道门的参照物是**用户自己的意图**（他要的东西写对没有），本门的参照物是**复核门交上来的待拍板冲突与关键取舍**（要的东西与现有系统撞了没有）。第 4 步定过稿 MUST NOT 被读成"本门可以跳过"，本门确认过也 MUST NOT 被读成"用户其实读过全文了"。

   **复核零发现时本门退化为一句话告知**：第 4 步刚定过稿，若复核门既没有交上「需用户拍板」的条目、也没有产生任何**实质性改稿**（改动了目标 / 非目标 / 现状结论 / 详细业务行为 / 验收项中的任何一处即为实质性；只在现状节补出处标注这类纯取证补录**不算**），则本门 MUST 退化为一句话告知（"双轴复核无发现，按你定的那一版落盘"，补过标注的一并带出）并直接进第 7 步，**MUST NOT 把同一份稿子再摆一遍、要用户点第二次头**。反之，只要有待拍板条目**或**有实质性改稿，本门 MUST 完整走一遍，MUST NOT 借这条退化规则省掉。

   **怎样算"确认了"（三条判据，MUST 照此判，MUST NOT 自行解释；第 4 步用的也是这三条）**：
   - 用户逐点回复，或明确说"就按你说的走 / 没问题 / 可以落盘"这类整体认可 → **算确认**，落盘。
   - 用户只回了其中一部分 → **只就未确认的那几项再回述一次**，已确认的不重复问；MUST NOT 因为部分未确认就整份重来。
   - **用户没有回复** → MUST NOT 落盘正式路径，也 MUST NOT 反复追问。把当前稿留在对话里，一句话告知"等你确认后我再写文件"，然后停在这里等——本门与第 4 步用户过稿门是**仅有的两个**允许因等用户而挂起的点（它们是门，不是对齐开销）。
7. 落盘（命名：变更 PRD → `docs/spec/YYYY-MM-DD-<name>-PRD.md`；**轻量 Issue PRD → 与变更 PRD 同一命名 `docs/spec/YYYY-MM-DD-<name>-PRD.md`**，只是模板不同，MUST NOT 另造一套命名；UI 原型 → `docs/spec/YYYY-MM-DD-<name>-prototype.html`；整品 → `docs/REQUIREMENTS.md`，唯一真相源放 `docs/` 根）。落盘的是**过完第 6 步那一版**，MUST NOT 落第 4 步用户看过的旧版，也 MUST NOT 把第 4 步的预览副本当正式文件挪进 `docs/`（预览副本落在项目外，路径与命名都不作数，MUST 按本步命名重新写出）。**原型 MUST 以预览副本为准整份落盘**：用户写的批注与界面上的 `data-anno-user` 锚点是需求的一部分，随原型一起进 `docs/spec/`，下游 `ai-dev-workflow` 按它们落用户可见行为；MUST NOT 重新生成一份干净原型顶替，也 MUST NOT 在落盘前清空批注块。已在稿子里落实的待拍板项 MAY 由你就地去掉 `data-anno-kind="question"`（气泡回落为普通说明），但 MUST NOT 删掉说明本身、更 MUST NOT 删用户批注条目。

   **目标文件已存在时**（同一天二次运行、同名需求、整品 PRD 已在）：**MUST 先读取该文件**，再向用户确认三选一——覆盖 / 改名（同名加序号，如 `YYYY-MM-DD-<name>-PRD-2.md`）/ 在原文件上增量更新；**MUST NOT 直接覆盖**，也 MUST NOT 不读就往里追加。PRD 与 UI 原型两个文件各自适用本条。
8. **项目有 `docs/index.md` 时**：MUST 同步更新（doc 治理要求）——**PRD 与 UI 原型都要进索引**，原型与 PRD 同条目并列标注。索引只放现行口径，PRD frontmatter 带 `lifecycle: active`；归档进 `docs/index-archive.md`（见下方 §PRD 生命周期）。项目**没有** `docs/index.md` 时，MUST NOT 为了本次落盘临时造一个索引，只做 frontmatter 一个动作（呼应 `<skills 根>/ai-dev-workflow/references/core/文档治理.md`）——新 PRD 首次落盘就是 `lifecycle: active`，此刻没有任何可归档对象；**归档头注属实现验收后的结算动作**，见 §PRD 生命周期。
9. 收尾提示：这份 PRD **连同 UI 原型**一并作为 `ai-dev-workflow` Step 1 的输入，接着做 Overview / 技术 Spec；告诉用户下游会按原型落用户可见行为，原型与 PRD 正文冲突会被立为开放问题。

## PRD 生命周期（两次动笔）

- **开发前**：本流程产出的是**意图**——变更 PRD 或整品 PRD 新章节，先于代码定稿；影响产品范围的变更必须先改 PRD 再动代码。**但 MUST NOT 在实现验收之前把本次口径写进整品 PRD**：那时它还只是意图，可能中途被推翻，写进去等于让真相源描述一件尚不存在的事（判据在 `<skills 根>/ai-dev-workflow/references/core/文档治理.md` §三层真相源）。
- **开发后（准出必做）**——需求实现验收后分三步：

  1. **归并口径**：把变更 PRD 中**改变了口径**的部分并回整品 PRD——**落点按"本次改变了什么"分派，权威定义在 `<skills 根>/ai-dev-workflow/references/core/文档治理.md` §6，MUST 照那张表逐类过一遍**。最易漏的一类是**已交付功能的行为规则变了而功能清单一动不动**（次数上限、权限范围、报错口径）：它归对应的一级子模块 `docs/requirements/<模块>.md` **就地改写**，**「功能清单没变化」MUST NOT 被读成「无需归并」**。旅程与成功指标被改变时**同步回填旅程叙事**，不能只在功能清单上增删一行就收工，否则旅程随迭代漂移成史前文档。**就地改写 MUST NOT 留前后对比**——真相源只写现状，"原来是 3 次"属于历史，去归档索引翻那份变更 PRD。
  2. **变更 PRD 转归档**：文件**原地不动**，三个动作在同一次提交里做完——frontmatter 标 `lifecycle: merged` + `archived: <日期>`、正文首行加"已归并"头注、从 `docs/index.md` 移入 `docs/index-archive.md`。归档后不再作为平行真相源维护。头注格式见 `<skills 根>/ai-dev-workflow/references/core/文档归档与账本收敛.md`。
  3. **UI 原型不随变更 PRD 归档**：它留在原地并升级为该能力的**现行界面依据**，整品 PRD 的 UI 原型节与 `docs/index.md` 指向它，供后续需求作为"现有 UI 样式依据"直接继承。只有当界面被后续需求改掉时，才由新原型接替——旧原型页面顶部加可见横幅"已被 <新原型> 取代"并移入归档索引（见 `UI原型纪律.md` §4.5）。
- **膨胀分层**：整品 PRD 过大时，主文档只留骨架（这是什么 / 为什么做 / 功能清单 / 用户怎么用 / 明确不做什么 / 成功标准 / 子模块划分），用户可感知的具体行为规则移入**一级子模块** `docs/requirements/<模块>.md`（子模块从属主文档，冲突以主文档为准）；**主文档永远单一，子模块 MUST NOT 再往下分层**。何时拆按 `<skills 根>/ai-dev-workflow/references/core/文档治理.md` §需求真相源写什么、怎么分层 的拆分阈值，**MUST NOT 在此另记一个数字**。**实现细节不进 PRD**——怎么做归 spec，代码现状归 card；PRD 的细节边界是"用户可感知的行为契约与验收口径"，与该节的细节边界是同一条线。

## 协作面差异在哪看

本流程与协作面无关：4 批提问、提问三纪律、组稿顺序、质量清单对谁都一样。**只有"跟谁对齐、谁拍板、开放问题去哪"随协作面变化**，按项目标记块的 `collaboration` 字段加载对应分册：

| 协作面 | 分册 | 管什么 |
|---|---|---|
| solo（无其他人类协作方） | `collab/solo.md` | 需求与拍板都是你本人；没有评审会，开放问题 MUST 在成稿前自己逐条闭环 |
| team（存在其他人类协作方） | `collab/team.md` | 业务方拍业务口径；开放问题写到可逐条对齐的粒度，评审结论 MUST 回写 PRD |

**写多细不由协作面决定**：模板分流看上方 §分流（按改动形态），现状取证的顺序看 §批 B（先查卡片、卡片没覆盖再读源码，与协作面和项目大小都无关），索引与归档看项目有没有 `docs/index.md`（§组稿）。**MUST NOT** 从"就我一个人"推出"默认写最简的那份"；也 MUST NOT 因"是团队项目"就把本可精简的运营度量硬写满。
