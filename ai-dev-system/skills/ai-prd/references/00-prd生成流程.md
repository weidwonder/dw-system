# PRD 生成流程（core）

> 用**批量提问**驱动：每批一次抛出该批全部问题，用户答完起草对应章节；只有对回复有疑问或有缺口时才再批量追问，否则直接进下一批。目标是少轮次成稿。
> 提问的具体问法见 `question-bank.md`；成稿骨架见 `assets/templates/`。
> 所有提问与成稿遵循 `业务语言纪律.md`，不得把程序实现问题交给用户。
> 涉及用户可见 UI 新增/调整时，额外遵循 `UI原型纪律.md`：先参考现有 UI，再输出独立 HTML 高保真交互原型。

## 提问三纪律（先于任何一批问题）

每批问题在抛出前必须过这三条，缺一不可：

1. **事实/决策分离——事实自己查，只把决策抛给用户。** 凡是能从已有材料（描述、Issue、聊天记录、旧文档）、代码（`ctx` 可用时用 `ctx find-scenes`/`discover`/`get-card` 取权威事实并附 cite；不可用时直接读代码）或本 skill 已加载内容查到的**事实**，MUST 先自己查清并写成草稿让用户确认，MUST NOT 拿去当问题问用户。问题清单里只允许出现**决策**：读完材料仍需用户拍板的取舍、偏好、边界。把可查事实混进提问 = 把"AI 偷懒没查"伪装成"需求不清"。
2. **每问尽量带草案，禁止编造推荐。** 有材料/代码依据时 MUST 附推荐答案 + 一句话理由（业务语言），让用户在"改一下推荐"而非"从零作答"上表态；依据不足时给 2–4 个典型候选 + 一个倾向；完全无依据的开放题（如首轮"这次到底要做什么"）MUST NOT 编造推荐，显式写"此题无推荐，需要你的输入"。推荐只是草案，决策权在用户；用户未回复某问时 MUST NOT 把推荐当作已确认。
3. **依赖分层，同层批量。** 组批时先看问题间的依赖：答案互不影响的问题（可并行）归入同一批一次抛全；某问的答案会改变后续问法的（依赖链），拆到下一层，等上一层答完再按答案组下一批。判据：**能并行的绝不串行，有依赖的绝不硬塞进同一批**——同批内出现"如果上一题选 X 则本题……"的分支句式，就说明该拆层。

## 分流：先选模板（尽量别问）

先从用户已有材料（描述、Issue、聊天记录、旧文档）自行判定类型，判不准再问：

| 判据 | 模板 |
|---|---|
| 单点小改动 / 一个 Issue / 4 项 Triage 全否 | `assets/templates/lite-issue-prd.md` |
| brownfield 变更 / 在既有系统上加功能（默认） | `assets/templates/change-prd.md` |
| 整品 / 从 0 定义产品 / 需要用户旅程与成功指标 | `assets/templates/product-prd.md` |

> Triage 4 问（业务表达）：①是否改变智能能力给用户的结果？②是否改变谁可以做什么或敏感信息保护？③是否影响多个业务环节、历史数据或存在不可逆影响？④是否改变经营指标、业务规则或对外承诺？

> **AI-native / Agent 产品的边界（重要）**：上面三个模板给的是 PRD 的"软件外壳"。若产品的**核心价值来自 AI 行为**（模型自主规划、直接调用工具/接口、跨会话记忆影响决策，或置信度/降级是产品级决策），本 skill 的模板**不足以**承载 AI 产品决策——你**必须额外补一张 AI Capability Card**（见批 C 的 AI 追问），写清自主程度、允许/禁止行为、置信度与降级策略、评测（eval）准出标准（自主程度用批 C 的四档：仅给建议 / 辅助操作 / 受控自动执行 / 高影响自动执行）；**Agent 类产品**还要逐档写明**审批闸门**（哪一档起必须有人把关、什么情况必须停下问人），并列一份**不回答清楚就不上线的问题清单**（如：它最坏能造成什么业务损失？如何一键停用？出错了谁负责向谁交代？）。这些属产品/安全决策，**必须在 PRD 定，不能下沉给工程 spec 补**。你所在团队若有自有的 Agentic 产品 PRD 规范，完整骨架以其为准——本 skill 不随包分发这类重型模板。

> **UI / 交互原型边界（重要）**：只要需求新增或调整用户可见页面、组件、入口、状态、信息层级或交互路径，MUST 补一个 HTML 高保真交互原型（**不改结构与交互的纯文案改动豁免**，在 PRD 写清改动前后文案即可）。样式依据**先自查代码里的设计 token / 组件库 / 同类现有页面**，查不到才向用户要材料。原型 MUST 可离线打开（单文件、零外链），用于体验对齐，不是给 PM 解释设计思路的文档页：屏幕内只放真实用户会看到的内容；设计说明、样式依据、开放问题放画布外。原型与 PRD 一并作为 `ai-dev-workflow` 的输入，下游按它落用户可见行为。若确认不涉及 UI，PRD 写明“不适用 + 原因”。

## 4 批提问

### 批 A —— 立项（一句话结论 · 背景 · 目标 · 非目标）

一次抛全下列问题（按需增删），产出 PRD 前四节。**非目标是硬产出**。

- 一句话说清这次到底要做什么？做完的标志是什么？
- 为什么现在做？触发它的问题/机会/事故是什么？
- 产品目标有哪些（尽量可衡量）？
- **明确不做什么 / 不改什么？** 每个目标尽量配一条边界。
- （整品追加）目标用户是谁？核心用户旅程一句话？成功指标（量化）？

起草批 A 章节后，若非目标为空或目标不可衡量 → 就这两点再批量追问一次。

### 批 B —— 现状与边界（现状/当前逻辑 · 改动范围 · 不改的线上逻辑）

- 现在这项业务由哪些角色参与，经过哪些环节，各方如何协作？
- 本次**改动范围**：新增什么、改造什么？
- **哪些现有业务流程、规则和职责明确不动？**（既有业务护栏）
- （涉及 UI）样式依据：**先自查**项目里的设计 token（`tailwind.config.*`/`theme.*`/`variables.css`/`*.tokens.json`）、组件库依赖、同类现有页面，把查到的样式基线写成草稿让用户确认；**查不到才问**用户要最接近的现有页面链接或截图，仍没有就按临时视觉假设推进。查得到却拿去问用户 = 违反提问三纪律第 1 条。

> **现状怎么取证（按项目有什么，不按协作面）**：
>
> **项目有 `engineering-context/`、`ctx` 可用时**——现状不靠口述、不 grep 旧代码：
> 1. `ctx find-scenes <关键词>` —— 除非任务已限定到单一 repo，先取端到端业务全景，避免漏跨服务链路；
> 2. `ctx discover "<意图>"` —— 收窄到应加载的权威条目（带 out-of-scope 提示）；
> 3. `ctx get-card <repo> [域]` —— 取该仓权威事实（职责/对外接口/上下游/废弃标记）；
> 4. 用取到的事实**预填现状草稿，每条附 cite**（`path#anchor @确认时间`），再请用户确认/纠偏。
>
> 命令找不到时 MUST NOT 判定"没有可信事实"，用 `node <skill 目录>/scripts/ctx/src/cli.js <命令>` 兜底；某能力未登记（discover 无命中）→ 提示可能需补 registry / card，别凭空写现状。
>
> **`ctx` 不可用时**（项目没有 `engineering-context/`，或命令与兜底都跑不通）：让用户口述现状 + AI 就模糊处追问，需要时直接读代码核实；**MUST 在 PRD 现状节显式标注"现状未经代码核实"**，并仍然显式区分"现状事实"与"我想要的样子"。
>
> 两种情况共同的硬线：**禁止把愿景写成现状**——现状以代码为准（见 `prd写作纪律.md` §4）。以上取证只用于内部；写入 PRD 前 MUST 翻译成业务事实（见 `业务语言纪律.md`）。

### 批 C —— 细节（详细业务行为与信息要求 · 特殊场景与冲突）

- 逐条问清谁在什么场景做什么、需要记录哪些业务信息、何时触发、按什么顺序和优先规则处理。鼓励**表格化**。
- 主动穷举**特殊场景与冲突**：多人或多次同时操作、信息迟到、前置条件不满足、处理失败、业务过期、跨阶段继续……把每种情况的期望处理问清。
- 涉及 UI 新增/调整时，额外产出 **UI Prototype Brief**：覆盖的核心用户路径、页面/状态清单、样式依据、真实示例数据，以及哪些设计说明不得出现在用户界面内；随后生成 `docs/spec/<name>-prototype-YYYYMMDD.html`。

> 含智能能力（生成/总结/分类/检索/识别等）时，额外产出一张 **AI Capability Card**（这是**产品决策**，必须在 PRD 定，不能下沉给工程实现；对话与成稿保持业务语言）：
> - **自主程度**：仅给建议 / 辅助操作 / 受控自动执行 / 高影响自动执行（高影响必须写明谁来人工把关）；
> - **允许 / 禁止行为**：尽量写成可验收的业务约束（如"不得直接给最终答案"）；
> - **可信度与兜底**：结果可信/不可信分别怎么呈现；智能能力不可用、超时或结果不安全时怎么兜底（不能让用户正在进行的工作受损）；什么情况下必须转人工或拒绝处理；
> - **准出标准**：用什么业务标准判断结果可用、达到什么线才能上线；高风险能力未达标即不上线；
> - **数据边界**：会使用哪些业务信息、哪些敏感信息需要保护/脱敏、是否允许用于改进智能能力。
> 这些为后续 `ai-dev-workflow` 的 AI overlay 提供产品侧契约。Agent 类产品另见分流表的边界声明。

### 批 D —— 准出（验收标准 · 运营度量与看板 · 风险与兜底）

- **验收标准**三分，逐条**可判定**：
  - 业务信息验收（信息是否完整、含义是否一致）；
  - 流程与规则验收（业务规则是否被正确执行）；
  - 端到端场景验收（给场景 → 给预期）。
- **运营度量与看板**：上线后要回答哪些经营问题？关键指标带**公式**与统计粒度。（有业务方 / 运营读者时写全；只有你自己看时可精简，但至少留一条"我怎么知道业务结果达成了"——见 `collab/`。）
- **风险与兜底**：每条风险配一条兜底。
- **UI 原型验收（涉及 UI 时）**：HTML 原型可**离线**直接打开（单文件、零外链 CDN / 网络字体 / 远程图片）；关键状态可切换；视觉继承现有设计 token 或明确标注临时假设；用户界面内没有 PM 解释、设计理由、开放问题。

## 盘问模式（需求高度模糊时的前置收敛）

批量提问假设"需求形状已基本清楚，缺的是细节"。若不满足这个前提，先进盘问模式把方向收敛，再回到 4 批流程。

- **进入条件**（任一命中）：用户只有一个念头/一句话，说不出做完的标志；批 A 抛出后过半问题答"不知道/都行"；用户的目标之间互相矛盾；方向性决策（做不做、给谁做、边界在哪）尚未定。
- **行为**：不再整批抛问。每轮只抛**当前最阻塞的一层决策**（1–3 问的小批，仍遵守提问三纪律：附推荐答案、可并行的并在同层），问透一条决策链再开下一条；主动挑战站不住的理由、把用户没说出口的隐含假设摆到明面确认，不接受"应该没问题"这类含糊保证。
- **退出条件**：一句话结论 + 做完标志 + 首批非目标能被用户确认 → 立即退出盘问模式，回到批 A 正常起草。盘问轮次 SHOULD ≤ 5 轮；超过说明需求还不到写 PRD 的时候，建议用户先做探索（原型/调研），不硬写。
- **禁止**：把盘问模式当默认（默认永远是批量）；在盘问中问可自查的事实；一轮只问一个本可并行的问题。

## 案例（一批长什么样）

**案例 1 — 批 A 批量提问（含推荐答案）**。输入：用户说"给作业辅导加错题重练"。一次抛全（每问带推荐）：

> 1. 一句话结论确认：本次是"学生在作业辅导里对错题一键发起重练"？做完的标志 = 学生能从错题入口发起重练并得到新一轮辅导？（推荐：是——依据你的描述与现有辅导流程）
> 2. 为什么现在做？（推荐：错题复练率低的运营反馈——若另有触发请纠正）
> 3. 目标怎么衡量：错题重练使用率 / 重练后正确率要到多少？（此题无推荐，需要你的输入）
> 4. 非目标：本次不改判题逻辑、不动错题本的收藏结构，对吗？（推荐：不改——两者均为既有稳定流程）

用户答完即起草前四节；仅"目标定多少"仍缺 → 只就该点追问一次，不整批重来。

**案例 2 — 盘问模式一轮**。输入：用户只有一句"我想做个学习激励的东西"，说不出做完的标志 → 命中进入条件。第一轮只抛最阻塞的一层（1–3 问）：激励谁（学生/家长/老师）？激励什么行为（完成作业/坚持打卡/成绩提升）？（附倾向：学生完成作业——从产品主线推断）。用户答"学生坚持打卡"后，下一轮再问打卡的定义与边界；收敛出一句话结论 + 首批非目标并获确认 → 退出盘问，回批 A 正常起草。

## 组稿

1. 按所选模板把四批产出拼装成完整 PRD，补流程图（mermaid）与 changelog。
2. 涉及 UI 时，按 `UI原型纪律.md` 与 `assets/templates/ui-prototype.html` 生成独立 HTML 原型；PRD 中只链接原型文件并说明覆盖路径、样式依据和关键状态。
3. 跑 `prd质量清单.md` 自检；不过则就缺项再批量追问或补写。
4. **交付门：先取得用户确认再落盘**。组稿后把关键取舍、非目标、验收口径回述给用户；涉及 UI 时同时回述原型覆盖范围和样式依据，**达成共识后才写文件**——不要在用户还没确认的情况下就当成定稿交付。
5. 落盘（命名：变更 PRD → `docs/spec/<name>-PRD-YYYYMMDD.md`；UI 原型 → `docs/spec/<name>-prototype-YYYYMMDD.html`；整品 → `docs/REQUIREMENTS.md`，唯一真相源放 `docs/` 根）。
6. **项目有 `docs/index.md` 时**：MUST 同步更新（doc 治理要求）——**PRD 与 UI 原型都要进索引**，原型与 PRD 同条目并列标注。索引只放现行口径，PRD frontmatter 带 `lifecycle: active`；归档进 `docs/index-archive.md`（见下方 §PRD 生命周期）。项目**没有** `docs/index.md` 时，MUST NOT 为了本次落盘临时造一个索引，只做 frontmatter 与归档头注两个动作（呼应 `ai-dev-workflow` 的 `references/core/文档治理.md`）。
7. 收尾提示：这份 PRD **连同 UI 原型**一并作为 `ai-dev-workflow` Step 1 的输入，接着做 Overview / 技术 Spec；告诉用户下游会按原型落用户可见行为，原型与 PRD 正文冲突会被立为开放问题。

## PRD 生命周期（两次动笔）

- **开发前**：本流程产出的是**意图**——变更 PRD 或整品 PRD 新章节，先于代码定稿；影响产品范围的变更必须先改 PRD 再动代码。
- **开发后（准出必做）**——需求实现验收后分三步：

  1. **归并口径**：把变更 PRD 中**改变了口径**的部分并回整品 PRD（`docs/REQUIREMENTS.md`）——更新 Product Scope 能力状态；用户旅程 / 成功指标被改变时**同步回填旅程叙事**。不能只翻状态位，否则旅程随迭代漂移成史前文档。
  2. **变更 PRD 转归档**：文件**原地不动**，三个动作在同一次提交里做完——frontmatter 标 `lifecycle: merged` + `archived: <日期>`、正文首行加"已归并"头注、从 `docs/index.md` 移入 `docs/index-archive.md`。归档后不再作为平行真相源维护。头注格式见 `ai-dev-workflow/references/core/文档归档与账本收敛.md`。
  3. **UI 原型不随变更 PRD 归档**：它留在原地并升级为该能力的**现行界面依据**，整品 PRD 的 UI 原型节与 `docs/index.md` 指向它，供后续需求作为"现有 UI 样式依据"直接继承。只有当界面被后续需求改掉时，才由新原型接替——旧原型页面顶部加可见横幅"已被 <新原型> 取代"并移入归档索引（见 `UI原型纪律.md` §4.5）。
- **膨胀分层**：整品 PRD 过大时，主文档只留骨架（Summary / Success Criteria / Scope 状态 / User Journeys / FR 摘要），FR/NFR 明细与验收基线移入 `docs/REQUIREMENTS-appendix.md`（附录从属主文档、与主文档同放 `docs/` 根，冲突以主文档为准）；主文档永远单一，附录可按域再拆。**实现细节不进 PRD**——怎么做归 spec，代码现状归 card；PRD 的细节边界是"用户可感知的行为契约与验收口径"。

## 协作面差异在哪看

本流程与协作面无关：4 批提问、提问三纪律、组稿顺序、质量清单对谁都一样。**只有"跟谁对齐、谁拍板、开放问题去哪"随协作面变化**，按项目标记块的 `collaboration` 字段加载对应分册：

| 协作面 | 分册 | 管什么 |
|---|---|---|
