# PRD 写作纪律

> 这是把 ai-prd 和"普通 AI 写 PRD"拉开差距的地方。成稿必须同时满足以下六条。

## 1. 非目标必须硬

- 无"非目标/不做什么"章节的 PRD **不准成稿**。
- 每个产品目标尽量配一条对应边界；模糊的"以后可能做"归到 Vision/后续，不混进本期目标。
- 非目标写具体：不是"不做优化"，而是"不改变现有审批职责 / 不扩大使用人群 / 不影响进行中的历史业务"。

## 2. 边界必须显式（brownfield 护栏）

- 在既有业务上改动时，必须有"**不改的现有业务**"章节，逐条列出本次明确不动的流程、规则和职责。
- 这层护栏防止实现阶段越界重排线上已验证能力，是变更 PRD 的核心价值之一。

## 3. 验收可判定

- 每条验收项必须能被测试或评审**直接勾验**：给输入/场景 → 给明确预期。
- 禁止不可判定表述："提升体验""更稳定""尽量准确"。要量化或给可观察的判据。
- 规范性措辞用 RFC2119：MUST / MUST NOT / SHOULD / MAY，边界清晰。
- 验收尽量三分：**业务信息 · 流程与规则 · 端到端场景**。

## 4. 真相方向

- **现状以代码为准，取证只有一条路径**：先用 `ctx find-scenes`/`discover`/`get-card` 查 `engineering-context/` 卡片，命中的每条现状附 cite（`path#anchor @确认时间`）；卡片没覆盖到的模块才读源码核实（有代码图谱走图谱、没有就外包子代理），条目带 `文件:行`，并在现状节照抄规定的标注原文。**取证顺序、读源码的定位方式与标注原文的完整定义只在 `00-prd生成流程.md` §批 B → 现状怎么取证**，本节不复述、冲突以该节为准。
- **无 card 依据的 cite 视为幻觉**：`discover`/`find-scenes` 对本次意图零命中时，MUST 转去读源码并按表标注，**MUST NOT 编造 cite**、MUST NOT 凭空写现状。零命中只说明这个模块的卡片还没建，MUST NOT 读成"这个项目没有卡片层"。
- **绝不把意图/愿景写成现状**。PRD 描述的"想要的样子"与线上"已落地的事实"常背离；把二者混写会误导后续设计。显式分区：现状 = 事实，目标 = 意图。
- PRD 意图与代码事实冲突时，标为**待人工复核**，不替产品拍板。
- **MUST NOT 从 PRD 生成 card 事实**：PRD 在代码事实链路上只做 scope 约束与业务语境补充；本次现读源码搞清楚的模块按 `00-prd生成流程.md` §批 B 第 3 步标出来，由 `ai-dev-workflow` 回到源码补卡。呼应姊妹 skill 的 `<skills 根>/ai-dev-workflow/references/core/代码事实纪律.md` §9（`<skills 根>` 的定义见 `00-prd生成流程.md` §批 B → 现状怎么取证）。

## 5. 无占位符成稿

- 交付前扫一遍：`【】`、TBD、TODO、"待补"必须清零，或转成显式的"开放问题"清单并说明来源。
- 开放问题要足够详细：说明问题源自哪里、卡住谁的决策。有协作方时供评审逐条对齐，没有协作方时 MUST 在成稿前自己逐条闭环（见 `collab/`）。

## 6. 全程使用业务语言

- 对话、问题和 PRD 正文只描述角色、场景、流程、信息含义、规则、指标、风险和结果。
- 不写程序组件、代码结构、通信方式、存储方式或技术选型。
- 内部查到的技术事实必须先翻译成业务事实；用户主动给出的技术方案只提取业务意图和约束。
- 具体翻译规则见 `业务语言纪律.md`。

## 7. 只写最新现状

- 适用于 PRD 正文与原型（含屏级注释、元素说明、设计说明），从起草到用户定稿的每一轮：只写此刻的样子，不写稿间对比。
- **MUST NOT** 写“相比上一轮”“原方案是……现在改为……”或“本轮把 X 挪到了 Y”等稿间对比；不得因此丢掉当前应有的信息。
- 相对现有线上系统的变化照写，这是业务现状与目标的参照，不是稿间对比。
- 定稿后的 changelog 不受此约束。
