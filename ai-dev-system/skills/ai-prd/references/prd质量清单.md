# PRD 质量清单（成稿前自检 gate）

> 组稿后逐条自检；任一"否"→ 就该项再批量追问或补写，不过 gate 不交付。
>
> **本清单不是最后一道关**：它在 `00-prd生成流程.md` §组稿 第 3 步跑，参照物是**模板骨架与写作纪律**——查的是节缺没缺、验收可不可判定、占位符清没清、落位对不对。本清单之后还有**三道门**：第 4 步的**用户过稿门**（把稿子交给用户读、提意见、定稿，**不派子代理**）、第 5 步的**复核门**（`prd复核纪律.md`，派子代理查两件本清单**结构上查不到**的事：PRD 内部有没有互相打架（自洽轴）、与现有系统的功能和约束有没有冲突（冲突轴））、第 6 步的**落盘确认门**。三者**先后固定、职责不重叠**，MUST NOT 互相顶替——本清单全过 MUST NOT 被读成"可以直接进落盘确认门"，更 MUST NOT 被读成"可以直接派复核子代理"（复核 MUST 等用户在第 4 步定稿，判据见 `prd复核纪律.md` §门禁），复核门也 MUST NOT 重跑本清单的骨架勾验。

## 完备性（对照骨架）

### 三类模板 × 必备节（先查本表，再逐条勾验）

三类模板的骨架不同，下面的勾验项**按本表判适用**，MUST NOT 一律照变更 PRD 勾验：

| 章节（下方勾验项） | 变更 PRD | 轻量 Issue PRD | 整品 PRD |
|---|---|---|---|
| 一句话结论 | 必备 | 必备 | 由「这是什么」承载 |
| 背景 | 必备 | 必备（背景 / 动机） | 由「为什么做」承载 |
| 目标 | 必备 | 必备 | 由「成功标准」（用户侧 + 度量）承载 |
| 非目标 | 必备 | 必备 | 必备（独立的「明确不做什么」节）。**MUST NOT 把「暂时没做」写进来**——那是 `docs/TODO.md` 的事，这一节写的是**当前边界** |
| 现状 / 当前逻辑 | 必备 | 不适用（无独立节）——「改动点」表里涉及现状的条目仍 MUST 按 `00-prd生成流程.md` §批 B → 现状怎么取证 注明来源 | 不适用（greenfield 无既有线上业务）；为**已上线**产品补写整品 PRD 时，现状即当前产品行为，仍 MUST 按 `00-prd生成流程.md` §批 B → 现状怎么取证 取证 |
| 改动范围 + 不改的现有业务 | 必备 | 由「改动点」表承载；本次不动什么写进非目标 | 不适用（无既有业务可护栏） |
| 详细业务行为与信息要求 | 必备 | 由「改动点」表承载 | 由「现在有哪些功能」各功能小节承载；已拆子模块时由 `docs/requirements/<模块>.md` 承载 |
| 特殊场景与冲突 | 必备 | 必备（「特殊场景」节；确实没有时写"无特殊场景"） | 必备，写进对应功能小节或子模块的「具体规则」（模板无独立节） |
| 验收标准三分 | 必备（业务信息 / 流程与规则 / 场景） | 单表「场景 → 预期」即可，不要求三分 | 由「成功标准」+ 各功能小节的可判定约束承载，不要求三分 |
| 运营度量与看板 | 必备（solo 可精简，至少一条"怎么知道业务结果达成了"） | 不适用（单点改动，验收表即准出判据） | 由「成功标准 → 度量」+「服务质量要求」承载 |
| 风险与兜底 | 必备 | 必备（「风险 / 兜底」；确实没有时写"无显著风险"） | **不进整品 PRD**——它只写已实现的现状，风险属尚未发生的事，MUST 写进 `docs/TODO.md` 的「已知风险」章节 |
| 流程图 | 复杂交互时必备 | 不适用 | 不适用（用户旅程用叙事体） |
| changelog | 必备 | 不适用（抬头「更新时间」追踪） | 不适用（frontmatter 的 date / status 追踪） |
| UI 原型五项 | 涉及 UI 时必备，不涉及时写"不适用 + 原因" | 同左 | 同左 |

怎么用这张表（三条，MUST 照此判）：

- **必备** → 缺即"否"，补写。
- **由 X 承载** → 判据落到 X 节：X 缺才算"否"；MUST NOT 因为模板里没有同名章节就判"否"，更 MUST NOT 为过这一项把变更 PRD 的重章节硬塞进轻量 / 整品模板。
- **不适用** → 本项**跳过不勾验**，不算"否"。整品 PRD 若确实是已上线产品的补写，按表中该格的后半句办。

下列逐条勾验项的适用范围一律以上表为准。

- [ ] 有**一句话结论**：一句话说清做什么、做完的标志。
- [ ] 有**背景**：为什么现在做。
- [ ] 有**目标**：尽量可衡量。
- [ ] 有**非目标**：非空、且具体（见纪律 §1）。
- [ ] 有**现状/当前逻辑**，且**每条都能溯源**（取证顺序与标注原文见 `00-prd生成流程.md` §批 B → 现状怎么取证，本清单不重复定义）：卡片命中的条目带 cite；本次现读源码的条目带 `文件:行`；只有用户口述的条目注明来源——现状节还 MUST 照抄该节规定的适用标注原文。**三种来源任一成立即通过**，MUST NOT 因为无 cite 就卡住成稿，更 MUST NOT 为过这一项编造 cite。
- [ ] 既有业务变更：有**改动范围** + **不改的现有业务**。
- [ ] 有**详细业务行为与信息要求**：关键项表格化。
- [ ] 有**特殊场景与冲突**：同时操作/信息迟到/前置条件/失败/过期等已覆盖。
- [ ] 有**验收标准**：业务信息/流程规则/场景三分，逐条可判定。
- [ ] 有**运营度量与看板**：有业务方 / 运营读者时关键指标带公式与粒度；只有你自己看时可精简，但至少一条"怎么知道业务结果达成了"。
- [ ] 有**风险与兜底**：每条风险配兜底。
- [ ] 有**流程图**（复杂交互时）与 **changelog**。
- [ ] 涉及 UI 新增/调整：“UI 原型”节五项齐全（原型文件 / 覆盖路径 / 样式依据 / 关键状态 / 不在用户界面内展示）；不涉及 UI 或纯文案改动时写明“不适用 + 原因”。

## 非功能 / 安全 / 上线（按适用，不适用要显式写"不适用+原因"，不能默默留空）

- [ ] **NFR 可度量**：涉及的性能（P50/P95/P99、吞吐）、可靠性、离线/弱网、无障碍、可观测等，写成可度量目标而非"要快要稳"。
- [ ] **数据 / 隐私 / 安全 / 合规**：涉及的敏感数据清单、采集/使用授权（consent）、留存期、是否用于训练（未成年数据默认不得）、鉴权与越权边界。
- [ ] **Rollout / 回滚 / 监控**：灰度或分批发布方式、回滚条件与动作、上线后监控什么指标、事故 owner。
- [ ] **AI 行为（含 AI 时）**：有 **AI Capability Card**——自主级别、允许/禁止行为、置信度与降级策略、**评测（eval）准出标准**都写清；高风险能力把 eval 作为上线阻断项；重要 AI 行为**没有藏进普通功能需求**里。

## 质量（对照纪律）

- [ ] 无占位符：`【】`/TBD/TODO 已清零，或转为显式"开放问题"——转成开放问题的，MUST 再过下面一条结算项才算完。
- [ ] **开放问题清单已按协作面结算**（4 批的死锁出口把闭不上的点沉淀成开放问题，这里是这条通路唯一的验收点；MUST NOT 因为"已经写成开放问题"就默认过 gate）：
  - solo —— **逐条闭环**：要么当场拍板写进正文，要么明确写"本期不解"并给出对应的**非目标条目**；不允许留无主条目（`collab/solo.md` §2）。
  - team —— 每条**写到可被逐条对齐的粒度**：问题源自哪里、卡住谁的决策、不解决会导致什么业务后果；已有评审结论的 MUST 回写进 PRD 正文（`collab/team.md` §2）。
  - 批 A 的一句话结论 / 做完的标志 / 非目标**不允许出现在开放问题清单里**——它们是硬产出，闭不上时走盘问模式（`00-prd生成流程.md` §4 批提问 的例外）。
- [ ] 验收无不可判定表述（"提升体验"等）；用 RFC2119。
- [ ] 现状与意图**分区清晰**，未把愿景写成现状。
- [ ] 非目标与"不改的现有业务"具体到可核对。
- [ ] 业务术语和信息项命名前后一致。
- [ ] 对话与成稿只用业务语言，不含需要用户理解的程序实现和技术选型（**取证出处豁免**：UI 原型节的「样式依据」与现状节的来源注记 MAY 出现设计 token 文件名与组件库名，判据见 `业务语言纪律.md` §取证出处豁免）。
- [ ] UI 原型（如适用）是可打开的 HTML 交互页，不是 Markdown；视觉参考现有设计 token / 组件库 / 现有页面，或明确标注临时假设；用户界面内没有 PM 说明、设计理由、开放问题或占位教学文字。
- [ ] UI 原型跑过 `node <skills 根>/ai-prd/scripts/preview.mjs check <原型文件>` 且**无 P0**（它查外链 / 占位符 / 固定实现区完整 / 屏结构 / 控件结构契约 / 图标引用 / 未定义 class / 写死颜色 / 脚本语法，见 `UI原型纪律.md` §6）。**样式依据查不到时不豁免**：`project-theme` 插槽 MUST 整段留空，MUST NOT 填臆造的品牌色冒充既有样式（§4、§8.4）。
- [ ] UI 原型的固定实现区**全部**未被改写（清单以 `UI原型纪律.md` §6 自检那条为准，`check` 命令会逐个验，MUST NOT 在此另记一套）；针对单个元素的说明写在该元素的 `data-anno` 上而非画进屏幕（§7.2）；改稿走 `slot` 命令，用户已写的批注与 `data-anno-user` 锚点一条不少（§7.1）。
- [ ] 原型里 `data-anno-kind="question"` 的待拍板项**已全部列进落盘确认门的回述清单**（用 `preview.mjs annotations` 取），MUST NOT 让它们跟着原型静默进库（§7.3）。

## 落位（doc 治理）

- [ ] **落盘计划里已确定**落盘位置（变更 PRD 与轻量 Issue PRD → `docs/spec/<name>-PRD-YYYYMMDD.md`，两者同一命名、只是模板不同；整品 → `docs/REQUIREMENTS.md` 放 `docs/` 根，超过拆分阈值时具体行为规则进 `docs/requirements/<模块>.md`；UI 原型 → `docs/spec/<name>-prototype-YYYYMMDD.html`，与 PRD 同目录，PRD 里的链接指向该路径）。（本清单在 §组稿 第 3 步跑，实际写入在第 7 步——此处只验计划。）
- [ ] frontmatter 三个字段齐：`lifecycle: active`、`last_confirmed`（本次成稿日期）、`authority_refs`（本 PRD 冻结了哪些对用户可见的行为契约，非空）。三类模板都带这三项。
- [ ] 项目有 `docs/index.md` 时：**落盘计划里已包含**同步新增条目（**PRD 与 UI 原型都进索引**），且索引里只有现行口径的文档；项目没有 index.md 时本项跳过（不为落盘临时造索引）。（本清单在 `00-prd生成流程.md` §组稿 第 3 步跑，索引实际写入在第 8 步——此处只验计划。）
- [ ] **落盘计划里已包含**收尾提示：可接 `ai-dev-workflow` 做 Overview / 技术 Spec，PRD 与 UI 原型一并作为其 Step 1 输入。（提示实际发出在 `00-prd生成流程.md` §组稿 第 9 步。）
- [ ] 变更 PRD：已注明收尾动作——实现验收后归并回整品 PRD，并标 `lifecycle: merged` + 加归档头注 + 移入 `index-archive.md`（见 `00-prd生成流程.md` §PRD 生命周期）。
