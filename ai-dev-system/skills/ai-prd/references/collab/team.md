# 协作面 = team

> 加载条件：存在其他人类协作方时加载。
> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD / MAY。
> 本文只管**因为有别人**才存在的约定：需求从谁来、谁拍板、结论怎么被评审。与项目有多少代码事实资产无关——现状怎么取证看 `00-prd生成流程.md` §批 B。

## 1. 需求来源与拍板人是业务方

- **业务目标、业务规则、边界、口径 MUST 找业务负责人确认**，AI 与工程侧 MUST NOT 代替业务方拍板。
- **MUST NOT 要求业务用户理解技术方案后回答问题**（`业务语言纪律.md`）。内部读代码取到的技术事实，写进提问与 PRD 前 MUST 翻译成业务角色、业务流程、业务规则和可观察结果。
- 批量提问的接收方是业务方：每批一次抛全、每问附推荐答案 + 一句业务语言理由，让对方在"改一下推荐"而非"从零作答"上表态。**用户未回复某问时 MUST NOT 把推荐当作已确认。**
- 非目标与"不改的现有业务"这两节 MUST 由业务方逐条确认——它们是后续实现阶段唯一的越界护栏，工程侧单方面写下的护栏拦不住业务临时加需求。

## 2. 开放问题供评审会逐条对齐

- 跨 ≥3 仓 / 影响面不清的需求，PRD 的**开放问题 MUST 写到可被逐条对齐的粒度**：问题源自哪里、卡住谁的决策、不解决会导致什么业务后果。含糊的"待确认"在评审会上等于没写。
- **评审结论 MUST 回写进 PRD 正文**（进对应章节，不是只留在会议记录里），避免下一次评审重新吵同一件事。
- 跨 <3 仓的需求 MAY 只做异步评审（把 PRD 发给相关负责人确认），但结论同样 MUST 回写。

## 3. 口径变更由业务方拍板

- 变更 PRD 改变了既有口径（现有流程、规则、职责、对外承诺）时，MUST 把"谁受影响、影响多久"写清，用业务语言送业务方拍板，**MUST NOT 由 AI 默认沿用或默认改变**。
- 拍板结论 MUST 落进 PRD；工程侧的兼容取舍确认门（`ai-dev-workflow` `00-流程总纲.md` §兼容取舍确认门）会以此为输入，PRD 没记的口径变更会在那里被重新提问一次。
- **复核门 MUST 等 PRD 起草人先定稿再派**（时机见 `00-prd生成流程.md` §组稿 第 4/5 步）：稿子还在改动中就复核，报告送到评审会时已经对不上正在议的那一版。
- **复核门（`prd复核纪律.md`）交上来标着「需用户拍板」的冲突，按同一条规矩分流**：动到业务口径、对外承诺或既有业务规则的，MUST 送业务方拍板，MUST NOT 由 AI 或工程侧单方面选一个写进 PRD；只动技术约束（唯一键、鉴权边界这类）的，工程侧可判，但结论同样 MUST 落进 PRD 正文。
- **本门是评审会前的地板，不替代评审**。评审会读的是**这份稿子**，而稿子与现有系统冲突不会因为多几个人读就自己显形——冲突轴带着 cite 把它挖出来，评审会才有得可议。

## 4. 衔接：定稿后交给谁

- PRD 定稿后作为 `ai-dev-workflow` Step 1 的输入（涉及 UI 时连同原型一并交付）。
- **跨仓需求 SHOULD 接着出 Overview（Step 2）**——它是各仓负责人之间唯一的共同心智模型；跨 ≥3 仓时 Overview 还要过评审会。
- 落盘位置、索引更新与归并动作与协作面无关，见 `00-prd生成流程.md` §组稿、§PRD 生命周期。

## 一句话

协作面 = team 意味着**需求有出处、口径有拍板人、开放问题有会要开**：业务方拍业务口径，评审会对齐跨仓影响，AI 只负责把事实查清、把问题问准、把结论落盘。
