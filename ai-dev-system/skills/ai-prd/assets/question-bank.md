# 提问库（供批量组批）

> 按批取用，一次抛一批。组批前先过 `references/00-prd生成流程.md` §提问三纪律（事实自己查只问决策 / 每问附推荐答案禁编造 / 依赖分层同层批量）——**细则以该文件为准，此处不重复**。问法保持"一次问全 + 给业务例子降低回答成本"，只用业务语言。下列各批内问题默认互不依赖、可一次抛全。

## 批 A — 立项

1. 一句话说清这次要做什么？做完的标志是什么？
2. 为什么现在做？触发它的问题 / 机会 / 事故是什么？
3. 产品目标有哪些？尽量可衡量（如"XX 成功率 ≥ N%"）。
4. **明确不做什么 / 不改什么？**（逼非目标；给例子："不改变审批职责、不扩大使用人群、不影响进行中的历史业务"）
5. （整品追加）目标用户是谁？核心用户旅程一句话？北极星指标？

## 批 B — 现状与边界

1. 现在这项业务由哪些角色参与，经过哪些环节，各方如何协作，需要记录哪些业务信息？
2. 本次改动范围：新增什么、改造什么？
3. 哪些线上逻辑本次**明确不动**？（brownfield 护栏）
4. 我查到现在的做法是【…（内部附来源，问用户时不出现来源与技术词）】，与实际是否一致？哪里要纠偏？
   > 取证走哪条路径、要不要带 cite、成稿怎么标注，都是**内部**动作，判据见 `references/00-prd生成流程.md` §批 B → 现状怎么取证。
   > **问法本身 MUST NOT 出现 `ctx` / cite / card / "读代码" 这类技术词**——业务负责人只需要判断"这个描述对不对"，不需要知道我是怎么查到的（`references/业务语言纪律.md`）。
5. （涉及 UI）我从项目里查到的界面样式基线是【设计 token / 组件库 / 同类页面，附具体来源】，原型是否就按这套画？（先自查再问；确实查不到材料时才改问：请给一个最接近的参考页面或截图，或确认可先用临时视觉假设。）

## 批 C — 细节

1. 各角色在什么场景下做什么？何时开始、得到什么结果、按什么顺序和优先规则处理？
2. 业务需要新增或调整哪些信息项？每项信息由谁提供、代表什么、谁可以查看或修改？
3. **特殊场景与冲突**：多人或多次同时操作、信息迟到、前置条件不满足、处理失败、业务过期、跨阶段继续——各自期望怎么处理？
4. （含智能能力）会使用哪些业务信息、给出什么结果、何时转人工或拒绝处理、效果怎么衡量？
5. （涉及 UI）原型需要覆盖哪条核心用户路径和哪些关键状态？推荐至少覆盖：默认、加载、空态、错误/无权限、成功反馈；不确认的设计说明只放画布外，不放进用户界面。

## 批 D — 准出

1. 怎么算验收通过？分三类给判据：业务信息、流程与规则、端到端场景（给场景→给预期）。
2. 上线后要能回答哪些问题？关键指标怎么算（公式 + 粒度）？
3. 主要风险有哪些？每条的兜底是什么？
4. （涉及 UI）HTML 原型验收口径是什么？建议为：可离线直接打开（单文件零外链）、关键状态可切换、样式依据明确、用户界面内不出现面向 PM 的设计解释。

## 追问触发（何时再批量追问，而非直接下一步）

> 本节是判定"这一批还有没有缺口"的**权威判据**；`references/00-prd生成流程.md` 各批的退出条件只是本节在该批的具体展开，两者冲突以本节为准。
>
> **每条都带批次标签**（`[A]` 立项 / `[B]` 现状与边界 / `[C]` 细节 / `[D]` 准出 / `[组稿]` 成稿阶段）：勾验某一批时**只看标记为该批的条目**，**MUST NOT** 拿别的批次的条目卡本批——那批的产出这时还不存在，必然误判成"永远不通过"。`[组稿]` 的条目在 4 批里一律不勾验，只在组稿与 `references/prd质量清单.md` 上勾验。
>
> 任一条命中 → 只就命中的那几点再批量追问一次，MUST NOT 整批重来、MUST NOT 带着命中项进下一批。例外：批 A 的一句话结论 / 做完的标志 / 非目标追问后仍闭不上时，按 `references/00-prd生成流程.md` §4 批提问 的例外转入盘问模式，MUST NOT 转成开放问题。

- `[A]` 非目标为空，或目标不可衡量 → 追问批 A 这两点。
- `[B]` 现状里出现"应该/希望/打算"等意图词混入事实 → 追问区分现状与目标。
- `[B]` 现状有条目**既没有 cite、也没有来源注记与规定的标注原文** → 先按 `references/00-prd生成流程.md` §批 B → 现状怎么取证 补取证（MUST NOT 编造 cite），补不齐的点才追问用户。
- `[B]` 涉及 UI 但**样式依据**未落定（既没查到设计基线并被确认，也没明确按临时视觉假设推进）→ 先自查再追问，仍拿不到就确认按临时视觉假设推进。
- `[C]` 批 C 的"角色 × 场景"有组合停在"待补"，或特殊场景表有类别既没写处理也没写"不适用 + 原因" → 追问该组合/该类别。
- `[C]` 含智能能力但 AI Capability Card 不足五项 → 追问缺的那几项。
- `[C]` 关键场景（失败/信息迟到/同时操作）无明确处理 → 追问期望处理。
- `[C]` 涉及 UI 但 UI Prototype Brief 缺项（核心用户路径 / 页面与状态清单 / 样式依据 / 真实示例数据 / 不得出现在用户界面内的内容）→ 追问缺的那几项。
- `[D]` 含智能能力但验收里没有该能力的准出标准 → 追问用什么业务标准判断结果可用、达到什么线才能上线。
- `[D]` 有风险条目没有配兜底 → 追问该风险的兜底。
- `[D]` 验收项出现"提升体验/更稳定"等不可判定表述 → 追问可勾验判据。
- `[组稿]` 涉及 UI 但还没有可离线打开的 HTML 原型 → 按 `references/00-prd生成流程.md` §组稿 第 2 步产出（样式依据确实拿不到时产出临时假设版），MUST NOT 在批 C 提前落盘。
- `[组稿]` 有开放问题未按协作面结算（solo 未逐条闭环 / team 未写到可逐条对齐的粒度）→ 按 `references/collab/` 结算后才交付。
