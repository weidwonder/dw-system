# 文档治理（core）

所有项目使用同一套项目级输出目录，与协作面、与项目有哪些代码事实资产都无关。生成文档前先创建所需目录，不得把交付物散落到项目根或 `docs/` 根。

| 文档类型 | 唯一目录 | 示例 |
|---|---|---|
| 需求真相源（整品 PRD）及其附录 | `docs/` 根 | `docs/REQUIREMENTS.md`、`docs/REQUIREMENTS-appendix.md` |
| 架构真相源 | `docs/` 根 | `docs/ARCHITECTURE.md` |
| 变更 PRD、Overview、Lean Change Spec、技术 Spec、测试 Spec、设计、契约 | `docs/spec/` | `docs/spec/payment-lean-change-spec.md` |
| Coding Plan、实施计划、迁移计划、交接文档（上下文交接） | `docs/plan/` | `docs/plan/payment-coding-plan.md` |
| 执行报告、验证报告、测试报告、审计报告 | `docs/report/` | `docs/report/payment-verification-report.md` |
| Bug 修复历史（**追加式**账本，见下方例外说明 + §5 收敛规则） | `docs/report/` | `docs/report/bug修复历史.md` |
| 测试场景覆盖度台账（**状态表**，见下方例外说明 + §5 收敛规则） | `docs/report/` | `docs/report/测试场景覆盖度.md` |
| 资产补建信号账本（**状态表 + 追加式**两部分，见下方例外说明） | `docs/report/` | `docs/report/资产补建信号.md` |
| 测试资产（真实输入样本，**不是文档**） | 项目测试目录，探测优先 | `tests/fixtures/<场景名>/` |
| 架构决策记录（ADR）| `docs/decisions/` | `docs/decisions/0007-use-outbox-for-mq.md` |

> **本文小节**：[三层真相源](#三层真相源零上下文交接的底线)（零上下文交接的底线 + 可验证判据）· [ADR](#adr架构决策记录按需) · [硬规则](#硬规则) · [文档生命周期与索引门控](#文档生命周期与索引门控)（`lifecycle` / `last_confirmed` / `authority_refs`）· [默认命名](#默认命名)

## 三层真相源（零上下文交接的底线）

> **为什么要这一节**：项目 MUST 对任何接手者——人或 AI agent——做到**零上下文交接**：需求、架构、实现三层真相源都能从项目自身定位，不依赖任何人口头介绍。层次固定为这三层，**承载形态随项目已有的资产变化**——小项目用 README 的一节就合规，MUST NOT 因为项目小就允许某一层缺失。

| 真相源层 | 回答的问题 | 最小承载形态（三选其一即合规） | 项目长大后 SHOULD 升级为 |
|---|---|---|---|
| **需求** | 要做什么、不做什么、为谁做 | README 的一节 **或** `docs/index.md`（二选一即可） | **现行区文档 >20 篇时** SHOULD 升为 `docs/REQUIREMENTS.md`（整品 PRD，放 `docs/` 根）+ `docs/index.md`（与 §2 索引分层同一阈值） |
| **架构** | 有哪些模块、各自职责与边界 | README 的一节"架构与边界"：模块划分 / 各自职责一句话 / 对外边界 / 不做什么，**可短至 10 行**；模块路径 MUST 写成反引号代码片段或相对链接（见 ↓ 可验证） | `docs/ARCHITECTURE.md`；存在跨服务场景时再补 `engineering-context/scenes/` |
| **实现** | 某件事落在哪段代码、哪个是权威实现 | 代码本身 + 子代理外包探索（`上下文卫生.md` 规则 4） | 图谱位：索引查询；权威位：`ctx` + cite（见 `capability/` 分册） |

- **可达性（MUST）**：三层真相源都 MUST 能从 README 或 `docs/index.md` 出发、**≤2 跳链接到达**。超过 2 跳等于不存在——接手者找不到就会去猜，猜出来的口径就是下一个错误的起点。
- **缺口只报告、不阻断（MUST）**：唤起或初始化时发现某层缺失或超过 2 跳，MUST 报告为"零上下文交接缺口"并指明补哪一份，MUST NOT 因此中止流程，也 MUST NOT 代用户自动创建——旧项目补齐需要时间，补的时机由用户定。上表的 SHOULD 升级项同理，只提示不代劳。
- **影响产品范围的变更 MUST 先改需求真相源**，再同步架构真相源与索引，最后才是 spec；反过来做会让真相源当场过期。
- **可验证（与能力位无关，MUST NOT 只在权威位项目上做）**：这三层的可达性与"实现真相源可用"都是**机器可判定**的检查，`ctx probe` 有四道专门的交接题型覆盖它们——`requirement-reachable`（需求真相源 ≤2 跳可达）、`architecture-reachable`（架构真相源 ≤2 跳可达）、`implementation-usable`（架构节列出的模块路径都存在）、`rationale-traceable`（索引现行区各 spec 的 `authority_refs` 非空）。

  **这四道题读的是项目自身文件，不依赖 `engineering-context/` 的内容**，所以**直读项目（一个能力位都没有）同样跑得起来、同样该跑**——`implementation-usable` 更是专为直读分支设计的。任何项目都 SHOULD 建一份只含这四道题的最小探针集：在项目里建 `engineering-context/probe-set.md`（只要这一个文件，不需要 registry、不需要 card）。建的时候 MUST 对用户说明**这不是权威口径层**——只放探针集的 `engineering-context/` 不构成权威位，项目仍是直读（`资产补建信号.md` §0 的具名例外），照 `assets/context-layer/probe-set.md` §零上下文交接检查 里那张标着**「示例（可直接抄进自己项目的探针表）」**的表抄一份（表头是 `| # | 类型 | 输入 | 期望 | severity | weight | status | authority_refs |`，四行 41–44），然后 `ctx probe`。
  **MUST NOT 抄错表**：同一文件里另有两张**说明用**的表（`## 题型与示例` 的 `| # | 题型 | …`、本节开头的 `| 检查项 | 类型名 | …`），它们的表头都不是解析器认的形状，抄了会解析出 0 道题。
  跑的频次跟着 `probe-set.md` §运行节奏：CI 发布或里程碑节点跑，**MUST NOT 塞进 coding agent 的每轮 loop**。

  两个易错点：**①探针表的表头首列必须是 `#`、次列必须写 `类型` 或 `type`**，写成「题型」整张表不会被解析。症状是 `ctx probe` 打出下面两行并以退出码 1 结束：

  ```
  门禁自检：🛑 失效 — context 层为空（无 registry/cards），无法自检
  🛑 GATE-BROKEN：门禁自检未通过，拒绝出具结论（流水线应红）。
  ```

  **这条报错在直读项目上真正的含义是探针表没被解析出来**，MUST 先查表头，**MUST NOT 照它字面去建 registry**（本节刚说过不需要 registry）；**②架构节里的模块路径 MUST 写成反引号代码片段（`` `src/app.js` ``）或相对链接**才会被 `implementation-usable` 计入——上表说"架构一节可短至 10 行"，但那 10 行里的路径若是散文里的裸文字，抽不到就判失败，而不是放行（零条目算通过就是假门禁）。

## ADR（架构决策记录，按需）

日常小决策记进 Overview 的"已定决策"一行表即可；只有**影响面大、以后可能被反复重议**的架构级取舍才单独立 ADR：

- 顺序编号存 `docs/decisions/NNNN-<短标题>.md`；每篇写 **Context（为什么要决策）/ Decision（定了什么）/ Alternatives Considered（考虑过哪些方案、为何否）/ Consequences（代价与影响）**。
- **不删旧 ADR**：决策被推翻时，写一篇新 ADR 引用并 supersede 旧的，保留决策演进史（防止把同一问题反复重决）。

## 硬规则

- 文件名必须表达业务主题与文档角色，不得使用生成工具名作为目录或文件名前缀。
- 不得创建 `docs/superpowers/`、`docs/claude/`、`docs/codex/` 等工具专属产物目录。
- 不得把 spec 或 plan 放项目根、仓库根或 `docs/` 根。唯一例外：需求与架构两层真相源（`REQUIREMENTS.md` 及其附录、`ARCHITECTURE.md`）放 `docs/` 根，便于发现。
- 同一需求的文档通过正文中的相对链接互相引用；移动文档时必须同步修复引用。
- `docs/index.md` 是发现入口，但不能替代上述目录规则；它**只索引现行口径**，历史文档进归档索引（见下方 §文档生命周期与索引门控）。
- 报告只有在流程要求形成书面报告时才创建；一旦创建，必须写入 `docs/report/`。
- **例外（三个固定文件名的单一账本）**：不按"每次新建一个 `<feature>-<report-type>-report.md`"的规则拆分。三者形态不同——`bug修复历史.md` 是**追加式**（每条都是发生过的一次性事实），`测试场景覆盖度.md` 是**状态表**（每行描述此刻的覆盖状态，同一场景只有一行），`资产补建信号.md` 两部分都有（上半状态表就地改、下半追加式只增不删）；收敛规则见 §5——
  - `docs/report/bug修复历史.md`：写入规则见 `bug诊断纪律.md` Phase 3 §归档问题处理历史，供 Phase 0 查重检索。
  - `docs/report/测试场景覆盖度.md`：写入规则见 `测试资产纪律.md` §3，模板 `assets/templates/test-coverage.md`，供批量向用户索要真实素材。
  - `docs/report/资产补建信号.md`：写入规则、行格式与阈值见 `资产补建信号.md`（`代码评审纪律.md` 残留轴与 `bug诊断纪律.md` Phase 3 是两个写入入口），供合并完成后的收尾汇报判定要不要建议补建权威位或图谱位。
- **三个账本的生命周期归属**：MUST 恒为 `lifecycle: active`、`authority_refs: ['无']`，**MUST NOT 被 §3 的权威面触发转归档**——它们记录的是发生过的事实与此刻的状态，不冻结任何会过期的权威口径；收敛靠各自的分卷/就地改行规则，不靠归档。
- **测试资产不是文档**：用户提供的真实输入样本落项目**测试目录**（探测既有惯例，兜底 `tests/fixtures/<场景名>/`），MUST NOT 塞进 `docs/`。含凭证的样本进同级 `secrets/` 并 gitignore，脱敏副本 `secrets.example/` 入库。规则见 `测试资产纪律.md` §2。

## 文档生命周期与索引门控

> **为什么要这一节**：`docs/spec/`、`docs/plan/` 是**过程产物**——它们记录的是当时的意图，会随代码演进与现实背离。代码侧有替换清单核销、context 层有 freshness 与权威面触发，文档层必须有同构的退出机制，否则索引单调增长、旧口径被后来的 agent 当成现行事实。**只增不减的索引既误导又烧上下文。**

### 1. 生命周期位（MUST，新建文档）

`docs/` 下新建的 spec / plan / report / PRD，头部 frontmatter MUST 声明：

```yaml
---
lifecycle: active          # active | merged | superseded | obsolete
superseded_by: ''          # lifecycle: superseded 时 MUST 填被谁取代（相对路径）
archived: ''               # 非 active 时 MUST 填转归档日期 YYYY-MM-DD
last_confirmed: ''         # 最近一次被 §3 触发复核、判定仍准确的日期 YYYY-MM-DD；新建时填当天
authority_refs:            # 本文描述的权威面，见 §3；本文不冻结任何权威面时写 ['无']
  - ''
---
```

| 值 | 含义 | 索引归属 |
|---|---|---|
| `active` | 现行有效，可据此实施 | `docs/index.md` |
| `merged` | 口径已归并进 `REQUIREMENTS.md` / `ARCHITECTURE.md` / 代码，本文只剩历史价值 | 归档索引 |
| `superseded` | 被更新的同类文档取代 | 归档索引 |
| `obsolete` | 描述的能力已下线或权威面已删除 | 归档索引 |

**字段名是 `lifecycle` 不是 `status`**——后者已被"写作进度"与 PRD 的自由文本状态占用，MUST NOT 混用。

**存量豁免**：升级前已存在、无 frontmatter 的文档默认视为 `active`，MUST NOT 为补齐字段而批量回改；只有当它被 §3 的权威面触发复核时才就地补齐并结算。

### 2. 索引分层（现行区文档 >20 篇时 MUST，否则 SHOULD）

**判据是文档数量，不是人数、不是协作面、也不是代码规模**：`docs/index.md` 现行区所列文档超过 20 篇时 MUST 分层，20 篇及以内 SHOULD 分层。索引分层要解决的问题只有一个——**索引长到没人读、AI 也读不完**，那是文档基数的函数；单人长期项目照样会长到那一步，十个人的新项目则未必。数到 20 篇就开始分层，MUST NOT 等到"感觉乱了"再补。

- `docs/index.md` **只索引现行口径**：三层真相源（`REQUIREMENTS.md` / `ARCHITECTURE.md`，或承载它们的 README 小节）、`lifecycle: active` 的 spec/plan/report、现行 ADR、现行 UI 原型、三个账本的入口，末尾加一行指向归档索引。
- `docs/index-archive.md` 索引全部非 active 文档，按年份分区，每条注明生命周期值与取代它的文档。**文件不存在则在首次归档时创建**。
- **文件原地不动，只有索引分层**——移动文件会破坏既有相对链接，代价高于收益。归档也不需要修改指向它的既有链接；但现行文档若把某篇归档文档当作实施依据，MUST 改指向接替它的现行文档。
- 文档转归档 MUST 在**同一次提交内**完成"从 `index.md` 移除 + 加进 `index-archive.md` + 插入归档头注"三个动作，MUST NOT 分次做。
- **项目没有 `docs/index.md` 时**（需求真相源承载在 README 时常见）：只做"改 frontmatter + 插入归档头注"两个动作，MUST NOT 为了归档而临时造一个索引。缺 index 是 §三层真相源 里"只报告不阻断"的缺口，由用户决定何时建，MUST NOT 借归档之名代建。

### 3. 归档触发：按权威面，不按日期

**MUST NOT 用"超过 N 天没动"当归档判据**——长期有效的设计文档会被误杀，而上周刚写、昨天就被推翻的 spec 会被放过。判据只有一条：**文档描述的权威面是否还成立**。

`authority_refs` 写本文所描述的权威实体，与 `assets/context-layer/probe-set.md` 的同名字段同构：接口签名与版本 / 路由或配置开关 / DB schema 与唯一键 / 命令与目录约定 / 对外契约与字段枚举。写具体到可比对的粒度，MUST NOT 写成"支付模块"这种笼统范围。

**触发点挂在既有的完成与自动合并门上，不新增门**。准出时执行三步：

1. **盘点本次触碰的权威面**——与 `capability/curated.md` §7 新鲜度纪律、`capability/context-engineering.md` §5 刷 card 用的是**同一个面**：canonical 接口签名与版本、废弃标记、路由与配置开关、DB schema 与唯一键、兼容窗口、命令与目录约定。**哪怕只改了 3 行**。
   **"触碰"不等于"删除"**：替换清单里被删除或被替换的条目必然在内，但**不止于此**——枚举加值、可选字段改必填、默认值或校验规则变更、错误码语义调整，这些一个都没删，却同样让描述它的文档失准。**MUST NOT 把这一步退化成"照抄替换清单"**；替换清单为"无"的改动照样可能触碰权威面。
2. **比对**：拿这份清单去查 `docs/index.md` 现行区所列文档的 `authority_refs`（**只查现行区**——归档过的本就不代表现行口径，不必再判；这也让扫描成本与现行文档数成正比而非与项目年龄成正比）。项目没有 index 时，用 `grep -rn -A5 "^authority_refs:" docs/` 取全部声明。
3. **逐篇判定，结果 MUST 落盘**：
   - 仍准确 → 保持 `active`，并把 `last_confirmed` 更新为当天。**判定不留痕等于没判**——下次准出还要重判，且没人能回答"这篇上次被确认准确是什么时候"。
   - 已失准 → 按上表转对应生命周期，并完成 §2 的三个动作。

   判定结果 MUST NOT 悬空。准出核对项见 `worktree开发纪律.md` §完成与自动合并门。

### 4. 归档降权而非删除

归档 MUST NOT 删文件——删掉会让历史链接烂尾，也丢掉"当初为什么这么定"的证据。改为在 frontmatter 之后、正文标题之前插入固定头注。

**头注模板、完整的端到端示例、以及三个账本的分卷与淘汰细则，见 `文档归档与账本收敛.md`**——判定出需要归档的文档时、或要写三个账本时才读，不必常驻。

### 5. 账本的读取纪律（常驻）

`docs/report/bug修复历史.md` 与 `docs/report/测试场景覆盖度.md` **是检索索引，不是阅读材料**：MUST 用关键词检索定位条目，MUST NOT 把整份账本读进上下文。两者形态不同（追加式 vs 状态表），收敛方式也不同，细则见 `文档归档与账本收敛.md` §账本收敛。

`docs/report/资产补建信号.md` 同一条纪律：读它时 MUST 只取状态表与本次任务新增的行，MUST NOT 整份读入（`资产补建信号.md` §3）。

### 6. 准出时归并需求真相源

准出（完成与自动合并门，见 `worktree开发纪律.md`）时，除**本文 §3 归档触发**定义的生命周期结算外还有一件事：**把本次的口径变化归并回需求真相源**。

- 本次若有变更 PRD、或改变了用户旅程 / 成功指标 / 能力状态，MUST 把口径变化归并回 `REQUIREMENTS.md`（真相源承载在 README 时归并回该节）——**含旅程叙事回填，MUST NOT 只翻一个 Scope 状态位**。
- 归并后变更 PRD 标 `lifecycle: merged`、加归档头注、移入归档索引（详见 `ai-prd` skill §PRD 生命周期与 `文档归档与账本收敛.md`）。
- 架构边界被本次改动的，同步改架构真相源；两层都改完才更新 `docs/index.md`。
- 这两件事（归并 + 结算）都在准出门内完成，MUST NOT 留作"下次一起做"——变更 PRD 一旦堆积，`REQUIREMENTS.md` 就退化成一份过期文档，三层真相源当场破一层。
