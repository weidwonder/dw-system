# 文档治理（core）

所有 mode 使用同一套项目级输出目录。生成文档前先创建所需目录，不得把交付物散落到项目根或 `docs/` 根。

| 文档类型 | 唯一目录 | 示例 |
|---|---|---|
| 整品 PRD（唯一真相源）及其附录 | `docs/` 根 | `docs/REQUIREMENTS.md`、`docs/REQUIREMENTS-appendix.md` |
| 变更 PRD、Overview、Lean Change Spec、技术 Spec、测试 Spec、设计、契约 | `docs/spec/` | `docs/spec/payment-lean-change-spec.md` |
| Coding Plan、实施计划、迁移计划、交接文档（上下文交接） | `docs/plan/` | `docs/plan/payment-coding-plan.md` |
| 执行报告、验证报告、测试报告、审计报告 | `docs/report/` | `docs/report/payment-verification-report.md` |
| Bug 修复历史（**追加式**账本，见下方例外说明 + §5 收敛规则） | `docs/report/` | `docs/report/bug修复历史.md` |
| 测试场景覆盖度台账（**状态表**，见下方例外说明 + §5 收敛规则） | `docs/report/` | `docs/report/测试场景覆盖度.md` |
| 测试资产（真实输入样本，**不是文档**） | 项目测试目录，探测优先 | `tests/fixtures/<场景名>/` |
| 架构决策记录（ADR）| `docs/decisions/` | `docs/decisions/0007-use-outbox-for-mq.md` |

## ADR（架构决策记录，按需）

日常小决策记进 Overview 的"已定决策"一行表即可；只有**影响面大、以后可能被反复重议**的架构级取舍才单独立 ADR：

- 顺序编号存 `docs/decisions/NNNN-<短标题>.md`；每篇写 **Context（为什么要决策）/ Decision（定了什么）/ Alternatives Considered（考虑过哪些方案、为何否）/ Consequences（代价与影响）**。
- **不删旧 ADR**：决策被推翻时，写一篇新 ADR 引用并 supersede 旧的，保留决策演进史（防止把同一问题反复重决）。

## 硬规则

- 文件名必须表达业务主题与文档角色，不得使用生成工具名作为目录或文件名前缀。
- 不得创建 `docs/superpowers/`、`docs/claude/`、`docs/codex/` 等工具专属产物目录。
- 不得把 spec 或 plan 放项目根、仓库根或 `docs/` 根。唯一例外：整品 PRD（`REQUIREMENTS.md` 及其附录）作为唯一真相源放 `docs/` 根，便于发现。
- 同一需求的文档通过正文中的相对链接互相引用；移动文档时必须同步修复引用。
- `docs/index.md` 是发现入口，但不能替代上述目录规则；它**只索引现行口径**，历史文档进归档索引（见下方 §文档生命周期与索引门控）。
- 报告只有在流程要求形成书面报告时才创建；一旦创建，必须写入 `docs/report/`。
- **例外（两个固定文件名的单一账本）**：不按"每次新建一个 `<feature>-<report-type>-report.md`"的规则拆分。两者形态不同——`bug修复历史.md` 是**追加式**（每条都是发生过的一次性事实），`测试场景覆盖度.md` 是**状态表**（每行描述此刻的覆盖状态，同一场景只有一行）；收敛规则见 §5——
  - `docs/report/bug修复历史.md`：写入规则见 `bug诊断纪律.md` Phase 3 §归档问题处理历史，供 Phase 0 查重检索。
  - `docs/report/测试场景覆盖度.md`：写入规则见 `测试资产纪律.md` §3，模板 `assets/templates/test-coverage.md`，供批量向用户索要真实素材。
- **测试资产不是文档**：用户提供的真实输入样本落项目**测试目录**（探测既有惯例，兜底 `tests/fixtures/<场景名>/`），MUST NOT 塞进 `docs/`。含凭证的样本进同级 `secrets/` 并 gitignore，脱敏副本 `secrets.example/` 入库。规则见 `测试资产纪律.md` §2。

## 文档生命周期与索引门控

> **为什么要这一节**：`docs/spec/`、`docs/plan/` 是**过程产物**——它们记录的是当时的意图，会随代码演进与现实背离。代码侧有替换清单核销、context 层有 freshness 与权威面触发，文档层必须有同构的退出机制，否则索引单调增长、旧口径被后来的 agent 当成现行事实。**只增不减的索引既误导又烧上下文。**

### 1. 生命周期位（MUST，新建文档）

`docs/` 下新建的 spec / plan / report / PRD，头部 frontmatter MUST 声明：

```yaml
---
lifecycle: active          # active | merged | superseded | obsolete
superseded_by: ''          # lifecycle: superseded 时 MUST 填被谁取代（相对路径）
archived: ''               # 非 active 时 MUST 填转归档日期 YYYY-MM-DD
last_confirmed: ''         # 最近一次被 §3 触发复核、判定仍准确的日期 YYYY-MM-DD；新建时填当天
authority_refs:            # 本文描述的权威面，见 §3；本文不冻结任何权威面时写 ['无']
  - ''
---
```

| 值 | 含义 | 索引归属 |
|---|---|---|
| `active` | 现行有效，可据此实施 | `docs/index.md` |
| `merged` | 口径已归并进 `REQUIREMENTS.md` / `ARCHITECTURE.md` / 代码，本文只剩历史价值 | 归档索引 |
| `superseded` | 被更新的同类文档取代 | 归档索引 |
| `obsolete` | 描述的能力已下线或权威面已删除 | 归档索引 |

**字段名是 `lifecycle` 不是 `status`**——后者已被"写作进度"与 PRD 的自由文本状态占用，MUST NOT 混用。

**存量豁免**：升级前已存在、无 frontmatter 的文档默认视为 `active`，MUST NOT 为补齐字段而批量回改；只有当它被 §3 的权威面触发复核时才就地补齐并结算。

### 2. 索引分层（MUST，团队版；个人版 SHOULD）

- `docs/index.md` **只索引现行口径**：真相源（`REQUIREMENTS.md` / `ARCHITECTURE.md`）、`lifecycle: active` 的 spec/plan/report、现行 ADR、现行 UI 原型、两个账本的入口，末尾加一行指向归档索引。
- `docs/index-archive.md` 索引全部非 active 文档，按年份分区，每条注明生命周期值与取代它的文档。**文件不存在则在首次归档时创建**。
- **文件原地不动，只有索引分层**——移动文件会破坏既有相对链接，代价高于收益。归档也不需要修改指向它的既有链接；但现行文档若把某篇归档文档当作实施依据，MUST 改指向接替它的现行文档。
- 文档转归档 MUST 在**同一次提交内**完成"从 `index.md` 移除 + 加进 `index-archive.md` + 插入归档头注"三个动作，MUST NOT 分次做。
- **项目没有 `docs/index.md` 时**（个人版常见）：只做"改 frontmatter + 插入归档头注"两个动作，MUST NOT 为了归档而临时造一个索引。

### 3. 归档触发：按权威面，不按日期

**MUST NOT 用"超过 N 天没动"当归档判据**——长期有效的设计文档会被误杀，而上周刚写、昨天就被推翻的 spec 会被放过。判据只有一条：**文档描述的权威面是否还成立**。

`authority_refs` 写本文所描述的权威实体，与 `assets/context-layer/probe-set.md` 的同名字段同构：接口签名与版本 / 路由或配置开关 / DB schema 与唯一键 / 命令与目录约定 / 对外契约与字段枚举。写具体到可比对的粒度，MUST NOT 写成"支付模块"这种笼统范围。

**触发点挂在既有的完成与自动合并门上，不新增门**。准出时执行三步：

1. **盘点本次触碰的权威面**——与 `company/mode-team.md` §新鲜度纪律、`company/context-engineering.md` §5 刷 card 用的是**同一个面**：canonical 接口签名与版本、废弃标记、路由与配置开关、DB schema 与唯一键、兼容窗口、命令与目录约定。**哪怕只改了 3 行**。
   **"触碰"不等于"删除"**：替换清单里被删除或被替换的条目必然在内，但**不止于此**——枚举加值、可选字段改必填、默认值或校验规则变更、错误码语义调整，这些一个都没删，却同样让描述它的文档失准。**MUST NOT 把这一步退化成"照抄替换清单"**；替换清单为"无"的改动照样可能触碰权威面。
2. **比对**：拿这份清单去查 `docs/index.md` 现行区所列文档的 `authority_refs`（**只查现行区**——归档过的本就不代表现行口径，不必再判；这也让扫描成本与现行文档数成正比而非与项目年龄成正比）。项目没有 index 时，用 `grep -rn -A5 "^authority_refs:" docs/` 取全部声明。
3. **逐篇判定，结果 MUST 落盘**：
   - 仍准确 → 保持 `active`，并把 `last_confirmed` 更新为当天。**判定不留痕等于没判**——下次准出还要重判，且没人能回答"这篇上次被确认准确是什么时候"。
   - 已失准 → 按上表转对应生命周期，并完成 §2 的三个动作。

   判定结果 MUST NOT 悬空。准出核对项见 `worktree开发纪律.md` §完成与自动合并门。

### 4. 归档降权而非删除

归档 MUST NOT 删文件——删掉会让历史链接烂尾，也丢掉"当初为什么这么定"的证据。改为在 frontmatter 之后、正文标题之前插入固定头注。

**头注模板、完整的端到端示例、以及两个账本的分卷与淘汰细则，见 `文档归档与账本收敛.md`**——判定出需要归档的文档时、或要写两个账本时才读，不必常驻。

### 5. 两个账本的读取纪律（常驻）

`docs/report/bug修复历史.md` 与 `docs/report/测试场景覆盖度.md` **是检索索引，不是阅读材料**：MUST 用关键词检索定位条目，MUST NOT 把整份账本读进上下文。两者形态不同（追加式 vs 状态表），收敛方式也不同，细则见 `文档归档与账本收敛.md` §账本收敛。

## 默认命名

- Lean Change Spec：`docs/spec/<change-name>-lean-change-spec.md`
- Overview：`docs/spec/<project-name>-overview.md`
- 技术 Spec：`docs/spec/<repo>-<feature>-eng-spec.md`
- 测试 Spec：`docs/spec/<repo>-<feature>-test-spec.md`
- Coding Plan：`docs/plan/<feature>-coding-plan.md`
- 交接文档：`docs/plan/<feature>-handoff.md`（见 `上下文卫生.md` 规则 2；任务未完成时随任务 worktree 走，合并时若已无用可不带回主分支）
- 报告：`docs/report/<feature>-<report-type>-report.md`

项目已有更严格的文件名约定时可以沿用，但目录不可改变。
