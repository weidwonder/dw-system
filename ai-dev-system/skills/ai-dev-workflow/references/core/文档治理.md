## 三层真相源（零上下文交接的底线）

> **为什么要这一节**：项目 MUST 对任何接手者——人或 AI agent——做到**零上下文交接**：需求、架构、实现三层真相源都能从项目自身定位，不依赖任何人口头介绍。层次固定为这三层，**承载形态随项目已有的资产变化**——小项目用 README 的一节就合规，MUST NOT 因为项目小就允许某一层缺失。

| 真相源层 | 回答的问题 | 最小承载形态（三选其一即合规） | 项目长大后 SHOULD 升级为 |
|---|---|---|---|
| **需求** | 现在是什么、为什么做、现在有哪些功能 | README 的一节 **或** `docs/index.md`（二选一即可） | `docs/REQUIREMENTS.md` 主文档（放 `docs/` 根）+ `docs/requirements/` 一级子模块；写什么、何时升级、何时拆，见 ↓ §需求真相源写什么、怎么分层 |
| **架构** | 有哪些模块、各自职责与边界 | README 的一节"架构与边界"：模块划分 / 各自职责一句话 / 对外边界 / 不做什么，**可短至 10 行**；模块路径 MUST 写成反引号代码片段或相对链接（见 ↓ 可验证） | `docs/ARCHITECTURE.md`；存在跨服务场景时再补 `engineering-context/scenes/` |
| **实现** | 某件事落在哪段代码、哪个是权威实现 | `engineering-context/` 的 registry + cards——**必备，不是升级项**：查不到卡片就读源码、读完当场补上（`代码事实纪律.md` §4），事实带 cite | 跨服务场景补 `engineering-context/scenes/`；探测到**代码图谱**时结构性定位走索引（`capability/graph.md`）|

- **可达性（MUST）**：三层真相源都 MUST 能从 README 或 `docs/index.md` 出发、**≤2 跳链接到达**。超过 2 跳等于不存在——接手者找不到就会去猜，猜出来的口径就是下一个错误的起点。
- **缺口只报告、不阻断（MUST）**：唤起或初始化时发现某层缺失或超过 2 跳，MUST 报告为"零上下文交接缺口"并指明补哪一份，MUST NOT 因此中止流程，也 MUST NOT 代用户自动创建——旧项目补齐需要时间，补的时机由用户定。上表的 SHOULD 升级项同理，只提示不代劳。
- **需求 MUST 先写清楚再动代码**，但真相源的**更新**在**准出门**完成（见 §6）。这是两件事，MUST NOT 混为一谈：开发前定稿的是**意图**（变更 PRD 或整品 PRD 新章节），开发后归并的才是**现状**。**MUST NOT 在实现验收之前把本次口径写进需求真相源**——那会让它描述一件尚未存在、甚至可能中途被推翻的事，而真相源的全部价值就在于"这里写的都已经是真的"。
- **可验证（不因卡片还少而豁免）**：这三层的可达性与"实现真相源可用"都是**机器可判定**的检查，`ctx probe` 有四道专门的交接题型覆盖它们——`requirement-reachable`（需求真相源 ≤2 跳可达）、`architecture-reachable`（架构真相源 ≤2 跳可达）、`implementation-usable`（架构节列出的模块路径都存在）、`rationale-traceable`（索引现行区各 spec 的 `authority_refs` 非空）。

  **这四道题读的是项目自身文件，不依赖卡片里有多少条目**，所以**卡片还没攒起来的起步态项目同样跑得起来、同样该跑**。骨架里已经有 `engineering-context/probe-set.md`（初始化时 `ctx init` 生成，见 `init-初始化.md` 第 5b 步），任何项目都 SHOULD 至少把这四道题填进去：照 `assets/context-layer/probe-set.md` §零上下文交接检查 里那张标着**「示例（可直接抄进自己项目的探针表）」**的表抄一份（表头是 `| # | 类型 | 输入 | 期望 | severity | weight | status | authority_refs |`，编号 41–44 的那四行），然后 `ctx probe`。
  **MUST NOT 抄错表**：同一文件里另有两张**说明用**的表（`## 题型说明（非探针表）` 的 `| # | 题型 | …`、本节开头的 `| 检查项 | 类型名 | …`），它们的表头都不是解析器认的形状，抄了会解析出 0 道题。
  跑的频次跟着 `probe-set.md` §运行节奏：CI 发布或里程碑节点跑，**MUST NOT 塞进 coding agent 的每轮 loop**。

  两个易错点：**①探针表的表头首列必须是 `#`、次列必须写 `类型` 或 `type`**，写成「题型」整张表不会被解析。症状是 `ctx probe` 打出下面两行并以退出码 1 结束：

  ```
  门禁自检：🛑 失效 — context 层为空（无 registry/cards），无法自检
  🛑 GATE-BROKEN：门禁自检未通过，拒绝出具结论（流水线应红）。
  ```

  **这条报错在卡片还空着的项目上真正的含义是探针表没被解析出来**，MUST 先查表头，**MUST NOT 照它字面去给 registry 现编条目**——registry 的内容按 `代码事实纪律.md` §4 在干活过程中真读了源码才补，为了让自检变绿而填等于制造过期权威；**②架构节里的模块路径 MUST 写成反引号代码片段（`` `src/app.js` ``）或相对链接**才会被 `implementation-usable` 计入——上表说"架构一节可短至 10 行"，但那 10 行里的路径若是散文里的裸文字，抽不到就判失败，而不是放行（零条目算通过就是假门禁）。

### 需求真相源写什么、怎么分层

> **一句话**：只写现在，不写来历。

- **定位（MUST）**：需求真相源只描述 **main 分支上已经实现的现状**，回答"这个项目是什么、为什么做、现在有哪些功能"。**MUST NOT 包含**：项目历史与演进过程、改动前后对比（"原来是 3 次"）、技术选型与实现方案、需求是怎么调整过来的。想知道某条口径当初为什么这么定，去归档索引翻当时那份变更 PRD——**那才是它的去处**。
- **尚未实现的一切 MUST 去 `docs/TODO.md`**（见 §TODO 出口）：在做中/待做的功能、下一步规划、长期形态、待澄清的开放问题、已知风险。**MUST NOT 在需求真相源里留一个"计划中"小节**——它一旦存在，读者就无法再信任"这里写的都是现状"这条前提，整份文档的价值随之归零；读者退回逐条去问人或读代码，等于这份文档不存在。
- **两层承载，MUST NOT 再往下分**：

  | 层 | 文件 | 写什么 |
  |---|---|---|
  | 主文档 | `docs/REQUIREMENTS.md` | **薄**：是什么 / 为什么做 / 有哪些功能（每条一句话 + 链到子模块）/ 用户怎么用 / 明确不做什么 / 服务质量要求 / 子模块划分方式 |
  | 一级子模块 | `docs/requirements/<模块>.md` | 用户可感知的具体行为规则：次数与额度上限、权限范围、状态流转、报错口径、边界条件 |

  **MUST NOT 出现 `docs/requirements/<域>/<模块>.md` 这样的二级目录**——两层是上限不是起点。
- **细节边界（MUST）**：判据是**用户能不能感知**。感知得到的（每天最多 5 次、没权限时看到什么、报错怎么给）写进子模块；感知不到的（缓存策略、内部阈值、数据结构、用了哪个库）**MUST NOT 写**——那是实现真相源（cards）与 spec 的事。这条线与 §膨胀分层 说的"PRD 的细节边界是用户可感知的行为契约与验收口径"是同一条。
- **何时拆（SHOULD）**：主文档 **<500 行 SHOULD NOT 拆**——没到量就拆只让读者多跳一次；**>800 行 SHOULD 拆**；500–800 行由作者判断。行数只是信号，**MUST NOT 拿它当强制门**去卡住一次本来该过的准出。
- **划分方式 MUST 写在主文档里**：主文档 MUST 有一节说明本项目的子模块**按什么维度切、切成哪几块、各自文件名**。没有这一节，下一个人补功能时就会自己发明一套切法；两套切法并存之后，没人能判断某条规则该往哪找，也没人敢删任何一份。
- **不够用时才升级（MUST）**：真相源承载在 README 一节或 `docs/index.md` 时，**平时 MUST NOT 强制升级**（那是上表"只提示不代劳"的一部分）。只有当**本次准出归并确实有一条用户可感知的规则要写、而现有承载放不下**时，MUST 当场创建 `docs/REQUIREMENTS.md` 把规则写进去，随后更新入口指向它。**`docs/index.md` 一定放不下**——它是索引，每条只有标题与一句话简介，写不下"每天最多 5 次"这种规则；把规则塞进索引会同时毁掉索引与真相源两件东西。

## ADR（架构决策记录，按需）

日常小决策记进 Overview 的"已定决策"一行表即可；只有**影响面大、以后可能被反复重议**的架构级取舍才单独立 ADR：

- 顺序编号存 `docs/decisions/NNNN-<短标题>.md`；每篇写 **Context（为什么要决策）/ Decision（定了什么）/ Alternatives Considered（考虑过哪些方案、为何否）/ Consequences（代价与影响）**。
- **不删旧 ADR**：决策被推翻时，写一篇新 ADR 引用并 supersede 旧的，保留决策演进史（防止把同一问题反复重决）。

## 硬规则

- 文件名必须表达业务主题与文档角色，不得使用生成工具名作为目录或文件名前缀。
- 不得创建 `docs/superpowers/`、`docs/claude/`、`docs/codex/` 等工具专属产物目录。
- 不得把 spec 或 plan 放项目根、仓库根或 `docs/` 根。例外只有三类，都为了一眼可见：需求与架构两层真相源（`REQUIREMENTS.md`、`ARCHITECTURE.md`）、`docs/TODO.md`。需求真相源的一级子模块住 `docs/requirements/`，**MUST NOT 平铺在 `docs/` 根**——模块一多会把根目录埋掉。
- 同一需求的文档通过正文中的相对链接互相引用；移动文档时必须同步修复引用。
- `docs/index.md` 是发现入口，但不能替代上述目录规则；它**只索引现行口径**，历史文档进归档索引（见下方 §文档生命周期与索引门控）。
- 报告只有在流程要求形成书面报告时才创建；一旦创建，必须写入 `docs/report/`。
- **例外（两个固定文件名的单一账本）**：不按"每次新建一个 `<feature>-<report-type>-report.md`"的规则拆分。两者形态不同——`bug修复历史.md` 是**追加式**（每条都是发生过的一次性事实），`测试场景覆盖度.md` 是**状态表**（每行描述此刻的覆盖状态，同一场景只有一行）；收敛规则见 §5——
  - `docs/report/bug修复历史.md`：写入规则见 `bug诊断纪律.md` Phase 3 §归档问题处理历史，供 Phase 0 查重检索。
  - `docs/report/测试场景覆盖度.md`：写入规则见 `测试资产纪律.md` §3，模板 `assets/templates/test-coverage.md`，供批量向用户索要真实素材。
- **两个账本的生命周期归属**：MUST 恒为 `lifecycle: active`、`authority_refs: ['无']`，**MUST NOT 被 §3 的权威面触发转归档**——它们记录的是发生过的事实与此刻的状态，不冻结任何会过期的权威口径；收敛靠各自的分卷/就地改行规则，不靠归档。
- **测试资产不是文档**：用户提供的真实输入样本落项目**测试目录**（探测既有惯例，兜底 `tests/fixtures/<场景名>/`），MUST NOT 塞进 `docs/`。含凭证的样本进同级 `secrets/` 并 gitignore，脱敏副本 `secrets.example/` 入库。规则见 `测试资产纪律.md` §2。

## 文档生命周期与索引门控

> **为什么要这一节**：`docs/spec/`、`docs/plan/` 是**过程产物**——它们记录的是当时的意图，会随代码演进与现实背离。代码侧有替换清单核销、context 层有 freshness 与权威面触发，文档层必须有同构的退出机制，否则索引单调增长、旧口径被后来的 agent 当成现行事实。**只增不减的索引既误导又烧上下文。**

### 1. 生命周期位（MUST，新建文档）

`docs/` 下新建的 spec / plan / report / PRD，头部 frontmatter MUST 声明：

```yaml
---
lifecycle: active          # active | merged | superseded | obsolete
superseded_by: ''          # lifecycle: superseded 时 MUST 填被谁取代（相对路径）
archived: ''               # 非 active 时 MUST 填转归档日期 YYYY-MM-DD
last_confirmed: ''         # 最近一次被 §3 触发复核、判定仍准确的日期 YYYY-MM-DD；新建时填当天
authority_refs:            # 本文描述的权威面，见 §3；不冻结任何权威面时写一条 无（注释里 MUST NOT 出现引号：ctx probe 的 rationale-traceable 见引号即不剥注释，整条注释会被当成已填的条目）
  - ''
---
```

| 值 | 含义 | 索引归属 |
|---|---|---|
| `active` | 现行有效，可据此实施 | `docs/index.md` |
| `merged` | 口径已归并进 `REQUIREMENTS.md` / `ARCHITECTURE.md` / 代码，本文只剩历史价值 | 归档索引 |
| `superseded` | 被更新的同类文档取代 | 归档索引 |
| `obsolete` | 描述的能力已下线或权威面已删除 | 归档索引 |

**字段名是 `lifecycle` 不是 `status`**——后者已被"写作进度"与 PRD 的自由文本状态占用，MUST NOT 混用。

**存量豁免**：升级前已存在、无 frontmatter 的文档默认视为 `active`，MUST NOT 为补齐字段而批量回改；只有当它被 §3 的权威面触发复核时才就地补齐并结算。

### 2. 索引分层（现行区文档 >20 篇时 MUST，否则 SHOULD）

**判据是文档数量，不是人数、不是协作面、也不是代码规模**：`docs/index.md` 现行区所列文档超过 20 篇时 MUST 分层，20 篇及以内 SHOULD 分层。索引分层要解决的问题只有一个——**索引长到没人读、AI 也读不完**，那是文档基数的函数；单人长期项目照样会长到那一步，十个人的新项目则未必。数到 20 篇就开始分层，MUST NOT 等到"感觉乱了"再补。

- `docs/index.md` **只索引现行口径**：三层真相源（`REQUIREMENTS.md` / `ARCHITECTURE.md`，或承载它们的 README 小节）、`lifecycle: active` 的 spec/plan/report、现行 ADR、现行 UI 原型、两个账本的入口，末尾加一行指向归档索引。
- `docs/index-archive.md` 索引全部非 active 文档，按年份分区，每条注明生命周期值与取代它的文档。**文件不存在则在首次归档时创建**。
- **文件原地不动，只有索引分层**——移动文件会破坏既有相对链接，代价高于收益。归档也不需要修改指向它的既有链接；但现行文档若把某篇归档文档当作实施依据，MUST 改指向接替它的现行文档。
- 文档转归档 MUST 在**同一次提交内**完成"从 `index.md` 移除 + 加进 `index-archive.md` + 插入归档头注"三个动作，MUST NOT 分次做。
- **项目没有 `docs/index.md` 时**（需求真相源承载在 README 时常见）：只做"改 frontmatter + 插入归档头注"两个动作，MUST NOT 为了归档而临时造一个索引。缺 index 是 §三层真相源 里"只报告不阻断"的缺口，由用户决定何时建，MUST NOT 借归档之名代建。

### 3. 归档触发：按权威面，不按日期

**MUST NOT 用"超过 N 天没动"当归档判据**——长期有效的设计文档会被误杀，而上周刚写、昨天就被推翻的 spec 会被放过。判据只有一条：**文档描述的权威面是否还成立**。

`authority_refs` 写本文所描述的权威实体，**类目只有一份权威清单，见下方 §3 第 1 步**（取值风格与 `assets/context-layer/probe-set.md` 的同名字段一致）。写具体到可比对的粒度，MUST NOT 写成"支付模块"这种笼统范围。

> **为什么类目不在这里列**：这里是"写文档时怎么填字段"，第 1 步是"评审时按什么盘点"，两处列同一份东西必然漂移——本节此前确实漂过（一份有「对外契约与字段枚举」、另一份有「废弃标记」「兼容窗口」，谁也不知道以哪份为准）。**MUST NOT 在本节复制那份清单**，要看就跳到 §3 第 1 步。

**触发点挂在既有的代码评审门上，不新增门**（判据仍在本节，那道门只是执行者；见 `代码评审纪律.md` §四条轴）。

**判定与落盘分属两个角色，MUST 分清**：第 1–2 步与第 3 步的**判定**由该门的 **D 文档轴**子代理做并写进报告（它只报告、MUST NOT 改文件，见 `代码评审纪律.md` §子代理 prompt 模板 内的〈硬要求〉段）；第 3 步的**落盘动作**（改 frontmatter、插归档头注、动两个索引、就地更正部分失准的那几行、把仍准确与已更正的 `last_confirmed` 更新为当天）由**主会话在收到报告后当场执行**。**MUST NOT 把落盘挂在"P0/P1 修完才过门"上**——"仍准确 → 更新 `last_confirmed`"根本不是一条问题，挂在那条口径下它永远不会被执行，而完成门却要核对它已执行。

**为什么不是主会话在完成门自己做**：完成门在任务最末尾、上下文最满，而这三步是一整套活，混在一串"核对既有产物"的条目里最容易被整条跳过；更要紧的是零命中时它不产出任何东西，事后分不出"扫了确实没有"和"压根没扫"——子代理天然交报告，零命中也留下书面结论。完成门只**核对**这份报告与落盘结果（见 `worktree开发纪律.md` §完成与自动合并门）。

三步是：

1. **盘点本次触碰的权威面**（**本清单是全文唯一权威，`authority_refs` 的类目也以此为准**）——**哪怕只改了 3 行**：

   | # | 权威面 | 也触发刷卡？ |
   |---|---|---|
   | 1 | canonical 接口签名与版本 | ✅ |
   | 2 | 废弃标记 | ✅ |
   | 3 | 路由与配置开关 | ✅ |
   | 4 | DB schema 与唯一键 | ✅ |
   | 5 | 兼容窗口 | ✅ |
   | 6 | 命令与目录约定 | ❌ 文档层专有 |
   | 7 | 对外契约与字段枚举 | ❌ 文档层专有 |
   | 8 | **流程与门禁契约**（门的位置与顺序、轴或步骤的集合与编号、准出项的语义、谁在哪一步执行什么）| ❌ 文档层专有 |

   **与刷卡面是同源但更宽，MUST NOT 说成"同一个面"**：凡「也触发刷卡？」列为 ✅ 的与 `代码事实纪律.md` §8 的刷卡面逐条对应，标 ❌ 的是**文档层专有、不触发刷卡**——卡片事实以合入后的源码为准（§9 真相方向铁律），而一道门的轴集合根本不是卡片描述的对象。**以表内该列为准，MUST NOT 在正文另记一个数字**。

   **「流程与门禁契约」这一类是给"交付物本身就是流程约定"的项目留的**（本体系自己就是）：其余各类都面向代码型权威面，纯 markdown 的流程变更套不进任何一类，于是"本次没触碰任何权威面"就成了一个合法的收工借口——而改一道门的轴集合恰恰是最该让描述它的文档跟着变的那种改动。

   **"触碰"不等于"删除"**：替换清单里被删除或被替换的条目必然在内，但**不止于此**——枚举加值、可选字段改必填、默认值或校验规则变更、错误码语义调整，这些一个都没删，却同样让描述它的文档失准。**MUST NOT 把这一步退化成"照抄替换清单"**；替换清单为"无"的改动照样可能触碰权威面。
2. **比对（两步都要做，MUST NOT 只做机械那步）**：先拿这份清单去查 `docs/index.md` 现行区所列文档的 `authority_refs`；**随后 MUST 再对本次改动的关键术语做一次现行区全文检索**（门名、轴名、步骤号、命令名、字段名等）。两步给出的命中集不一样：一篇 spec 的正文大段描述某道门，`authority_refs` 里却可能一条都没登记它——只做机械比对就会整篇漏掉。**漏登记本身也是一条发现**，MUST 在报告里指出该篇的 `authority_refs` 需要补。（**只查现行区**——归档过的本就不代表现行口径，不必再判；这也让扫描成本与现行文档数成正比而非与项目年龄成正比）。项目没有 index 时，用 `grep -rn -A5 "^authority_refs:" docs/` 取全部声明。
3. **逐篇判定，结果 MUST 落盘**：
   - **仍准确** → 保持 `active`，并把 `last_confirmed` 更新为当天。**判定不留痕等于没判**——下次准出还要重判，且没人能回答"这篇上次被确认准确是什么时候"。
   - **部分失准** → **就地更正 + 更新 `last_confirmed`**，生命周期保持 `active`。判据：**本篇的主体仍是现行口径，只有若干行被新口径推翻**。处置是改正那几行，或给不该改写的历史记载加一句"当时口径为 X"的括注（哪些行属历史记载见 ↓ 勾验表那条），改完把 `last_confirmed` 更新为当天。**MUST NOT 因为几行失准就把整篇转 `superseded`**——那会让仍现行的主体连同失准的几行一起失效，读者再没有任何一篇现行文档可依据，而本次改动其实并没有取代它。
   - **已失准** → 按上表转对应生命周期，并完成 §2 的三个动作。判据：**整篇的结论已被取代**——本篇描述的那件事现在由另一篇（或另一套口径）说了算，逐行更正救不回来。**MUST NOT 反过来把这一档做成就地更正**：把一篇已被取代的文档逐行改成新口径，等于凭空多出一篇与接替者重复的现行文档，且丢掉"当初为什么这么定"的证据（§4 归档降权而非删除）。

   **勾验表（"如何验证"这类 checklist）按勾选状态判**：**未勾选**的项会被续跑，按**现行口径**判——口径变了就是失准，MUST 改；**已勾选**的项是"当时确实这么跑过"的历史记录，属历史记载，MUST NOT 为了对齐新口径去改写它（要标注可加一句"当时口径为 X"）。`ai-dev-system/migrations/` 下的历史指南同理，一律豁免。

   **本步只改文字，MUST NOT 翻转勾选位**：勾选位是一条**事实主张**（"这一项按它现在写的内容跑过了"），而本步做的是口径对齐，两者不是一回事。口径一变，原先跑过的那次往往已经不满足新写法——此时把 `[ ]` 翻成 `[x]` 等于用新口径追认一次并未发生的执行。历史执行事实要留就写成不带勾选位的括注（"当次实跑的是 X 口径"）。反向亦然：MUST NOT 因为口径变了就把 `[x]` 翻回 `[ ]`，那是抹掉历史记载。勾选位只由**真的跑了那一项**的那次执行来改。

   判定结果 MUST NOT 悬空。**零命中同样 MUST 留下书面结论**（"扫了 N 篇现行文档、0 篇失准"）——这是本节唯一能与"没执行"区分的凭据。准出核对项见 `worktree开发纪律.md` §完成与自动合并门。

**`ctx probe` 是这三步的辅助，不是替代**（与 `代码评审纪律.md` §替换清单 对静态检查工具的定位一致：判据是 MUST，工具是 SHOULD）：它的 B 类题型验的是**可达性与字段非空**（真相源从入口 ≤2 跳可达、架构节列出的模块路径存在、现行区各 spec 的 `authority_refs` 非空），**不读正文**。所以 **probe 全绿 MUST NOT 被读成"文档还准"**——一篇 spec 的 `authority_refs` 填得好好的、正文里的默认值和错误码语义却早已背离，probe 照样绿。

### 4. 归档降权而非删除

归档 MUST NOT 删文件——删掉会让历史链接烂尾，也丢掉"当初为什么这么定"的证据。改为在 frontmatter 之后、正文标题之前插入固定头注。

**头注模板、完整的端到端示例、以及两个账本的分卷与淘汰细则，见 `文档归档与账本收敛.md`**——判定出需要归档的文档时、或要写这两个账本时才读。

### 5. 账本的读取纪律

`docs/report/bug修复历史.md` 与 `docs/report/测试场景覆盖度.md` **是检索索引，不是阅读材料**：MUST 用关键词检索定位条目，MUST NOT 把整份账本读进上下文。两者形态不同（追加式 vs 状态表），收敛方式也不同，细则见 `文档归档与账本收敛.md` §账本收敛。

### 6. 准出时归并需求真相源

准出（完成与自动合并门，见 `worktree开发纪律.md`）时，除**核对**本文 §3 归档触发定义的生命周期结算**结论**外还有一件事：**把本次的口径变化归并回需求真相源**。结算本身在评审门已经做完（判定归 D 轴、落盘归主会话），准出 MUST NOT 重做盘点。

**归并落点按"本次改变了什么口径"分派（MUST 逐类过一遍，MUST NOT 只看功能清单）**：

| 本次改变了什么 | 归并落点 | 主文档动不动 |
|---|---|---|
| 新增一个功能，或去掉一个功能 | 主文档功能清单增删一行 + 建或删对应子模块文档 | 动 |
| **已交付功能的行为规则变了**（次数上限、权限范围、状态流转、报错口径、边界条件）| **对应子模块文档就地改写** | 不动 |
| 用户怎么用变了、成功指标变了 | 主文档的旅程节与服务质量节，**含旅程叙事回填** | 动 |
| 明确不做什么变了 | 主文档非目标节 | 动 |
| 本次冒出来、但不做的事 | `docs/TODO.md`（够格判据见 §TODO 出口）| 不动 |
| 本次做掉了 `TODO.md` 里的条目 | 删掉那条 | 不动 |

- **「功能清单没变化」MUST NOT 被读成「无需归并」**——**改已交付功能的行为规则、而功能清单一动不动，是最常见的迭代形态**（"每天 3 次改 5 次"：功能还是那个功能，状态还是已交付，旅程一字不改）。照着功能清单看一眼就收工，这条规则会跟着变更 PRD 一起进归档区，真相源里从此没有它，而**没有任何机器闸能发现**：`ctx probe` 只验可达性，D 文档轴要比对的那条正文压根不存在。逐类过表是唯一防线。
- **就地改写，MUST NOT 留前后对比**：把 3 改成 5，不写"原为 3 次"、不加变更记录、不留删除线。想知道它当初为什么是 3，去归档索引翻那份变更 PRD。真相源里出现历史，读者就无法再判断哪一句是现状（判据在 §需求真相源写什么、怎么分层）。
- **承载放不下时 MUST 当场创建**：真相源还承载在 `docs/index.md` 或 README 一节，而本次确有一条用户可感知的规则要写、现有承载放不下时，MUST 当场建 `docs/REQUIREMENTS.md` 写进去并更新入口指向。平时不强制，判据同上节。
- **触碰存量文档时 MUST 顺手收敛**（2.8.0 起）。**"触碰"= 本次归并确实要往那份文件里写东西**；只是读过它、或被 `ctx probe`／D 轴扫到，**MUST NOT 算触碰**——否则一次无关改动会被拖去做文档大修。触碰时分两档：
  - **当场做**：删掉该文件里的规划类章节（在做/待做状态、下一步规划、长期形态、开放问题、风险），内容移进 `docs/TODO.md`；存量的 `REQUIREMENTS-appendix.md` 拆进 `docs/requirements/`。这是分钟级动作，不做的话真相源当场违反本篇 §需求真相源写什么、怎么分层。
  - **先问用户**：主文档同时超过拆分阈值、需要拆子模块时，MUST 向用户提出建议并由用户拍板，**MUST NOT 未经确认就自行拆分**——一份上千行的存量主文档拆起来是小时级工程，会把一次改阈值的小迭代变成文档大重构。
- 归并后变更 PRD 标 `lifecycle: merged`、加归档头注、移入归档索引（详见 `ai-prd` skill §PRD 生命周期与 `文档归档与账本收敛.md`）。
- 架构边界被本次改动的，同步改架构真相源；两层都改完才更新 `docs/index.md`。
- **归并**在准出门内完成；**结算**的判定已前移到代码评审门的 D 文档轴、落盘由主会话当场做，准出只核对结论（见 §3）。因此 D 轴对"尚未归并"的真相源只标记「待归并」，MUST NOT 报失准——归并的时机本就在它之后。两件事都 MUST NOT 留作"下次一起做"——变更 PRD 一旦堆积，`REQUIREMENTS.md` 就退化成一份过期文档，三层真相源当场破一层。

## TODO 出口（还没做的事都去这里）

> **为什么要这一节**：需求真相源只写已实现的现状（§需求真相源写什么、怎么分层），于是"还没做的"必须有一个固定去处，否则它们会重新渗回真相源，把那条"这里写的都是真的"的前提毁掉。给它一个出口，真相源才守得住。

`docs/TODO.md` 是项目内**还没做的事的唯一出口**，与真相源同放 `docs/` 根。它同样是**快照**——只记此刻仍未做的，做掉的当场删，**MUST NOT 保留"已完成"区**（那是历史，归档索引才是它的去处）。

- **章节按类型分，取值是闭集，MUST NOT 自造第五类**：**想做的功能** / **待澄清的问题** / **已知风险** / **技术欠账**。按类型而不按模块分，是因为读它的人问的是"哪些要拍板、哪些要排期"，而不是"这个模块还欠什么"。
- **每条 MUST 带提出日期**（`YYYY-MM-DD`）。没有日期就无从判断陈旧，陈旧提醒（↓）整条失效。行格式：`- YYYY-MM-DD ｜ <归属模块或"跨模块"> ｜ <一句话>`。
- **准入门槛（MUST）——只收够格的**：

  | 收 | 不收 |
  |---|---|
  | 会改变用户能感知到的行为 | 改个变量名、调整格式 |
  | 会新增或去掉一个功能 | 清掉一行死代码 |
  | 会动某个模块的边界 | 补一个测试、局部重构 |

  **MUST NOT 把 `TODO.md` 当随手记**——把局部小事收进来，清单几周内就长到没人读，届时真正该拍板的那几条会一起被淹掉。局部小事写进代码注释或当场做掉，不进这里。
- **什么时候写**：写需求文档时、写 spec 时、写代码时，只要冒出"这个以后再说"且够格，**当场追加一条**；需求验收时再统一过一遍，把本次做掉的删掉。**MUST NOT 攒到最后一起写**——攒着的必然忘掉一部分。
- **陈旧提醒（SHOULD）**：条目提出日期距今**超过 3 个月**时，SHOULD 提示用户"这条还留着吗"。**AI MUST NOT 自行删除任何条目**——留不留是用户的判断，一条搁置半年的风险项可能正是最该留的那条。3 个月是默认值，项目可在 `TODO.md` 头部声明改写（如 `> 陈旧阈值：6 个月`），声明了就以声明为准。
- **不阻断**：项目没有 `docs/TODO.md` 不是缺陷，第一次有够格条目时才建（与三层真相源"缺口只报告、不阻断"同源）。初始化时 **MUST NOT 代用户创建**。

## 默认命名

- Lean Change Spec：`docs/spec/YYYY-MM-DD-<change-name>-lean-change-spec.md`
- Overview：`docs/spec/YYYY-MM-DD-<project-name>-overview.md`
- 技术 Spec：`docs/spec/YYYY-MM-DD-<repo>-<feature>-eng-spec.md`
- 测试 Spec：`docs/spec/YYYY-MM-DD-<repo>-<feature>-test-spec.md`
- Coding Plan：`docs/plan/YYYY-MM-DD-<feature>-coding-plan.md`
- 交接文档：`docs/plan/YYYY-MM-DD-<feature>-handoff.md`（见 `上下文卫生.md` 规则 2；任务未完成时随任务 worktree 走，合并时若已无用可不带回主分支）
- 报告：`docs/report/YYYY-MM-DD-<feature>-<report-type>-report.md`

**日期前缀（MUST）**：`docs/spec/`、`docs/plan/`、`docs/report/` 下**按次产出**的文档，文件名一律以 `YYYY-MM-DD-` 开头，日期取该文档的**创建日期**。上面七条范式因此写全就是 `docs/spec/YYYY-MM-DD-<change-name>-lean-change-spec.md`、`docs/plan/YYYY-MM-DD-<feature>-coding-plan.md`，以此类推。

- **常青档不加**：需求真相源 `REQUIREMENTS.md`、架构真相源 `ARCHITECTURE.md`、`docs/TODO.md`、两份索引（`docs/index.md` / `docs/index-archive.md`）、两个固定账本（`docs/report/bug修复历史.md` / `docs/report/测试场景覆盖度.md`）、`docs/requirements/` 下的一级子模块——它们是固定名字的长期文档，不属于某一天。
- **目录形态同样适用**：某次产出大到要拆成一个目录时，目录名同样以 `YYYY-MM-DD-` 开头，规则不因形态改变。
