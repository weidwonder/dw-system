# Spec 写作纪律（core）

> 一切 spec / plan / 文档的通用纪律。目标：**让一个不熟悉本项目的工程师或 coding agent，不用追问作者就能动手。**

## 1. 零上下文原则

假设读者是"技能不错、但对我们的工具链和问题域几乎一无所知"的工程师，或一个零上下文的 coding agent。文档要自带一切它需要的东西：

- **精确文件路径**，不写"改那个 controller"，写 `src/api/user.controller.ts:42`。
- **完整代码**：凡是让读者写代码的步骤，直接把代码写出来，不写"实现相应逻辑"。
- **精确命令 + 预期输出**：`npm test -- user` → 预期 `3 passing`。
- **每条外部事实带来源**：接口名/字段/topic 来自哪份文档或哪段源码。

## 2. RFC 2119 规范性措辞

在需要约束力的地方用大写关键词，减少歧义：

- **MUST / 必须**：违反即错误。
- **SHOULD / 应当**：强烈建议，偏离需说明理由。
- **MAY / 可以**：可选。

## 3. 无占位符（硬规则）

以下是**文档失败**，永远不要写：

- `TBD`、`TODO`、"稍后补充"、"填写细节"。
- "加上适当的错误处理" / "做好校验" / "处理边界情况"——要写清具体处理什么、怎么处理。
- "为上面写测试"——直接给测试代码。
- "同 Task N"——把代码重复写出来（读者可能乱序阅读）。
- 引用了任何任务里都没定义的类型/函数/方法。

## 4. 边界对称

每一条"我们做 X"，强制配一条"我们不做 Y"。Brownfield 项目最常见的失败是集成方**过度归因**新系统的能力。列出"不做 / 不负责 / 维持现状"能消掉大量集成误解。

## 5. 结构 > 篇幅

- 能用表格就别用长段落。
- 决策一旦拍板，记成一行 `决策名 | 方向 | 影响组件`，作为文档的记忆，避免每份 spec 重新吵一遍。
- 开放问题写成"能驱动决策"的具体问句，不写"搞清楚 X"这种含糊句。

## 6. 自检清单（提交前过一遍）

- [ ] 每个需求都能指到实现它的任务/章节？
- [ ] 扫一遍有没有第 3 节的占位符？
- [ ] 前后任务用的类型/函数名一致？（`clearLayers()` 别在别处变成 `clearFullLayers()`）
- [ ] 每条外部事实都有来源？
- [ ] Goal 与 Non-Goal 对称？
