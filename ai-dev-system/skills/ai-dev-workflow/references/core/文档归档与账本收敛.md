# 文档归档与账本收敛（core，条件加载）

> **什么时候读**：按 `文档治理.md` §3 判定出某篇文档需要转归档时、或要写 `bug修复历史.md` / `测试场景覆盖度.md` 时。判据与字段定义在 `文档治理.md` §文档生命周期与索引门控，本文只讲**怎么落地**。

## 归档头注

在 frontmatter 之后、正文标题之前插入，三种归档态各一句：

```markdown
> **已归档（2026-08-10）｜lifecycle: merged**：本文口径已归并至 `docs/REQUIREMENTS.md`。与现行文档冲突时**以现行为准**，MUST NOT 据本文实施。

> **已归档（2026-08-10）｜lifecycle: superseded**：本文已被 `docs/spec/YYYY-MM-DD-order-v2-eng-spec.md` 取代。与现行文档冲突时**以现行为准**，MUST NOT 据本文实施。

> **已归档（2026-08-10）｜lifecycle: obsolete**：本文所述能力已于 2026-08-01 下线。MUST NOT 据本文实施。
```

HTML UI 原型无法写 frontmatter，改为在页面顶部加**可见横幅**（做法见 `ai-prd/references/UI原型纪律.md` §4.5）——HTML 注释挡不住任何人照着旧图实现。

## 完整示例：一次改动如何结算文档

**本次改动**：给 `POST /api/v2/orders` 的 `status` 字段加了新枚举值 `partially_refunded`，没有删除任何旧值，替换清单写的是"无"。

1. **盘点触碰的权威面**（`文档治理.md` §3 第 1 步）：替换清单为空，但对外契约的字段枚举变了 → 触碰面为 `POST /api/v2/orders 响应体 status 枚举`。**这类改动正是只看替换清单会漏掉的。**
2. **比对（两步都 MUST 做，`文档治理.md` §3 第 2 步）**——
   - **2a 机械比对 `authority_refs`**：查 `docs/index.md` 现行区的三篇文档，命中两篇——
     - `docs/spec/YYYY-MM-DD-order-eng-spec.md`，其 `authority_refs` 含 `POST /api/v2/orders 响应体契约`；
     - `docs/spec/YYYY-MM-DD-order-test-spec.md`，其 `authority_refs` 含 `订单状态机的合法流转集合`。
   - **2b 关键术语全文检索**（`status`、`partially_refunded`、`退款`）：**又多命中一篇** `docs/spec/YYYY-MM-DD-order-refund-design.md`——它正文第 3 节整节在讲退款态流转，`authority_refs` 里却一条相关登记都没有。**只做 2a 会把它整篇漏掉**；**漏登记本身也是一条发现**，判定时一并指出它的 `authority_refs` 需要补。
3. **逐篇判定**（判定由 **D 文档轴**做并写进报告，**落盘由主会话在收到报告后当场执行**——见 `文档治理.md` §3 开头的角色切分）：
   - `order-eng-spec.md` §4 的状态机图只画了旧的五个状态 → **已失准**，且本次同步写了新的 `order-refund-eng-spec.md` 接过这块口径 → 标 `lifecycle: superseded` + `superseded_by: ./order-refund-eng-spec.md` + `archived: 2026-08-10`，插入 superseded 头注，从 `index.md` 移入 `index-archive.md`。
   - `order-test-spec.md` 的流转集合本就写成"以 spec §4 为准"、未硬编码枚举 → **仍准确**，保持 `active`，`last_confirmed` 改成 `2026-08-10`。
   - `order-refund-design.md`（2b 命中的那篇）正文与新枚举一致 → **仍准确**，`last_confirmed` 改成 `2026-08-10`，并**补上遗漏的 `authority_refs` 条目**。
4. **产出**：`index.md` 少一条、`index-archive.md` 多一条、三篇文档的 frontmatter 各改一次、一条归档头注、一条补登记的 `authority_refs`。全部在同一次提交内完成。

两条反面对照：

- 若按"照抄替换清单"执行，第 1 步就是空清单，三篇文档都不会被看一眼，`order-eng-spec.md` 会带着过时的状态机图继续挂在现行索引上——**门跑了，但什么都没拦住**。
- 若只做 2a 而跳过 2b，`order-refund-design.md` 会被整篇漏掉——**它恰恰是最危险的那一篇**：正文整节讲这块口径、却没在 `authority_refs` 里登记自己，机械比对永远够不到它。

## 账本收敛

两个账本形态不同，收敛方式**不通用**，MUST NOT 互相套用。

### 追加式账本：`docs/report/bug修复历史.md`

每条都是发生过的一次性事实，只增不减是设计使然（查重需要全部历史）。

- **分卷**：主文件超过 **300 条或 1500 行**时，MUST 把最早的条目整体切出到 `docs/report/bug修复历史-<年份>.md`，主文件顶部保留卷索引表（卷文件 / 时间范围 / 条目数）。切卷**只搬运不改写**——条目格式一变，`bug诊断纪律.md` Phase 0 的检索就废了。
- **失效标注**：条目引用的测试文件或样本目录已不存在时，MUST 在该条目末尾追加一行 `- 权威面已变更：<日期>，<原引用> 已不存在`，下次分卷优先切出。
- **MUST NOT 删除、合并或概括历史条目**。收敛靠分卷与检索，不靠丢信息——删掉等于让同一个坑再踩一次。
- 写入格式见 `bug诊断纪律.md` Phase 3 §归档问题处理历史。

### 状态表：`docs/report/测试场景覆盖度.md`

每行描述**此刻**的覆盖状态，同一场景只有一行。

- **MUST NOT 分卷**。按年份切走"最早的行"会把仍需保覆盖的场景移出主表，直接制造覆盖盲区——分卷规则只适用于追加式账本。
- 状态变化 MUST 就地改那一行，MUST NOT 追加新行表示变化。
- 场景淘汰、主表体积复核（100 行）、「已淘汰场景」区的写法，权威定义在 `测试资产纪律.md` §3，模板见 `assets/templates/test-coverage.md`。
