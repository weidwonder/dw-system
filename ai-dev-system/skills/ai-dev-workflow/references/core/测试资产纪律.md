# 测试资产纪律（core）

> 适用：Step 8–10 设计与落地测试时、bug 修复归档时、以及任何用户提供了真实数据/凭证/样例的时刻。两个协作面（solo / team）与任意能力位组合下同样适用：可裁剪的是**深度**（如台账只登记高重要度场景），**MUST NOT 裁剪机制**——端到端用例、真实输入固化、缺口挂账三件事一件不减。
> 解决三件事：**长链路必须有端到端用例**、**真实输入必须固化成可复用资产**、**没覆盖的重要场景必须显式挂账**。
> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD。

## 1. 端到端用例（长链路必须有）

**判定：命中任意一条，本次需求 MUST 有端到端用例**，不能只靠单元测试和单接口用例交差。

- 一条业务流程跨 **≥3 个组件 / 服务 / 进程**才走完；
- 流程含**异步或多阶段**环节：队列、定时任务、回调、重试、多轮模型推理；
- 流程中有**中间产物**落盘、落库或传给下一环（解析结果、中间态、任务记录、embedding、生成的文件）。

**中间结果 MUST 一并断言，不能只断言末端。** 只验最终输出的端到端测试有两个致命问题：中间环节坏了而末端碰巧正确时它是绿的；末端错了它只会告诉你"错了"，不会告诉你**哪一环**开始错。

写法：把链路拆成有序环节，每个环节的**交接产物**各写一条断言，最后再断言末端结果。

```text
链路 L1：上传作业图片 → 识别 → 判题 → 生成错题 → 推送

环节 1 上传    断言：落库记录存在，status=pending，文件校验和与源文件一致
环节 2 识别    断言：识别结果条目数 = 3，每条含题号与坐标，status=recognized
环节 3 判题    断言：判定结果 [对,错,对]，错题项带原因码 wrong_step
环节 4 生成    断言：错题本新增 1 条，关联原题 ID 正确，未重复插入
环节 5 推送    断言：推送记录 1 条，投递态 delivered，内容含错题标题
末端           断言：用户在错题本列表能看到该题，且计数 +1
```

- 每条断言 MUST 有**独立来源**的预期值（PRD/spec 口径、手工推演的具体值、已确认的黄金样本），MUST NOT 用被测代码的算法现场重算（同义反复，见 test-spec §纪律）。
- 断言挂在**环节间的契约**（落库记录、消息体、返回结构）上，不挂在内部函数调用次序上。
- 异步环节 SHOULD 用条件轮询等待目标状态达成，MUST NOT 用固定 sleep 猜耗时（呼应 `bug诊断纪律.md` Phase 1）。
- 环节里含模型推理时，断言写**结构与不变量**（字段齐全、枚举合法、条目数、引用的原文存在），不写逐字比对的自然语言输出。

产出落在 test-spec §8「端到端链路测试方案」的步骤序列里，每步显式写出"本步断言的中间产物"。

## 2. 真实输入固化为测试资产

**用户给的每一份真实数据都是资产，MUST 落盘，MUST NOT 只在对话里用一次就丢。** 口头描述、贴在对话里的报文、发来的文件、失败现场的日志，都算。

### 目录

**先探测项目既有测试资产惯例**（按序：`tests/fixtures/` → `tests/data/` → `test/fixtures/` → `__tests__/fixtures/` → `spec/fixtures/` → `testdata/` → 项目 README/CI 配置里声明的路径），**探测到就跟随**；都没有时才新建 `tests/fixtures/`。一个场景一个子目录，目录名即场景名。

```text
tests/fixtures/
  订单超时自动取消/
    README.md                  ← 场景说明 + 覆盖特征标签（见下）
    input-正常下单.json
    input-支付回调迟到.json
    secrets/                   ← gitignored，放真凭证
      credentials.json
    secrets.example/           ← 入库，脱敏副本，结构与 secrets/ 一一对应
      credentials.json
```

### 命名与改写

- 用户提供的文件 **MUST 重命名为场景语义名**（`input-支付回调迟到.json`），MUST NOT 保留 `WX20260801-153022.png`、`导出(3).csv` 这类原始文件名——半年后没人知道它测的是什么。
- 只改名，**MUST NOT 改内容**（除脱敏外）。真实数据的价值就在于它的不规整：多余空格、异常编码、超长字段、缺失键，恰恰是构造数据永远想不到的。脱敏时 MUST 保持长度、格式与字符类型不变。
- 用户**口头/文字描述**的场景（"上次有个用户改了三次地址就重复扣款了"）同样 MUST 落成文件：写成该场景的输入数据或 `README.md` 里的场景条目，让它变成可执行用例的依据，而不是聊天记录里的一句话。

### 敏感信息

含账号、密码、token、密钥、真实个人信息的样本：**MUST 保存**（丢了就复现不了），但 MUST 放进场景目录下的 `secrets/`；同时 MUST 在 `secrets.example/` 留一份**结构相同、值已脱敏**的副本入库——否则别人 clone 下来只会得到一个跑不起来的用例。

在项目 `.gitignore` **幂等追加**下面两行（已存在则不重复追加，MUST NOT 改动用户已有的忽略规则）：

```gitignore
# 测试资产中的真实凭证，不入库；脱敏副本见同级 secrets.example/
tests/fixtures/**/secrets/
```

> 测试资产目录不是 `tests/fixtures/` 时，把路径换成实际探测到的目录。追加后 MUST 用 `git check-ignore -v <该文件路径>` 实测确认凭证文件确实被忽略了——**先确认忽略生效，再把凭证写进去**，顺序反了就等于把密钥提交进了历史。

`README.md` 里 MUST 写清 `secrets/` 需要哪些文件、每个字段从哪里获取。

### 覆盖去重（同场景多份样本时）

在场景 `README.md` 里给每份样本登记它触发的**覆盖特征标签**（分支、状态、字段组合、异常类型各算一维）：

```markdown
| 样本 | 覆盖特征标签 |
|---|---|
| input-正常下单.json | 支付成功 / 单商品 / 有优惠券 |
| input-支付回调迟到.json | 支付成功 / 单商品 / 有优惠券 / 回调迟到 |
| input-多商品下单.json | 支付成功 / 多商品 / 无优惠券 |
```

**淘汰规则**：样本 A 的标签集是样本 B 的**子集**时，MUST 弃 A 留 B（上表中 `input-正常下单.json` 被第二份完全覆盖，应删）。标签集互不包含的一律保留——它们各自覆盖了别人没有的维度。**MUST NOT 以"文件看起来差不多"为由删样本**，判据只有标签集包含关系。

## 3. 测试场景覆盖度台账

**位置**：`docs/report/测试场景覆盖度.md`（固定文件名的单一账本，与 `bug修复历史.md` 同属 `文档治理.md` 报告命名规则的显式例外）。模板见 `assets/templates/test-coverage.md`。

**这份台账是"当前状态表"，不是流水账**——与 `bug修复历史.md` 的追加式账本不同：bug 历史每条都是一次性事实（发生过就永远为真），覆盖度每一行描述的是**此刻**的覆盖状态，同一场景只应有一行。**MUST NOT 为同一场景追加新行来表示状态变化**，MUST 就地改那一行。

**作用**：把"这个场景很重要但我们还测不了，因为缺真实素材"从个人记忆变成项目资产，后续可以据此**批量向用户索要素材**。

**MUST 更新的时机**：

1. Step 8 写完 test-spec 后——把识别出的高风险场景逐条登记，标注覆盖状态；
2. 新增或淘汰测试样本后——更新对应场景的样本列表；
3. bug 修复归档时——把该问题对应的场景登记进去（见 §5）；
4. 需求准出时——复核状态位，别留下"已覆盖"其实没写用例的假账。

**场景淘汰（MUST）**：场景对应的业务能力下线、或它描述的权威面已不存在时，MUST 把该行从主表移入文末 `## 已淘汰场景` 区，并注明淘汰日期与一句原因（"下单改走新履约链路，本场景由 XX 场景取代"）。

- **MUST NOT 留在主表里标个"已废弃"了事**——主表的每一行都会被读成"当前需要保覆盖的场景"，废弃行留在里面会持续制造假缺口，也让覆盖率统计失真。
- **MUST NOT 直接删行**：淘汰记录本身说明"这条链路曾经被测过、后来为什么不测了"，删掉之后没人能回答这个问题。
- 主表超过 **100 行**时，MUST 复核一遍是否有该淘汰而没淘汰的行——状态表长到读不完，就已经不是状态表了。

**索要素材的方式**：台账里"缺什么素材"一列写成用户能直接照着找的东西（"一份支付回调比订单创建晚到 30 秒以上的真实报文"），MUST NOT 写成技术要求（"构造一个 callback 延迟的 mock"）。向用户索要 MUST 按 `用户沟通纪律.md` 用业务语言，并且**攒够一批一次问**，不要每想起一个就打扰一次。用户暂时给不出的，保持 `❌ 缺素材` 挂账，不要偷偷降级成"不重要"。

## 4. 与测试设计的衔接

- test-spec §4 的 Fixture 表，凡有真实样本可用的，**MUST 直接引用场景目录里的文件路径**，MUST NOT 另写一份构造数据——构造数据只用于真实样本覆盖不到的维度（极值、并发、故意的非法输入）。
- 真实样本与 spec 口径冲突时（真实数据里出现了 spec 没定义的字段值），按 test-spec 的输入权威等级处理：标"待确认"，MUST NOT 改样本去迁就 spec，也 MUST NOT 脑补规则。这类冲突往往正是 spec 漏掉的真实场景。

## 5. 与 bug 流程的衔接

`bug诊断纪律.md` Phase 3 要求把复现命令固化为回归测试。在此之上：

- 触发这个 bug 的**真实输入** MUST 按 §2 固化为一份测试样本，场景名即问题的一句话描述；用户提供的现场文件/日志/报文同样落进去。
- 该 bug 跨 §1 判定的长链路时，回归测试 MUST 是**端到端用例并带中间结果断言**——只补一个末端断言的单测，下次同类问题仍然定位不到是哪一环。
- MUST 在 `docs/report/测试场景覆盖度.md` 登记该场景（状态 ✅ 已覆盖，样本指向新固化的文件），让台账同时成为"哪些真实故障已经被钉住"的清单。
