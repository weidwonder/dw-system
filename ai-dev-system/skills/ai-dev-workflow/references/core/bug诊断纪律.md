# Bug 诊断纪律（core，红回路优先）

> 适用：修 bug、查回归、解释异常行为、处理测试失败——**任何"先要弄清为什么坏"的任务**，在动手改代码之前执行。
> 核心信念：诊断的全部精髓在 Phase 1——先造出一条**能变红的紧反馈回路**，再谈假设。跳过回路直接猜原因，正是本纪律要消灭的失败模式。
> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD。

## Phase 1：构造红回路（先于一切假设）

找到或构造一条**复现命令**，同时满足四个属性：

| 属性 | 含义 | 反例 |
|---|---|---|
| **能变红** | 命令跑完能明确失败（非零退出码 / 断言失败 / 输出与预期 diff） | "跑起来看看日志"——没有失败判据 |
| **确定性** | 重复跑结果一致 | 依赖时序/随机数据、偶发才失败 |
| **快** | 秒级到十秒级，能高频重跑 | 要手工点十步 UI、要等定时任务 |
| **可自跑** | AI/脚本能独立执行并读到结果 | 需要人眼比对截图 |

构造手段（按成本从低到高选）：已有失败测试 → 新写最小失败单测 → 最小复现脚本 → CLI/curl 命令 + 预期输出断言 → 带断言的日志检查命令。找不到入口时，把系统入口逐层缩小（整条链路 → 单服务 → 单函数），直到某一层能被一条命令打红。

**完成判据**：这条命令已经**真实跑过至少一次**并确认变红。没跑过 = 没有回路。

## 硬门禁

- 红回路存在之前，MUST NOT 提出修复假设、MUST NOT 修改产品代码。
- **发现自己正在"读代码构建理论"而回路还不存在——立即停下**，回去构造回路。先有理论后找证据，是诊断的头号反模式。
- 例外（显式声明后走）：确实无法确定性复现（并发竞争、特定环境、外部依赖抖动）时，本次任务的第一步交付 MUST 改为"缩小复现窗口"——加可观测性（日志/断言/计数）、固定随机种子、录制回放输入——直到回路可造；MUST NOT 以"复现不了"为由直接猜改。

## Phase 2：可证伪假设

1. 基于回路的失败输出与代码事实（团队版跨服务链路先 `ctx find-scenes`/`get-card` 取权威事实附 cite，MUST NOT 全仓裸 grep），列 **3–5 条可证伪假设**，按可能性排序。每条写成"若假设成立，则做 X 观察应看到 Y"。
2. **一次只验一条**：用回路（加日志/断言/最小改动）验证或排除，排除即划掉换下一条。MUST NOT 一次改多处"广撒网"。
3. 全部排除仍红 → 假设集错在更上游，回 Phase 1 缩小回路范围，不凭空追加第 6 条。

## Phase 3：修复与防回归

- 修复后红回路 MUST 变绿，且连续重跑两次全绿。
- 复现命令 SHOULD 固化为回归测试进入测试套件（它已经天然满足四属性）；确实不适合入库的，在 report 中记录命令与结论。
- 修复触碰权威面（接口/路由/废弃标记）时，团队版按 context-engineering §5 刷新 card。

## 与主流程的关系

bug 类需求照常过路由、worktree 隔离门与 Step 0 Triage（多数走 Lean 路径）；本纪律插在"进入实现之前"——Lean 也不豁免。诊断结论改变影响面判断（如发现跨服务/不可逆）时，按 Triage 规则升级回完整流程。
