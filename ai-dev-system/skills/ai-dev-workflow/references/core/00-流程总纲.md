# 开发流程总纲（core，技术栈无关）

> 适用于任何技术栈（Web 全栈 / 后端服务 / AI-LLM 应用 / 数据脚本）。个人版和团队版共用本总纲，只是**走多深、要不要评审/多仓协作**不同。
> 用法：从 Step 0 分流开始。每步给了**输入 / 产出 / 参考 prompt / 对应模板**；prompt 里的 `【】` 是你要替换的占位符。
> 与用户的所有对话按 `用户沟通纪律.md` 使用业务语言；技术词只留在内部工程产物中。
> 所有项目修改按 `worktree开发纪律.md` 隔离：路由后先建独立 worktree，完成门通过后自动合并主分支。

## 流程总览

```
路由/初始化 → 工作区隔离门（独立 worktree）→ Step 0 分流(Triage)
  ├─ 小改动 & 4 项全否 → 一页 Lean Change Spec → 直接实现
  └─ 大需求 / 任一为是 → 完整流程：
        1 PRD 粗澄清 → 2 Overview 顶层设计 → 3 PRD 细澄清
        → 4 技术 Spec(含 AI overlay) → 5 Spec 澄清 → 6 Coding Plan → 7 执行编码
        → 8 测试 Spec → 9 测试代码 → 10 链路测试
  └─ 两条路径最终都进入：完成与自动合并门 → 主分支
```

---

## 工作区隔离门：进入开发前强制执行

完成 mode 路由后，按 `worktree开发纪律.md` 检查 Git 状态、识别主分支，并从最新主分支创建本次任务的独立 worktree。任何 spec、plan、report、代码或测试落盘前必须通过此门；Lean 小改动同样执行。多仓需求为每个仓库分别创建 worktree。

主工作树有未提交改动、项目不是 Git 仓库或无法创建 worktree 时，中止开发，不直接在当前目录继续。

---

## Step 0：需求体量与风险分流（Triage）

**先判断体量，再决定走多重的流程。** 对没有完整 PRD 的小 Issue / 体验改进，回答 4 个判定问题：

1. 是否改变智能能力给用户的结果或判断方式？
2. 是否改变谁可以做什么、敏感信息保护或使用场景？
3. 是否影响多个业务环节、需要搬迁历史数据或存在不可逆影响？
4. 是否改变经营指标、业务规则或对外承诺？

- **4 项均为「否」** → 用 **一页 Lean Change Spec**（`assets/templates/lean-change-spec.md`）作为唯一交付物，写入 worktree 内的 `docs/spec/<change-name>-lean-change-spec.md`，直接进入实现，**跳过 Step 1–10，但不得跳过完成与自动合并门**。
- **任意一项为「是」** → 升级回完整流程；涉及 AI/LLM 的，在 Step 4 叠加 AI overlay。

> 意义：既不给小改动套重流程，也不给有风险的改动（AI 行为、安全、跨服务、对外承诺）走捷径。
>
> **个人版**：默认所有需求先假设走 Lean Spec，只有自己都 hold 不住的复杂改动才升级。
> **团队版**：跨仓 / 影响面不清时，宁可升级到 Step 2 出 Overview，让协作方对齐。

---

## Step 1：PRD 粗澄清

**输入** PRD ｜ **产出** 需求理解 + 问题清单 ｜ **对应模板** 无（对话）

让 AI 建立对需求的整体理解，找出 PRD 的**模糊点、重复点、矛盾点**。

```text
# 参考 prompt
这是一个【业务域】【项目名】相关的需求（参考 PRD @【PRD 文件】）。
先理解整体要做什么？不做什么？方向和边界在哪？并列出 PRD 的模糊点、重复点、矛盾点。
```

> **团队版（业务全景门限）**：除非任务已明确限定到某一个具体 repo，**先 `ctx find-scenes <关键词>` 取端到端业务全景，再 `ctx discover` 收窄到涉及仓库的 card**——先看全景再钻细节，避免漏掉跨服务链路。带着问题清单和产品做第一轮澄清。

---

## Step 2：生成 Overview（顶层设计）

**输入** 澄清后的 PRD ｜ **产出** Overview 顶层架构文档 ｜ **对应模板** `assets/templates/overview.md`

把 PRD 做一次"技术翻译"。产出物介于产品 PRD 和详细 spec 之间——告诉工程师**该打开哪些仓库、每个仓库改造范围多大**，但不讲怎么实现。至少包含：

1. 顶层模块与架构设计（粗颗粒度，不涉及实现细节）。
2. 功能模块之间的边界与关系。
3. 哪些模块新增、哪些涉及现有仓库改造；每个仓库改动范围（只圈范围，不展开）。**这就是 Project Map，是最常被读的一节。**
4. **待澄清的开放问题**：足够详细，说明问题源自 PRD 哪里，便于评审会讨论。

```text
# 参考 prompt
帮我产出顶层架构设计，输出到 @【docs/spec/ProjectName-overview.md】。
它本质是一个简化版的、面向技术的 PRD 说明：圈出涉及改造的项目和改造点，不展开实现。
```

> **个人版**：单人项目通常跳过此步；只有自己都记不住的复杂改动才写一份精简 Overview 帮自己理清。
> **团队版**：跨 ≥3 仓的需求**必须**出 Overview，作为评审会与后续按仓拆 spec 的基础。写 Overview 前若还没跑过业务全景门限（`ctx find-scenes`），先补跑——Project Map 的完整性依赖它。

### 大架构确认门

只要 Overview 改变业务能力划分、关键职责边界、主业务流程、重要协作关系、历史数据归属或不可逆风险，就必须先形成“用户确认摘要（业务语言）”。摘要只讲业务能力、角色、流程、影响、风险和不做什么，不展示程序结构。

用户明确确认大架构后才能进入 Step 4。若用户要求调整，先修订 Overview 和业务语言摘要，再次确认。

---

## Step 3：业务细节与模块约束澄清

**输入** Overview ｜ **产出** 修订后的 Overview ｜ **对应模板** 无

逐条确认 Overview 中尚未确定的业务规则、角色职责、处理顺序、时效要求、异常处理、权限边界和历史业务延续方式。

模块内结构设计需要取舍时，不向用户展示技术方案；改问可由业务判断的问题，例如“失败时阻断还是转人工”“结果要立即可见还是允许稍后完成”“多人同时操作时以谁为准”。AI 根据回答在内部完成设计和选型。

> ⏳ 这一步最花时间，Overview 会被反复修改。让 AI **按代码仓库划分 spec**，每个仓库该做什么写清楚，AI 会更专注。
> **个人版**：此步基本省略（你既是产品也是技术）。

---

## Step 4：生成技术 Spec

**输入** Overview + PRD ｜ **产出** `docs/spec/<repo>-<feature>-eng-spec.md` ｜ **对应模板** `assets/templates/eng-spec.md`（+ `AI-LLM-overlay.md`）

```text
# 参考 prompt
根据顶层设计 @【设计文件】 和 PRD @【PRD 文件】，按 eng-spec 模板推进各子仓库的 spec。
```

**含 AI/LLM workflow 时叠加 overlay**：若模型推理参与功能行为（生成/总结/分类/检索增强/排序推荐/OCR/语音手写识别/内容审核/固定 prompt 流程），在基础 spec 之上叠加 `references/core/AI-LLM-overlay.md` 的 AI 契约。判定边界见该文件。

---

## Step 5：内部技术自检

**输入/产出** spec（内部反复修订）｜ **对应模板** 无

AI 自行核对现有代码事实、信息定义一致性、实现边界、失败处理、兼容方式和验证闭环，并自主完成详细程序设计。不得要求用户确认文件、接口、数据结构、存储方式、框架或具体落地方向。

只有发现未确定的业务规则或用户可感知取舍时，才返回 Step 3，用业务语言提问；不得把技术选择原样抛给用户。

---

## Step 6：生成 Coding Plan

**输入** spec ｜ **产出** 对应仓库的 coding plan ｜ **对应模板** `assets/templates/coding-plan.md`

把 spec 拆成"假设执行者对代码库零上下文"的、bite-sized 的任务：每个任务带**文件路径、完整代码/测试、验证命令、commit**。适合直接交给 coding agent。

```text
# 参考 prompt
阅读此 spec @【spec 文件】，生成 coding plan（写入 docs/plan/，命名 <feature>-coding-plan.md），
尽量贴近具体实现，适合交给 coding agent 执行。
```

---

## Step 7：执行 Coding

**输入** coding plan ｜ **产出** 代码改动 ｜ **对应模板** 无

在任务 worktree 内加载 plan、批判性 review，再逐任务执行、验证和提交。不得回到主工作树直接修改。

向用户汇报时只说明完成了哪些业务能力、哪些业务边界保持不变、验证了哪些业务场景和还存在哪些业务风险；文件与代码细节留在 plan/report 中，除非用户明确索要。

> 💰 此步对 AI 能力要求不高，可切更省钱的模型。
> 📦 **团队版**：文档不够、需读其他服务真实源码时，按决策树浅克隆对应仓库（`git clone --depth=1`），读完把关键发现回写，别全仓 grep。
> ✅ 完成后运行项目，确保无基础语法/编译错误。

---

## Step 8：生成测试 Spec

**输入** PRD + Overview + spec + coding plan ｜ **产出** `docs/spec/<repo>-<feature>-test-spec.md` ｜ **对应模板** `assets/templates/test-spec.md`

```text
# 参考 prompt
配合 PRD @【】、overview @【】、spec @【】、coding plan @【】，
对当前代码仓库涉及的内容增加测试方案。只专注当前仓库涉及的部分，功能代码已开发完成。
```

---

## Step 9：生成测试代码

**输入** 测试方案 ｜ **产出** 测试代码 ｜ 随后执行**单仓 test** 和**模拟链路 test**。

---

## Step 10：链路测试

跨服务流水线测试，确认端到端链路打通。

> **个人版**：Step 8–10 通常压缩成"给关键路径补几个测试 + 手动跑一遍"。
> **团队版**：链路测试是准出的一部分；发布与线上验证参考团队自己的基建手册。
> 若需要形成书面验证/测试/执行报告，统一写入 `docs/report/<feature>-<report-type>-report.md`。

---

## 完成与自动合并门

Lean 路径和完整流程都必须以此门收尾。按 `worktree开发纪律.md` 确认需求、文档、代码、测试、提交、最新主分支同步以及团队评审门禁全部完成。条件满足后无需再次询问用户，自动合并到仓库主分支并做合并后验证，再清理 worktree。

任一条件失败时不得合并或清理 worktree。团队仓库必须通过 PR、审批、CI 和保护分支规则，禁止为了“自动”而绕过项目治理。

---

## 个人版 vs 团队版 的裁剪对照

| Step | 个人版 | 团队版 |
|---|---|---|
| 0 Triage | 默认假设走 Lean | 认真分流，跨仓必升级 |
| 1 粗澄清 | 简化 | 用 ctx 查 context |
| 2 Overview | 复杂才写 | ≥3 仓必写 |
| 3 细澄清 | 省略 | 评审会 |
| 4-5 Spec | 大需求才写 | 按仓出 spec + 叠 AI overlay |
| 6-7 Plan/编码 | 直接干 | plan → agent 执行 |
| 8-10 测试 | 关键路径 | 单仓 + 链路，准出 |
