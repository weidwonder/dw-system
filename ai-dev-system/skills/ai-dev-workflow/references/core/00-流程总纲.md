# 开发流程总纲（core，技术栈无关）

> 适用于任何技术栈（Web 全栈 / 后端服务 / AI-LLM 应用 / 数据脚本），也适用于任何项目形态——**本总纲无条件常驻**。
> 项目形态只决定在它之上**额外加载哪些分册**：**协作面**（`collab/solo.md` 或 `collab/team.md`，按标记块的 `collaboration` 字段二选一）与**能力位**（`capability/graph.md`、`capability/curated.md`，按运行时探测项目资产的结果，可零个、可两个都启用）。分册只能**追加**约定，MUST NOT 削减本总纲的任何一条（见 ↓ §六条"不裁剪"护栏）。
> **本文是骨架层**：分流判据 + 四道门 + 步骤索引 + 与项目形态无关的常驻约定。每步的执行细节按分流结果再加载对应分册，不要一次性全读。
> 与用户的所有对话按 `用户沟通纪律.md` 使用业务语言；技术词只留在内部工程产物中。
> 全程遵守 `上下文卫生.md`：方向性决策在聪明区内完成，逼近上限交接而非硬撑。

> **本文小节**：[流程总览](#流程总览) · [四道门](#四道门贯穿两条路径lean-一道也不豁免) · [Step 0 Triage 分流](#step-0需求体量与风险分流triage) · [默认倾向](#默认倾向四问全否之后) · [完整流程步骤索引](#完整流程步骤索引) · [兼容取舍确认门](#兼容取舍确认门spec-定稿前由拍板人拍板) · [代码评审门](#代码评审门编码完成后强制执行) · [完成与自动合并门](#完成与自动合并门) · [六条"不裁剪"护栏](#六条不裁剪护栏) · [按边界拆的粒度](#按边界拆spec--issue--pr-的粒度)

## 流程总览

```
路由/初始化 → 工作区隔离门（独立 worktree）→ Step 0 分流(Triage)
  ├─ 小改动 & 4 项全否 → 读 路径-lean.md：一页 Lean Change Spec → 兼容门 → 实现 → 评审门
  └─ 大需求 / 任一为是 → 读 步骤-1-7-设计与实现.md：
        1 PRD 粗澄清 → 2 Overview 顶层设计 → 3 PRD 细澄清
        → 4 技术 Spec(含 AI overlay，登记替换清单) → 5 Spec 自检
        → 兼容取舍确认门 → 6 Coding Plan → 7 执行编码
        → 代码评审门 → 读 步骤-8-10-测试.md：8 测试 Spec → 9 测试代码 → 10 链路测试
  └─ 两条路径最终都进入：完成与自动合并门 → 主分支
```

## 四道门（贯穿两条路径，Lean 一道也不豁免）

| 门 | 触发时机 | 判据在哪 | 不过门的后果 |
|---|---|---|---|
| **工作区隔离门** | 路由完成后、任何文档或代码落盘前 | `worktree开发纪律.md` §工作区隔离门 | 改动落进主工作树，与用户未提交的工作纠缠在一起 |
| **兼容取舍确认门** | spec 定稿前（完整流程 Step 5 后 / Lean 开始实现前）| 本文 ↓ §兼容取舍确认门 | AI 替用户决定了要不要兼容，包袱或断裂二选一都没人知情 |
| **代码评审门** | 编码完成、基础验证通过后 | 本文 ↓ §代码评审门 + `代码评审纪律.md` | 漏实现、镀金、越界、旧逻辑残留一起进主分支 |
| **完成与自动合并门** | 合并前 | `worktree开发纪律.md` §完成与自动合并门 | 未验证的改动进主分支，失败现场也被清掉；过期文档继续挂在索引里误导后来的 agent |

**工作区隔离门补充**：多仓需求为每个仓库分别创建 worktree。主工作树有未提交改动、项目不是 Git 仓库或无法创建 worktree 时，中止开发，不直接在当前目录继续。

另有两道**条件触发**的门，不贯穿两条路径，命中才过：

- **红回路门**：bug / 回归 / 异常行为类需求，动手改代码前先过（Lean 路径也不豁免）。→ `bug诊断纪律.md`
- **大架构确认门**：**只要本次改动命中大架构判据**（产品或技术架构的**主干路形状**变了——形状变才算，主干路上的取值变不算；判据与正反例的权威定义在 `用户沟通纪律.md` §1，本文 MUST NOT 复述），就必须先形成**业务语言摘要**交用户确认，确认后才能继续。
  **触发条件是"改动命中判据"，MUST NOT 写成"Overview 改变了什么"**——Overview 可以被合法跳过（`步骤-1-7` §本步必做还是可跳过），Lean 路径更是从不产出 Overview，绑在 Overview 上等于让这道门在最常见的路径上静默消失。落地：完整流程在 Step 4 前过（→ `步骤-1-7-设计与实现.md` §大架构确认门），Lean 路径在开始实现前与兼容取舍**同一批**抛给用户（→ `路径-lean.md` 第 5 步）。

**资产补建信号不是门**（放在这里只为免得被当成第五道门找不到）：项目已经出现"同一能力多处实现""模块多到每次都要翻半个仓库"这类**实际返工**时，把它记进 `docs/report/资产补建信号.md`，累计到阈值后在**合并完成后的收尾汇报**里向用户建议补建权威位或图谱位。它**只产出建议、不阻断任何流程**，也 MUST NOT 挂进完成与自动合并门（非交互门）。判据、账本格式、阈值与状态机的权威定义在条件加载的 `资产补建信号.md`，写信号或做判定时才读。

## Step 0：需求体量与风险分流（Triage）

**先判断体量，再决定走多重的流程。** 对没有完整 PRD 的小 Issue / 体验改进，回答 4 个判定问题：

1. 是否改变智能能力给用户的结果或判断方式？
2. 是否改变谁可以做什么、敏感信息保护或使用场景？
3. 是否影响多个业务环节、需要搬迁历史数据或存在不可逆影响？
4. 是否改变经营指标、业务规则或对外承诺？

- **4 项均为「否」** → **默认**走 Lean 路径（先过下方 §默认倾向，未命中升级条件再**加载 `路径-lean.md`**），用一页 Lean Change Spec（`assets/templates/lean-change-spec.md`）作为唯一交付物，写入 worktree 内的 `docs/spec/<change-name>-lean-change-spec.md`。跳过 Step 1–10，但四道门一道不少。
  ——"默认"二字是实义的：四问全否**之后**还要过一遍 [§默认倾向](#默认倾向四问全否之后)，命中升级条件时改走完整流程。**MUST NOT 把本条读成无条件结论**。
- **任意一项为「是」** → 走完整流程：**加载 `步骤-1-7-设计与实现.md`**；涉及 AI/LLM 的，在 Step 4 叠加 AI overlay。

> 意义：既不给小改动套重流程，也不给有风险的改动（AI 行为、安全、跨服务、对外承诺）走捷径。

**4 问 MUST 逐题过一遍，不是"假设"全否**；误把有风险的改动当小改动，才是真正的风险。

### 默认倾向（四问全否之后）

四问都不触发之后，还有一个**默认倾向**决定这次要不要主动加重——该倾向由**能力位**决定，MUST NOT 由协作面决定：

> 无能力位 → 默认走 Lean；含权威位 → 影响面说不清时宁可升级到完整流程。

- **无能力位**（既未探测到代码图谱索引，也未探测到已填写的 `capability-registry.md`）：默认所有需求先假设走 Lean Change Spec，只有确实 hold 不住的复杂改动才升级。
- **含权威位**（探测到已填写的 `capability-registry.md`）：registry 里存在权威条目，本身就是"这个项目已经出现过实现歧义"的证据，此时"我觉得改动很小"的自我判断不可信——**影响面说不清**时，宁可升级到 Step 2 出 Overview。细则见 `capability/curated.md` §1。
  **"影响面说不清"的判据（命中任一即算说不清）**——**本组判据只在探测到权威位时适用**。
  四条分两批，因为它们**能被评估的时点不同**：

  | # | 判据 | 什么时候过 |
  |---|---|---|
  | 1 | 本次要改的能力在 registry 里跨 ≥2 个权威仓库 | **Triage 当场**，MUST 逐条过 |
  | 2 | `ctx discover` 给出了 out-of-scope 警告（命中废弃或中间产物实现）| **Triage 当场**，MUST 逐条过 |
  | 3 | 关键事实里有任何一条给不出 cite 或 `文件:行` | **回溯触发**：Step 1 进行中命中即当场升级 |
  | 4 | `ctx discover` / `search-semantic` 都收不窄，得靠子代理外包重探索才拿到现状 | **回溯触发**：Step 1 进行中命中即当场升级 |

  **判据 3/4 是回溯触发的，MUST NOT 在 Triage 强行判定**：它们要求关键事实已经开始收集，而 Triage 发生在
  Step 1 之前，此时手上还没有"关键事实"这个对象，逐条过只会得到一个编出来的答案。它们在 Step 1（Lean 走
  `路径-lean.md` 第 3 步写〈既有系统清单〉）进行中命中，就**当场升级回完整流程**，与 `路径-lean.md`
  §Lean 特有的三个提醒 首条"中途发现影响面变大（跨服务、要迁数据、动了对外承诺）同样立即升级，不要将错就错走完"
  是同一条处置。

  **判据 1/2 怎么当场核对**：按 `capability/curated.md` §3 的顺序跑 `ctx find-scenes <关键词>` → `ctx discover "<意图>"`
  （合计 10 秒级），拿到端到端全景与命中的仓库、out-of-scope 警告，再逐条对照。**MUST NOT 跳过 find-scenes 直接 discover**
  ——`curated.md` §3 的排序铁律：除非用户已把任务限定到某一个具体 repo，否则第一步 MUST 先取业务全景，跨服务需求
  直接钻单个 card 最常见的失败就是漏掉链路上的其它服务。两者的结果一并进 Step 1 的〈既有系统清单〉，不重复跑。
  MUST NOT 用"我感觉不复杂"代替。

  **MUST NOT 把这四条套到无能力位项目上**：没有 registry 就永远没有 cite，第三条会**恒为真**，
  于是每个直读项目都被判成"说不清"而升级——与"无能力位 → 默认走 Lean"正好相反。
  无能力位项目的判据只有一条：**确实 hold 不住**（改动铺开后自己都说不清动了哪些地方）才升级。
- **图谱位不改变本默认假设**：索引只让"查得快"，不代表"实现有歧义"（`capability/graph.md` §3）。
- **MUST NOT 从"只有我一个人"推出"默认走最短流程"**：一个人维护的十万行遗留系统，默认走 Lean 是危险的。协作面不参与本判据。

## 兼容取舍确认门：spec 定稿前，由拍板人拍板

**兼容不是默认项。** 无条件保留旧行为会让包袱永久累积，无条件砍掉又可能打伤还在用旧口径的人——**这是业务取舍，不是技术选择，必须每次由人拍板，AI 在任何项目形态下都 MUST NOT 自行默认。**

**谁拍板由协作面决定**：solo → 开发者本人（`collab/solo.md` §3）；team → 业务负责人（`collab/team.md` §3）。下面的流程两个协作面完全一致，只是"问谁"不同。

1. **先列清单（AI 做）**：把本次改动会改变的**既有可观察行为**逐条列出来——旧接口的请求/响应形状、旧字段与旧枚举值、旧数据在新逻辑下的解读、旧调用方（含外部系统、老版本客户端、定时任务、报表）依赖的行为、用户已经形成的操作习惯。**清单为空时也要显式写一句"本次不改变任何既有可观察行为，无兼容取舍"**，不许静默跳过这道门。
2. **逐条问拍板人（业务语言）**：每条给三个选项 + 一个推荐 + 一句理由，按 `用户沟通纪律.md` 只讲业务影响（谁会受影响、影响多久、代价是什么），不讲实现方案。多条时一次性批量抛出，不要一条一条问。

   | 选项 | 含义 | 代价 |
   |---|---|---|
   | **不兼容** | 直接切到新行为，旧行为立刻消失 | 仍在用旧行为的人立即受影响，但代码干净、无长期包袱 |
   | **兼容一段时间** | 新旧并存到某个到期日，到期后删旧的 | 需要维护两套；**MUST 同时定下到期日与到期后的动作** |
   | **永久兼容** | 旧行为长期保留 | 包袱永久化；只有对外契约或不可控调用方才值得 |

3. **结论落盘（MUST）**：写进 eng-spec §8.1 兼容取舍决策表（Lean 路径写进 lean-change-spec 的兼容取舍一行）。选了"兼容一段时间"的，MUST 在替换清单里把对应被取代物登记为**保留例外**，带上同一个到期日与到期动作——两处日期不一致就是漏洞。
4. **拍板人未回复不算确认**：MUST NOT 以"先按兼容做，以后再说"推进——那等于替用户选了代价最高的一项。

## 代码评审门：编码完成后强制执行

按 `代码评审纪律.md` 执行，**完整流程与 Lean 路径都不豁免**：

- **完整流程**：派 3 个并行子代理，**规范轴 / 忠实轴 / 残留轴**各一个，各自独立报告。
- **Lean 路径**：派 1 个子代理跑三轴精简版，报告仍分三节写。
- 子代理 prompt **必须点名加载 ai-dev-workflow skill**（模板见该纪律 §子代理 prompt 模板）——评审者要和实现者守同一套纪律，而靠关键词自动触发不可靠。
- harness 不支持子代理时降级为主会话分轮执行，一轴一轮、一轮一份报告，不许合并成一次"总体看看"。

**P0 与 P1 全部修完才算过门**；未过门不得进入 Step 8，也不得进入完成与自动合并门。残留轴以 spec 的替换清单为判据，逐条核销引用数。走 PR 合并的项目（`merge-gate="pr"`）另需记住：本门是 PR 前的**地板不是天花板**，MUST NOT 用它替代人审，且 MUST 在开 PR **之前**过完（`代码评审纪律.md` §处置——判据只认 `merge-gate` 这一个字段，与协作面无关）。

## 完成与自动合并门

Lean 路径和完整流程都必须以此门收尾。按 `worktree开发纪律.md` 确认需求、文档、代码、测试、提交、最新主分支同步以及 `merge-gate` 所声明的合并门禁全部完成。条件满足后无需再次询问用户，按 `merge-gate` 合并到仓库主分支并做合并后验证，再清理 worktree。

**本门同时结算文档生命周期**：盘点本次**触碰的权威面**（启用权威位时，与刷 card 用的是同一个面，见 `capability/curated.md` §7），拿去比对 `docs/index.md` 现行区各文档的 `authority_refs`，命中的逐篇判定"仍准确（更新 `last_confirmed`）"或转归档（`文档治理.md` §3）。**注意不是照抄替换清单**——只改语义没删东西（枚举加值、可选改必填、校验规则变更）同样让描述它的文档失准，而这类改动的替换清单往往是空的。**代码里的口径变了，描述它的文档不能还挂在现行索引上。**

任一条件失败时不得合并或清理 worktree。`merge-gate="pr"` 的仓库必须通过 PR、审批、CI 和保护分支规则，禁止为了"自动"而绕过项目治理。

**本门之后还有一段收尾汇报**：合并与清理完成后，按 `资产补建信号.md` 判定本次累计的资产补建信号是否达阈值，达到则向用户提一次具体建议（补权威位或补图谱位）。**判定 MUST 在门外做**——本门是非交互门且要求 worktree 干净，把提问或记账挂进来会卡住自动合并（`worktree开发纪律.md` §合并后的收尾汇报）。

## 六条"不裁剪"护栏

**轻量不等于可省。** Triage 可以让小改动走得快，协作面可以砍掉对齐开销，能力位可以决定去哪取代码事实——但下面六条**在任何协作面、任何能力位、任何分流路径下都 MUST NOT 被裁剪**，Lean 路径一条也不豁免。它们全部写成否定式，因为它们要阻断的正是"这次改动很小 / 就我一个人 / 这项目没那么正式，所以可以省"这条推断。

1. **目录不裁剪。** 轻量不等于散放：spec 仍 MUST 写进 `docs/spec/`，coding plan 仍 MUST 写进 `docs/plan/`，报告仍 MUST 写进 `docs/report/`。MUST NOT 因为"就一份文档"把设计散放在代码注释、聊天记录或仓库其它位置。文件命名与例外见 `文档治理.md`。
2. **沟通纪律不裁剪。** 用户只确认业务目标、业务边界和必要的大架构；模块内设计通过业务问题取约束；详细程序设计直接完成，MUST NOT 就它发起技术确认（`用户沟通纪律.md`）。
3. **worktree 与自动合并不裁剪。** 再小的 Lean 改动也 MUST 先进入独立 worktree；全部验证通过后按 `merge-gate` 合并，失败则保留 worktree，MUST NOT 直接修改主工作树（`worktree开发纪律.md`）。
4. **代码评审门不裁剪。** MUST NOT 因为"改动很小"就一个子代理都不派：完整流程 3 个并行子代理，Lean 路径 1 个跑三轴精简版，但不能跳过（`代码评审纪律.md`）。
5. **兼容取舍不裁剪。** 每次 MUST 把被改变的既有可观察行为逐条列出交拍板人明确拍一次，结论落进 spec 的兼容取舍节；清单为空时也 MUST 显式写一句"本次不改变任何既有可观察行为"，MUST NOT 静默跳过这道门。
6. **测试资产与覆盖度台账不裁剪。** 真实样本不因项目小而变便宜——遇到的真实输入照样 MUST 固化进测试 fixture，长链路照样 MUST 写断言中间结果的端到端用例（`测试资产纪律.md`）。可以裁剪的只有**深度**：覆盖度台账 MAY 只记高重要度场景。

## 按边界拆：spec / Issue / PR 的粒度

**拆分判据是边界，不是人数。** 这里的"边界"指代码仓库、独立部署单元、模块或限界上下文。一个需求跨越多个边界时，无论项目有几个人在做，都按下列规则拆。

### 按边界拆 spec

- 需求跨多个边界时，**MUST 按边界划分 spec**，每个边界一份，明确该边界做什么、不做什么、与上下游的契约。
- **每份 spec 写入对应边界所在仓库的 `docs/spec/`，coding plan 写入同仓的 `docs/plan/`，报告写入 `docs/report/`。** MUST NOT 把多个边界的设计混成一份"全写在一起"的大文档，也 MUST NOT 散放到仓库其它位置。
- 跨边界的 Overview（Step 2）是这些 spec 的共同上文，MUST 先于它们定稿；Overview 的"已定决策"表是各份 spec 之间不重复争论的依据。

### 大 PRD 先做垂直切片，再按边界拆

- 一份 PRD 含多个可独立交付的能力时，**MUST 先按垂直切片拆成一组 feature Issue**（INVEST：独立 / 可协商 / 有价值 / 可估 / 小 / 可测）。每个 Issue 带 Scope 锚点 + 参照的现有实现指针 + 约束护栏 + 测试信号，并标出 Issue 间依赖顺序与显式 out-of-scope。
- 再对每个切片走 Overview → 按边界出 spec。项目若有自己的 PRD 拆解规范，完整拆解方法以其为准。

### PR / 提交粒度

- 一个 coding plan 任务 SHOULD 对应一个小而可 review 的 PR 或提交，规模控制在**约 3–8 文件**。
- 这条与人数无关：agent 单次可产出上千行改动，粒度限制是人类审阅者（以及下一个零上下文 agent）唯一的审查窗口。`merge-gate="pr"` 时的平台动作见 `代码评审纪律.md` §处置 与 `worktree开发纪律.md` §完成与自动合并门——它们只认 `merge-gate` 这一个字段；`collab/team.md` §4 只补"因为有别人"才多做的那几件（指派评审人、与 owner 约合并窗口）。

### 多边界的合并顺序

- 多边界改动 MUST 全部通过完成与自动合并门后再开始合并，并按**依赖顺序**执行：**谁的对外契约先被别人依赖，谁先合**（提供方先于消费方；互不依赖的边界 MAY 任意顺序）。
- 任一步失败立即停止后续合并，并报告已合并与未合并的业务范围（`worktree开发纪律.md`）。
- 协作面 = team 时，合并顺序还 MUST 与各边界 owner 协商确认后再执行（`collab/team.md` §5）。
