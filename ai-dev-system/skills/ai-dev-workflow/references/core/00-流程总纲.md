# 开发流程总纲（core，技术栈无关）

> 适用于任何技术栈（Web 全栈 / 后端服务 / AI-LLM 应用 / 数据脚本）。个人版和团队版共用本总纲，只是**走多深、要不要评审/多仓协作**不同。
> **本文是骨架层**：分流判据 + 四道门 + 步骤索引。每步的执行细节按分流结果再加载对应分册，不要一次性全读。
> 与用户的所有对话按 `用户沟通纪律.md` 使用业务语言；技术词只留在内部工程产物中。
> 全程遵守 `上下文卫生.md`：方向性决策在聪明区内完成，逼近上限交接而非硬撑。

## 流程总览

```
路由/初始化 → 工作区隔离门（独立 worktree）→ Step 0 分流(Triage)
  ├─ 小改动 & 4 项全否 → 读 路径-lean.md：一页 Lean Change Spec → 兼容门 → 实现 → 评审门
  └─ 大需求 / 任一为是 → 读 步骤-1-7-设计与实现.md：
        1 PRD 粗澄清 → 2 Overview 顶层设计 → 3 PRD 细澄清
        → 4 技术 Spec(含 AI overlay，登记替换清单) → 5 Spec 自检
        → 兼容取舍确认门 → 6 Coding Plan → 7 执行编码
        → 代码评审门 → 读 步骤-8-10-测试.md：8 测试 Spec → 9 测试代码 → 10 链路测试
  └─ 两条路径最终都进入：完成与自动合并门 → 主分支
```

## 四道门（贯穿两条路径，Lean 一道也不豁免）

| 门 | 触发时机 | 判据在哪 | 不过门的后果 |
|---|---|---|---|
| **工作区隔离门** | 路由完成后、任何文档或代码落盘前 | `worktree开发纪律.md` §工作区隔离门 | 改动落进主工作树，与用户未提交的工作纠缠在一起 |
| **兼容取舍确认门** | spec 定稿前（完整流程 Step 5 后 / Lean 开始实现前）| 本文 ↓ §兼容取舍确认门 | AI 替用户决定了要不要兼容，包袱或断裂二选一都没人知情 |
| **代码评审门** | 编码完成、基础验证通过后 | 本文 ↓ §代码评审门 + `代码评审纪律.md` | 漏实现、镀金、越界、旧逻辑残留一起进主分支 |
| **完成与自动合并门** | 合并前 | `worktree开发纪律.md` §完成与自动合并门 | 未验证的改动进主分支，失败现场也被清掉 |

**工作区隔离门补充**：多仓需求为每个仓库分别创建 worktree。主工作树有未提交改动、项目不是 Git 仓库或无法创建 worktree 时，中止开发，不直接在当前目录继续。

另有两道**条件触发**的门，不贯穿两条路径，命中才过：

- **红回路门**：bug / 回归 / 异常行为类需求，动手改代码前先过（Lean 路径也不豁免）。→ `bug诊断纪律.md`
- **大架构确认门**：完整流程 Step 2 之后，只要 Overview 改变业务能力划分、关键职责边界、主业务流程、重要协作关系、历史数据归属或不可逆风险，就必须先形成**业务语言摘要**交用户确认，确认后才能进 Step 4。→ `步骤-1-7-设计与实现.md` §大架构确认门

## Step 0：需求体量与风险分流（Triage）

**先判断体量，再决定走多重的流程。** 对没有完整 PRD 的小 Issue / 体验改进，回答 4 个判定问题：

1. 是否改变智能能力给用户的结果或判断方式？
2. 是否改变谁可以做什么、敏感信息保护或使用场景？
3. 是否影响多个业务环节、需要搬迁历史数据或存在不可逆影响？
4. 是否改变经营指标、业务规则或对外承诺？

- **4 项均为「否」** → 走 Lean 路径：**加载 `路径-lean.md`**，用一页 Lean Change Spec（`assets/templates/lean-change-spec.md`）作为唯一交付物，写入 worktree 内的 `docs/spec/<change-name>-lean-change-spec.md`。跳过 Step 1–10，但四道门一道不少。
- **任意一项为「是」** → 走完整流程：**加载 `步骤-1-7-设计与实现.md`**；涉及 AI/LLM 的，在 Step 4 叠加 AI overlay。

> 意义：既不给小改动套重流程，也不给有风险的改动（AI 行为、安全、跨服务、对外承诺）走捷径。
>
> **个人版**：默认所有需求先假设走 Lean Spec，只有自己都 hold 不住的复杂改动才升级。
> **团队版**：跨仓 / 影响面不清时，宁可升级到 Step 2 出 Overview，让协作方对齐。

## 兼容取舍确认门：spec 定稿前，由用户拍板

**兼容不是默认项。** 无条件保留旧行为会让包袱永久累积，无条件砍掉又可能打伤还在用旧口径的人——**这是业务取舍，不是技术选择，必须每次由用户决定，AI 不得自行默认。**

1. **先列清单（AI 做）**：把本次改动会改变的**既有可观察行为**逐条列出来——旧接口的请求/响应形状、旧字段与旧枚举值、旧数据在新逻辑下的解读、旧调用方（含外部系统、老版本客户端、定时任务、报表）依赖的行为、用户已经形成的操作习惯。**清单为空时也要显式写一句"本次不改变任何既有可观察行为，无兼容取舍"**，不许静默跳过这道门。
2. **逐条问用户（业务语言）**：每条给三个选项 + 一个推荐 + 一句理由，按 `用户沟通纪律.md` 只讲业务影响（谁会受影响、影响多久、代价是什么），不讲实现方案。多条时一次性批量抛出，不要一条一条问。

   | 选项 | 含义 | 代价 |
   |---|---|---|
   | **不兼容** | 直接切到新行为，旧行为立刻消失 | 仍在用旧行为的人立即受影响，但代码干净、无长期包袱 |
   | **兼容一段时间** | 新旧并存到某个到期日，到期后删旧的 | 需要维护两套；**MUST 同时定下到期日与到期后的动作** |
   | **永久兼容** | 旧行为长期保留 | 包袱永久化；只有对外契约或不可控调用方才值得 |

3. **结论落盘（MUST）**：写进 eng-spec §8.1 兼容取舍决策表（Lean 路径写进 lean-change-spec 的兼容取舍一行）。选了"兼容一段时间"的，MUST 在替换清单里把对应被取代物登记为**保留例外**，带上同一个到期日与到期动作——两处日期不一致就是漏洞。
4. **用户未回复不算确认**：MUST NOT 以"先按兼容做，以后再说"推进——那等于替用户选了代价最高的一项。

## 代码评审门：编码完成后强制执行

按 `代码评审纪律.md` 执行，**完整流程与 Lean 路径都不豁免**：

- **完整流程**：派 3 个并行子代理，**规范轴 / 忠实轴 / 残留轴**各一个，各自独立报告。
- **Lean 路径**：派 1 个子代理跑三轴精简版，报告仍分三节写。
- 子代理 prompt **必须点名加载 ai-dev-workflow skill**（模板见该纪律 §子代理 prompt 模板）——评审者要和实现者守同一套纪律，而靠关键词自动触发不可靠。
- harness 不支持子代理时降级为主会话分轮执行，一轴一轮、一轮一份报告，不许合并成一次"总体看看"。

**P0 与 P1 全部修完才算过门**；未过门不得进入 Step 8，也不得进入完成与自动合并门。残留轴以 spec 的替换清单为判据，逐条核销引用数。团队版：本门是 PR 前的地板，不替代人审。

## 完成与自动合并门

Lean 路径和完整流程都必须以此门收尾。按 `worktree开发纪律.md` 确认需求、文档、代码、测试、提交、最新主分支同步以及团队评审门禁全部完成。条件满足后无需再次询问用户，自动合并到仓库主分支并做合并后验证，再清理 worktree。

任一条件失败时不得合并或清理 worktree。团队仓库必须通过 PR、审批、CI 和保护分支规则，禁止为了"自动"而绕过项目治理。

## 个人版 vs 团队版 的裁剪对照

| Step | 个人版 | 团队版 |
|---|---|---|
| 0 Triage | 默认假设走 Lean | 认真分流，跨仓必升级 |
| 1 粗澄清 | 简化 | 用 ctx 查 context |
| 2 Overview | 复杂才写 | ≥3 仓必写 |
| 3 细澄清 | 省略 | 评审会 |
| 4-5 Spec | 大需求才写 | 按仓出 spec + 叠 AI overlay |
| 兼容取舍门 | **不裁剪**（自己也常忘了旧数据还在） | **不裁剪**，结论进 spec §8.1 |
| 6-7 Plan/编码 | 直接干 | plan → agent 执行 |
| 代码评审门 | **不裁剪**，Lean 走单子代理精简版 | **不裁剪**，3 子代理；不替代人审 |
| 8-10 测试 | 关键路径；长链路端到端不压缩 | 单仓 + 链路，准出 |
| 测试资产/覆盖度台账 | **不裁剪**（真实样本对个人项目一样贵） | 不裁剪；缺素材攒批向业务方索要 |
