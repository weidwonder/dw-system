# 开发流程总纲（core，技术栈无关）

> **本总纲属常驻集合，但"常驻"说的是"哪几份构成完整流程的基本盘"，不是"每次唤起都读"**：分流前只取 ↓ §Step 0（做 Triage 本身要用），其余前置节在 Triage 判成"任一为是"、按 `SKILL.md` 第 4 步补齐常驻时才读；**Lean 分支整篇不取本文**，它的投影是 `路径-lean.md`。本文适用于任何技术栈与项目形态，后者只决定额外加载哪些分册：**协作面**（`collab/solo.md` / `collab/team.md`，按标记块 `collaboration` 二选一）、**代码图谱**（`capability/graph.md`，探测到索引才加载）。分册只**追加**，MUST NOT 削减本总纲任何一条（↓ §七条"不裁剪"护栏）。
> **本文是骨架层**：分流判据 + 四道门 + 步骤索引 + 常驻约定；执行细节按分流结果再加载分册，不要一次性全读。
> **全程遵守**：`用户沟通纪律.md`（与用户只用业务语言）、`上下文卫生.md`（方向性决策在聪明区内完成，逼近上限交接而非硬撑）、`代码事实纪律.md`——代码事实层（`engineering-context/`）不是分册也不是可选项，任何项目都 MUST 先查卡片、查不到就读源码并当场补卡，永不裸 grep 找权威实体。
> **"为什么这么定"不在本文**：立论依据在分发源仓库 ai-dev-system 的 `docs/spec/2026-08-23-流程总纲历史沿革.md`；照本文执行 MUST NOT 依赖它，要改判据时才读。

> **本文不是一次读完的**：每个小节标题下都有一行 `> **何时读本节**`，取值只有两类——**前置**（本文被取到的那一刻立即读完，读完就能开工；除 §Step 0 外都是完整分支补齐常驻时才被取到）与**触发式**（各自的触发点到了才读，触发条件写在该节自己那一行里）。**MUST NOT 因为"反正都在一个文件里"就整篇预读**：那等于把渐进式披露作废，把聪明区填给这次可能根本不触发的判据。触发式节未触发时 MUST NOT 预读，触发点一到 MUST 当场读那一节、MUST NOT 凭印象复述它的判据。

## Step 0：需求体量与风险分流（Triage）

> **何时读本节**：**分流前就取**（前置，本文唯一在分流前取的一节）——路由做完当场就要用它分流，分流结果决定后面加载哪一册；两条路径都取。

**先判断体量，再决定走多重的流程。** 没有完整 PRD 的小 Issue / 体验改进，回答 4 个判定问题：

1. 是否改变智能能力给用户的结果或判断方式？
2. 是否改变谁可以做什么、敏感信息保护或使用场景？
3. 是否影响多个业务环节、需要搬迁历史数据或存在不可逆影响？
4. 是否改变经营指标、业务规则或对外承诺？

- **4 项均为「否」** → **默认**走 Lean（先过 ↓ §默认倾向，未命中升级条件再**加载 `路径-lean.md`**），唯一交付物是一页 Lean Change Spec（`assets/templates/lean-change-spec.md`），写入 worktree 内 `docs/spec/<change-name>-lean-change-spec.md`；跳过 Step 1–10，四道门一道不少。
  ——**MUST NOT 把本条读成无条件结论**：四问全否**之后**还要过一遍 §默认倾向，命中升级条件即改走完整流程。
- **任意一项为「是」** → 走完整流程：**加载 `步骤-1-7-设计与实现.md`**；涉及 AI/LLM 的，在 Step 4 叠加 AI overlay。

**第 3 问命中时另有一项确认义务（MUST）**：MUST 按 `用户沟通纪律.md` §1 的格式形成**业务语言摘要**交用户确认后才能动手；摘要 MUST 写清**动了哪些历史数据、影响哪些既有业务、出错后能不能退回去、退不回去的部分是什么**。

**4 问 MUST 逐题过一遍，不是"假设"全否**。

### 默认倾向（四问全否之后）

> **何时读本节**：Triage 四问全否、要判"走 Lean 还是升级回完整流程"时才读；判据 3/4 在写〈既有系统清单〉时还要回溯复核一次。四问任一为是（已在完整流程里）时它没有适用对象，未命中前 MUST NOT 预读。

本倾向**无条件适用于所有项目**，MUST NOT 由协作面、项目大小或有没有代码图谱来改变：

> **影响面说不清时，MUST 升级到完整流程出 Overview；说得清才走 Lean。**

**"影响面说不清"的判据（命中任一即算）**，按可评估的时点分两批：

| # | 判据 | 什么时候过 |
|---|---|---|
| 1 | 本次要改的能力在 registry 里跨 ≥2 个权威仓库 | **Triage 当场**，MUST 逐条过 |
| 2 | `ctx discover` 给出了 out-of-scope 警告（命中废弃或中间产物实现）| **Triage 当场**，MUST 逐条过 |
| 3 | 关键事实里有任何一条**给不出出处**（卡片 cite 或 `文件:行`）| **回溯触发**：Step 1 进行中 / Lean 第 3 步写〈既有系统清单〉时命中即当场升级 |
| 4 | 卡片、`discover`、`search-semantic` 都收不窄，**读完源码仍说不清模块边界** | 同上 |

**判据 3/4 回溯触发，MUST NOT 在 Triage 当场强行判定**。**Lean 没有 Step 1，落点是 `路径-lean.md` 第 3 步**（〈既有系统清单〉）——MUST NOT 因为"我走的是 Lean、没有 Step 1"就认为这两条对自己不适用；在那一步命中即**当场升级回完整流程**（同 `路径-lean.md` §15. Lean 特有的四个提醒 首条）。

**判据 3 MUST NOT 被读成"卡片里查不到就算说不清"**：查不到的正确处置是**读源码 + 当场补卡**（`代码事实纪律.md` §4），补完就有 `文件:行` 出处，判据 3 即不命中。真正命中的是**读了源码也说不出这条事实从哪来**——动态派发、配置化路由、反射调用这类"代码在这儿但决定权不在这儿"。

**判据 4 同理**：卡片没命中不算，**读完源码仍说不清**才算。

**判据 1/2 怎么当场核对**：按 `代码事实纪律.md` §3 的固定顺序跑 `ctx find-scenes` → `ctx discover`，拿到端到端全景、命中仓库与 out-of-scope 警告后逐条对照；**MUST NOT 跳过 find-scenes 直接 discover**——`代码事实纪律.md` §3 的排序铁律：除非用户已把任务限定到某一个具体 repo，否则第一步 MUST 先取业务全景。结果一并进 Step 1 的〈既有系统清单〉，不重复跑。
**registry 还是空的时候，判据 1/2 自然都不命中**——这是正常起步态，MUST NOT 因此判定"说不清"，也 MUST NOT 因此判定"说得清"：此时该看的是判据 3/4 在 Step 1 里的回溯结果。

MUST NOT 用"我感觉不复杂"代替以上任何一条。
**MUST NOT 从"只有我一个人"推出"默认走最短流程"**——协作面不参与本判据。
**MUST NOT 从"这项目还没几张卡片"推出"这项目简单"**——卡片少只说明还没人读过这块代码，与代码本身的复杂度无关。

## 兼容取舍确认门：spec 定稿前，由拍板人拍板

> **何时读本节**：spec 定稿前（完整流程 Step 5 之后 / Lean 开始实现前）要拍板兼容取舍时才读，未命中前 MUST NOT 预读——本节要逐条列清单、逐条问拍板人、结论落进 spec，凭印象复述最先漏掉的就是"清单为空也 MUST 显式写一句"。

**兼容不是默认项。这是业务取舍不是技术选择，MUST 每次由人拍板，AI 在任何项目形态下都 MUST NOT 自行默认。**

**谁拍板**：solo → 开发者本人（`collab/solo.md` §3）；team → 业务负责人（`collab/team.md` §3）。流程一致，只是"问谁"不同。

1. **先列清单（AI 做）**：逐条列出本次改动会改变的**既有可观察行为**——旧接口请求/响应形状、旧字段与旧枚举值、旧数据在新逻辑下的解读、旧调用方（外部系统、老版本客户端、定时任务、报表）依赖的行为、用户已形成的操作习惯。**清单为空时也要显式写一句"本次不改变任何既有可观察行为，无兼容取舍"**，不许静默跳过。
2. **逐条问拍板人（业务语言）**：每条给三个选项 + 一个推荐 + 一句理由，按 `用户沟通纪律.md` 只讲业务影响（谁受影响、影响多久、代价是什么），不讲实现方案；多条时一次性批量抛出。

   | 选项 | 含义 | 代价 |
   |---|---|---|
   | **不兼容** | 直接切到新行为，旧行为立刻消失 | 仍在用旧行为的人立即受影响，代码干净无长期包袱 |
   | **兼容一段时间** | 新旧并存到某个到期日，到期后删旧的 | 要维护两套；**MUST 同时定下到期日与到期后的动作** |
   | **永久兼容** | 旧行为长期保留 | 包袱永久化；只有对外契约或不可控调用方才值得 |

3. **结论落盘（MUST）**：写进 eng-spec §8.1 兼容取舍决策表（Lean 写进 lean-change-spec 的兼容取舍一行）。选"兼容一段时间"的，MUST 在替换清单里把对应被取代物登记为**保留例外**，带同一个到期日与到期动作——两处日期不一致就是漏洞。
4. **拍板人未回复不算确认**：MUST NOT 以"先按兼容做，以后再说"推进——那等于替用户选了代价最高的一项。

## 代码评审门：编码完成后强制执行

> **何时读本节**：编码完成、基础验证（能跑起来、无编译/语法错）通过、要过代码评审门时才读，未命中前 MUST NOT 预读——编码期预读它只会挤占聪明区，本节一条判据都轮不到用。

按 `代码评审纪律.md` 执行，**完整流程与 Lean 路径都不豁免**：

- **完整流程**：派 4 个并行子代理，**规范轴 / 忠实轴 / 残留轴 / 文档轴**各一个，各自独立报告。
- **Lean 路径**：派 1 个子代理跑 `代码评审纪律.md` §四条轴 的精简版，报告仍逐轴分节写。
- **D 文档轴恒跑**：参照物是 `docs/` 的现行文档与真相源，查「正文与代码是否一致 / 断链与孤儿 / 真相源跟上没有」。MUST NOT 由主会话先判「本次有没有碰文档」再决定派不派。文档生命周期的**盘点与逐篇判定**归它（判据在 `文档治理.md` §3），完成门只核对它的报告。
- 子代理 prompt **必须点名加载 ai-dev-workflow skill**（模板见该纪律 §子代理 prompt 模板）。
- harness 不支持子代理时降级为主会话分轮执行，一轴一轮、一轮一份报告，不许合并成一次"总体看看"。

**P0 与 P1 全部修完才算过门**；未过门不得进入 Step 8 与完成门。残留轴以 spec 的替换清单为判据，逐条核销引用数。`merge-gate="pr"` 的项目：本门是 PR 前的**地板不是天花板**，MUST NOT 用它替代人审，且 MUST 在开 PR **之前**过完（`代码评审纪律.md` §处置——只认 `merge-gate` 这一个字段，与协作面无关）。

## 完成与自动合并门

> **何时读本节**：代码评审门的 P0/P1 清零、要合并回主分支时才读，未命中前 MUST NOT 预读。

Lean 与完整流程都以此门收尾。按 `worktree开发纪律.md` 确认需求、文档、代码、测试、提交、主分支同步与 `merge-gate` 声明的合并门禁全部完成；满足后无需再问用户，按 `merge-gate` 合并——`direct` 在主工作树 `git merge --no-ff` + 最小合并后验证；`pr` 推分支开 PR，评审与 CI 过了才合，MUST NOT 绕过保护分支、审批、CI 或 owner 规则，也 MUST NOT 在平台未放行时改用本地直合。字段缺失时按**仓库现状 > 协作面推断**取值（远端主分支受保护或有 PR 规则 → `pr`；判不出才由 `collaboration` 推），MUST NOT 反过来。合并后验证通过再清理 worktree。

**本门只核对文档结算的结果，MUST NOT 在此重做盘点**（盘点归 D 文档轴）。核对三件事：D 轴报告在且其中的文档结论已**落盘**（失准的完成归档三动作、仍准确的 `last_confirmed` 更新为当天）、零命中时也有书面结论（"扫了 N 篇、0 篇失准"）、本次新建文档的 `lifecycle` 与 `authority_refs` 字段齐。判据见 `文档治理.md` §3，准出细则见 `worktree开发纪律.md` §完成与自动合并门。

**过不了怎么办**：测试失败、合并冲突、主工作树出现新改动、权限不足或门禁未通过时，MUST NOT 宣称完成、MUST NOT 合并；保留任务分支与 worktree、不清理现场，用业务语言说明尚未交付的能力、影响和下一步条件。

## 七条"不裁剪"护栏

> **何时读本节**：**完整分支补齐常驻时读**（前置）——裁剪一旦发生就已经发生了，事后读它没有用。Lean 分支不取本节，用 `路径-lean.md` §13 的投影（同一批护栏，Lean 一条也不豁免）。

**轻量不等于可省。** 下面七条在任何协作面、有没有代码图谱、任何分流路径下都 MUST NOT 被裁剪，Lean 一条也不豁免。

1. **目录不裁剪。** spec 仍 MUST 写进 `docs/spec/`、plan 仍 MUST 写进 `docs/plan/`、报告仍 MUST 写进 `docs/report/`；MUST NOT 因为"就一份文档"把设计散放在代码注释、聊天记录或仓库其它位置。命名与例外见 `文档治理.md`。
2. **沟通纪律不裁剪。** 用户只确认业务目标、业务边界和必要的大架构；模块内设计通过业务问题取约束；详细程序设计直接完成，MUST NOT 就它发起技术确认（`用户沟通纪律.md`）。
3. **worktree 与自动合并不裁剪。** 再小的 Lean 改动也 MUST 先进入独立 worktree；验证通过后按 `merge-gate` 合并，失败则保留 worktree，MUST NOT 直接改主工作树（`worktree开发纪律.md`）。
4. **代码评审门不裁剪。** MUST NOT 因为"改动很小"就一个子代理都不派：派几个、跑哪几条轴见 ↑ §代码评审门，Lean 也不能跳过。
5. **兼容取舍不裁剪。** 每次 MUST 走完 ↑ §兼容取舍确认门（逐条列出、交拍板人拍一次、结论落进 spec 的兼容取舍节）；清单为空时也 MUST 显式写一句"本次不改变任何既有可观察行为"，MUST NOT 静默跳过这道门。
6. **测试资产与覆盖度台账不裁剪。** 遇到的真实输入照样 MUST 固化进测试 fixture，长链路照样 MUST 写断言中间结果的端到端用例（`测试资产纪律.md`）。可裁剪的只有**深度**：覆盖度台账 MAY 只记高重要度场景。
7. **补卡不裁剪。** 本次为推进任务而读了源码的模块，MUST 在本次任务内把卡片补上并随分支提交（`代码事实纪律.md` §4）；MUST NOT 因为"改动很小""就查了一个字段""这项目还没建几张卡"就跳过。可裁剪的只有**范围**：只补本次真读过并核对过的那部分，MUST NOT 为了"补全"去写没核对过的字段。

## 按边界拆：spec / Issue / PR 的粒度

> **何时读本节**：需求跨多个边界、手里是含多个可独立交付能力的大 PRD、或要切 PR 与提交粒度时才读；三种情形都不命中就整节不读（禁止预读的规范条款见文首）。

**拆分判据是边界，不是人数。**"边界"指代码仓库、独立部署单元、模块或限界上下文。

### 按边界拆 spec

> **何时读本节**：本次需求跨 ≥2 个边界时才读（Lean 恒为单边界，走到自足册就说明本次不命中）；未命中前 MUST NOT 预读。

- 需求跨多个边界时 **MUST 按边界划分 spec**，每份明确该边界做什么、不做什么、与上下游的契约。
- **每份 spec 写入对应边界所在仓库的 `docs/spec/`，plan 写同仓 `docs/plan/`，报告写 `docs/report/`。** MUST NOT 把多个边界混成一份大文档，也 MUST NOT 散放到仓库其它位置。
- **出** Overview 时它是这些 spec 的共同上文，MUST 先于它们定稿；其"已定决策"表是各份 spec 之间不重复争论的依据。**要不要出**由 `步骤-1-7-设计与实现.md` §本步必做还是可跳过 的判据表单独决定（跨边界数 × 协作面），本处 MUST NOT 另立一套——跨 2 个边界的 solo 改动同样产出 2 份 spec，把本条读成"有 spec 就必须有 Overview"会与那张表的 MAY 跳过冲突。

### 大 PRD 先做垂直切片，再按边界拆

> **何时读本节**：一份 PRD 含多个可独立交付的能力、要先拆成一组 feature Issue 时才读；未命中前 MUST NOT 预读。

- 一份 PRD 含多个可独立交付的能力时，**MUST 先按垂直切片拆成一组 feature Issue**（INVEST：独立 / 可协商 / 有价值 / 可估 / 小 / 可测）。每个 Issue 带 Scope 锚点 + 参照的现有实现指针 + 约束护栏 + 测试信号，并标出 Issue 间依赖顺序与显式 out-of-scope。
- 再对每个切片走 Overview → 按边界出 spec。项目若有自己的 PRD 拆解规范，完整拆解方法以其为准。

### PR / 提交粒度

> **何时读本节**：要切 PR 或提交、需要定粒度时才读（禁止预读的规范条款见文首）。

- 一个 coding plan 任务 SHOULD 对应一个小而可 review 的 PR 或提交，约 **3–8 文件**；与人数无关。`merge-gate="pr"` 的平台动作见 `代码评审纪律.md` §处置 与 `worktree开发纪律.md` §完成与自动合并门（只认 `merge-gate` 这一个字段）；`collab/team.md` §4 只补"因为有别人"才多做的那几件（指派评审人、与 owner 约合并窗口）。

### 多边界的合并顺序

> **何时读本节**：多边界改动全部过完完成与自动合并门、要开始逐个合并时才读；单边界改动 MUST NOT 预读。

- 多边界改动 MUST 全部通过完成与自动合并门后再开始合并，并按**依赖顺序**执行：**谁的对外契约先被别人依赖，谁先合**（提供方先于消费方；互不依赖的边界 MAY 任意顺序）。
- 任一步失败立即停止后续合并，并报告已合并与未合并的业务范围（`worktree开发纪律.md`）；协作面 = team 时合并顺序还 MUST 与各边界 owner 协商确认后再执行（`collab/team.md` §5）。

## 移出常驻的三篇：结论行与展开指针

> **何时读本节**：**完整分支补齐常驻时读**（前置）——三篇已不常驻，这几行是它们在完整流程里的最小地板（落任何文档的目录与 frontmatter、动笔写字的三条硬规则、两道 worktree 门最易漏的两项），补齐之后任一步都可能当场要用；要展开哪一篇按本节末尾的指针在触发时取。Lean 分支不取本节，用 `路径-lean.md` §4.2、§10.1、§10.2 与入口 `SKILL.md` §工作区隔离门要点 的投影。

`文档治理.md`、`spec写作纪律.md`、`worktree开发纪律.md` **不再常驻**，按加载点触发时才取。下面是最小判据不是摘要——要改其中任何判据、或遇到本节没覆盖的情形，MUST 取原篇对应小节，MUST NOT 凭这几行推断。

**`文档治理.md`**

- **输出目录只有三个**：spec → `docs/spec/`，plan → `docs/plan/`，report → `docs/report/`。MUST NOT 放项目根、仓库根或 `docs/` 根（唯一例外：需求与架构两层真相源 `REQUIREMENTS.md`、`ARCHITECTURE.md` 放 `docs/` 根），MUST NOT 建 `docs/superpowers/`、`docs/claude/`、`docs/codex/` 这类工具专属目录，文件名 MUST 表达业务主题与文档角色。→ `文档治理.md` §硬规则。
- **两个账本是检索索引不是阅读材料**：`docs/report/bug修复历史.md` 与 `docs/report/测试场景覆盖度.md` MUST 用关键词检索定位条目，MUST NOT 整份读进上下文。→ `文档治理.md` §5 账本的读取纪律。
- **新建文档的 frontmatter MUST 有两个字段**：`lifecycle` = 本文此刻还算不算现行口径，取 `active` / `merged` / `superseded` / `obsolete`，只有 `active` 进 `docs/index.md`、其余进归档索引（字段名是 `lifecycle` 不是 `status`）；`authority_refs` = 本文冻结了哪些权威面，一条都不冻结时 MUST 显式写一条 `无`，MUST NOT 留空。→ `文档治理.md` §文档生命周期与索引门控。

**`spec写作纪律.md`**

- **零上下文可动手**：读者零上下文，文档 MUST 自带精确文件路径（写 `src/api/user.controller.ts:42`，MUST NOT 写"改那个 controller"）、可直接抄走的完整代码、精确命令与预期输出、每条外部事实的出处。→ `spec写作纪律.md` §1 零上下文原则。
- **RFC 2119 规范性措辞**：有约束力处 MUST 用大写关键词（MUST / MUST NOT / SHOULD / SHOULD NOT / MAY / Implementation-defined），并在文档顶部声明一次按 RFC 2119 解释。→ `spec写作纪律.md` §2 RFC 2119 规范性措辞。
- **无占位符**：实现步骤里 MUST NOT 出现 `TBD`、`TODO`、"稍后补充"、"加上适当的错误处理"、"同 Task N"，也 MUST NOT 引用任何任务里都没定义的类型/函数——这些是文档失败，不是待办。显式标注的"后续 / Out-of-scope 待办"区不在此列，其中每条 MUST 说明为什么这期不做。→ `spec写作纪律.md` §3 无占位符（硬规则）。

**`worktree开发纪律.md`**

- **工作区隔离门怎么过**：要点已在入口 `SKILL.md` §工作区隔离门要点（每次唤起必读），本文只重申两条最易漏的——目录 MUST 每次重新读标记块 `worktree-dir`（未声明时默认 `./.worktrees/`），MUST NOT 沿用上次会话记住的路径；过不了时 MUST 中止并用业务语言说明，MUST NOT 替用户 stash / reset / checkout 覆盖 / 删除未知文件，MUST NOT 降级为直接改当前目录。→ `worktree开发纪律.md` §工作区隔离门。
- **完成与自动合并门怎么过**：判据已收进 ↑ §完成与自动合并门（`direct`/`pr` 各做什么、`merge-gate` 缺失时的取值顺序、过不了怎么办），MUST 照那节执行。→ 展开读 `worktree开发纪律.md` §完成与自动合并门 与 §失败与阻塞。
