# 完整流程 Step 1–7：澄清 → 设计 → 实现

> 加载条件：Step 0 Triage 有任一项为「是」，走完整流程。测试阶段的细节在 `步骤-8-10-测试.md`，进入 Step 8 前再读。
> 两道门（兼容取舍确认门、代码评审门）的判据在总纲，本文只标出它们插在哪两步之间。
> 每步给了**输入 / 产出 / 参考 prompt / 对应模板**；prompt 里的 `【】` 是你要替换的占位符。

> **本文小节**：[Step 1 PRD 粗澄清](#step-1prd-粗澄清) · [Step 2 生成 Overview](#step-2生成-overview顶层设计)（含 §本步必做还是可跳过、§大架构确认门）· [Step 3 业务细节澄清](#step-3业务细节与模块约束澄清) · [Step 4 生成技术 Spec](#step-4生成技术-spec) · [Step 5 内部技术自检](#step-5内部技术自检) · [Step 6 生成 Coding Plan](#step-6生成-coding-plan) · [Step 7 执行 Coding](#step-7执行-coding)

## Step 1：PRD 粗澄清

**输入** PRD（+ UI 原型 HTML，如 PRD 含"UI 原型"节）｜ **产出** 需求理解 + 问题清单 ｜ **对应模板** 无（对话）

让 AI 建立对需求的整体理解，找出 PRD 的**模糊点、重复点、矛盾点**。

```text
# 参考 prompt
这是一个【业务域】【项目名】相关的需求（参考 PRD @【PRD 文件】、UI 原型 @【原型文件，无则删除本项】）。
先理解整体要做什么？不做什么？方向和边界在哪？并列出 PRD 的模糊点、重复点、矛盾点。
```

> **UI 原型是 PRD 的一部分，必须一并读**：PRD 若有"UI 原型"节（`ai-prd` 产出的 `docs/spec/<name>-prototype-YYYYMMDD.html`），MUST 打开该文件，把它当作用户可见行为的权威描述读——页面结构、状态流转、空态/错误文案、控件层级都以原型为准。原型与 PRD 正文冲突时**不要自行取舍**，立成问题清单里的一条（严重度按影响判）。PRD 声明"不适用 + 原因"或无该节时跳过。

> **问题清单怎么写才好澄清**（否则清单等于没列）：
> - **锚定位置**：每个问题标出它源自 PRD 的哪一节/哪句话，评审时能直接回溯。
> - **给选项不给开放题**：能给方向的，附 2–4 个具体候选 + 一个推荐，让产品/技术在选项上表态，而不是从零作答。
> - **标严重度**：P0 阻塞（不定就没法往下做）/ P1 重要 / P2 次要 / P3 可延后——先解决 P0。
> - **能查代码定的先查**，别把可查事实混进澄清清单（呼应 spec写作纪律 §6 事实门）：启用权威位时用 `ctx` 并附 cite（`capability/curated.md`），启用图谱位时查代码图谱（`capability/graph.md`），都未启用时子代理外包读码（`上下文卫生.md` 规则 4）。

> **启用权威位时（业务全景门限）**：除非任务已明确限定到某一个具体 repo，**先 `ctx find-scenes <关键词>` 取端到端业务全景，再 `ctx discover` 收窄到涉及仓库的 card**——先看全景再钻细节，避免漏掉跨服务链路。带着问题清单和产品做第一轮澄清。
>
> **额外产出〈既有系统清单〉**（Step 2 的 A 核查要拿它逐条对照）：把 `discover`/`find-scenes` 推荐的卡片/场景、每张卡片列出的**子模块与已有机制**（准入/白名单/校验/开关/状态机/存储等）、以及 discover 的 **out-of-scope 警告**，原样抄成一个列表。这份清单是"这次改动会碰到的既有世界"的快照，不做判断，只做穷举。
>
> **它落在哪（MUST 择一，MUST NOT 只存在于对话里）**：出 Overview → 落 `overview.md` §6 Project Map 之前的一小节；不出 Overview → 落 `eng-spec.md` §1 范围 的子节；走 Lean → 落 `lean-change-spec.md` §影响范围 / 不做什么。清单要被 Step 2 的 A 核查逐条对照、被替换清单引用、还要当资产补建信号的出处，没有落点就三处都悬空。
> 写这份清单时若**被迫打开源码或 clone ≥2 个"入手时不知道它存在"、且最终进了本清单的模块**，MUST 同时记一条**图谱位**信号进 `docs/report/资产补建信号.md`。**只做了检索（grep / 语义搜索）而没打开源码的不算**；三条判据、格式与阈值的完整定义见 `references/core/资产补建信号.md` §1，此处不重复。记的是"本不该做的探索真的做了"，不是"这次查得比较久"。
>
> **未启用权威位的项目同样要出这份清单**（Step 2 的 A 核查照样要用它）：改从入口出发列出会被碰到的模块、已有机制与外部依赖——启用图谱位时用代码图谱查调用链与影响面（`capability/graph.md`），两位都没有时把探索外包给子代理（`上下文卫生.md` 规则 4），MUST NOT 因为"没有 card"就跳过这一步。

## Step 2：生成 Overview（顶层设计）

**输入** 澄清后的 PRD（+ UI 原型 HTML，如有）｜ **产出** Overview 顶层架构文档 ｜ **对应模板** `assets/templates/overview.md`

### 本步必做还是可跳过

判据只有两项：**本次改动跨几个边界**（边界 = 仓 / 模块 / 限界上下文）与**协作面**（标记块的 `collaboration` 字段）。

| 跨边界数 | 协作面 = team | 协作面 = solo |
|---|---|---|
| **≥3** | **MUST 出 Overview** | **SHOULD 出 Overview** |
| **≤2** | SHOULD 出（改动触及别人 owner 的仓时）；否则 MAY 跳过 | **MAY 跳过** |

- **MUST（team + 跨 ≥3 边界）**：Overview 是评审会（`collab/team.md` §2）与后续按边界拆 spec 的基础；没有它，每份 spec 都会把同一个架构问题重吵一遍。
- **SHOULD（solo + 跨 ≥3 边界）**：收益方是两个月后的你自己和零上下文的 agent；打算把执行拆给多个 agent 会话时更要写——Overview 是它们之间唯一的通信信道（`collab/solo.md` §1）。
- **跳过的是"对齐用的文档"，不是决策记录**：已定决策照样 MUST 落进 Lean Change Spec 或 spec 的决策表。
- **跳过 Overview MUST NOT 跳过大架构确认门**：那道门认的是"本次改动命中没命中大架构判据"，不认"有没有出 Overview"（见 ↓ §大架构确认门）。

> ⚠️ **本判据是纯协作语义，MUST NOT 与能力位挂钩。** 一个人维护的十万行遗留系统可能图谱位、权威位全启用，照样不需要为了对齐而写 Overview——**能力位决定"到哪查代码事实"，不决定"要不要跟人对齐"**。反过来，能力位也不构成跳过的理由：card 齐全不等于三个仓的改造范围已经和人对齐过。（能力位真正影响的是**分流默认假设**，见 `00-流程总纲.md` §Triage。）

写 Overview 前若启用了权威位而还没跑过业务全景门限（`ctx find-scenes`），先补跑——Project Map 的完整性依赖它。

把 PRD 做一次"技术翻译"：告诉工程师**该打开哪些仓库、每个仓库改造范围多大**，但不讲怎么实现。四个必备内容——顶层模块与架构（粗颗粒度）、模块边界与关系、**Project Map**（哪些新增/哪些改造 + 每仓改动范围，最常被读的一节）、待澄清开放问题（说明源自 PRD 哪里）。

```text
# 参考 prompt
帮我产出顶层架构设计，输出到 @【docs/spec/ProjectName-overview.md】。
它本质是一个简化版的、面向技术的 PRD 说明：圈出涉及改造的项目和改造点，不展开实现。
定稿前必须做完模板 §14 的 A/B 两道核查，缺一不可；宁多列勿漏，完整性优先于简洁。
```

**定稿前两道核查**（**只要出 Overview 就 MUST 做**，包括只为自己理清而写的精简版）：补两类最常漏的点——"与既有系统交互"型（A：拿 Step 1 的〈既有系统清单〉逐项过）和"PRD 隐含要求"型（B：拿 PRD 逐节过）。**表格与逐列判据见 `assets/templates/overview.md` §14**，两张表连同 Overview 一起输出，命中的漏点补进正文或立成开放问题。

**结合真实代码回码核对**（把"倾向"变"事实"）：Overview 里凡是"翻代码就能定"的阻塞/倾向（接口签名、字段、哪个是权威实现、有没有某前置闸门），照开放问题表逐条进对应 repo（切最新 release 分支）证实，变成"已确认事实/已定决策"回写进已定决策表与 OQ 表；读码时发现与文档不符或文档里没有的事实，一并补进来。此步与 spec写作纪律 §6 的事实门同源——先查清能查的，再登记剩下的。

> **出处随能力位变，"必须有出处"不变**：启用权威位时 MUST 用 `ctx` 取权威事实并附 cite（path#anchor @确认时间）；启用图谱位时用代码图谱定位并给 `文件:行`；两位都没有时直读源码并给 `文件:行`。**无出处的结论一律不得回写进已定决策表。**

> 这是典型的"读得多、结论少"的活，harness 支持子代理时 SHOULD 外包（见 `上下文卫生.md` 规则 4）：

```text
# 回码核对子代理 prompt
你是 ai-dev-workflow 的回码核对子代理。先加载 ai-dev-workflow skill，读
references/core/spec写作纪律.md §6 事实门。
本项目已启用能力位 =【图谱位 / 权威位 / 无】。
启用权威位时按 references/capability/curated.md 用 ctx 取权威事实并附 cite，
MUST NOT 全仓裸 grep；card 不够用时按其 §6 clone 决策树取源码。
启用图谱位时按 references/capability/graph.md 用代码图谱定位调用链与影响面。
两位都未启用时直读源码，每条结论给出 文件:行 作为出处。
skill 未能按名字唤起时直接读：【skill 根目录绝对路径】/references/…

待核实清单（逐条给出结论，不要扩散到清单外）：
1.【接口/字段/权威实现/闸门的具体问句】
2.【…】

每条返回：结论（已确认事实 / 与文档不符 + 实际情况 / 查不到 + 卡在哪）+ 出处
（启用权威位时 MUST 是 cite：path#anchor @确认时间；否则给 文件:行）。
无出处的结论视为无效。只报告，MUST NOT 修改任何文件。
```

### 大架构确认门

**触发条件是「本次改动命中大架构判据」**——产品或技术架构的**主干路形状**变了（形状变才算，主干路上的取值变不算；判据与正反例的权威定义在 `用户沟通纪律.md` §1，本文 MUST NOT 复述）。命中即过门，必须先形成"用户确认摘要（业务语言）"。摘要只讲业务能力、角色、流程、影响、风险和不做什么，不展示程序结构。

**跳过 Overview MUST NOT 跳过本门。** 上面的判据表允许 solo + 跨 ≤2 边界 MAY 跳过 Overview，那跳过的是"对齐用的文档"；一个跳过了 Overview、却确实改变了主干路形状的改动，仍 MUST 单独形成业务语言摘要交用户确认。把触发条件读成"Overview 改了什么"，这道门就会在最常见的那条路上静默消失。

用户明确确认大架构后才能进入 Step 4。若用户要求调整，先修订摘要（出了 Overview 的连同 Overview 一起改），再次确认。

## Step 3：业务细节与模块约束澄清

**输入** Overview ｜ **产出** 修订后的 Overview ｜ **对应模板** 无

逐条确认 Overview 中尚未确定的业务规则、角色职责、处理顺序、时效要求、异常处理、权限边界和历史业务延续方式。

模块内结构设计需要取舍时，不向用户展示技术方案；改问可由业务判断的问题，例如"失败时阻断还是转人工""结果要立即可见还是允许稍后完成""多人同时操作时以谁为准"。AI 根据回答在内部完成设计和选型。

> ⏳ 这一步最花时间，Overview 会被反复修改。让 AI **按边界划分 spec**（仓 / 模块 / 限界上下文），每个边界内该做什么写清楚，AI 会更专注。
> **协作面 = solo**：此步基本省略——你既是产品也是技术，没有第二方要澄清（`collab/solo.md` §1）。仍有拿不准的业务规则时，自己明确拍板一次并落进决策表，MUST NOT 悬着不写。

## Step 4：生成技术 Spec

**输入** Overview + PRD（+ UI 原型 HTML，如有）｜ **产出** `docs/spec/<repo>-<feature>-eng-spec.md` ｜ **对应模板** `assets/templates/eng-spec.md`（+ `AI-LLM-overlay.md`）

```text
# 参考 prompt
根据顶层设计 @【设计文件】、PRD @【PRD 文件】和 UI 原型 @【原型文件，无则删除本项】，
按 eng-spec 模板推进各子仓库的 spec。
```

> **含前端/用户界面改动时**：用户可见的页面结构、状态与交互路径 MUST 以 PRD 的 UI 原型为准落进 spec，不得凭 spec 作者的想象另起一套。原型未覆盖的界面细节（次要页面、边缘状态）标为待确认，不脑补；原型与 PRD 正文冲突的，按 Step 1 已立的问题清单结论走，仍未定则标"待确认"，不在 spec 里替产品拍板。原型只定"用户看到什么"，**不定实现**——组件拆分、状态管理、样式方案仍由 spec 决定。

> **同时登记替换清单**：本次新逻辑取代了哪些既有函数/文件/配置/开关/DB 字段/接口版本，逐条登进 spec §8.2（格式与核销规则见 `代码评审纪律.md` §替换清单）。**登记发生在这一步，核销发生在编码后的评审门**——写 spec 时不登记，改完代码就没人记得该删什么了。

**含 AI/LLM workflow 时叠加 overlay**：若模型推理参与功能行为（生成/总结/分类/检索增强/排序推荐/OCR/语音手写识别/内容审核/固定 prompt 流程），在基础 spec 之上叠加 `AI-LLM-overlay.md` 的 AI 契约。判定边界见该文件。

## Step 5：内部技术自检

**输入/产出** spec（内部反复修订）｜ **对应模板** 无

AI 自行核对现有代码事实、信息定义一致性、实现边界、失败处理、兼容的**实现方式**和验证闭环，并自主完成详细程序设计。不得要求用户确认文件、接口、数据结构、存储方式、框架或具体落地方向。

> **注意"兼容"这个词的两面**：**怎么兼容**（双写、版本路由、适配层、灰度开关）是技术实现，AI 在本步自主决定，不问用户；**要不要兼容、兼容多久**是业务取舍，MUST 在下一道门交用户拍板。别把两者混为一谈——AI 替用户决定"要不要兼容"，是这一步最常见的越权。

只有发现未确定的业务规则或用户可感知取舍时，才返回 Step 3，用业务语言提问；不得把技术选择原样抛给用户。

> ⛔ **本步之后、Step 6 之前插入「兼容取舍确认门」**——判据见 `00-流程总纲.md` §兼容取舍确认门。

## Step 6：生成 Coding Plan

**输入** spec ｜ **产出** 对应仓库的 coding plan ｜ **对应模板** `assets/templates/coding-plan.md`

把 spec 拆成"假设执行者对代码库零上下文"的、bite-sized 的任务：每个任务带**文件路径、完整代码/测试、验证命令、commit**。适合直接交给 coding agent。

> **垂直切片（tracer bullet）拆任务**：每个任务 SHOULD 是一条穿透各层的端到端细流（一个最小场景从入口到出口打通、可独立验证），而不是水平分层（先建全部模型、再写全部逻辑、最后统一接线——集成风险全部压到最后）。任务间有先后依赖的，在任务头显式声明"依赖 Task N 的【产物】"；宽幅重构确实无法垂直切的（如全局换接口），用"先扩后收"（expand-contract）拆成可分步合并的任务，作为显式例外。
> **替换清单里的删除动作在这一步就要成为具体任务**（改哪个文件、删哪个符号），不是笼统一句"清理旧代码"。

```text
# 参考 prompt
阅读此 spec @【spec 文件】，生成 coding plan（写入 docs/plan/，命名 <feature>-coding-plan.md），
尽量贴近具体实现，适合交给 coding agent 执行。
```

---

## Step 7：执行 Coding

**输入** coding plan ｜ **产出** 代码改动 ｜ **对应模板** 无

在任务 worktree 内加载 plan、批判性 review，再逐任务执行、验证和提交。不得回到主工作树直接修改。

**边写边删**：实现新逻辑时，被它取代的旧逻辑**当场删除**，不要留到"最后统一清理"——留到最后就是留到永远。

向用户汇报时只说明完成了哪些业务能力、哪些业务边界保持不变、验证了哪些业务场景和还存在哪些业务风险；文件与代码细节留在 plan/report 中，除非用户明确索要。

> 💰 此步对 AI 能力要求不高，可切更省钱的模型。plan 按零上下文标准编写，因此本步可在新会话/子 agent 中执行；连续多任务上下文变重时在 checkpoint 处切换（见 `上下文卫生.md` 规则 3）。
> 📦 **启用权威位时**：card 不够用、需读其他服务真实源码时，按 `capability/curated.md` §6 的 **clone 决策树**（先穷尽文档路径 → 不猜 repo URL 问用户 → 按 Card Index 别全仓 grep → 回写发现）浅克隆对应仓库（`git clone --depth=1`）。
> ✅ 完成后运行项目，确保无基础语法/编译错误。

> ⛔ **本步之后、Step 8 之前插入「代码评审门」**——判据见 `00-流程总纲.md` §代码评审门与 `代码评审纪律.md`。过门后再读 `步骤-8-10-测试.md`。
