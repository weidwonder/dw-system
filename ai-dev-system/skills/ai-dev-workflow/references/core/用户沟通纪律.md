# 用户沟通与确认纪律（core）

## 核心原则

所有与用户的沟通必须用业务语言（业务目标、角色、流程、规则、影响、风险、可观察结果）；不得要求用户理解程序实现才能回答或拍板。

面向工程执行者的内部产物（技术 Spec、Coding Plan、代码注释）可用程序语言，但不得把其中的详细程序设计转成用户确认项。

## 三层确认边界

### 1. 大架构：必须由用户确认

> 本文用 RFC2119：MUST / MUST NOT / SHOULD / MAY。

**大架构 = 产品架构或技术架构的「主干路」形状发生变化。**

- **产品架构主干路**：业务能力怎么切分成模块、模块间的主调用与主数据流、对外协作契约。
- **技术架构主干路**：分层、存储选型、**数据归属**（数据由哪个模块拥有与维护，**不含**把已有数据从一处搬到另一处）、同步/异步边界、部署单元切分。

**一句话判据：主干路「形状」变了才算，「取值」变了不算。**

判"形状还是取值"时按这两条消歧，MUST NOT 凭语感：

- **槽位换实现 / 换取值不算，槽位本身增删、或职责跨槽位搬移才算。**
- **对外协作契约的新增、删除、语义变更算；纯扩展性加值不算。**

| | 例子 |
|---|---|
| **算** | 审批从单人审批改成两级会签；把「退款」从售后模块拆出来独立成模块；同步调用改成消息队列异步；新增一个对外部商家开放的回调入口；订单数据的所有权从订单服务移交给归档服务；删掉一个枚举值或改变某个已有取值的含义 |
| **不算** | 审批人从组长换成店长（换 role 取值）；订单库从 MySQL 换成 PostgreSQL（换实现，分层、边界、部署单元都没动）；给已有状态枚举加一个值（调用方不改代码也能跑）；加字段、改实现顺序、拆函数；新增不改变任何角色权限的只读页面 |

拿不准时 SHOULD 当作命中。

**「历史数据搬迁」与「不可逆风险」不在本判据里**：它们是**后果**属性、不是结构属性（本节管结构变没变，Q3 管后果可不可逆），由 Triage 第 3 问识别、**并在那里各自过一次同样的用户确认**（见 `00-流程总纲.md` §Step 0：需求体量与风险分流（Triage））；MUST NOT 把任一方并进另一方。

命中时 MUST 先给用户一份业务语言摘要，至少说明：

- 哪些业务能力新增、调整或保持不变。
- 哪些角色在什么环节做什么。
- 主流程如何变化，哪些业务边界不变。
- 对现有业务、外部协作方、历史数据与运营的影响。
- 主要业务风险、兜底方式与不做什么。

用户明确确认后才可进入详细设计；否定或修订时先更新大架构再确认。**Lean 路径上本门挂在动手实现之前**（与兼容取舍同一批抛出，见 `路径-lean.md` 第 5 步）。

### 2. 模块内结构设计：通过业务问题取约束

模块内的职责拆分、处理顺序、信息归属与方案选型无需用户理解技术选项；需要判断时只问业务问题：

- 结果要立即可见还是允许稍后完成？
- 多人 / 多次同时操作时哪一次结果有效？
- 业务失败时阻断、等待、跳过还是转人工？
- 谁可查看、修改、撤销、审批？
- 高峰期业务量多少、最长可接受等待多久？
- 记录保留多久、哪些动作必须可追溯？
- 新旧流程并行多久、历史业务如何继续？

把答案在内部转成设计与选型依据，不向用户展示程序组件、存储、通信方式、框架或代码结构选项。

### 3. 详细程序设计：无需用户确认

文件、类、函数、接口、数据结构、存储、任务调度、异常处理与技术选型无需用户确认，由 AI 依据已确认的业务约束、现有代码事实与项目规范自主完成并自检。

详细设计暴露出尚未确定的业务规则、用户可感知行为、权限边界、数据归属、成本上限或风险取舍时，才回到用户处提问；问题仍必须改写成业务语言。

## 发送前检查

每次提问、汇报或请求确认前检查：

- 用户能只凭业务知识回答吗？不能则改写。
- 是否出现文件、类、函数、接口、表、消息、缓存、框架、部署等程序词汇？除非用户明确要求技术细节，否则删除或翻译。
- 是否在请求用户确认详细程序设计？是则停止确认，改为内部决策。
- 是否属于大架构变化？是则先给业务语言摘要并取得明确确认。
