# 用户沟通与确认纪律（core）

## 核心原则

所有与用户的沟通必须使用业务语言，说明业务目标、角色、流程、规则、影响、风险和可观察结果。不得要求用户理解程序实现后才能回答问题或做决定。

技术 Spec、Coding Plan、代码注释等面向工程执行者的内部产物可以使用程序语言，但不得把其中的详细程序设计转成用户确认项。

## 三层确认边界

### 1. 大架构：必须由用户确认

> 本文用 RFC2119：MUST / MUST NOT / SHOULD / MAY。

**大架构 = 产品架构或技术架构的「主干路」形状发生变化。**

- **产品架构主干路**：业务能力怎么切分成模块、模块之间的主调用与主数据流、对外协作契约。
- **技术架构主干路**：分层、存储选型与数据归属、同步/异步边界、部署单元切分。

**一句话判据：主干路的「形状」变了才算，主干路上的「取值」变了不算。**

| | 例子 |
|---|---|
| **算** | 审批从单人审批改成两级会签；把「退款」从售后模块拆出来独立成模块；同步调用改成消息队列异步；新增一个对外部商家开放的回调入口 |
| **不算** | 审批人从组长换成店长（换 role 取值，主干路不变）；给已有状态枚举加一个值；加字段、改实现顺序、拆函数；新增不改变任何角色权限的只读页面 |

拿不准时 SHOULD 当作命中——多问一次的代价远小于漏问。

**「历史数据搬迁」与「不可逆风险」MUST NOT 写进本判据**：它们由 Triage 第 3 问负责（命中即走完整流程，见 `00-流程总纲.md` §Step 0），在这里再列一遍会让同一件事在两处被判，两处措辞迟早分叉。

命中本判据时，MUST 先向用户提供一份业务语言摘要，至少说明：

- 哪些业务能力新增、调整或保持不变。
- 哪些角色在什么环节做什么。
- 主流程如何变化，哪些业务边界不变。
- 对现有业务、外部协作方、历史数据和运营方式的影响。
- 主要业务风险、兜底方式和不做什么。

用户明确确认后，才可以进入详细设计。用户否定或修订时，先更新大架构再确认。
**Lean 路径上本门挂在动手实现之前**（与兼容取舍同一批抛出，见 `路径-lean.md` 第 5 步）：Lean 的详细设计就写在那一页 spec 里，所以「确认后才进详细设计」在 Lean 上等价于「确认后才动手实现」。

### 2. 模块内结构设计：通过业务问题取约束

模块内的职责拆分、处理顺序、信息归属和方案选型无需让用户理解技术选项。需要判断时，只问业务问题，例如：

- 结果必须立即可见，还是允许稍后完成？
- 多人或多次同时操作时，哪一次结果有效？
- 业务失败时应阻断、等待、跳过，还是转人工处理？
- 谁可以查看、修改、撤销或审批？
- 高峰期大约有多少业务量，最长可接受等待多久？
- 需要保留多久的记录，哪些动作必须可追溯？
- 新旧流程需要并行多久，历史业务如何继续？

把用户答案在内部转成设计和选型依据，不向用户展示程序组件、存储方式、通信方式、框架或代码结构选项。

### 3. 详细程序设计：无需用户确认

详细程序设计无需与用户确认。文件、类、函数、接口、数据结构、存储、任务调度、异常处理实现和技术选型，由 AI 依据已确认的业务约束、现有代码事实和项目规范自主完成并自检。

只有当详细设计暴露出尚未确定的业务规则、用户可感知行为、权限边界、数据归属、成本上限或风险取舍时，才回到用户处提问；问题仍必须改写成业务语言。

## 发送前检查

每次向用户提问、汇报或请求确认前检查：

- 用户是否能只凭业务知识回答？不能则改写。
- 是否出现文件、类、函数、接口、表、消息、缓存、框架、部署等程序词汇？除非用户明确要求技术细节，否则删除或翻译。
- 是否在请求用户确认详细程序设计？如果是，停止确认，改为内部决策。
- 是否属于大架构变化？如果是，先给业务语言摘要并取得明确确认。
