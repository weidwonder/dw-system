# Lean 路径（一页走完）

> 加载条件：Step 0 Triage 四问全否。读完本页就能把这次改动做完，**不需要读 `步骤-1-7-设计与实现.md` 与 `步骤-8-10-测试.md`**。
> Lean 的轻量体现在"文档只有一页、跳过 Step 1–10"，**不体现在跳过门**——四道门一道都不能少。

## 顺序

| # | 动作 | 产出 / 判据 |
|---|---|---|
| 1 | **工作区隔离门**（已在路由后完成，未完成先补） | 独立 worktree，见 `worktree开发纪律.md` |
| 2 | 【bug 类才做】过红回路门 | 先查 `docs/report/bug修复历史.md`，再造出能变红的复现命令，见 `bug诊断纪律.md`。**回路不存在不许提假设、不许改代码** |
| 3 | 写一页 Lean Change Spec | `docs/spec/<change-name>-lean-change-spec.md`，模板 `assets/templates/lean-change-spec.md` |
| 4 | 填**兼容取舍**一行 + **替换清单**表 | 判据见总纲 §兼容取舍确认门、`代码评审纪律.md` §替换清单 |
| 5 | **兼容取舍确认门**：把清单抛给用户拍板 | 用户逐条选定后才动手实现；无既有行为变更时显式写"无兼容取舍" |
| 6 | 实现 + **边写边删** | 被取代的旧逻辑当场删除，不留到"最后统一清理" |
| 7 | 跑"如何验证"里的命令 | 每条都真跑过，不靠"应该没问题" |
| 8 | 【命中判定才做】补端到端用例 | 跨 ≥3 组件 / 异步多阶段 / 有中间产物时**必须**有，且断言每个环节的中间产物，见 `测试资产纪律.md` §1 |
| 9 | 【有真实输入才做】固化测试样本 | 落 `tests/fixtures/<场景名>/`，凭证进 `secrets/` 并先确认 gitignore 生效，见 `测试资产纪律.md` §2 |
| 10 | **代码评审门**：派 1 个子代理跑三轴精简版 | 规范 / 忠实 / 残留，报告分三节写；P0/P1 修完才算过门。prompt 模板见 `代码评审纪律.md` |
| 11 | 【bug 类才做】归档 | 追加 `docs/report/bug修复历史.md`，格式固定见 `bug诊断纪律.md` Phase 3 |
| 12 | **完成与自动合并门** | 见 `worktree开发纪律.md` §完成与自动合并门 |

## Lean 特有的三个提醒

- **拿不准就升级，别硬塞进一页**：Triage 有任何一问是 borderline，在 spec 的「Triage 复核」里写清哪一问、为什么倾向"否"；实在拿不准就升级回完整流程（读 `步骤-1-7-设计与实现.md`）。中途发现影响面变大（跨服务、要迁数据、动了对外承诺）同样立即升级，不要将错就错走完。
- **验收标准别只写 happy path**：小改动最常翻车在异常路径——边界值、空值、并发、依赖不可用各留一条可勾验的验收项。
- **Lean 不等于不写测试**：第 8/9 步的判定命中就照做，个人版也不压缩。压缩的是文档篇幅，不是验证强度。

## 与用户沟通

全程业务语言（见 `用户沟通纪律.md`）。Lean 路径通常只需要用户在两处表态：**兼容取舍**（第 5 步）和**验收标准是否是他要的**。其余技术决策自主完成，不要拿实现方案去问用户。
