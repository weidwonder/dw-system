## 1. 进门之前：分流复核

> **何时读本节**：Triage 四问全否后立即读（前置）——§1.1/§1.2 决定本册这次到底该不该用；§1.2 的判据 3/4 在 §4 写〈既有系统清单〉时还要回溯复核一次。

### 1.1 Triage 四问

四个判定问题，**MUST 逐题过一遍，MUST NOT "假设"全否**：

1. 是否改变智能能力给用户的结果或判断方式？
2. 是否改变谁可以做什么、敏感信息保护或使用场景？
3. 是否影响多个业务环节、需要搬迁历史数据或存在不可逆影响？
4. 是否改变经营指标、业务规则或对外承诺？

- 任意一项为「是」→ MUST 升级到完整流程（按 §0.2 丢弃本册）。
- 四项均为「否」→ **默认**走 Lean。"默认"二字是实义的：MUST 再过一遍 §1.2 的默认倾向，命中升级条件时改走完整流程。**MUST NOT 把"四问全否"读成无条件结论。**
- **第 3 问命中时另有一项确认义务（MUST）**：需要搬迁历史数据、或存在不可逆影响时，MUST 先形成一份**业务语言摘要**交用户确认，确认后才能动手；摘要 MUST 写清**动了哪些历史数据、影响哪些既有业务、出错后能不能退回去、退不回去的部分是什么**。（第 3 问命中本身已经把本次升级到完整流程，这条义务在完整流程里继续成立。）

  来源：`00-流程总纲.md` §Step 0；`用户沟通纪律.md` §1. 大架构

### 1.2 默认倾向：影响面说不清就升级

> **影响面说不清时，MUST 升级到完整流程出 Overview；说得清才走 Lean。**

这条**无条件适用于所有项目**，**MUST NOT 由协作面、项目大小或有没有代码图谱来改变**。

"影响面说不清"的判据共四条，命中任一即算说不清。它们能被评估的时点不同：

| # | 判据 | 什么时候过 |
|---|---|---|
| 1 | 本次要改的能力在 registry 里跨 ≥2 个权威仓库 | **Triage 当场**，MUST 逐条过 |
| 2 | `ctx discover` 给出了 out-of-scope 警告（命中废弃或中间产物实现）| **Triage 当场**，MUST 逐条过 |
| 3 | 关键事实里有任何一条**给不出出处**（卡片 cite 或 `文件:行`）| **回溯触发**：本册 §4 写〈既有系统清单〉时命中即当场升级 |
| 4 | 卡片、`ctx discover`、`ctx search-semantic` 都收不窄，**读完源码仍说不清模块边界** | 同上 |

- **判据 1/2 怎么当场核对**：按 §3.1 的固定顺序跑 `ctx find-scenes <关键词>` → `ctx discover "<意图>"`（合计 10 秒级），拿到端到端全景、命中的仓库与 out-of-scope 警告，再逐条对照。结果一并进〈既有系统清单〉，不重复跑。
- **判据 3/4 MUST NOT 在 Triage 当场强行判定**。**Lean 没有 Step 1，它们的落点是本册 §4**——MUST NOT 因为"我走的是 Lean、没有 Step 1"就认为这两条对自己不适用。
- **判据 3 MUST NOT 被读成"卡片里查不到就算说不清"**。查不到卡片的正确处置是**读源码 + 当场补卡**（§3.3），补完就有 `文件:行` 出处，判据 3 即不命中。它真正命中的是**读了源码也说不出这条事实从哪来**：动态派发、配置化路由、反射调用这类"代码在这儿但决定权不在这儿"的情况。**判据 4 同理**：卡片没命中不算，读完源码仍说不清才算。
- registry 还是空的时候，判据 1/2 自然都不命中——这是正常起步态，MUST NOT 因此判定"说不清"，也 MUST NOT 因此判定"说得清"，此时该看的是判据 3/4 的回溯结果。
- **MUST NOT 用"我感觉不复杂"代替以上任何一条。**
- **MUST NOT 从"只有我一个人"推出"默认走最短流程"**——一个人维护的十万行遗留系统，默认走 Lean 是危险的；协作面不参与本判据。
- **MUST NOT 从"这项目还没几张卡片"推出"这项目简单"**——卡片少只说明还没人读过这块代码。
- 跨仓需求一律升级。

  来源：`00-流程总纲.md` §默认倾向；`solo.md` §5. 分流默认倾向不由本文决定

## 2. 第 1 步：工作区隔离门

> **何时读本节**：要建（或补建）worktree 时才读——正常时序下本门在 Triage **之前**就已经过了，那一刻手里只有入口〈工作区隔离门要点〉与 `worktree开发纪律.md` §工作区隔离门。Triage 之后 MUST NOT 预读。

入口〈工作区隔离门要点〉已经给出本门的判定要点（要不要建、目录取哪个字段、过不了怎么办、进门之后先做什么），**本节只补建 worktree 的动作细则与多仓条款**；两处冲突时 MUST 以 `worktree开发纪律.md` §工作区隔离门 原篇为准，MUST NOT 用本节推翻入口的任何一条。

1. **认主分支**：确认目标是 Git 仓库，并按仓库配置识别默认主分支；优先读远端默认分支，**MUST NOT 写死 `main` 或 `master`**。
2. **建目录**：目录读该仓库 `CLAUDE.md`（优先）或 `AGENTS.md` 的 `ai-dev-workflow` 标记块内的 `worktree-dir`，**每次创建前都重新读，MUST NOT 沿用上次会话记住的路径**；首次唤起（标记块还没写）时用初始化当场定下的值。子目录名包含业务主题。`.gitignore` 尚未忽略该 worktree 根目录时，先幂等追加一行忽略规则。
3. **门内结清初始化挂账，再开始任务**：首次唤起把标记块注入 worktree 内的 `CLAUDE.md` 与 `AGENTS.md`、执行用户已决断的环境冲突处置；项目根下还没有 `engineering-context/capability-registry.md` 时在 worktree 内跑 `ctx init` 建代码事实层骨架（**MUST NOT 跑 `--minimal`**）。两者随本次任务分支提交。骨架里只有模板占位、没有真实数据行，这是**正常起步状态**，MUST NOT 因此告警或提示用户。
4. **多仓**：需求涉及多个仓库时，每仓一个独立任务分支 + 独立 worktree，**MUST NOT 共用**；先确认所有仓库都能进入隔离状态再开始落盘。（跨仓需求按 §1.2 一律升级，这条在 Lean 上通常无适用对象，但多 worktree 的约束本身不变。）
5. **开发期间**：每个 worktree 只承载一个业务任务；按步骤分段提交；主分支有新提交时先把最新主分支合入任务分支、解决冲突并重跑受影响验证；**MUST NOT 为了制造"干净状态"去处理主工作树里的用户改动**。

## 3. 第 2 步：取代码事实

> **何时读本节**：本节引言与 §3.1／§3.3／§3.4／§3.5／§3.6／§3.7／§3.10 在 Triage 四问全否后立即读（前置）——它是第 2 步本体，且 cite 与补卡的要求全程适用；**§3.2／§3.8／§3.9 是触发式的**，触发条件见它们各自那一行，未触发前不读。bug 类另有 §3bis 的红回路门。

### 3.1 取事实的固定顺序

凡涉及"这个能力对应哪个仓库/接口""跨服务影响面""哪个是权威实现"的问题，MUST 先用 `ctx`，**MUST NOT 直接 grep 旧代码**。

**★ 业务全景门限（排序铁律）**：**除非用户已把任务限定到某一个具体 repo / 服务 / 代码路径**，否则**第一步 MUST 先 `ctx find-scenes <关键词>`** 取端到端业务全景，再据此收窄。**MUST NOT 跳过 find-scenes 直接 discover**。提取 2–5 个高置信关键词（需求名、业务入口、核心动作）喂给它。

```bash
ctx find-scenes 作业辅导 错题 重练          # ← 未限定单仓时先跑这个，取端到端全景
ctx discover "给作业辅导加错题重练入口"      # 意图 → 应加载的 card 清单 + out-of-scope 警告
ctx get-card <repo> [域]                     # 收窄后取某仓 Codebase Card
ctx list-services                            # 已登记仓库/能力
ctx search-semantic "<自然语言>"             # discover 未命中时的兜底
```

- **`find-scenes` 无命中不是错误**：`scenes/` 在骨架起步态本来就是空的。MUST NOT 阻断、MUST NOT 反复重试，改走 `discover` + `get-card`；两者也收不窄时进 §3.3。
- `find-scenes` 返回的是**场景蓝图指针**，本身不直接给"涉及哪些服务"。从蓝图正文读到 / 推断出的涉及服务都是**推断**，MUST 逐个用 `ctx get-card` 核实到权威 card 才能当事实用。
- `discover` 随命中结果给出的 **out-of-scope 警告** MUST 抄进〈既有系统清单〉（Lean 的落点见 §4）。

  来源：`代码事实纪律.md` §3. 取事实的固定顺序

### 3.2 卡片是地基；`ctx` 命令找不到怎么办

> **何时读本节**：`ctx` 敲不动（command not found）、跑出来是空、或术语说法对不上时才读（触发式）——命令正常时 §3.1 的示例已够用，未命中前不预读。兜底调用方式在入口 `SKILL.md` §关键纪律 也有一份，那一份在读本节之前就已在手，所以等着读本节的时候也不必去 grep。

- 装了本体系的项目**一律**维护 `engineering-context/`（registry + cards），不分项目大小、不分协作面、不由任何探测开关决定。**MUST NOT 因为 registry 里还没有条目就退回裸 grep 找权威实体**——没有条目意味着"还没人读过这块代码并把结论固化下来"，处置是读源码 + 补卡（§3.3），不是绕过这一层。
- **MUST NOT 反过来把它当准入门槛**：卡片没建齐 MUST NOT 阻断流程、降级交付或拒绝干活；缺卡片时当场补，任务照常推进。
- 代码图谱（`.codegraph/codegraph.db`）与卡片**MUST NOT 互相替代**：图谱答"找得到吗"（会如实列出 v1 与 v2 两处支付实现，但不知道哪个权威），卡片答"信哪个"。**两者冲突时以卡片为准**，并按 §3.5 就地修正卡片。

  来源：`代码事实纪律.md` §1. 卡片是地基

- **"`ctx` 命令找不到"绝不等于这一层不可用**——CLI 本体随本 skill 一起落盘。命令不可用时 MUST 改用 `node <本skill根目录>/scripts/ctx/src/cli.js <命令>`。`<本skill根目录>` 就是当前这份 `ai-dev-workflow` 的 `SKILL.md` 所在目录；安装后目标项目下有两份逐字节相同的副本（Claude Code 读 `.claude/skills/ai-dev-workflow/`，Codex 读 `.agents/skills/ai-dev-workflow/`），**MUST NOT 写死其中一份**，拿不准就用你自己加载 skill 的那一侧。
- **任何情况下都 MUST NOT 因为找不到 `ctx` 命令就退回 grep 源码。**
- `ctx` 默认读 `<cwd>/engineering-context`，所以 **MUST 在项目根执行**，或用 `--dir <项目根>/engineering-context` 显式指定；在子目录里跑它会返回空且退出码为 0（静默），把"有卡片"误判成"没卡片"。
- 术语说法不一致时查 `engineering-context/glossary.md`：glossary 管说法一致，card 管事实权威，registry 管能力落点。

  来源：`代码事实纪律.md` §2. 调用方式

### 3.3 没有卡片时怎么办（本册最容易被跳过的一条）

`ctx` 查不到，只意味着**这个模块的卡片还没建**。MUST 按序处置，**三步一次做完，MUST NOT 只做前两步**：

1. **读源码建立事实。** 探测到代码图谱 → 用图谱做结构性定位；没有图谱 → 把重探索**外包给子代理**，主会话只收结论。**MUST NOT 在主会话裸 grep 全仓**——裸 grep 指没有收窄目标、没有外包、直接把命中内容读进主上下文。
2. **把读到的权威事实补成卡片**（最小形态见 §3.4），随本次任务分支提交。
3. 补完的卡片即成为后续事实来源；本次任务后续引用它时照常带 cite（§3.6）。

**补卡是本次任务的一部分，MUST NOT 顺延**。"以后有空再补"等于这次读源码的成果只活在本次会话里，下一个零上下文 agent 要把同样的路重走一遍。**MUST NOT 把"读了源码"本身当成交付**——读完不落卡，下次唤起 `ctx` 依然查不到，这条纪律等于没执行过。

  来源：`代码事实纪律.md` §4. 没有卡片时怎么办

### 3.4 补一张卡片的最小形态

在 `engineering-context/cards/<repo>.md` 里新建文件，或在既有卡片里追加一个 `## <域>` 段。最小内容四项：

| 项 | 写什么 |
|---|---|
| 职责 | 这个模块负责什么业务能力，一句话 |
| 对外接口 | 本次真正读到并核对过的接口 / 字段 / 事件，每条带 `文件:行` |
| 陷阱项 | 相似但不该用的旧实现；确实没有就写 `无` |
| 确认时间 | 本次读源码的日期 |

同时在 `engineering-context/capability-registry.md` 追加一行（三列即可用）：`Capability` / `权威实现` / `陷阱项（废弃或中间产物）`。**第三列 MUST NOT 省**——它是最小 schema 里唯一的防误用装置。

- **MUST NOT 为了凑满模板把没核对过的字段填上。** 没读到的就不写；**一个看起来权威但已过期的来源比没有来源更危险**。
- **MUST NOT 把机器可派生的事实抄进卡片**（调用图、依赖边、最后修改时间、DB schema 全文）——那些随时可现查，手抄一份就是主动制造腐化。卡片只放人工判断。

  来源：`代码事实纪律.md` §4.1 补一张卡片的最小形态

### 3.5 卡片只增不减

- 卡片库**只增不减**：**MUST NOT 因为"这次没用上"删除既有卡片内容。**
- 发现既有卡片与源码不符 → **就地修正并更新确认时间**，MUST NOT 保留两份互相矛盾的说法，也 MUST NOT 只在本次上下文里绕过它继续干活。
- 卡片记录的实现被本次改动彻底删除时 → 把它移进该卡片的**陷阱项**（写清"已删除"与日期），**MUST NOT 直接抹掉**——后来的 agent 需要知道这个名字曾经存在过、现在不该再用。

  来源：`代码事实纪律.md` §4.2 只增不减

### 3.6 cite 纪律

- **每条来自卡片的事实（接口名、字段、topic、RPC 签名）MUST 附 cite**（path + anchor + 最近确认时间）。**无 cite 的接口 / 字段一律视为幻觉，MUST 回查。**
- 本次现读源码得到的事实，在卡片落盘前 MUST 带 `文件:行`；落盘后按卡片的 cite 引用。**两种出处都算数，MUST NOT 出现第三种"我记得"。**

  来源：`代码事实纪律.md` §5. cite 纪律

### 3.7 检索纪律

- 查**精确 token**（字段名 / 接口名 / 表名）时 MUST 优先用精确匹配（`ctx get-card <repo> <域>`、grep card 正文），不要只靠 `ctx search-semantic`。
- **语义检索结果只作"去哪找"的索引，MUST NOT 当最终事实直接引用**——命中后仍要落到权威 card 段并附 cite。
- card 没有独立的 README 段，服务级 README 信息（部署 / 排障 / 路径）已并入 card 的对应节。
- `freshness` 列留空时 `ctx` 会标注「未声明新鲜度」，此时 **MUST NOT** 假定该条新鲜，按 §3.9 回查后再当事实用。

  来源：`代码事实纪律.md` §6. 检索纪律

### 3.8 卡片不够用、必须读真实源码时

> **何时读本节**：卡片与 `ctx` 都不够用、要 clone 本仓之外的仓库取证时才读（触发式）；本仓源码按 §3.3 第 1 步处置即可，未命中前不预读。

以下属工程侧内部取证；向用户只说明正在核对哪项业务事实及其影响，**不报告仓库、类、方法等程序细节**，除非用户明确要求。

1. **先穷尽文档路径**——接口签名 / 字段去 card 的"对外接口"段；部署 / 配置 / 排障去 card 对应段；跨服务流程去 `ctx find-scenes`。以上都不够，才真正 clone。
2. **clone 前**：先明确要看哪个仓、为什么要看源码、要核对的具体事实；**没有 repo 地址时向工程 owner / 用户索取，MUST NOT 凭服务名猜 git URL**；用 `git clone --depth=1 <url>` 浅克隆到一次性临时目录，别污染工作区。
3. **clone 后**：**MUST NOT 全仓 grep**——按 card 的"业务域 Card Index"按图索骥（探测到代码图谱时结构性定位改走图谱）；读完 MUST 按 §3.3 把关键发现落成卡片。
4. **发现卡片有缺漏或与源码不符** → **就地补上 / 改正并更新确认时间**，随本次分支提交。协作面为 team 时 SHOULD 在合并说明里点一句改了哪张卡片；**但 MUST NOT 因为等 owner 而把卡片留在错误状态**——错的卡片比没有卡片更危险。

  来源：`代码事实纪律.md` §7. 卡片不够用

### 3.9 新鲜度纪律

> **何时读本节**：本次改动碰到了权威面（接口签名／废弃标记／路由与配置版本／DB schema／兼容窗口）要判刷不刷卡时，或开新任务要看 `engineering-context/` 的跨会话增量时才读（触发式）；未命中前不预读。

- 你的改动若**触碰权威面**（canonical 接口签名、废弃标记、路由 / 配置版本、DB schema、兼容窗口）——**哪怕只有 3 行**——MUST 触发对应卡片刷新。
- 纯内部实现改动（不碰接口 / 权威）MAY 不刷卡。**判断标准是是否碰权威面，不是改了多少行。**
- **会话开始时先看增量**：`ctx` 读的是本地活文件，没有跨会话的变更推送。开一个新任务前 SHOULD 先看清"上次到现在 card/registry 变了什么"：

```bash
git log --oneline -20 -- engineering-context/
git diff 'HEAD@{2.weeks.ago}'..HEAD --stat -- engineering-context/cards/ engineering-context/capability-registry.md
```

  用时间锚而不是"上次的 commit"——本体系不记录"上次是哪个 SHA"。**reflog 不够长（新 clone）时这条命令 MUST NOT 被当作"没变过"**：git 会回退到最旧的 reflog 条目，输出**空 diff 且退出码 0**，只在 stderr 打一行 `warning: log for 'HEAD' only goes back to …`。看到这行 warning 即表示本次 diff **不可信**，MUST 改用 `git log --since='2 weeks' -- engineering-context/`。

  来源：`代码事实纪律.md` §8. 新鲜度纪律

### 3.10 真相方向铁律

card 事实 **MUST 以合入后的源码为准，MUST NOT 从 PRD 生成**——PRD 描述意图，意图常与已落地事实背离（典型："PRD 说可复用，查代码发现不可复用"）。

  来源：`代码事实纪律.md` §9. 真相方向铁律

## 3bis. 【bug 类才做】红回路门

> **何时读本节**：本次是 bug / 回归 / 异常行为类需求、且要动手改代码时才读；不是这类需求 MUST NOT 预读。命中时本节排在 §3 取事实之后、§4 写 spec 之前（顺序见 §14）。

**bug / 回归 / 异常行为类需求**：动手改代码前 MUST 先过红回路门——先用关键词检索 `docs/report/bug修复历史.md` 查重（账本 MUST 用关键词检索定位，MUST NOT 整份读进上下文，判据见 §10.5），再造出一条能真的变红的复现命令。**回路不存在时 MUST NOT 提假设、MUST NOT 改代码**。这一步要展开时才读 `bug诊断纪律.md`，Lean 不豁免本门。

修完之后按 §10.5 末条把这次的结论追加进 `docs/report/bug修复历史.md`（格式见 `bug诊断纪律.md` Phase 3）；本门产生的临时探针与调试日志归 §9 的残留轴，**MUST NOT 留在合并进主分支的改动里**。

## 4. 第 3 步：写一页 Lean Change Spec

> **何时读本节**：本节引言与 §4.1 在 Triage 四问全否后立即读（前置）——它是第 3 步本体，也是判据 3/4 的回溯落点；**§4.2／§4.3 是触发式的**，触发条件见它们各自那一行，未触发前不读。

产出：`docs/spec/<change-name>-lean-change-spec.md`，骨架用 `assets/templates/lean-change-spec.md`。**MUST 写进 worktree 内的 `docs/spec/`**，MUST NOT 散放在项目根、仓库根、`docs/` 根或代码注释里（目录判据见 §10.1）。

### 4.1 〈既有系统清单〉与补卡

- 清单里的每条事实**先查卡片**（§3.1），查不到就读源码并**当场补卡**（§3.3–§3.4）。**用到哪个模块的事实，就补哪张卡**；补卡随本次分支提交，**MUST NOT 顺延**。
- 清单 MUST 记录每条事实"从哪知道它的"：来自卡片的填 cite，本次现读源码的填 `文件:行`。`ctx discover` 的 out-of-scope 警告 MUST 抄进来。
- 清单落进 spec 的 §影响范围 / 不做什么——**它是 Lean 路径上替换清单唯一的出处**。
- 写这一步时 MUST 逐条复核 §1.2 的判据 3/4；命中即**当场升级**（§0.2），MUST NOT 将错就错把这一页写完。
- **输入里有 UI 原型时，MUST 连元素批注一起读**：针对某个控件的说明与待拍板项放在该元素的 `data-anno` / `data-anno-kind="question"` 属性里（界面上只显示一枚悬浮气泡），与屏幕上的可见内容**同属用户可见行为契约**，MUST NOT 因为界面上看不到就漏进 spec；文件末尾 `ANNOTATIONS:BEGIN … ANNOTATIONS:END` 之间是用户写的批注与全局反馈。**取这三类只有一个命令**：`node <skills 根>/ai-prd/scripts/preview.mjs annotations <原型文件>`（`<skills 根>` = 你加载的这份 `SKILL.md` 所在目录的**父目录**——Claude Code 下是 `.claude/skills/`、Codex 下是 `.agents/skills/`，两侧内容一致，用你自己这一侧那份，**MUST NOT 写死其中一侧**），一次给出全部三类，每条带所在屏与元素；命令跑不起来时才降级为只读 `ANNOTATIONS:BEGIN … END` 那一段加 `grep -n "data-anno="`，**MUST NOT 通读整份 HTML**。`data-anno-kind="question"` 的每一条 MUST 在写这一页 spec 前向用户拍板，MUST NOT 自行替产品定。来源：`00-流程总纲.md` §完整流程步骤索引

### 4.2 写作纪律（RFC 2119 与零上下文）

> **何时读本节**：真要动笔写这一页 spec 时读，或出现过载信号要写交接文档时读（触发式）——两种情形都是"字要落到文件里"的那一刻；只在脑子里过方案时不预读。

- 在有约束力的地方 MUST 用大写关键词，并**在文档顶部声明一次**"本文按 RFC 2119 解释下列关键词"，全文统一使用：**MUST / REQUIRED / 必须**（违反即错误）、**MUST NOT / 禁止**（绝对不允许）、**SHOULD / RECOMMENDED / 应当**（强烈建议，偏离需说明理由）、**SHOULD NOT / 不应**、**MAY / OPTIONAL / 可以**（可选）、**Implementation-defined / 实现自定**（契约要求存在，但取值/策略交由实现决定——用它区分"没规定"和"故意留给实现"）。

  来源：`spec写作纪律.md` §2. RFC 2119 规范性措辞

- **零上下文可动手**：读者是对本项目一无所知的工程师或零上下文 coding agent。MUST 写精确文件路径（`src/api/user.controller.ts:42`，不写"改那个 controller"）、可直接抄走的完整代码、精确命令与预期输出、每条外部事实的出处。
- **无占位符**：实现步骤里 MUST NOT 出现 `TBD`、`TODO`、"稍后补充"、"加上适当的错误处理"、"同 Task N"，也 MUST NOT 引用任何地方都没定义的类型 / 函数。显式标注的"后续 / Out-of-scope 待办"区不在此列，其中每条 MUST 说明为什么这期不做。
- **需求与验收编号**：需求编 `FR-###`、验收项编 `AC-###`，**编号永不复用、永不重排**——评审门的忠实轴按它产出覆盖矩阵（§9.3）。
- **验收标准别只写 happy path**：小改动最常翻车在异常路径——边界值、空值、并发、依赖不可用各留一条可勾验的验收项。
- **frontmatter MUST 有生命周期字段**（判据见 §10.2）。

### 4.3 替换清单（Replacement Ledger）

> **何时读本节**：写这一页 spec、要登记本次被取代物时才读（触发式）——"本次有没有取代既有实现"这个判断本身就发生在写 spec 那一刻，未命中前不预读。

**登记时机（MUST）**：就在写这一页 lean spec 的时候。凡是新逻辑取代了既有实现的，把被取代物逐条登记；把删除动作拆成具体任务，**MUST NOT 笼统写一句"清理旧代码"**。没有清单，评审门的残留轴无从下手。

登记对象覆盖六类：**函数/类/模块**、**文件/目录**、**配置项与环境变量**、**feature flag / 开关**、**DB 字段与表**、**接口或接口版本**。旧文档段落、旧注释掉的实现同样算。

| 被取代物 | 类型 | 取代者 | 引用数 | 处置 | 核销 |
|---|---|---|---|---|---|
| `calcPriceV1()` | 函数 | `calcPrice()` | 0 | 删除 | ✅ |
| `ENABLE_NEW_FLOW` | 开关 | 已全量，无需开关 | 0 | 删除 | ✅ |
| `orders.legacy_memo` | DB 字段 | 无（数据已迁走） | 0 | 保留至迁移窗口结束 | ⏳ 2026-09-01 起删 |

**核销规则**：

- 引用数为 0 且不在保留例外内 → **MUST 立即删除**，不得留着"以后可能还要用"。版本控制就是那个"以后"。
- 引用数不为 0 → 迁移没做完，MUST 先补完调用点迁移，再回来核销。
- **保留例外必须同时给出理由和到期日，以及到期后的动作。只有三类理由成立**：① 对外契约仍在兼容窗口内（呼应本次的兼容取舍决策）；② 数据迁移未完成；③ 回滚预案显式依赖它。**"以防万一"不是理由。**
- 到期日到了没人删，下一个碰这块代码的任务 MUST 在残留轴把它重新提出来。
- 保留例外的到期日 MUST 与 §6.1 兼容取舍那一行的到期日一致——**两处日期不一致就是漏洞**。
- **工具辅助是 SHOULD，不是替代**（`knip` / `ts-prune` / `vulture` / `staticcheck -checks U1000` / `cargo check` 的 `dead_code`，或"精确检索被取代物名字统计引用数"）：清单负责"知道该找什么"，工具负责"发现清单漏了什么"。**清单是 MUST，工具是 SHOULD**；工具链不具备时清单核销照做。

  来源：`代码评审纪律.md` §替换清单

## 5. 与用户沟通

> **何时读本节**：Triage 四问全否后立即读（前置）——业务语言的约束**全程适用**，第一句话就可能违反它。

全程业务语言：说明业务目标、角色、流程、规则、影响、风险和可观察结果，**MUST NOT 要求用户理解程序实现后才能回答问题或做决定**。技术 spec 等面向工程执行者的内部产物可以用程序语言，但**MUST NOT 把其中的详细程序设计转成用户确认项**。

Lean 路径通常只需要用户在两处表态：**兼容取舍**（§6.1）和**验收标准是否是他要的**。其余技术决策自主完成，**MUST NOT 拿实现方案去问用户**。模块内需要判断时只问业务问题（结果必须立即可见还是允许稍后完成？多人同时操作时哪一次有效？失败时阻断、等待、跳过还是转人工？谁可以查看/修改/撤销/审批？高峰期业务量与最长可接受等待？记录保留多久、哪些动作必须可追溯？新旧流程并行多久？）。

**协作面差异**：

- **solo**（用户就是开发者本人）：**MUST NOT 对用户隐藏技术细节**——团队场景里"不得要求业务用户理解技术方案后拍板"的保护在这里不适用。但仍 MUST NOT 用技术细节淹没业务判断：先说业务影响，再给技术理由。
  来源：`solo.md` §3. 用户既是产品又是技术
- **team**：**业务目标、规则、边界 MUST 找业务负责人确认**；详细程序设计是工程侧内部决策。**MUST NOT 要求业务用户理解技术方案后拍板**，向业务方陈述时把技术取舍翻译成业务影响再问。每个仓库有明确 owner，**改动别人仓库前 MUST 先对齐 owner**——至少含要改什么、为什么、对该仓对外契约的影响、合并时机。
  来源：`team.md` §1. 角色与澄清分工
- **solo 的裁剪边界**：solo 砍掉的是**对齐开销**。Step 2（Overview）与 Step 3（PRD 细澄清）MAY 省略——但这条 MAY 以"本次分流未被默认倾向上调"为前提，跨仓 / 影响面说不清的改动 MUST 升级（§1.2），此时该 MAY **不适用**，MUST NOT 用它抵掉升级。**省略的是"对齐用的文档"，不是"决策记录"**：已定决策照样 MUST 落盘进 Lean Change Spec，否则下一个会话无从继承。
  来源：`solo.md` §1. 可跳步
- **solo 不等待不存在的人**：**MUST NOT 向不存在的 owner 求证**，MUST NOT 因"等待 owner / 业务方 / 评审人确认"而挂起任务，**MUST NOT 开评审会**这类等待人类到场的动作（需要第二意见时走子代理）。**例外是门，不是对齐开销**：用户本人的兼容取舍拍板、以及 `merge-gate="pr"` 时的平台审批与 CI 都 MUST 照等。协作面是 `solo` **不代表** `merge-gate` 就是 `direct`——两者互不推导。`merge-gate="pr"` 时 PR 的审批人就是用户本人：开出 PR 后 MUST 把 PR 链接与各轴报告结论摆到用户面前请他放行，**MUST NOT 静默等待一个不存在的外部审批**，**MUST NOT 用代码评审门的自查结论替代这次放行**，也 MUST NOT 因为"等不到人审"就改用本地直合。

## 6. 第 4 步：兼容取舍确认门（含大架构 / 不可逆确认门）

> **何时读本节**：本节引言与 §6.2 在 Triage 四问全否后立即读（前置）——§6.2 的大架构判据决定这一页详细设计能不能开始写；**§6.1 是触发式的**，到 spec 定稿前拍板兼容取舍那一刻才读。两者的衔接是：§4.3 保留例外的到期日 MUST 与 §6.1 拍板结论的到期日一致。

**兼容不是默认项。这是业务取舍，不是技术选择，MUST 每次由人拍板，AI 在任何项目形态下都 MUST NOT 自行默认。**

### 6.1 兼容取舍确认门

> **何时读本节**：spec 定稿前、要拍板兼容取舍时才读（触发式）——本节要逐条列清单、逐条问拍板人、结论落进 spec，未命中前不预读，也不凭印象复述它的清单口径。

**谁拍板由协作面决定**：solo → 开发者本人；team → 业务负责人。流程两个协作面完全一致，只是"问谁"不同。

1. **先列清单（AI 做）**：把本次改动会改变的**既有可观察行为**逐条列出——旧接口的请求/响应形状、旧字段与旧枚举值、旧数据在新逻辑下的解读、旧调用方（含外部系统、老版本客户端、定时任务、报表）依赖的行为、用户已形成的操作习惯。**清单为空时也 MUST 显式写一句"本次不改变任何既有可观察行为，无兼容取舍"**，MUST NOT 静默跳过这道门。
2. **逐条问拍板人（业务语言）**：每条给三个选项 + 一个推荐 + 一句理由，只讲业务影响（谁会受影响、影响多久、代价是什么），不讲实现方案。多条时一次性批量抛出，MUST NOT 一条一条问。

   | 选项 | 含义 | 代价 |
   |---|---|---|
   | **不兼容** | 直接切到新行为，旧行为立刻消失 | 仍在用旧行为的人立即受影响，但代码干净、无长期包袱 |
   | **兼容一段时间** | 新旧并存到某个到期日，到期后删旧的 | 需要维护两套；**MUST 同时定下到期日与到期后的动作** |
   | **永久兼容** | 旧行为长期保留 | 包袱永久化；只有对外契约或不可控调用方才值得 |

3. **结论落盘（MUST）**：写进 lean-change-spec 的兼容取舍一行。选了"兼容一段时间"的，MUST 在替换清单里把对应被取代物登记为**保留例外**，带上同一个到期日与到期动作（§4.3）。
4. **拍板人未回复不算确认**：**MUST NOT 以"先按兼容做，以后再说"推进**——那等于替用户选了代价最高的一项。
5. 用户逐条选定后才动手实现。

  来源：`00-流程总纲.md` §兼容取舍确认门

- **team 协作面下的拍板人是业务方**，不是工程侧、更不是 AI：**AI MUST NOT 默认兼容，也 MUST NOT 自行决定不兼容**；spec 定稿前 MUST 把被改变的既有行为逐条列出（谁受影响、影响多久、三个选项 + 推荐）送业务方逐条拍板；结论 MUST 落进 spec 的兼容取舍节，保留项 MUST 带理由与到期日并登记进替换清单。
  来源：`team.md` §3. 兼容取舍由业务方拍板
- **solo 协作面下每次由你自己拍板**：**AI MUST NOT 默认兼容**。单人项目最容易"顺手就把旧行为砍了"，然后被自己两个月前造的数据打脸；照样把被改变的既有行为逐条列出，自己明确拍板一次。被新逻辑取代的旧函数 / 文件 / 配置 / 开关当场删除，不留"以后可能用"；保留项 MUST 带理由与到期日。
  来源：`solo.md` §3. 用户既是产品又是技术

### 6.2 大架构确认门（命中判据时与兼容取舍同一批抛出）

**大架构 = 产品架构或技术架构的「主干路」形状发生变化。**

- **产品架构主干路**：业务能力怎么切分成模块、模块之间的主调用与主数据流、对外协作契约。
- **技术架构主干路**：分层、存储选型、**数据归属**（数据由哪个模块拥有与维护，**不含**把已有数据从一处搬到另一处这件事本身）、同步/异步边界、部署单元切分。

**一句话判据：主干路的「形状」变了才算，主干路上的「取值」变了不算。** 判"形状还是取值"时按这两条消歧，**MUST NOT 凭语感**：

- **槽位换实现 / 换取值不算，槽位本身增删、或职责跨槽位搬移才算。** 订单库从 MySQL 换成 PostgreSQL 是换实现 → 不算；把订单数据的所有权从订单服务移交给归档服务 → 跨槽位搬移 → 算。
- **对外协作契约的新增、删除、语义变更算；纯扩展性加值不算。** 给已有状态枚举加一个取值、调用方不改代码也能继续跑 → 不算；删掉一个枚举值、或改变某个已有取值的含义 → 算。

| | 例子 |
|---|---|
| **算** | 审批从单人审批改成两级会签；把「退款」从售后模块拆出来独立成模块；同步调用改成消息队列异步；新增一个对外部商家开放的回调入口；订单数据的所有权从订单服务移交给归档服务 |
| **不算** | 审批人从组长换成店长（换 role 取值）；订单库从 MySQL 换成 PostgreSQL（换实现）；给已有状态枚举加一个值；加字段、改实现顺序、拆函数；新增不改变任何角色权限的只读页面 |

**拿不准时 SHOULD 当作命中**——多问一次的代价远小于漏问。

命中本判据时，MUST 先向用户提供一份业务语言摘要，至少说明：哪些业务能力新增/调整/保持不变；哪些角色在什么环节做什么；主流程如何变化、哪些业务边界不变；对现有业务、外部协作方、历史数据和运营方式的影响；主要业务风险、兜底方式和不做什么。**用户明确确认后才可以进入详细设计**；用户否定或修订时先更新大架构再确认。**Lean 的详细设计就写在那一页 spec 里，所以"确认后才进详细设计"在 Lean 上等价于"确认后才动手实现"**——本门 MUST 与兼容取舍**同一批**抛出，MUST NOT 分两轮问。

**「历史数据搬迁」与「不可逆风险」不在本判据里**：它们是**后果**属性、不是结构属性，由 Triage 第 3 问识别并在那里各自过一次同样的用户确认（§1.1）。两个判据各管一件事，**MUST NOT 把任一方并进另一方**。

**改动小 MUST NOT 作为豁免理由**——三行代码把单人审批改成两级会签，和三百行改成两级会签是同一件事。

**每次向用户提问、汇报或请求确认前 MUST 检查**：用户能否只凭业务知识回答（不能则改写）？是否出现文件、类、函数、接口、表、消息、缓存、框架、部署等程序词汇（除非用户明确要求技术细节，否则删除或翻译）？是否在请求用户确认详细程序设计（是则停止确认，改为内部决策）？是否属于大架构变化（是则先给业务语言摘要并取得明确确认）？

  来源：`用户沟通纪律.md` §1. 大架构

### 9.2 四条轴各看什么

| 轴 | 只看什么 | 不看什么 | 典型命中 |
|---|---|---|---|
| **A 规范轴** | 改动是否符合本仓库既有编码规范与惯例（命名、目录结构、错误处理方式、日志措辞），有没有引入坏味道 | 需求对不对 | 重复代码、过长函数、霰弹式修改、依赖泄漏、和邻居文件风格打架 |
| **B 忠实轴** | 逐条对照 lean spec 的需求与验收项：每条都实现了吗？有没有 spec 没要求却擅自加的行为（镀金）？"不做什么"的边界有没有被越过？ | 代码风格 | 漏实现一条验收项、顺手加了个没人要的开关、动了声明不碰的模块 |
| **C 残留轴** | 替换清单是否逐条核销；被新流程取代的旧逻辑是否已删干净；有没有新产生的死代码；**改动是否落在非权威副本上**；**卡片有没有跟上**（〈既有系统清单〉里标着本次新补的，卡片真的在吗；被删掉的实现进陷阱项了吗）| 新代码写得好不好 | 旧函数没人调却还在、feature flag 全量后没摘、旧配置项/旧字段/旧文档段落遗留、被注释掉的旧实现、**改了废弃副本而权威实现原封不动**、**为本次改动读了源码却没补卡片** |
| **D 文档轴** | 参照物是 **`docs/` 的现行文档与真相源**（其余各轴都不看它）。只查三件事：①**正文与代码逻辑是否一致**——本次触碰的权威面，描述它的现行文档说的还对吗；②**断链与孤儿文档**；③**真相源跟上没有**——`REQUIREMENTS.md`、`docs/requirements/` 子模块与 `ARCHITECTURE.md` 描述的能力被本次改动改了吗（**尚未归并只标「待归并」、MUST NOT 报失准**；正文与本次口径**已经背离**才算失准）。**真相源里出现尚未实现的内容、或出现改动前后对比**同样算失准，去处分别是 `docs/TODO.md` 与归档索引| 代码本身怎么写；文档的措辞好不好；**skill / 产品代码内部的口径残留**（那归 C 轴——判据是**看参照物不看文件类型**）| 现行 spec 描述的接口/默认值/错误码语义已与代码背离却还挂在 `index.md` 现行区、真相源正文与本次口径已经背离、新建文档没有任何入口指向（孤儿）、指向已归档文档的实施依据没改指向接替者 |
| **E agent 架构轴**（仅 Agentic 项目）| 加载 `agentic-principle`，按它 `SKILL.md` 的评审入口跑它的全部评估项 | 上面四轴管的事 | 判据、项数与文件路径全部以该 skill 当前版本为准 |

**D 轴的判据不在评审纪律里**：什么算"触碰权威面"、失准了怎么归档、仍准确怎么留痕，判据在 §10.3，D 轴只是**执行**它，MUST NOT 另立一套。

### 9.3 派子代理的 prompt 要点

- **前置里点名加载本 skill 是必须的**——子代理默认不带本流程的纪律，靠关键词自动触发不可靠；同时把 skill 根目录的绝对路径也给它，作为按名字唤起失败时的兜底。
- **派发时 MUST 把 prompt 里的每个 `【…】` 占位符替换成真实值**（worktree 绝对路径、目标主分支名、lean spec 路径、**协作面与代码图谱是否可用**）。带着占位符派出去的子代理只会返回一份泛泛而谈的报告。
- **协作面与代码图谱是数据模型字段，不是修辞**：协作面取自标记块的 `collaboration`（`solo` / `team`）；代码图谱由路由阶段探测得出——`.codegraph/codegraph.db` 存在则填「可用」，否则填「无」，它只决定子代理**用什么手段查引用与影响面**。
- **出处是无条件要求**：每条模块事实都 MUST 有出处——来自卡片的给 cite（path#anchor @确认时间），本次现读源码的给 `文件:行`，**MUST NOT 因为"这项目卡片还少"就免掉这一项**，MUST NOT 全仓裸 grep，MUST NOT 编造 cite。
- **评审对象**：`git diff 【目标主分支】...HEAD` 这个范围（不做全仓体检）；工作区若还有未提交改动（`git status --porcelain` 非空），这些改动同样在范围内。
- **忠实轴每条发现 MUST 标一个「偏离类型」**，取值是这五个的闭集，MUST NOT 自造第六类：`漏做`（一行代码都没落地）/ `做一半`（缺分支、缺错误处理，或验收项某一面没做到）/ `做反了`（语义与 spec 相反，如默认值取反、边界判断写反）/ `越界`（做了 spec 明确写"不做"或声明不碰的事）/ `镀金`（spec 没要求、也不在"不做什么"边界内的过度实现）。**`越界` 与 `镀金` MUST 分列、MUST NOT 合并成一类**：越界是 P0，镀金通常 P1/P2。
- **spec 里的需求带 `FR-###` 编号时，忠实轴 MUST 产出覆盖矩阵**：把每条 `FR-###` 与各任务的 `满足:` 引用双向对齐，矩阵随报告给出。**哪条需求没有任何任务覆盖，记一条 `漏做`；哪个任务不对应任何一条需求，记一条 `镀金`。**
- **降级契约**：spec 里没有 `FR-###` 编号时（存量 spec 就是这样），退回自然语言逐条对照，并在报告**首行**原样输出一行 `本次未跑覆盖矩阵：spec 无编号`。这是降级不是缺陷：**MUST NOT 因此报一条问题，MUST NOT 因此阻断门禁，MUST NOT 自己回头给存量 spec 补编号。**
- **残留轴的卡片核销判据来源是落盘的文档、不是猜主会话读过什么**：Lean 看 lean-change-spec 的〈本次补的卡片〉行——凡"卡片补了吗"列标着本次新补的，逐条到 `engineering-context/cards/` 核对该域真的存在（按 §3.4 的最小四项）且随本次分支提交；凡列在清单里、"从哪知道它的"填的是 `文件:行` 却没有任何补卡记录的，即为未核销。清单表本身缺列或整表缺失，同样记一条。
- **D 轴的两步比对**：先拿本次触碰的权威面清单去查现行区文档的 `authority_refs`；**随后 MUST 再对关键术语（门名、轴名、步骤号、命令名、字段名）做一次现行区全文检索**——只做机械那步会整篇漏掉"正文大段描述本次改动、却没在 `authority_refs` 里登记它"的文档，**漏登记本身也是一条发现**。项目没有 `index.md` 时用 `grep -rn -A5 "^authority_refs:" docs/` 取全部声明，**MUST NOT 因此报"无法执行"**。本次没触碰任何权威面时，明确回答"扫了 N 篇现行文档、0 篇失准"，**MUST NOT 因为"看起来没碰文档"就不扫**。
- **硬要求**：子代理**只报告，MUST NOT 修改任何文件、MUST NOT 提交**；每条问题必须给出 `位置(文件:行) + 问题描述 + 建议修改 + 严重度`，不接受"感觉不好"；判不准的写进「存疑」段并说明缺什么信息，**不要为了凑数编问题，也不要把拿不准的降级放过**；本轴没有问题就明确回答"本轴无发现"。
- **返回格式表头按轴取**：规范轴 / 残留轴 / 文档轴（以及 agent 架构轴）一律 `| # | 严重度 | 位置 | 问题 | 建议修改 |`；**只有忠实轴多「偏离类型」一列** `| # | 偏离类型 | 严重度 | 位置 | 问题 | 建议修改 |`。**MUST NOT 把「偏离类型」加到忠实轴之外的任何一轴**。覆盖矩阵或降级那行写在表格之前。
- **严重度口径**：P0 = 正确性 / 安全 / 契约违背 / 越过 spec 的"不做什么"边界；P1 = 应当修（明显坏味道、残留旧逻辑、漏实现的次要验收项）；P2 = 建议考虑。

  来源：`代码评审纪律.md` §子代理 prompt 模板

### 9.4 处置

- **P0 与 P1 MUST 全部修完**才算过门；P2 由主会话决定当场修或记入 `docs/report/<feature>-review-report.md`。
- **D 轴报告里的文档结算结论 MUST 由主会话当场落盘**，且**不受 P0/P1 口径限制**：失准的完成"改 frontmatter + 插归档头注 + 移出 `index.md` 进 `index-archive.md`"三动作，仍准确的把 `last_confirmed` 更新为当天。子代理只报告不写文件，落盘没有别的执行者；而"仍准确"不是一条问题，挂在"P0/P1 修完才过门"下它永远轮不到执行。
- 修完后 MUST 重跑**受影响的那一轴**确认（只重跑改动涉及的轴，不必全跑）。
- **子代理判断有误时，主会话 MUST 在报告里写明"不改 + 一句话理由"，MUST NOT 默默忽略**——沉默的忽略无法与遗漏区分。
- **`merge-gate="pr"` 的项目**（判据由该字段**单独**判定，与协作面无关）：**开 PR 前 MUST 先过本门**。本门是 PR 前的**地板不是天花板**，**MUST NOT 用它替代人审**；各轴报告结论 SHOULD 附进 PR 描述。**PR 描述 MUST 引用对应 spec / 任务号**，并附影响范围说明（为什么没扩大）。
- **残留轴的卡片核销项命中时，MUST 当场补上再过门**：缺的卡片按 §3.4 补齐、被删实现按 §3.5 移进陷阱项，随本次分支提交。它与"该删的旧逻辑没删"同级，**MUST NOT 以"下次再补"放过**。

  来源：`代码评审纪律.md` §处置

### 9.5 与其它纪律的衔接

- 本门产出问题清单，修复动作回到 §7 执行；改动较大时按 §12 的规则 3 在 checkpoint 处交接。
- **残留轴查出的旧逻辑属于"这次就该删"，不是新需求，MUST NOT 以"超出本次范围"为由推给下次。**
- **bug 类任务同样过本门**（走 Lean 精简版）；修复引入的临时探针、调试日志、被替换掉的旧分支都归残留轴。

  来源：`代码评审纪律.md` §与其他纪律的关系

## 10. 第 10 步：文档落位（目录与生命周期字段）

> **何时读本节**：Triage 四问全否后立即读（前置）——§4 写那一页 spec 时就要用：文件落哪个目录看 §10.1，frontmatter 要写哪几个字段看 §10.2。归档与结算判据不在本节，在 §10bis。

### 10.1 目录与命名硬规则

- **输出目录只有三个**：spec → `docs/spec/`，plan → `docs/plan/`，report → `docs/report/`。**MUST NOT 把 spec 或 plan 放项目根、仓库根或 `docs/` 根**（例外只有三类：需求与架构两层真相源 `REQUIREMENTS.md`、`ARCHITECTURE.md`、还有 `docs/TODO.md`；需求真相源的一级子模块住 `docs/requirements/`，MUST NOT 平铺在 `docs/` 根）。
- **MUST NOT 建 `docs/superpowers/`、`docs/claude/`、`docs/codex/` 这类工具专属目录**；文件名 MUST 表达业务主题与文档角色，**不得用生成工具名作前缀**。
- 同一需求的文档用正文中的相对链接互相引用；**移动文档时 MUST 同步修复引用**。
- `docs/index.md` 是发现入口，**只索引现行口径**，历史文档进归档索引。
- 报告只有在流程要求形成书面报告时才创建；一旦创建 MUST 写入 `docs/report/`。
- **两个固定文件名的账本是例外**，不按"每次新建一个 `<feature>-<report-type>-report.md`"拆分：`docs/report/bug修复历史.md`（**追加式**，每条是发生过的一次性事实）与 `docs/report/测试场景覆盖度.md`（**状态表**，同一场景只有一行）。两者 **MUST 恒为 `lifecycle: active`、`authority_refs: ['无']`，MUST NOT 被 §10.3 的权威面触发转归档**。
- **测试资产不是文档**：真实输入样本落项目测试目录（兜底 `tests/fixtures/<场景名>/`），**MUST NOT 塞进 `docs/`**；含凭证的进同级 `secrets/` 并 gitignore，脱敏副本 `secrets.example/` 入库。
- Lean 的默认命名：`docs/spec/<change-name>-lean-change-spec.md`；交接文档 `docs/plan/<feature>-handoff.md`；报告 `docs/report/<feature>-<report-type>-report.md`。
- 落盘的文件名 MUST 以 `YYYY-MM-DD-` 开头（`docs/spec/YYYY-MM-DD-<change-name>-lean-change-spec.md`）；常青档与两份索引不加；拆成目录时目录名同样带前缀。项目自己有更严格的命名约定可以更严格，MUST NOT 豁免掉这条前缀。
  来源：`文档治理.md` §默认命名

  来源：`文档治理.md` §硬规则

### 10.2 新建文档的生命周期字段（MUST）

`docs/` 下新建的 spec / plan / report / PRD，头部 frontmatter MUST 声明：

```yaml
---
lifecycle: active          # active | merged | superseded | obsolete
superseded_by: ''          # lifecycle: superseded 时 MUST 填被谁取代（相对路径）
archived: ''               # 非 active 时 MUST 填转归档日期 YYYY-MM-DD
last_confirmed: ''         # 最近一次被复核、判定仍准确的日期 YYYY-MM-DD；新建时填当天
authority_refs:            # 本文冻结了哪些权威面；一条都不冻结时 MUST 显式写一条 无，MUST NOT 留空
  - ''
---
```

| 值 | 含义 | 索引归属 |
|---|---|---|
| `active` | 现行有效，可据此实施 | `docs/index.md` |
| `merged` | 口径已归并进 `REQUIREMENTS.md` / `ARCHITECTURE.md` / 代码 | 归档索引 |
| `superseded` | 被更新的同类文档取代 | 归档索引 |
| `obsolete` | 描述的能力已下线或权威面已删除 | 归档索引 |

- **字段名是 `lifecycle` 不是 `status`**——后者已被"写作进度"与 PRD 的自由文本状态占用，**MUST NOT 混用**。
- `authority_refs` 写具体到可比对的粒度，**MUST NOT 写成"支付模块"这种笼统范围**；注释里 MUST NOT 出现引号。
- **存量豁免**：升级前已存在、无 frontmatter 的文档默认视为 `active`，**MUST NOT 为补齐字段而批量回改**；只有被 §10.3 触发复核时才就地补齐并结算。

  来源：`文档治理.md` §1. 生命周期位

## 10bis. 生命周期结算与归档（小节号续 §10.3–§10.6）

> **何时读本节**：要判文档去留、要归档、要归并需求真相源时才读——落点是代码评审门 D 轴的判定与主会话当场落盘（§9.4），以及 §11 完成门的核对。Triage 之后 MUST NOT 预读。

本节与 §10 同属第 10 步，小节号续着 §10 排（§10.3–§10.6），既有交叉引用照旧成立。

### 10.3 归档触发：按权威面，不按日期

**MUST NOT 用"超过 N 天没动"当归档判据。** 判据只有一条：**文档描述的权威面是否还成立**。

**判定与落盘分属两个角色，MUST 分清**：判定由代码评审门的 **D 文档轴**子代理做并写进报告（它只报告、MUST NOT 改文件）；**落盘动作由主会话在收到报告后当场执行**。**MUST NOT 把落盘挂在"P0/P1 修完才过门"上**。

1. **盘点本次触碰的权威面**（**哪怕只改了 3 行**）——这份清单是唯一权威，`authority_refs` 的类目也以此为准：

   | # | 权威面 | 也触发刷卡？ |
   |---|---|---|
   | 1 | canonical 接口签名与版本 | ✅ |
   | 2 | 废弃标记 | ✅ |
   | 3 | 路由与配置开关 | ✅ |
   | 4 | DB schema 与唯一键 | ✅ |
   | 5 | 兼容窗口 | ✅ |
   | 6 | 命令与目录约定 | ❌ 文档层专有 |
   | 7 | 对外契约与字段枚举 | ❌ 文档层专有 |
   | 8 | **流程与门禁契约**（门的位置与顺序、轴或步骤的集合与编号、准出项的语义、谁在哪一步执行什么）| ❌ 文档层专有 |

   标 ✅ 的与 §3.9 的刷卡面逐条对应；标 ❌ 的是**文档层专有、不触发刷卡**。**以表内该列为准，MUST NOT 在别处另记一个数字。**

   **"触碰"不等于"删除"**：替换清单里被删除或被替换的条目必然在内，但**不止于此**——枚举加值、可选字段改必填、默认值或校验规则变更、错误码语义调整，这些一个都没删，却同样让描述它的文档失准。**MUST NOT 把这一步退化成"照抄替换清单"**；替换清单为"无"的改动照样可能触碰权威面。
2. **比对（两步都要做，MUST NOT 只做机械那步）**：先查现行区文档的 `authority_refs`；**随后 MUST 再对关键术语做一次现行区全文检索**。**漏登记本身也是一条发现**，MUST 在报告里指出该篇的 `authority_refs` 需要补。只查现行区。
3. **逐篇判定，结果 MUST 落盘**：
   - **仍准确** → 保持 `active`，并把 `last_confirmed` 更新为当天。**判定不留痕等于没判。**
   - **部分失准**（主体仍是现行口径、只有若干行被新口径推翻）→ **就地更正那几行**（不该改写的历史记载加一句"当时口径为 X"的括注）+ 把 `last_confirmed` 更新为当天，生命周期保持 `active`。**MUST NOT 因为几行失准就把整篇转 `superseded`**——那会让仍现行的主体一起失效。
   - **已失准**（整篇的结论已被取代）→ 转对应生命周期，并完成 §10.4 的三个动作。**MUST NOT 把这一档做成就地更正**——那会凭空多出一篇与接替者重复的现行文档。
   - **勾验表按勾选状态判**：**未勾选**的项会被续跑，按**现行口径**判——口径变了就是失准，MUST 改；**已勾选**的项属历史记载，**MUST NOT 为了对齐新口径去改写它**（要标注可加一句"当时口径为 X"）。
   - **本步只改文字，MUST NOT 翻转勾选位**：口径一变，把 `[ ]` 翻成 `[x]` 等于用新口径追认一次并未发生的执行；反向亦然，**MUST NOT 因为口径变了就把 `[x]` 翻回 `[ ]`**。勾选位只由**真的跑了那一项**的那次执行来改。
   - **零命中同样 MUST 留下书面结论**（"扫了 N 篇现行文档、0 篇失准"）——这是唯一能与"没执行"区分的凭据。
- **`ctx probe` 是这三步的辅助，不是替代**：它的 B 类题型验的是**可达性与字段非空**，**不读正文**。所以 **probe 全绿 MUST NOT 被读成"文档还准"**。

  来源：`文档治理.md` §3. 归档触发

### 10.4 归档降权而非删除；索引分层

- 归档 **MUST NOT 删文件**——删掉会让历史链接烂尾，也丢掉"当初为什么这么定"的证据。改为在 frontmatter 之后、正文标题之前插入固定头注（头注模板与端到端示例在 `文档归档与账本收敛.md`，判定出需要归档时才读）。
  来源：`文档治理.md` §4. 归档降权而非删除
- **索引分层的判据是文档数量，不是人数、不是协作面、也不是代码规模**：`docs/index.md` 现行区所列文档超过 20 篇时 **MUST** 分层，20 篇及以内 SHOULD 分层。**数到 20 篇就开始分层，MUST NOT 等到"感觉乱了"再补。**
  - `docs/index.md` 只索引现行口径，末尾加一行指向归档索引；`docs/index-archive.md` 索引全部非 active 文档，按年份分区，每条注明生命周期值与取代它的文档，**文件不存在则在首次归档时创建**。
  - **文件原地不动，只有索引分层**——移动文件会破坏既有相对链接。归档不需要修改指向它的既有链接；但现行文档若把某篇归档文档当作实施依据，**MUST 改指向接替它的现行文档**。
  - 文档转归档 **MUST 在同一次提交内**完成"从 `index.md` 移除 + 加进 `index-archive.md` + 插入归档头注"三个动作，**MUST NOT 分次做**。
  - **项目没有 `docs/index.md` 时**：只做"改 frontmatter + 插入归档头注"两个动作，**MUST NOT 为了归档而临时造一个索引**。
  来源：`文档治理.md` §2. 索引分层

### 10.5 三层真相源与账本读取

- 项目 MUST 对任何接手者——人或 AI agent——做到**零上下文交接**：**需求 / 架构 / 实现**三层真相源都能从项目自身定位。层次固定为这三层，承载形态随项目已有资产变化——小项目用 README 的一节就合规，**MUST NOT 因为项目小就允许某一层缺失**。
  - 需求层最小形态：README 的一节 **或** `docs/index.md`；架构层：README 的"架构与边界"一节（模块划分 / 各自职责一句话 / 对外边界 / 不做什么，可短至 10 行，**模块路径 MUST 写成反引号代码片段或相对链接**，散文里的裸文字抽不到就判失败）；实现层：`engineering-context/` 的 registry + cards（**必备，不是升级项**）。
  - **可达性（MUST）**：三层都 MUST 能从 README 或 `docs/index.md` 出发、**≤2 跳链接到达**。超过 2 跳等于不存在。
  - **缺口只报告、不阻断（MUST）**：发现某层缺失或超过 2 跳，MUST 报告为"零上下文交接缺口"并指明补哪一份，**MUST NOT 因此中止流程，也 MUST NOT 代用户自动创建**。
  - **需求 MUST 先写清楚再动代码**，但真相源的**更新**在准出门完成（见 §10.6）。**MUST NOT 在实现验收之前把本次口径写进需求真相源**——那会让它描述一件尚未存在、甚至可能中途被推翻的事。
  - **需求真相源只写现状**：只描述 main 分支上**已经实现的**东西，回答"是什么、为什么做、现在有哪些功能"。**MUST NOT 包含**历史与演进、改动前后对比、技术选型、需求调整过程；**尚未实现的一切 MUST 去 `docs/TODO.md`**（见 §10.7），**MUST NOT 在真相源里留"计划中"小节**。
  - **两层承载，MUST NOT 再往下分**：主文档 `docs/REQUIREMENTS.md`（薄：是什么 / 为什么做 / 功能清单每条一句话 / 用户怎么用 / 非目标 / 服务质量 / 子模块划分方式）+ 一级子模块 `docs/requirements/<模块>.md`（用户可感知的具体规则：次数上限、权限范围、状态流转、报错口径）。**MUST NOT 出现二级目录**。细节边界判据是**用户能不能感知**——感知不到的（缓存策略、内部阈值、用了哪个库）MUST NOT 写。
  - **划分方式 MUST 写在主文档里**（按什么维度切、切成哪几块、各自文件名）；何时拆按 `文档治理.md` §需求真相源写什么、怎么分层 的拆分阈值，**MUST NOT 在别处另记一个数字**。
  - 可验证：`ctx probe` 有四道交接题型（`requirement-reachable` / `architecture-reachable` / `implementation-usable` / `rationale-traceable`）读项目自身文件，**卡片还没攒起来的起步态项目同样跑得起来、同样该跑**；频次按 `probe-set.md` §运行节奏（CI 发布或里程碑节点跑，**MUST NOT 塞进 coding agent 的每轮 loop**）。
  来源：`文档治理.md` §三层真相源、§需求真相源写什么、怎么分层
- **两个账本是检索索引，不是阅读材料**：`docs/report/bug修复历史.md` 与 `docs/report/测试场景覆盖度.md` **MUST 用关键词检索定位条目，MUST NOT 把整份账本读进上下文。**
  来源：`文档治理.md` §5. 账本的读取纪律
- 【bug 类才做】归档：修完后追加 `docs/report/bug修复历史.md`，格式固定见 `bug诊断纪律.md` Phase 3。

### 10.6 准出时归并需求真相源

- **归并落点按"本次改变了什么口径"分派，MUST 逐类过一遍**：

  | 本次改变了什么 | 归并落点 | 主文档动不动 |
  |---|---|---|
  | 新增或去掉一个功能 | 主文档功能清单增删一行 + 建或删对应子模块文档 | 动 |
  | **已交付功能的行为规则变了**（次数上限、权限范围、状态流转、报错口径）| **对应子模块 `docs/requirements/<模块>.md` 就地改写** | **不动** |
  | 用户怎么用变了、成功指标变了 | 主文档旅程节与服务质量节，**含旅程叙事回填** | 动 |
  | 明确不做什么变了 | 主文档非目标节 | 动 |
  | 本次冒出来、但不做的事 | `docs/TODO.md`（见 §10.7）| **不动** |
  | 本次做掉了 `TODO.md` 里的条目 | 删掉那条 | **不动** |

  **「主文档动不动」这一列 MUST 读成信号而不是结论**：有三类落点根本不碰主文档，**MUST NOT 拿「主文档没动」当收工信号**。

- **「功能清单没变化」MUST NOT 被读成「无需归并」**——改已交付功能的行为规则而功能清单一动不动，是最常见的迭代形态，漏了它这条规则会跟着变更 PRD 一起进归档区，**且没有任何机器闸能发现**。
- **就地改写，MUST NOT 留前后对比**（不写"原为 3 次"、不加变更记录、不留删除线）。
- **承载放不下时 MUST 当场创建**：真相源还在 `docs/index.md` 或 README 一节、而本次确有用户可感知的规则要写时，MUST 当场建 `docs/REQUIREMENTS.md`；平时 MUST NOT 强制。
- **触碰存量文档时 MUST 顺手收敛**：**"触碰"= 本次归并确实要往那份文件里写东西**（只读或被扫到 MUST NOT 算）。当场做：删规划类章节、内容移进 `docs/TODO.md`、存量 appendix 拆进 `docs/requirements/`；**先问用户**：超过拆分阈值需要拆子模块时 MUST 由用户拍板，**MUST NOT 自行拆分**。
- 归并后变更 PRD 标 `lifecycle: merged`、加归档头注、移入归档索引。
- 架构边界被本次改动的，同步改架构真相源；**两层都改完才更新 `docs/index.md`**。
- **归并在准出门内完成；结算的判定已前移到代码评审门的 D 文档轴、落盘由主会话当场做，准出只核对结论、MUST NOT 重做盘点。** 因此 D 轴对"尚未归并"的真相源只标记「待归并」，**MUST NOT 报失准**。
- **两件事都 MUST NOT 留作"下次一起做"**——变更 PRD 一旦堆积，`REQUIREMENTS.md` 就退化成一份过期文档，三层真相源当场破一层。

  来源：`文档治理.md` §6. 准出时归并需求真相源

### 10.7 TODO 出口（还没做的事都去这里）

- `docs/TODO.md` 是项目内**还没做的事的唯一出口**，与真相源同放 `docs/` 根。它同样是**快照**——只记此刻仍未做的，做掉的当场删，**MUST NOT 保留"已完成"区**。
- **章节按类型分，取值是闭集，MUST NOT 自造第五类**：想做的功能 / 待澄清的问题 / 已知风险 / 技术欠账。
- **每条 MUST 带提出日期**（`YYYY-MM-DD`），行格式 `- YYYY-MM-DD ｜ <归属模块或"跨模块"> ｜ <一句话>`。没有日期，陈旧提醒整条失效。
- **准入门槛（MUST）**：只收会改变用户可感知行为、会新增或去掉一个功能、会动某个模块边界的条目；改名、清死代码、补测试、局部重构这类局部小事 **MUST NOT 写入**——**MUST NOT 把它当随手记**，清单一膨胀，真正该拍板的几条就被淹掉。
- **随时冒随时写**（写 spec 时、写代码时都算），准出时再统一过一遍把本次做掉的删掉；**MUST NOT 攒到最后一起写**。
- **陈旧提醒（SHOULD）**：条目超过 3 个月 SHOULD 提示用户"这条还留着吗"；**AI MUST NOT 自行删除任何条目**，留不留由用户定。项目可在 `TODO.md` 头部声明改写阈值，声明了以声明为准。
- **不阻断**：没有 `docs/TODO.md` 不是缺陷，第一次有够格条目时才建；初始化时 **MUST NOT 代用户创建**。

  来源：`文档治理.md` §TODO 出口

## 11. 第 11 步：完成与自动合并门

> **何时读本节**：要过完成与自动合并门时才读（代码评审门 P0/P1 清零之后）。Triage 之后 MUST NOT 预读。

Lean 路径 MUST 以此门收尾。只有**同时**满足以下条件，才算"全部完成"：

- 已确认范围内的业务能力、文档和代码全部完成，没有未决业务问题或大架构确认项。
- 计划内测试、构建、静态检查和必要链路验证全部通过，并形成要求的报告。
- 任务分支的改动已提交，worktree 状态干净；不存在调试文件、临时产物或未解释变更。
- **代码评审门已通过**：逐轴（规范 / 忠实 / 残留 / 文档）报告齐全，P0 与 P1 已清零；替换清单逐条核销，该删的旧逻辑引用数为 0 且已删除。
- **兼容取舍已有用户结论**：改变了既有可观察行为的每一条都有用户拍板记录（或显式声明"本次无兼容取舍"）。
- **文档生命周期已结算**（本门**只核对结论，MUST NOT 在此重做盘点**）：D 轴报告在，其中 P0/P1 已清零，且判定结果**已落盘**（失准的完成三动作，仍准确的 `last_confirmed` 已更新为当天）；**零命中也要有书面结论**；**本次新建的文档** `lifecycle` 与 `authority_refs` 两个字段齐。
- 已吸收最新主分支并重新验证，没有未解决冲突。
- `merge-gate="pr"` 时，仓库要求的评审、持续集成、owner 或发布门禁全部通过。

满足完成条件后，**无需再次询问用户**，自动合并任务分支到识别出的主分支。**合并方式读标记块字段 `merge-gate`**，只有两个取值：

- **`direct`（本地直合）**：在主工作树执行非快进合并（`git merge --no-ff`），并运行最小的合并后验证。不开 PR、不等外部门禁。
- **`pr`（走平台）**：推送任务分支，创建或更新 PR，评审与持续集成通过后启用或执行平台自动合并；**MUST NOT 绕过保护分支、审批、CI 或 owner 规则强行写入主分支，也 MUST NOT 在平台未放行时改用本地直合。**

**字段缺失时的判据**，按顺序取第一个命中的：① **仓库现状**——远端主分支受保护、或仓库有 PR 规则 → `pr`；② **仍判不出**（无远端、探测失败、本地仓库）→ 由协作面推：`team` → `pr`，`solo` → `direct`；③ 两步做完后 MUST 在完成报告里提示补齐该字段。**优先级 MUST 是现状 > 协作面推断，MUST NOT 反过来**——反过来会让 `solo` 且主分支受保护的项目稳定判成 `direct`，每次合并都撞门禁。

**失败与阻塞**：测试失败、合并冲突、主工作树出现新改动、权限不足或保护分支门禁未通过时，**MUST NOT 宣称完成、MUST NOT 合并**；**保留任务分支与 worktree、不清理现场**，用业务语言说明尚未交付的能力、影响和下一步条件。

合并与合并后验证成功后，移除任务 worktree，并按仓库规则删除已合并的任务分支。**自动合并不等于擅自发布上线**；发布、部署和外部通知仍遵循项目原有授权与门禁。

  来源：`worktree开发纪律.md` §完成与自动合并门；`00-流程总纲.md` §完成与自动合并门

**team 协作面额外要做的（因为有别人）**：

- **指派评审人**：PR MUST 指到具体的人（受影响仓的 owner 优先），**MUST NOT 只开 PR 不指人等着谁来看**。
- **合并窗口 SHOULD 提前与 owner 约定**，尤其是会影响对方仓库对外契约的改动；**对方未确认时 MUST NOT 单方面按自己的时间表推进**。
- **人审提出的结论 MUST 回写**到 spec 的"已定决策"表——口头共识不落文档，等于下一个零上下文 agent 拿不到。
- **本次补了或改了哪张卡片 SHOULD 在 PR 描述 / 合并说明里点名**，让该仓 owner 有机会复核；**但 MUST NOT 因为等 owner 复核就把已知有错的卡片留在原样，也 MUST NOT 因此挂起本次任务**。
- `merge-gate="pr"` 本身要做的事与协作面无关（判据在 §9.4 与本节），team 分册**MUST NOT 复述**它们。

  来源：`team.md` §4. PR 平台动作

## 12. 全程适用：上下文卫生

> **何时读本节**：Triage 四问全否后立即读（前置）——名字就是判据，交接信号随时可能出现。

- **方向性决策 SHOULD 在聪明区内完成**：上下文窗口的**前半段**推理最清晰；经验值是把窗口前 ~60% 当作"聪明区"。需求澄清、spec 取舍属于方向性决策；机械执行（照 spec 写代码）对聪明区要求最低。**这条是 SHOULD 不是 MUST**，因为 agent 通常读不到自己当前的 token 占用；**可判定的落点是下面的三个可观察过载信号，MUST NOT 把 MUST 挂回"逼近 60%"这个不可自判的量。**
  来源：`上下文卫生.md` §1. 聪明区
- 五条规则：
  1. **决策链保持连续**：澄清 → spec SHOULD 在同一连续会话内完成，中途不插入无关任务。
  2. **交接，不硬撑**：出现下面规则 5 任一**可观察**过载信号、而决策链未走完时，**MUST 写一份交接文档**（已定决策表 / 未定开放问题 / 证据与 cite / 下一步）再开新会话继续，**而不是硬撑到窗口极限，也不依赖自动压缩**。交接文档落任务 worktree 内的 `docs/plan/<feature>-handoff.md`，它遵循 §4.2 的写作纪律——读者就是那个零上下文的新会话。
  3. **编码任务零上下文起步**：连续执行多个任务后上下文变重时，SHOULD 在 checkpoint 处收尾，让新会话只带 spec 从下一步继续；**任务间 MUST NOT 依赖"上个任务的会话记忆"传递信息**——该传递的信息必须写在文档里。
  4. **重探索外包**：大范围代码探索、全仓检索、多方案对比这类"读得多、结论少"的工作，harness 支持子 agent 时 SHOULD 交给子 agent，主会话只收结论（编码后的代码评审逐轴更进一步，是 MUST 交子代理）。**取事实的顺序不变**（§3.1）。**外包不豁免补卡**：子代理返回结论后，**主会话 MUST 按 §3.3–§3.4 把结论落成卡片并随本次分支提交**——子代理只报告、不落盘，**MUST NOT 指望子代理顺手写掉**。
  5. **识别过载信号，立即交接**：开始忘记已拍板的决策、重复问已答过的问题、引用不存在的文件 / 函数——任一出现即视为上下文过载，**MUST 按规则 2 交接**，不再"再撑一会儿"。
  来源：`上下文卫生.md` §2. 五条规则
- **决策沉淀进 memory**：SHOULD 用所在 AI 工具的 memory 机制记录三类内容——**非显而易见的**技术决策、踩过的坑、项目特有约定。**MUST NOT 记录代码本身已经能说明的东西**（目录结构、类型定义、历史 fix 的实现细节），它们会随代码漂移。每条 memory 一个事实并写清"为什么"。需要被引用、被评审、被 cite 的结论 **MUST 进 `docs/`**，memory 只放"下次开工前想知道、但不值得单独成文"的短事实。这条**与协作面无关**。
  来源：`上下文卫生.md` §3. 决策沉淀进 memory

## 13. 七条"不裁剪"护栏（Lean 一条也不豁免）

> **何时读本节**：Triage 四问全否后立即读（前置）——裁剪一旦发生就已经发生了，事后读它没有用。

**轻量不等于可省。** 下面七条在任何协作面、有没有代码图谱、任何分流路径下都 **MUST NOT 被裁剪**：

1. **目录不裁剪。** spec 仍 MUST 写进 `docs/spec/`，plan 仍 MUST 写进 `docs/plan/`，报告仍 MUST 写进 `docs/report/`。**MUST NOT 因为"就一份文档"把设计散放在代码注释、聊天记录或仓库其它位置。**（§10.1）
2. **沟通纪律不裁剪。** 用户只确认业务目标、业务边界和必要的大架构；模块内设计通过业务问题取约束；详细程序设计直接完成，**MUST NOT 就它发起技术确认**。（§5）
3. **worktree 与自动合并不裁剪。** 再小的 Lean 改动也 MUST 先进入独立 worktree；全部验证通过后按 `merge-gate` 合并，失败则保留 worktree，**MUST NOT 直接修改主工作树**。（§2、§11）
4. **代码评审门不裁剪。** **MUST NOT 因为"改动很小"就一个子代理都不派**：Lean 派 1 个跑四条轴的精简版，但不能跳过。（§9）
5. **兼容取舍不裁剪。** 每次 MUST 把被改变的既有可观察行为逐条列出交拍板人明确拍一次，结论落进 spec 的兼容取舍节；清单为空时也 MUST 显式写一句"本次不改变任何既有可观察行为"，**MUST NOT 静默跳过这道门**。（§6.1）
6. **测试资产与覆盖度台账不裁剪。** 真实样本不因项目小而变便宜——遇到的真实输入照样 MUST 固化进测试 fixture，长链路照样 MUST 写断言中间结果的端到端用例。可以裁剪的只有**深度**：覆盖度台账 MAY 只记高重要度场景。（§8）
7. **补卡不裁剪。** 本次为推进任务而读了源码的模块，**MUST 在本次任务内把卡片补上并随分支提交**。**MUST NOT 因为"改动很小""就查了一个字段""这项目还没建几张卡"就跳过。** 可以裁剪的只有**范围**：只补本次真读过并核对过的那部分，**MUST NOT 为了"补全"去写没核对过的字段**。（§3.3–§3.5）

  来源：`00-流程总纲.md` §七条"不裁剪"护栏

## 15. Lean 特有的四个提醒

> **何时读本节**：Triage 四问全否后立即读（前置）。

- **拿不准就升级，别硬塞进一页**：Triage 有任何一问是 borderline，在 spec 的「Triage 复核」里写清哪一问、为什么倾向"否"；实在拿不准就按 §0.2 升级回完整流程。中途发现影响面变大（跨服务、要迁数据、动了对外承诺）同样立即升级，不要将错就错走完。
- **验收标准别只写 happy path**：小改动最常翻车在异常路径——边界值、空值、并发、依赖不可用各留一条可勾验的验收项。
- **Lean 不等于不写测试**：§8 的判定命中就照做，协作面为 solo 时也不压缩。压缩的是文档篇幅，不是验证强度。
- **Lean 也不豁免补卡**：本次为写〈影响范围〉或为动手实现而读过源码的每个模块，MUST 在本次任务内把卡片补上并随分支提交；被本次删掉的旧实现移进该卡片的陷阱项。第 10 步的残留轴会逐条核销这件事。
