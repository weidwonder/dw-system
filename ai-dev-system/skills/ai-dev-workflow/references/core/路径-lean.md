# Lean 路径（一页走完）

> 加载条件：Step 0 Triage 四问全否。读完本页就能把这次改动做完，**不需要读 `步骤-1-7-设计与实现.md` 与 `步骤-8-10-测试.md`**。
> Lean 的轻量体现在"文档只有一页、跳过 Step 1–10"，**不体现在跳过门**——四道门一道都不能少。
> 分流默认倾向**无条件适用**（MUST NOT 由协作面、项目大小或有没有代码图谱改变，见 `00-流程总纲.md` §默认倾向（四问全否之后））：**影响面说不清时 MUST 升级到完整流程出 Overview，说得清才走 Lean。**
> **读到这里就说明四问已全否、且四条"说不清"判据一条都没命中**（跨 ≥2 个权威仓库 / `ctx discover` 给出 out-of-scope 警告 / 关键事实给不出出处 / 读完源码仍说不清模块边界）。后两条是**回溯触发**的：第 3 步写〈既有系统清单〉时命中即 MUST 当场升级回完整流程（读 `步骤-1-7-设计与实现.md`），MUST NOT 将错就错把这一页写完。
> **卡片查不到不算"说不清"**——那只说明这个模块还没人建过卡，正确处置是读源码 + 当场补卡（`代码事实纪律.md` §4），补完就有出处。

## Lean 特有的四个提醒

- **拿不准就升级，别硬塞进一页**：Triage 有任何一问是 borderline，在 spec 的「Triage 复核」里写清哪一问、为什么倾向"否"；实在拿不准就升级回完整流程（读 `步骤-1-7-设计与实现.md`）。中途发现影响面变大（跨服务、要迁数据、动了对外承诺）同样立即升级，不要将错就错走完。
- **验收标准别只写 happy path**：小改动最常翻车在异常路径——边界值、空值、并发、依赖不可用各留一条可勾验的验收项。
- **Lean 不等于不写测试**：第 8/9 步的判定命中就照做，协作面为 solo 时也不压缩。压缩的是文档篇幅，不是验证强度。
- **Lean 也不豁免补卡**（`00-流程总纲.md` §七条"不裁剪"护栏 第 7 条）：本次为写〈影响范围〉或为动手实现而读过源码的每个模块，MUST 在本次任务内把卡片补上（`代码事实纪律.md` §4.1 的最小四项）并随分支提交；被本次删掉的旧实现按 §4.2 移进该卡片的陷阱项。第 10 步的残留轴会逐条核销这件事。可以裁剪的只有**范围**——只补本次真读过并核对过的那部分，MUST NOT 为凑满模板写没核对过的字段。

## 与用户沟通

全程业务语言（见 `用户沟通纪律.md`）。Lean 路径通常只需要用户在两处表态：**兼容取舍**（第 5 步）和**验收标准是否是他要的**。其余技术决策自主完成，不要拿实现方案去问用户。

**例外只有一个：改动命中大架构判据时，多一件事要用户确认**——产品或技术架构的**主干路形状**变了（形状变才算，取值变不算；判据与正反例见 `用户沟通纪律.md` §1）。Lean 从不产出 Overview，所以这道门在本路径上**只能挂在第 5 步**：与兼容取舍同一批抛业务语言摘要，用户确认后才实现。改动小 MUST NOT 作为豁免理由——三行代码把单人审批改成两级会签，和三百行改成两级会签是同一件事。
