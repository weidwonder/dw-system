# 代码事实纪律（core，无条件常驻）

> **本文无条件常驻**，任何项目、任何分流路径都适用。
> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD / MAY。
> 它回答的是「**信哪个**」——同一能力有多处实现时，哪一处是权威。
> 与它正交的是「**找得到吗**」（检索），由 `capability/graph.md` 的代码图谱负责，**探测到索引才加载**。
> 资产层的完整设计（场景蓝图怎么生产、探针集怎么维护、registry 有哪些字段）见 `engineering-context设计.md`，**要动资产结构时才读**；日常补一张卡片只需本文 §4。

## 0. 一句话规矩

> **要用某个模块的事实，先查卡片；没有卡片就读源码，读完把卡片补上。**

卡片库**只增不减**，每一张都是真读过代码才写的。

## 1. 卡片是地基，不是升级项

装了本体系的项目**一律**维护 `engineering-context/`——registry（能力到权威实现的映射）+ cards（每仓一张事实卡）。它不分项目大小、不分协作面、不由任何探测开关决定。

**初始化时只建骨架**（`init-初始化.md` 第 5b 步跑 `ctx init`），骨架里只有模板占位、没有真实数据行——**这是正常起步状态**，MUST NOT 因此告警、提示用户、或判定这层不可用。内容按 §4 在干活过程中渐进补齐。

**MUST NOT 因为 registry 里还没有条目就退回裸 grep 找权威实体。** 没有条目意味着"还没人读过这块代码并把结论固化下来"，处置是**读源码 + 补卡**（§4），不是绕过这一层。

**MUST NOT 反过来把它当准入门槛**：卡片没建齐 MUST NOT 阻断流程、降级交付或拒绝干活。缺卡片时按 §4 当场补，任务照常推进。

| | 本文（代码事实层） | 代码图谱（`capability/graph.md`）|
|---|---|---|
| 回答的问题 | **信哪个**（消歧） | **找得到吗**（检索） |
| 承载物 | `engineering-context/`：registry → cards → scenes → probe-set | codegraph 索引（`.codegraph/codegraph.db`）|
| 事实性质 | **人工确认过的权威口径**，带 cite 与确认时间 | **现状代码事实**，随文件变更同步 |
| 是否可选 | **必备**，缺哪块补哪块 | **可选**，探测到索引才启用，查不了就外包子代理 |

两者 **MUST NOT 互相替代**：图谱会如实列出 v1 与 v2 两处支付实现，但它不知道哪个是权威；卡片知道哪个权威，但不保证覆盖每一个符号与调用边。两者冲突时**以卡片为准**，并按 §7 第 4 条就地修正卡片。

## 2. 调用方式

安装器会把 `ctx` 链接成全局命令，正常情况下直接 `ctx <命令>` 即可。

**"`ctx` 命令找不到"绝不等于这一层不可用**——CLI 本体随本 skill 一起落盘。命令不可用时 MUST 改用：

```bash
node <本skill根目录>/scripts/ctx/src/cli.js <命令>
```

**`<本skill根目录>` 怎么得到**：就是当前这份 `ai-dev-workflow` 的 `SKILL.md` 所在的目录。安装后它在目标项目下有两份逐字节相同的副本，任选一份都行——Claude Code 读 `.claude/skills/ai-dev-workflow/`，Codex 读 `.agents/skills/ai-dev-workflow/`。**MUST NOT 写死其中一份**：同一份指导文件会被注入两个入口，写死 `.claude/` 那份在 Codex 侧就是错路径。拿不准就先试你自己加载 skill 的那一侧。

功能完全相同（想恢复全局命令则一次性 `cd <本skill根目录>/scripts/ctx && npm link`）。**任何情况下都 MUST NOT 因为找不到 `ctx` 命令就退回 grep 源码。** 命令清单与输出格式见 `scripts/ctx/README.md`。下文简写为 `ctx`。

`ctx` 默认读 `<cwd>/engineering-context`，所以 MUST 在**项目根**执行，或用 `--dir <项目根>/engineering-context` 显式指定；在子目录里跑它会返回空且退出码为 0（静默），把"有卡片"误判成"没卡片"，于是白白重读一遍源码。

术语说法不一致时查 `engineering-context/glossary.md`（领域词汇表）：glossary 管说法一致，card 管事实权威，registry 管能力落点；发现"同一实体多种叫法"造成误会时补词条（见 `engineering-context设计.md` §2.4）。

## 3. 取事实的固定顺序

凡涉及"这个能力对应哪个仓库/接口""跨服务影响面""哪个是权威实现"的问题，MUST 先用 `ctx`，MUST NOT 直接 grep 旧代码。

**★ 业务全景门限（排序铁律）**：**除非用户明确把任务限定到某一个具体 repo / 服务 / 代码路径**，否则**第一步 MUST 先 `ctx find-scenes <关键词>`** 取端到端业务全景，再据此收窄。跨服务需求跳过全景直接钻单个 card，最常见的失败就是漏掉链路上的其它服务。提取 2–5 个高置信关键词（需求名、业务入口、核心动作）喂给 find-scenes。

```bash
ctx find-scenes 作业辅导 错题 重练          # ← 未限定单仓时先跑这个，取端到端全景
ctx discover "给作业辅导加错题重练入口"      # 意图 → 应加载的 card 清单 + out-of-scope 警告
ctx get-card <repo> [域]                     # 收窄后取某仓 Codebase Card
ctx list-services                            # 已登记仓库/能力
ctx search-semantic "<自然语言>"             # discover 未命中时的兜底
```

**`find-scenes` 无命中不是错误**：`scenes/` 在骨架起步态本来就是空的，此时 `find-scenes` **必然**返回空。处置：MUST NOT 阻断、MUST NOT 反复重试，改走 `discover` + `get-card`；两者也收不窄时进 §4。本次需求**确实跨服务**（涉及 ≥2 个 registry 登记的权威仓库）时，SHOULD 顺手按 `engineering-context设计.md` §2.3 补一张场景蓝图——跨服务链路正是蓝图价值最高的地方。

> 注意：`ctx find-scenes` 返回的是**场景蓝图指针**（scene 名 + 命中分 + 路径），本身不直接给"涉及哪些服务"。你从蓝图正文里读到 / 推断出的涉及服务，都是**推断**，MUST 逐个用 `ctx get-card` 核实到权威 card 才能当事实用。
> `discover` 会随命中结果给出 **out-of-scope 警告**（哪些是废弃/中间产物、别当权威用），这些警告 MUST 抄进 Step 1 的〈既有系统清单〉，并在 Step 2 的 A 核查里逐条确认。

## 4. 没有卡片时怎么办（本纪律的核心）

`ctx` 查不到，只意味着**这个模块的卡片还没建**。MUST 按序处置，**三步一次做完，MUST NOT 只做前两步**：

1. **读源码建立事实。** 定位方式按项目实际：探测到代码图谱 → 走 `capability/graph.md`；没有图谱 → 按 `上下文卫生.md` 规则 4 把重探索**外包给子代理**，主会话只收结论。**MUST NOT 在主会话裸 grep 全仓**——裸 grep 指没有收窄目标、没有外包、直接把命中内容读进主上下文。
2. **把读到的权威事实补成卡片**（最小形态见 §4.1），随本次任务分支提交。
3. 补完的卡片即成为后续事实来源；本次任务后续引用它时照常带 cite（§5）。

**补卡是本次任务的一部分，MUST NOT 顺延**。"以后有空再补"等于这次读源码的成果只存在于本次会话的上下文里，下一个零上下文 agent 要把同样的路重走一遍——那正是这一层要消灭的浪费。

**MUST NOT 把"读了源码"本身当成交付**：读完不落卡，下次唤起时 `ctx` 依然查不到，这条纪律就等于没有执行过。

### 4.1 补一张卡片的最小形态

在 `engineering-context/cards/<repo>.md` 里新建文件，或在既有卡片里追加一个 `## <域>` 段。最小内容四项：

| 项 | 写什么 |
|---|---|
| 职责 | 这个模块负责什么业务能力，一句话 |
| 对外接口 | 本次真正读到并核对过的接口 / 字段 / 事件，每条带 `文件:行` |
| 陷阱项 | 相似但不该用的旧实现；确实没有就写 `无` |
| 确认时间 | 本次读源码的日期 |

同时在 `engineering-context/capability-registry.md` 追加一行（三列即可用）：`Capability` / `权威实现` / `陷阱项（废弃或中间产物）`。**第三列 MUST NOT 省**——它是最小 schema 里唯一的防误用装置，省掉就只剩一份"该用哪个"的清单，挡不住"改错了那个"。

**MUST NOT 为了凑满模板把没核对过的字段填上。** 没读到的就不写；写了就等于制造一条过期权威，而**一个看起来权威但已过期的来源比没有来源更危险**（`engineering-context设计.md` §0）。

**MUST NOT 把机器可派生的事实抄进卡片**（调用图、依赖边、最后修改时间、DB schema 全文）——那些随时可现查，手抄一份就是主动制造腐化（`engineering-context设计.md` §4）。卡片只放人工判断。

### 4.2 只增不减

- 卡片库**只增不减**：MUST NOT 因为"这次没用上"删除既有卡片内容。
- 发现既有卡片与源码不符 → **就地修正并更新确认时间**，MUST NOT 保留两份互相矛盾的说法，也 MUST NOT 只在本次上下文里绕过它继续干活。
- 卡片记录的实现被本次改动彻底删除时 → 把它移进该卡片的**陷阱项**（写清"已删除"与日期），MUST NOT 直接抹掉——后来的 agent 需要知道这个名字曾经存在过、现在不该再用。

## 5. cite 纪律

**每条来自卡片的事实（接口名、字段、topic、RPC 签名）MUST 附 cite**（path + anchor + 最近确认时间）。无 cite 的接口/字段一律视为幻觉，MUST 回查。

本次现读源码得到的事实，在卡片落盘前 MUST 带 `文件:行`；落盘后按卡片的 cite 引用。**两种出处都算数，MUST NOT 出现第三种"我记得"。**

## 6. 检索纪律

- 查**精确 token**（字段名/接口名/表名）时 MUST 优先用精确匹配（`ctx get-card <repo> <域>`、grep card 正文），不要只靠 `ctx search-semantic`。
- **语义检索结果只作"去哪找"的索引，MUST NOT 当最终事实直接引用**——命中后仍要落到权威 card 段并附 cite。
- card 没有独立的 README 段，服务级 README 信息（部署/排障/路径）已并入 card 的对应节。
- `freshness` 列留空时 `ctx` 会标注「未声明新鲜度」，此时 **MUST NOT** 假定该条新鲜，按 §8 回查后再当事实用。

## 7. 卡片不够用、必须读真实源码时（clone 决策树）

以下属工程侧内部取证；向用户只说明正在核对哪项业务事实及其影响，不报告仓库、类、方法等程序细节，除非用户明确要求。

1. **先穷尽文档路径**——接口签名/字段去 card 的"对外接口"段；部署/配置/排障去 card 对应段；跨服务流程去 `ctx find-scenes`。以上都不够，才真正 clone。
2. **clone 前**：工程侧先明确要看哪个仓、为什么要看源码、要核对的具体事实；**若没有 repo 地址，向工程 owner / 用户索取，MUST NOT 凭服务名猜 git URL**；用 `git clone --depth=1 <url>` 浅克隆到一次性临时目录，别污染工作区。
3. **clone 后**：**MUST NOT 全仓 grep**——按 card 的"业务域 Card Index（哪个文件做什么）"按图索骥（探测到代码图谱时，结构性定位改走 `capability/graph.md`）；读完 MUST 按 §4 把关键发现落成卡片，让后续 agent 不用重新 clone；对用户仍保持业务语言。
4. **发现卡片有缺漏或与源码不符**（如新增接口没记进去）→ **就地补上 / 改正并更新确认时间**，随本次分支提交。协作面为 team 时 SHOULD 在合并说明里点一句改了哪张卡片，让卡片的既有 owner 有机会复核（`collab/team.md`）；**但 MUST NOT 因为等 owner 而把卡片留在错误状态**——错的卡片比没有卡片更危险。

## 8. 新鲜度纪律

- 你的改动若**触碰权威面**（canonical 接口签名、废弃标记、路由/配置版本、DB schema、兼容窗口）——哪怕只有 3 行——MUST 触发对应卡片刷新（见 `engineering-context设计.md` §5）。
- 纯内部实现改动（不碰接口/权威）MAY 不刷卡。
- 判断标准是**是否碰权威面**，不是改了多少行。
- **会话开始时先看增量**：`ctx` 读的是本地活文件，没有跨会话的变更推送。开一个新任务前，SHOULD 先看清"上次到现在 card/registry 变了什么"，避免拿脑子里的旧上下文干活：

```bash
# engineering-context/ 通常就在项目仓库里（不是独立仓库），所以在项目根跑，路径当参数传
git log --oneline -20 -- engineering-context/
git diff 'HEAD@{2.weeks.ago}'..HEAD --stat -- engineering-context/cards/ engineering-context/capability-registry.md
```

用时间锚（`HEAD@{2.weeks.ago}`）而不是"上次的 commit"——**本体系不记录"上次是哪个 SHA"，没有那个落点**，写成 `<上次>..HEAD` 就是一条填不出来的命令。时间跨度按你上次碰这个项目的间隔调。
**reflog 不够长（新 clone）时这条命令 MUST NOT 被当作"没变过"**：git 会回退到最旧的 reflog 条目（= HEAD），输出**空 diff 且退出码 0**，只在 stderr 打一行 `warning: log for 'HEAD' only goes back to …`。看到这行 warning 即表示时间锚被截断、本次 diff **不可信**，MUST 改用 `git log --since='2 weeks' -- engineering-context/`。`engineering-context/` 确实是独立仓库时才用 `git -C engineering-context …`。

## 9. 真相方向铁律

card 事实 **MUST 以合入后的源码为准，MUST NOT 从 PRD 生成**——PRD 描述意图，意图常与已落地事实背离（典型："PRD 说可复用，查代码发现不可复用"）。详见 `engineering-context设计.md` §3。

## 一句话

要用某个模块的事实就先查卡片，没有卡片就读源码、读完当场补上；卡片只增不减，每条事实带出处，永远不裸 grep 找权威实体。
