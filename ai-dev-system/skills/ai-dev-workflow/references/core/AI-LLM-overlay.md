# AI / LLM 工作流 Overlay（core）

> 当需求包含 **AI/LLM 功能**（模型推理参与到功能行为），在基础 eng-spec 骨架之上**叠加**本 overlay 定义的 AI 契约。先按基础规范产出完整骨架，再补 AI 契约部分。

## 何时叠加：判定边界

**需要叠加**（模型推理参与功能行为）：生成、总结、分类、检索增强问答、排序/推荐、OCR、语音/手写识别、内容审核，或固定 prompt 工作流。

**判定层级**：

1. **模型只在确定性软件主导下辅助受限步骤** → 用本 overlay 即可。
2. **模型具备自主规划或直接产生状态变更**（自主多步规划；直接调用工具/接口/数据库；或未经确定性闸门即创建/修改/删除/发送/审批）→ 属 **AI Agent 主导场景**，本 overlay 之外还要补 agent 循环、工具契约、自主级别与审批闸门、记忆、轨迹可观测与 eval（团队版可在 `context-engineering.md` 基础上扩展；本体系不内置完整 agent 平台规范，按需引用 origin 的 Agent 指南）。

## AI 契约清单（叠加到 spec）

在基础 spec 的相应章节补充以下内容，每项都要写到可执行、可验证：

| 契约项 | 要写清什么 |
|---|---|
| **模型 / prompt 版本化** | 用哪个模型（含 ID）、prompt 存哪、如何版本化、如何回滚 |
| **推理请求生命周期** | 入参构造 → 调用 → 超时/重试 → 结果落地，每个环节的错误处理 |
| **输出契约与校验** | 期望输出结构（JSON schema / 字段），如何校验，校验失败怎么办 |
| **置信度路由** | 低置信度时走人工 / 降级 / 拒答的阈值与分支 |
| **安全管线** | 输入输出的敏感内容过滤、注入防护、越权防护 |
| **降级回退** | 模型不可用 / 超预算 / 校验失败时的兜底行为（返回什么、是否阻断主流程）|
| **成本 / token 预算** | 单次调用与整体的 token/成本上限，超限如何处理 |
| **eval 质量门** | 上线前用什么评测集、什么指标、达到什么线才准出 |
| **可观测性** | 记录哪些字段（prompt 版本、耗时、token、置信度、是否降级），便于排障与回归 |
| **数据 / 训练边界** | 哪些数据能进 prompt / 能否用于训练、脱敏要求 |
| **可审计性** | 关键决策能否复现（保留 prompt+输出+版本快照）|

## 与基础 spec 的关系

- 不要另起一份"AI spec"；**叠加**进同一份 eng-spec 的对应章节（如"接口契约"里补输出校验，"降级"里补模型不可用兜底）。
- 用 `references/core/spec写作纪律.md` 的纪律：AI 契约同样不许占位符，阈值、上限、指标都写具体数值。
