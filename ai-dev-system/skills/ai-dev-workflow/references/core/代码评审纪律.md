# 代码评审纪律（core，强制门）

> 适用：任何写过产品代码的任务。完整流程在 Step 7 编码完成后、Step 8 之前执行；Lean 路径在实现完成后、完成与自动合并门之前执行。**两条路径都不豁免。**
> 本文同时定义**替换清单**（旧逻辑的登记与核销机制）——它是残留轴的判据来源，登记发生在 Step 4/Lean spec，核销发生在本门。
> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD。

> **本文小节**：[为什么必须交给子代理](#为什么必须交给子代理) · [门禁](#门禁) · [四条轴](#四条轴分开查分开报) · [子代理 prompt 模板](#子代理-prompt-模板)（含 §前置 / §评审对象 / §本轴职责 / §硬要求 / §返回格式）· [处置](#处置) · [替换清单](#替换清单replacement-ledger) · [与其他纪律的关系](#与其他纪律的关系)

## 为什么必须交给子代理

写完代码的会话已经被实现细节浸透：它记得"我当初为什么这么写"，于是 review 时最容易替自己辩护，也最容易看不见自己刚加的多余行为和刚绕开的边界。子代理不带这段记忆，只带 spec 和 diff，判断更接近真实的第三方读者。附带收益是省主上下文（见 `上下文卫生.md` 规则 4）。

## 门禁

- 编码完成、基础验证（能跑起来、无编译/语法错）通过后 MUST 执行本门。**未过门 MUST NOT 进入 Step 8，MUST NOT 进入完成与自动合并门。**
- **完整流程**：MUST 派 **4 个并行子代理**，规范轴 / 忠实轴 / 残留轴 / 文档轴各一个，各自独立返回报告。
- **Lean 路径**：MUST 派 **1 个子代理**跑四轴精简版，报告仍分四节写，MUST NOT 合并成一段总评。
- **D 文档轴恒跑，MUST NOT 由主会话先判"本次有没有碰文档"再决定派不派**——判断"有没有触碰权威面"本身就是盘点，而盘点正是本轴的第一步；把它交回主会话，等于把最容易漏的判断交给最容易漏的人（`文档治理.md` §3 明写"只改语义不删东西同样让文档失准"，而这类改动的替换清单往往是空的，最容易被据此判成"没碰"）。
- **Agentic 项目**（判定见 `AI-LLM-overlay.md` §Agentic 应用）：在上述基础上**增派 1 个 agent 架构轴子代理**（完整流程 5 个 / Lean 2 个）。这一轴**加载 `agentic-principle` 而不是本 skill**，按它 `SKILL.md` 的评审入口进入 review 模式（该入口指向的评审序列文件以它当前结构为准），执行其中列出的全部评估项，并遵守它写明的评审边界（哪些问题要先与用户确认成立才给建议、哪些是客观缺陷可直接给处置、以及不得径自改动实现）——**以该 skill 当前内容为准，本纪律不复述、不锁定项数与文件路径**。只有**该 skill 整体不在场**时本轴才标"未执行 + 原因"；**某个内部文件按记忆中的路径没找到 MUST NOT 算作不在场**——回到它的 `SKILL.md` 找当前的评审入口。MUST NOT 用其余四轴顶替本轴。
- harness 不支持子代理时：降级为主会话**分轮**执行，一轴一轮、一轮一份报告。MUST NOT 合并成一次"总体看看"——合并会让一轴的显眼问题掩盖另一轴。

## 四条轴（分开查、分开报）

| 轴 | 只看什么 | 不看什么 | 典型命中 |
|---|---|---|---|
| **A 规范轴** | 改动是否符合本仓库既有编码规范与惯例（命名、目录结构、错误处理方式、日志措辞），有没有引入坏味道 | 需求对不对 | 重复代码、过长函数、霰弹式修改、依赖泄漏、和邻居文件风格打架 |
| **B 忠实轴** | 逐条对照 spec / lean spec 的需求与验收项：每条都实现了吗？有没有 spec 没要求却擅自加的行为（镀金）？"不做什么"的边界有没有被越过？ | 代码风格 | 漏实现一条验收项、顺手加了个没人要的开关、动了声明不碰的模块 |
| **C 残留轴** | 替换清单是否逐条核销；被新流程取代的旧逻辑是否已删干净；有没有新产生的死代码；**改动是否落在非权威副本上**（同一逻辑存在多处副本，改的不是权威那处）；**卡片有没有跟上**（〈既有系统清单〉里标着本次新补的，卡片真的在吗；被删掉的实现进陷阱项了吗）| 新代码写得好不好 | 旧函数没人调却还在、feature flag 全量后没摘、旧配置项/旧字段/旧文档段落遗留、被注释掉的旧实现、**改了废弃副本而权威实现原封不动**、**为本次改动读了源码却没补卡片** |
| **D 文档轴** | 参照物是 **`docs/` 的现行文档与真相源**（其余各轴都不看它）。只查三件事：①**正文与代码逻辑是否一致**——本次触碰的权威面，描述它的现行文档说的还对吗；②**断链与孤儿文档**——本次新建/移动的文档有没有断链，新建的有没有任何入口指向；③**真相源跟上没有**——`REQUIREMENTS.md` / `ARCHITECTURE.md` 描述的能力被本次改动改了吗，改了同步没有 | 代码本身怎么写；文档的措辞好不好；**skill / 产品代码内部的口径残留**（那归 C 轴——判据是**看参照物不看文件类型**：本轴只看 `docs/` 与真相源，C 轴看替换清单）| 现行 spec 描述的接口/默认值/错误码语义已与代码背离却还挂在 `index.md` 现行区、真相源没跟上本次的口径变更、新建文档没有任何入口指向（孤儿）、指向已归档文档的实施依据没改指向接替者 |
| **E agent 架构轴**（仅 Agentic 项目）| 加载 `agentic-principle`，按它 `SKILL.md` 的评审入口跑它的全部评估项 | 上面四轴管的事 | 判据、项数与文件路径全部以该 skill 当前版本为准，本表不复述 |

**D 轴与 `ctx probe` 的分工**：本轴 SHOULD 先跑 `ctx probe` 拿机器结论当补充——**它是辅助不是门禁，绿了也不等于文档还准，跑不起来也不豁免本轴**，完整定位见 `文档治理.md` §3 末段（与 §替换清单 对静态检查工具的既有定位同源：判据是 MUST，工具是 SHOULD）。

**判据不在本文重复定义**：什么算"触碰权威面"、失准了怎么归档（改 frontmatter + 插头注 + 移出 `index.md` 进 `index-archive.md`）、仍准确怎么留痕（更新 `last_confirmed`），权威定义都在 `文档治理.md` §3，本轴**执行**它、MUST NOT 另立一套。

## 子代理 prompt 模板

四个子代理共用同一段前置，只换【轴】那一段。**前置里点名加载本 skill 是必须的**——子代理默认不带本流程的纪律，靠关键词自动触发不可靠（见 `SKILL.md` 开头的「触发提示」引用块）；同时把 skill 根目录的绝对路径也给它，作为按名字唤起失败时的兜底。派发时 MUST 把 prompt 里的每个 `【…】` 占位符替换成真实值（worktree 路径、主分支名、spec 路径、**协作面与代码图谱是否可用**；`##` 开头的是段落标题，不用替换），带着占位符派出去的子代理只会返回一份泛泛而谈的报告。

**协作面与代码图谱是数据模型字段，不是修辞**：协作面取自标记块的 `collaboration`（`solo` / `team`）；代码图谱由 skill 路由阶段探测得出——`.codegraph/codegraph.db` 存在则为「可用」，否则填「无」，它只决定子代理**用什么手段查引用与影响面**。**出处则是无条件要求**：代码事实层是必备资产（`代码事实纪律.md`），每条模块事实都 MUST 有出处——来自卡片的给 cite，本次现读源码的给 `文件:行`，MUST NOT 因为"这项目卡片还少"就免掉这一项。

```text
你是 ai-dev-workflow 的代码评审子代理，本次只负责【规范轴 / 忠实轴 / 残留轴 / 文档轴】其中一轴。

## 前置
先加载 ai-dev-workflow skill，读 references/core/代码评审纪律.md 与
references/core/spec写作纪律.md。**轴 = 文档轴时另读 references/core/文档治理.md §3**
——本轴的全部判据（七类权威面、比对两步、勾验表怎么判、失准了怎么归档）都在那一节。
本项目协作面 =【solo / team】，代码图谱 =【可用 / 无】。
另读 references/core/代码事实纪律.md——查代码事实 MUST 先用 ctx 查卡片并附 cite
（path#anchor @确认时间）；卡片查不到就读源码并给 文件:行，MUST NOT 全仓裸 grep，
MUST NOT 编造 cite。
代码图谱可用时，"谁调用了谁 / 影响面多大"用 codegraph 查（见 references/capability/graph.md）。
skill 未能按名字唤起时，直接读这些文件：【skill 根目录绝对路径】/references/core/…

## 评审对象
worktree：【worktree 绝对路径】
改动范围：`git diff 【目标主分支】...HEAD`（只评审这个范围内的改动，不做全仓体检）
工作区若还有未提交改动（`git status --porcelain` 非空），这些改动同样在评审范围内。
参考文档：spec @【spec 或 lean-change-spec 路径】、coding plan @【路径，无则删除本项】、
替换清单：见 spec 的「替换清单」节

## 本轴职责
- 规范轴：只看改动是否符合本仓库既有规范与惯例、有没有坏味道。不评判需求对错。
- 忠实轴：只逐条对照 spec 的需求与验收项，查漏实现、镀金、越界。不评判代码风格。
- 残留轴：只查替换清单逐条核销情况 + 新产生的死代码 + 改动是否落在非权威副本上
  + 卡片有没有跟上。对每个被取代物实际统计引用数（先用 ctx 核对哪处是权威实现、再在
  本仓精确检索；代码图谱可用时用 codegraph 查引用），引用数为 0 且不在保留例外里的，
  即为未清理。发现"同一逻辑有多处副本、本次改的不是权威那处"MUST 单列一条，注明改了
  哪处、权威在哪处。卡片核销两项，**判据来源是落盘的文档、不是你猜主会话读过什么**——
  你观测不到主会话开过哪些文件，只能按 spec 里已经写下来的清单核：
  ① 完整流程看 eng-spec §1 / overview §5.5 的〈既有系统清单〉表，Lean 看 lean-change-spec
  的〈本次补的卡片〉行。凡"卡片补了吗"列标着本次新补的，逐条到 engineering-context/cards/
  核对该域真的存在（按 代码事实纪律.md §4.1 的最小四项）且随本次分支提交；凡列在清单里、
  "从哪知道它的"填的是 文件:行（而不是卡片 cite）却没有任何补卡记录的，即为未核销。
  ② 卡片里记着、而被本次改动彻底删除的实现，有没有按 代码事实纪律.md §4.2 移进陷阱项。
  清单表本身缺列或整表缺失，同样记一条——那说明写 spec 时就没登记，不是"本次没读源码"。
  不评判新代码质量。
- 文档轴：只查 `docs/` 的现行文档与真相源跟本次改动对不对得上，三件事：
  ① **正文与代码逻辑是否一致**——先盘点本次触碰的权威面（**七类面逐项见 references/core/
  文档治理.md §3 第 1 步，本 prompt 不复述**；只记两条要害：**改语义不删东西也算触碰**、
  替换清单为"无"不等于没触碰）。再按 §3 第 2 步比对——**机械比对 authority_refs 之后
  MUST 再做一次关键术语的现行区全文检索**，两步的命中集不一样，只做机械那步会整篇漏掉
  正文大段描述本次改动、却没在 authority_refs 里登记它的文档（漏登记本身也是一条发现）。
  命中的**逐篇打开正文核对**说的还对不对。项目没有 index.md 时用
  `grep -rn -A5 "^authority_refs:" docs/` 取全部声明。
  ② **断链与孤儿文档**——本次新建或移动的文档，链接指向的目标存在吗；新建的文档有没有
  任何入口指向它（index.md 或别的现行文档），没有就是孤儿。现行文档若把某篇已归档文档
  当作实施依据，MUST 改指向接替它的现行文档。
  ③ **真相源跟上没有**——docs/REQUIREMENTS.md / ARCHITECTURE.md 描述的能力被本次改动
  改了吗？改了而它们没同步，单列一条。**但归并动作本身允许留到完成门**（见
  references/core/文档治理.md §6）：本轴对"尚未归并"只标记「待归并」，
  MUST NOT 据此报失准——否则凡是改了真相源口径的变更，本轴每次都会稳定误报一条。
  真相源正文与代码**已经背离**（不是尚未归并，是说错了）才报失准。
  SHOULD 先跑 `ctx probe` 拿机器结论当补充（B 类题型），但 **probe 报绿 MUST NOT 读成
  本轴无发现**——它验可达性与字段非空，你查的是内容还对不对；probe 跑不起来时照常执行，
  MUST NOT 标"未执行"。
  每条 MUST 指到具体文档的具体位置（`文件:行` 或 `文件#小节`）并说明与哪处代码/哪个
  权威面对不上。**本次没触碰任何权威面时，明确回答"扫了 N 篇现行文档、0 篇失准"**——
  MUST NOT 因为"看起来没碰文档"就不扫。不评判代码本身怎么写，也不评判文档措辞好不好。
- agent 架构轴（仅 Agentic 项目；本轴改为【加载 agentic-principle skill】，不加载
  ai-dev-workflow）：读它的 SKILL.md，按其中的评审入口进入 review 模式，执行该入口
  列出的**全部**评估项（项数、内容与文件路径以该 skill 当前版本为准，不要按本 prompt
  的记忆凑数；按记忆的路径找不到文件时回 SKILL.md 找入口，MUST NOT 就此跳过本轴）。
  守它写明的边界：问题必须带证据、哪些要先与用户确认成立才给建议、不得径自改动实现。
  不评判上面四轴管的事。

## 硬要求
- 只报告，MUST NOT 修改任何文件、MUST NOT 提交。
- 每条问题必须给出 位置(文件:行) + 问题描述 + 建议修改 + 严重度，不接受"感觉不好"。
- 判不准的写进「存疑」段并说明缺什么信息，不要为了凑数编问题，也不要把拿不准的降级放过。
- 本轴没有问题就明确回答"本轴无发现"，不要为凑数扩到其他轴。

## 返回格式
| # | 严重度 | 位置 | 问题 | 建议修改 |
严重度口径：P0 = 正确性/安全/契约违背/越过 spec 的"不做什么"边界；
P1 = 应当修（明显坏味道、残留旧逻辑、漏实现的次要验收项）；P2 = 建议考虑。
```

## 处置

- **P0 与 P1 MUST 全部修完**才算过门；P2 由主会话决定当场修或记入 `docs/report/<feature>-review-report.md`。
- **D 轴报告里的文档结算结论 MUST 由主会话当场落盘**，且**不受 P0/P1 口径限制**：失准的完成"改 frontmatter + 插归档头注 + 移出 `index.md` 进 `index-archive.md`"三动作，仍准确的把 `last_confirmed` 更新为当天。子代理只报告不写文件，落盘没有别的执行者；而"仍准确"不是一条问题，挂在"P0/P1 修完才过门"下它永远轮不到执行（判据见 `文档治理.md` §3）。
- 修完后 MUST 重跑**受影响的那一轴**确认（只重跑改动涉及的轴，不必四轴全跑）。
- 子代理判断有误时，主会话 MUST 在报告里写明"不改 + 一句话理由"，MUST NOT 默默忽略——沉默的忽略无法与遗漏区分。
- **走 PR 合并的项目**（`merge-gate="pr"`，判据由该字段**单独**判定）：
  - **开 PR 前 MUST 先过本门。** 本门是 PR 前的**地板不是天花板**：把 AI 能自查出来的问题挡在 PR 之前，让人审的注意力留给业务正确性与架构取舍，**MUST NOT 用它替代人审**。四轴报告结论 SHOULD 附进 PR 描述。
  - PR 描述 MUST 引用对应 spec / plan 任务号，并附影响范围说明（为什么没扩大）。
  - **MUST NOT 再加"协作面 = team"这一条**——一个人的开源项目照样可能走 PR 与外部审阅。把这几条写进只有 `collaboration="team"` 才加载的分册，等于让 solo + pr 的项目读不到，那是判据解耦了、内容还耦合着。所以它们在本文（常驻），不在 `collab/`。
  - `collab/team.md` §4 只补**因为有别人**而额外要做的事（指派评审人、与 owner 约合并窗口），不重复上面这几条。
- **残留轴的卡片核销项命中时，MUST 当场补上再过门**：缺的卡片按 `代码事实纪律.md` §4.1 补齐、被删实现按 §4.2 移进陷阱项，随本次分支提交。它与"该删的旧逻辑没删"同级，MUST NOT 以"下次再补"放过——补卡是本次任务的一部分（`00-流程总纲.md` §七条"不裁剪"护栏 第 7 条）。

## 替换清单（Replacement Ledger）

**目的**：让"这次改动淘汰了什么"变成一份可核销的清单，而不是靠改完之后凭印象回忆。**没有清单，残留轴无从下手。**

**登记时机（MUST）**：Step 4 写 eng-spec 时（Lean 路径写 lean-change-spec 时）。凡是新逻辑取代了既有实现的，把被取代物逐条登记。写 coding plan 时把删除动作拆成具体任务，不要笼统写一句"清理旧代码"。

登记对象覆盖六类：**函数/类/模块**、**文件/目录**、**配置项与环境变量**、**feature flag / 开关**、**DB 字段与表**、**接口或接口版本**。旧文档段落、旧注释掉的实现同样算。

| 被取代物 | 类型 | 取代者 | 引用数 | 处置 | 核销 |
|---|---|---|---|---|---|
| `calcPriceV1()` | 函数 | `calcPrice()` | 0 | 删除 | ✅ |
| `ENABLE_NEW_FLOW` | 开关 | 已全量，无需开关 | 0 | 删除 | ✅ |
| `orders.legacy_memo` | DB 字段 | 无（数据已迁走） | 0 | 保留至迁移窗口结束 | ⏳ 2026-09-01 起删 |

**核销规则**：

- 引用数为 0 且不在保留例外内 → **MUST 立即删除**，不得留着"以后可能还要用"。版本控制就是那个"以后"，被删的代码随时可以从历史里取回。
- 引用数不为 0 → 说明迁移没做完，MUST 先补完调用点迁移，再回来核销。
- **保留例外**必须同时给出**理由**和**到期日**，以及到期后的动作。只有三类理由成立：① 对外契约仍在兼容窗口内（呼应本次的兼容取舍决策）；② 数据迁移未完成；③ 回滚预案显式依赖它。**"以防万一"不是理由。**
- 到期日到了没人删，下一个碰这块代码的任务 MUST 在残留轴把它重新提出来。

**工具辅助（SHOULD，作为清单的补充而非替代）**：清单负责"知道该找什么"，工具负责"发现清单漏了什么"。

| 语言 | 可用检查 |
|---|---|
| TypeScript / JavaScript | `knip`、`ts-prune`、ESLint `no-unused-vars` |
| Python | `vulture`、Ruff `F401`/`F841` |
| Go | 编译器本身 + `staticcheck -checks U1000` |
| Rust | `cargo check` 的 `dead_code` 警告 |
| 任意语言 | 精确检索被取代物名字统计引用数；新流程跑完后覆盖率为 0 的旧分支是嫌疑段 |

走 PR 合并的项目（`merge-gate="pr"`）SHOULD 把上述检查挂进 PR gate；工具链不具备时，替换清单核销仍然照做——**清单是 MUST，工具是 SHOULD**。
