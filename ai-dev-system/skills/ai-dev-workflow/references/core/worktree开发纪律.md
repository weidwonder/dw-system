# Worktree 开发与自动合并纪律（core）

本纪律对所有项目强制执行，不因协作面（solo / team）、项目有哪些代码事实资产、Lean 流程、单人项目、小改动或紧急修复而裁剪。合并**方式**由标记块字段 `merge-gate` 决定（见下方"完成与自动合并门"），合并**要不要做、什么时候做**不由任何字段决定。

## 工作区隔离门

完成路由或初始化后，在任何文档或代码向项目落盘前，必须先进入独立 Git worktree。Lean Change Spec 也必须在 worktree 中创建，不得跳过隔离门直接修改主工作树。

1. 确认目标是 Git 仓库，并按仓库配置识别默认主分支；优先读取远端默认分支，不得写死为 `main` 或 `master`。
2. 检查主工作树是否干净。发现未提交改动时，不得替用户 stash、reset、提交或删除；中止进入开发并用业务语言说明已有工作需要先妥善保存。
3. 从最新主分支创建本次任务分支与独立 worktree。worktree 目录位置读取该仓库 CLAUDE.md（优先）或 AGENTS.md 的 `ai-dev-workflow` 标记块内的设置，未显式覆盖时默认落在仓库根的 `./.worktrees/`；每次创建前都从该设置读取，不得沿用上次会话记住的路径或凭空自定义。子目录名包含业务主题，避免与其他任务冲突。若 `.gitignore` 尚未忽略该 worktree 根目录，先幂等追加一行忽略规则，避免其内容污染主工作树的 `git status`。用户显式要求改到其它位置时，更新标记块内的设置后再创建。
4. 从此刻起，需求文档、spec、plan、report、代码、测试、生成文件、验证和提交全部在该 worktree 内完成。不得中途切回主工作树落盘。
5. 非 Git 仓库无法建立 worktree 时中止开发，不得降级为直接修改当前目录。

需求涉及多个仓库时，每个仓库全程使用独立任务分支和独立 worktree。先确认所有仓库都能进入隔离状态，再开始落盘；不得让多个仓库共用一个 worktree。**这条与协作人数无关**——一个人同时改 3 个仓，同样是 3 个任务分支、3 个 worktree；共用一个工作区会让跨仓改动混进同一次提交，任一仓未就绪时无法单独回退。

## 开发期间

- 每个 worktree 只承载一个业务任务，任务改动不得混入其他未完成工作。
- 按 plan 分段提交，确保任务分支可独立验证、可追溯。
- 主分支有新提交时，先把最新主分支合入任务分支并解决冲突，再重新运行受影响验证。
- 不得为了制造“干净状态”而处理主工作树里的用户改动；尤其不得自动 stash、reset、checkout 覆盖或删除未知文件。

## 完成与自动合并门

只有同时满足以下条件，才算“全部完成”：

- 已确认范围内的业务能力、文档和代码全部完成，没有未决业务问题或大架构确认项。
- 计划内测试、构建、静态检查和必要链路验证全部通过，并形成要求的报告。
- 任务分支的改动已提交，worktree 状态干净；不存在调试文件、临时产物或未解释变更。
- **代码评审门已通过**：三轴（规范/忠实/残留）报告齐全，P0 与 P1 已清零；替换清单逐条核销，该删的旧逻辑引用数为 0 且已删除（见 `代码评审纪律.md`）。
- **兼容取舍已有用户结论**：改变了既有可观察行为的每一条都有用户拍板记录（或显式声明"本次无兼容取舍"）。
- **文档生命周期已结算**：已盘点**本次触碰的权威面**（与刷 card 用的是同一个面：接口签名、废弃标记、路由配置、DB schema、兼容窗口、命令与目录约定；**改语义不删东西也算触碰**，替换清单为"无"不等于没触碰），与 `docs/index.md` 现行区各文档的 `authority_refs` 比对；命中的逐篇判定——仍准确的已更新 `last_confirmed`，失准的已完成"改 frontmatter + 插入归档头注 + 移出 `index.md` 进 `index-archive.md`"。本次新建的文档已带 `lifecycle` 与 `authority_refs`。判定结果不得悬空——判据见 `文档治理.md` §3，落地写法见 `文档归档与账本收敛.md`。
- 已吸收最新主分支并重新验证，没有未解决冲突。
- `merge-gate="pr"` 时，仓库要求的评审、持续集成、owner 或发布门禁全部通过。
- 多仓任务的所有仓库均已达到合并条件；任一仓未就绪时，不提前合并其他仓。

满足完成条件后，无需再次询问用户，自动合并任务分支到识别出的主分支：

**合并方式读标记块字段 `merge-gate`**（`CLAUDE.md` 优先，其次 `AGENTS.md` 的 `ai-dev-workflow` 标记块），只有两个取值：

- **`merge-gate="direct"`（本地直合）**：在主工作树执行非快进合并（`git merge --no-ff`），并运行最小的合并后验证。不开 PR、不等外部门禁。
- **`merge-gate="pr"`（走平台）**：推送任务分支，创建或更新 PR，并在评审与持续集成通过后启用或执行平台自动合并；不得绕过保护分支、审批、CI 或 owner 规则强行写入主分支，也不得在平台未放行时改用本地直合。

字段缺失时（旧标记块或被手工删掉）不得凭印象猜：按仓库现状判定——远端主分支受保护或仓库有 PR 规则则按 `pr`，否则按 `direct`，并在完成报告里提示补齐该字段。

多仓任务：全部仓库先通过完成门，再**按依赖顺序合并**：

- 顺序规则是**被依赖方先合**——提供接口、schema、事件或配置契约的一侧先落地，调用方后合，使任一时刻主分支上的组合都能自洽；互相依赖时先合"只加不改"的一侧（新增接口、加可选字段），再合切换调用的一侧。
- 顺序在 Overview 或 coding plan 里预先写死并逐仓核销，不得临场决定；存在其他协作方时，顺序还需与各仓 owner 协商确认后再执行（见 `collab/team.md`）。
- 任何一步失败，立即停止后续合并并报告已合并与未合并的业务范围。

合并与合并后验证成功后，移除任务 worktree，并按仓库规则删除已合并的任务分支。自动合并不等于擅自发布上线；发布、部署和外部通知仍遵循项目原有授权与门禁。

## 失败与阻塞

测试失败、合并冲突、主工作树出现新改动、权限不足或保护分支门禁未通过时，不得宣称完成，也不得合并。合并失败后保留任务分支和 worktree，不删除现场；用业务语言说明尚未交付的能力、影响和下一步条件。
