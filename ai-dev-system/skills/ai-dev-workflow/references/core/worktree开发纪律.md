# Worktree 开发与自动合并纪律（core）

本纪律由个人版和团队版共同强制执行，不因 Lean 流程、单人项目、小改动或紧急修复而裁剪。

## 工作区隔离门

完成 mode 路由或初始化后，在任何文档或代码向项目落盘前，必须先进入独立 Git worktree。Lean Change Spec 也必须在 worktree 中创建，不得跳过隔离门直接修改主工作树。

1. 确认目标是 Git 仓库，并按仓库配置识别默认主分支；优先读取远端默认分支，不得写死为 `main` 或 `master`。
2. 检查主工作树是否干净。发现未提交改动时，不得替用户 stash、reset、提交或删除；中止进入开发并用业务语言说明已有工作需要先妥善保存。
3. 从最新主分支创建本次任务分支与独立 worktree。worktree 目录位置读取该仓库 CLAUDE.md（优先）或 AGENTS.md 的 `ai-dev-workflow` 标记块内的设置，未显式覆盖时默认落在仓库根的 `./.worktrees/`；每次创建前都从该设置读取，不得沿用上次会话记住的路径或凭空自定义。子目录名包含业务主题，避免与其他任务冲突。若 `.gitignore` 尚未忽略该 worktree 根目录，先幂等追加一行忽略规则，避免其内容污染主工作树的 `git status`。用户显式要求改到其它位置时，更新标记块内的设置后再创建。
4. 从此刻起，需求文档、spec、plan、report、代码、测试、生成文件、验证和提交全部在该 worktree 内完成。不得中途切回主工作树落盘。
5. 非 Git 仓库无法建立 worktree 时中止开发，不得降级为直接修改当前目录。

需求涉及多个仓库时，每个仓库建立独立任务分支和独立 worktree。先确认所有仓库都能进入隔离状态，再开始落盘；不得让多个仓库共用一个 worktree。

## 开发期间

- 每个 worktree 只承载一个业务任务，任务改动不得混入其他未完成工作。
- 按 plan 分段提交，确保任务分支可独立验证、可追溯。
- 主分支有新提交时，先把最新主分支合入任务分支并解决冲突，再重新运行受影响验证。
- 不得为了制造“干净状态”而处理主工作树里的用户改动；尤其不得自动 stash、reset、checkout 覆盖或删除未知文件。

## 完成与自动合并门

只有同时满足以下条件，才算“全部完成”：

- 已确认范围内的业务能力、文档和代码全部完成，没有未决业务问题或大架构确认项。
- 计划内测试、构建、静态检查和必要链路验证全部通过，并形成要求的报告。
- 任务分支的改动已提交，worktree 状态干净；不存在调试文件、临时产物或未解释变更。
- **代码评审门已通过**：三轴（规范/忠实/残留）报告齐全，P0 与 P1 已清零；替换清单逐条核销，该删的旧逻辑引用数为 0 且已删除（见 `代码评审纪律.md`）。
- **兼容取舍已有用户结论**：改变了既有可观察行为的每一条都有用户拍板记录（或显式声明"本次无兼容取舍"）。
- 已吸收最新主分支并重新验证，没有未解决冲突。
- 团队仓库要求的评审、持续集成、owner 或发布门禁全部通过。
- 多仓任务的所有仓库均已达到合并条件；任一仓未就绪时，不提前合并其他仓。

满足完成条件后，无需再次询问用户，自动合并任务分支到识别出的主分支：

- 本地或未保护仓库：在主工作树执行非快进合并，并运行最小的合并后验证。
- 有保护分支或 PR 规则的团队仓库：推送任务分支，创建或更新 PR，并在评审与持续集成通过后启用或执行平台自动合并。不得绕过保护分支、审批、CI 或 owner 规则强行写入主分支。
- 多仓任务：全部仓库先通过完成门，再按既定依赖顺序合并；任何一步失败，立即停止后续合并并报告已合并与未合并的业务范围。

合并与合并后验证成功后，移除任务 worktree，并按仓库规则删除已合并的任务分支。自动合并不等于擅自发布上线；发布、部署和外部通知仍遵循项目原有授权与门禁。

## 失败与阻塞

测试失败、合并冲突、主工作树出现新改动、权限不足或保护分支门禁未通过时，不得宣称完成，也不得合并。合并失败后保留任务分支和 worktree，不删除现场；用业务语言说明尚未交付的能力、影响和下一步条件。
