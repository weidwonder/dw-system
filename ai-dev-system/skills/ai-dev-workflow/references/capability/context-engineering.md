# Engineering Context 完整设计（权威位）

> 加载条件：**要新建或修改 `engineering-context/` 资产时**才读（建 registry / 写 card / 画场景蓝图 / 维护探针集 / 判新鲜度）。日常取事实只读同目录 `curated.md`，不必读本文。
> 权威位的完整设计。本文是 `curated.md` 背后的资产层设计。目标：**让 AI 在具体任务中读到正确代码、避开错误的相似旧代码，并能证明这层上下文"一直新鲜"。**
> 落地形态：项目内 `engineering-context/` 目录（markdown card）+ `ctx` CLI（查询）。用 `ctx init` 生成骨架。
> 目录：§0 为什么自建 ｜ §1 四层栈 ｜ §2 核心资产（registry / card / scene / glossary）｜ §3 真相方向铁律 ｜ §4 资产分层 ｜ §5 新鲜度 ｜ §6 Validation ｜ §7 当前可用程度 ｜ §8 要避免的误区

## 0. 为什么必须自建这一层

通用 skill kit 解决"流程骨架"，但解决不了"在我们这堆历史包袱重的仓库里，哪个才是当前线上权威实体"。AI 直接访问全仓会被相似命名、旧实现、重构中间产物、多仓副本误导。这一层就是**告诉 AI 去哪找、哪个权威、哪个是陷阱**的起始上下文。

> **一句话**：我们交付的不是"更多卡片"，而是"**可信的新鲜度**"。一张带来源、带 freshness、被门禁守护的卡片，价值高于十张无法证明新鲜的卡片；一个看起来权威但已过期的来源，比没有来源更危险。

## 1. 四层栈 + 横向防腐

| 层 | 内容 | 核心产物 |
|---|---|---|
| 1 Code Foundations | 让代码对 AI 可解释 | 仓库登记、接口登记（含版本）、废弃/中间产物标记、owner、测试入口 |
| 2 Code Sources of Truth | 让 AI 先访问权威实体 | **Capability/API 语义层**、调用图、业务场景卡片 |
| 3 Coding Context Skills | 约束 AI 的查询路径 | `ctx` 的 discover/get-card 路由、Bugfix/Test 流程 |
| 4 Validation | 验证上下文正确、修改可接受 | Dogfooding（产品验证）+ **Frozen Probe Set**（防腐检测）|
| 横向地基 | 防腐 & 新鲜度（"Loop Engineering"）| 资产分层、按权威面触发、code-rooted 生成、衰减告警 |

## 2. 两个核心资产

### 2.1 Capability Registry（`engineering-context/capability-registry.md`）
产品能力 → 权威代码实体的映射（**人工确认**）。字段见 `assets/context-layer/capability-registry.md` 模板：Capability / 业务含义 / 权威仓库 / 权威接口(含版本) / 废弃或中间产物替代 / 兼容窗口 / owner / 测试入口 / freshness / 理由链。

### 2.2 Codebase Card（`engineering-context/cards/<repo>.md`）
每仓一张：职责、对外接口、上下游、废弃标记、测试入口。**只放人工判断**——机器能自己算出来的事实（调用图、最后修改、DB schema）MUST NOT 抄进 card，需要时现查。模板见 `assets/context-layer/card.md`。

### 2.3 业务场景蓝图（`engineering-context/scenes/<场景>.md`）★ scene 的生产端
card 是"单仓视角"，scene 蓝图是"端到端视角"——`ctx find-scenes` 查的就是它。**它不是查询出来的，是生产出来的**：以一个业务场景为粒度，**从入口线索出发闭合追踪每一条跨服务调用链**，产出入口清单、跨服务调用链明细、一页式时序（project.Class 粒度）、核心类方法总览、动态/配置化接口核对，每条标 ✅已确认/⏳待确认/⛔未生效。模板见 `assets/context-layer/scene-blueprint.md`。

> **真相方向同样是"代码→蓝图"**：读入口顺调用链追到底，PRD 仅作 scope。没有 scene 蓝图，业务全景门限（`curated.md` §3）就没有东西可查——所以高频跨服务场景应优先补蓝图。这套"以 project 为粒度闭合追踪调用链、按代码证据标三态"的方法，未启用任何能力位的项目调试老系统链路也用得上。

### 2.4 领域词汇表（`engineering-context/glossary.md`，辅助资产）

**纯词汇表，禁实现细节**：术语 / 业务定义 / 同义词与弃用叫法 / 易混淆项。分工：**glossary 管说法一致，card 管事实权威，registry 管能力落点**——词汇表条目里出现表名/接口/类名即为越界，移去 card。价值：人与 AI 对同一概念用同一个词，堵住"同一实体多种叫法"这一相似陷阱的源头；同义词列供 `synonyms.md`（search-semantic 查询扩展）参考。模板见 `assets/context-layer/glossary.md`，`ctx init` 生成骨架。属"耐用的人工判断"层（§4），低频人工维护。

## 3. 真相方向铁律（最重要）

**card 的事实以合入后的源码为准**，通过读真实 diff（本次发布 vs 上一基线）派生。**PRD/Spec 只用于两件事**：

1. **扫描范围约束**——告诉生成者"这次该看哪块"。
2. **业务语境补充**——让"业务含义"字段更准。

> ❌ **绝不能从 PRD 生成 card 事实**。PRD 描述**意图**，意图常与已落地的**事实**背离（典型："PRD 说可复用，查代码发现不可复用"）。从 PRD 生卡会把这种偏差固化进权威层，正好制造我们要消灭的失败模式。
> ✅ PRD 意图与代码事实的差异，应沉淀为**人工复核队列**——这是只属于人的判断点。

**AI 可以草拟** card、接口说明、能力映射；但**"哪个接口权威、哪个是中间产物、哪个旧实现不能用、兼容切点在哪"必须人确认**。

## 4. 资产分层：只人工维护第一类

| 类型 | 示例 | owner |
|---|---|---|
| **耐用的人工判断**（低频、高价值、代码推不出） | 哪个实现是线上事实、废弃意图、中间产物认定、兼容切点、业务含义、"这个相似项是陷阱" | 人，带门禁 |
| **机器可派生的事实**（随时刷新，禁止手改） | 调用图、依赖边、who-calls-this、最后修改时间、测试入口、DB schema | 工具，自动 |

> 手工维护"机器可派生"那一列 = 主动制造腐化。

## 5. 新鲜度：按"权威面"触发，而非变更大小

最伤的权威/版本变更恰恰是小提交（一次 3 行的路由切换 V1→V2、一次翻转废弃标记）。所以：

- **不以变更行数为轴**。2000 行内部功能不碰接口可不刷；3 行翻转废弃标记/路由版本**必须**刷新权威层。
- **触发条件 = 是否触碰 Authority Surface**：canonical 接口签名、废弃注解、路由/配置、DB schema、兼容窗口。
- **默认节奏绑发布周期**；**hotfix 保留人工研判**，逐例判断是否要改上下文层。
- **理由保鲜**：每条废弃/权威判定挂一条指回其"诞生压力"的理由链（当初解决的事故/重构/bug）；理由失效则该判定进入退役复核，而不是被永远供奉。

## 6. Validation：两类不同的仪器

| 仪器 | 回答 | 角色 |
|---|---|---|
| **Dogfooding** | "这套方法能不能跑通？" | 产品级验证，必要 |
| **Frozen Probe Set** | "相比上个周期，它有没有变差？" | 防腐检测器，充分性所需 |

**为什么真实项目不能当回归基线**：每个项目都不同，变量无法 held-constant，永远分不清一次糟糕结果是"卡片腐化"还是"这项目本来就难"。所以另建一个**冻结、可重复、每发布周期重跑**的小评测集（Frozen Probe Set）作衰减告警。种子题来自真实歧义案例（见 `assets/context-layer/probe-set.md`）。

**门禁自检**（防止"永远全绿"的假门禁）：每次跑全量探针前，先注入一个已知必然失败的合成样本，断言门禁能抓到；抓不到 → 门禁失效，流水线红。伪码：
```
runProbeGate():
  plantKnownStaleEntity()        # 构造一个必然该被判错的样本
  assert gate(sample) == FAIL    # 抓不到 → 门禁失效
  return gate(realProbeSet)      # 自检通过才跑真实探针
```

**棘轮（ratchet）**：把暂时容忍的腐化债登记成一份基线清单（过期实体、未清旧标记、批准的例外，各带日期/责任人/复查时间），立一条机器规则：**这份清单只许变短**。CI 比对：出现清单外新腐化 → 失败；清单内已不再腐化 → 也失败，强制删除该条。单调递减是极少数能被机器验证的"正在变好"。

**探针自防腐**：探针的"已知正确答案"本身也是权威事实，会过期——**拿过期真相打分比没有评测更糟**（绿着脸掩盖上下文已腐化）。所以探针集必须与 §5 的权威面触发**共用同一套刷新机制**：每题用 `authority_refs` 挂到它依赖的权威面，被挂权威面一变更，对应探针自动置 `needs-reconfirm`、暂不计入通过率，等人重新确认后再恢复计分（详见 `assets/context-layer/probe-set.md`）。门禁报告须显式列出 `needs-reconfirm` 题数。

## 7. 当前可用程度（诚实标注）

| 组件 | 状态 | 说明 |
|---|---|---|
| capability-registry / card / scene-blueprint | ✅ 模板 + 指南 | 真实内容由团队按指南填；高频跨服务场景优先补 scene 蓝图 |
| `ctx` discover/get-card/find-scenes/list-services/init | ✅ 可运行骨架 | 读本地 markdown card，关键词匹配 |
| `ctx search-semantic`（语义兜底检索）| ✅ 可运行（零依赖本地向量）| 字符 bigram 余弦 + 可选 synonyms；结果带 freshness/权威标记，`--as-of` 启用过期降权。神经 embedding 后端为可选升级 |
| `ctx probe`（Frozen Probe Set 门禁）| ✅ 可运行 | 机器可判题型 + 门禁自检 + 棘轮 + 衰减报告；`--json` 退出码供 CI |
| 新鲜度按权威面触发接入 CI | ⏳ 文档 | 棘轮/自检已在 `ctx probe` 落地；"按权威面自动触发重扫"仍需接 CI hook |

## 8. 要避免的误区

- ❌ 让 AI 直接访问全仓 → 先走 `ctx` 路由。
- ❌ 从 PRD 生 card 事实 → 事实以代码为准，PRD 仅作 scope。
- ❌ 按变更大小决定是否刷卡 → 按是否碰权威面。
- ❌ 用真实项目当回归基线 → 另建冻结 Probe Set。
- ❌ 默认门禁全绿就没问题 → 门禁自检 + 棘轮。
