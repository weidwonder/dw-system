# 协作面 = team

> 加载条件：存在其他人类协作方时加载。
> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD / MAY。
> 本文只管**因为有别人**才存在的约定：谁拍板、跟谁对齐、结论怎么落。与项目有多少代码事实资产无关——那是 `capability/` 的事。

## 1. 角色与澄清分工

- **业务目标、规则、边界 → MUST 找业务负责人确认**；**详细程序设计 → 工程侧内部决策与评审**。
- **MUST NOT 要求业务用户理解技术方案后拍板。** 向业务方陈述时用业务语言（`core/用户沟通纪律.md`），把技术取舍翻译成业务影响再问。
- 每个仓库有明确 **owner**；**改动别人仓库前 MUST 先对齐 owner**——对齐内容至少含：要改什么、为什么、对该仓对外契约的影响、合并时机。

## 2. 评审会

- 跨 ≥3 仓的需求，**Step 2 出 Overview 后 MUST 开评审会**。先用"用户确认摘要（业务语言）"跟业务方确认大架构，再由工程侧内部评审详细设计。
- **评审结论 MUST 回写进 Overview 的"已定决策"表**，避免每份 spec 重新吵。
- 跨 <3 仓的需求 MAY 只做异步评审（把 Overview 或 spec 发给相关 owner 确认），但结论同样 MUST 回写。

## 3. 兼容取舍由业务方拍板

兼容取舍确认门（`00-流程总纲.md` 四道门之二）在本协作面下的拍板人是**业务方**，不是工程侧、更不是 AI：

- **AI MUST NOT 默认兼容**，也 MUST NOT 自行决定不兼容。
- spec 定稿前 MUST 把被改变的既有行为逐条列出（谁受影响、影响多久、三个选项 + 推荐），用业务语言送业务方逐条拍板。
- 拍板结论 MUST 落进 spec 的兼容取舍节；保留项 MUST 带理由与到期日，并登记进替换清单。

## 4. PR 平台动作

合并**方式**由标记块的 `merge-gate` 字段决定（见 `core/worktree开发纪律.md`），不由本文决定。本节只规定 `merge-gate="pr"` 时**因为有人审**而额外要做的事：

- **开 PR 前 MUST 先过代码评审门**（见 `core/代码评审纪律.md`）。它是**地板不是天花板**：把 AI 能自查出来的问题挡在 PR 之前，让人审的注意力留给业务正确性与架构取舍，**MUST NOT 用它替代人审**。评审报告结论 SHOULD 附进 PR 描述。
- PR 描述 MUST 引用对应 spec / plan 任务号，并附影响范围说明（为什么没扩大）。
- 团队 SHOULD 把死代码检查（`knip` / `vulture` / `staticcheck -checks U1000` 等）挂进 PR gate，作为替换清单核销的自动补充；工具链不具备时清单核销照做。
- 保护分支仓库 MUST 在审批与 CI 全部通过后才启用平台自动合并；**MUST NOT 绕过保护分支直接写主分支**。

> PR 的**粒度**要求（一个 coding plan 任务对应一个小而可 review 的 PR，约 3–8 文件）与人数无关——agent 单次可产出 2000 行，粒度限制是人类唯一的审查窗口。该要求在 `core/` 常驻，两个协作面都适用。

## 5. 多仓合并顺序协商

- 多仓需求全部就绪后，MUST 按依赖顺序合并——**顺序本身**的推导规则在 `core/`（谁的契约先落地谁先合）。
- 本协作面额外要求：**合并顺序 MUST 与各仓 owner 协商确认后再执行**，并把确认结果写进 Overview 或 coding plan 的完成清单；跨 owner 的合并窗口 SHOULD 提前约定，MUST NOT 单方面按自己的时间表推进。

## 6. 与其它分册的边界

| 想找的东西 | 在哪 |
|---|---|
| 合并走本地非快进合并还是 PR | `core/worktree开发纪律.md`（按 `merge-gate`） |
| 三轴代码评审怎么派、判什么 | `core/代码评审纪律.md` |
| 按边界拆 spec / 垂直切片拆 Issue | `core/00-流程总纲.md` |
| 文档目录、生命周期结算、索引分层 | `core/文档治理.md` |
| 哪个是权威实现、怎么查代码事实 | `capability/curated.md`、`capability/graph.md`（按探测启用） |

## 一句话

协作面 = team 意味着**有人要对齐、有人要拍板、有人要审**：业务方拍兼容、owner 拍跨仓改动、人审拍最终 PR，AI 的自查只是这三者之前的地板。
