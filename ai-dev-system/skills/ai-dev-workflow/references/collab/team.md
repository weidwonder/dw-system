# 协作面 = team

> 加载条件：存在其他人类协作方。
> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD / MAY。
> 本文只管**因为有别人**才存在的约定：谁拍板、跟谁对齐、结论怎么落。

## 1. 角色与澄清分工

- **业务目标、规则、边界 → MUST 找业务负责人确认**；**详细程序设计 → 工程侧内部决策与评审**。
- **MUST NOT 要求业务用户理解技术方案后拍板。** 向业务方用业务语言陈述，技术取舍翻译成业务影响（`core/用户沟通纪律.md`）。
- 每仓有明确 **owner**；**改别人的仓前 MUST 先对齐 owner**，至少含：改什么、为什么、对该仓对外契约的影响、合并时机。

## 2. 评审会

- 跨 ≥3 仓，**Step 2 出 Overview 后 MUST 开评审会**：先用"用户确认摘要（业务语言）"与业务方确认大架构，再工程侧内部评审详细设计。
- **评审结论 MUST 回写进 Overview 的"已定决策"表**。
- 跨 <3 仓 MAY 只做异步评审（Overview 或 spec 发给相关 owner 确认），结论同样 MUST 回写。

## 3. 兼容取舍由业务方拍板

兼容取舍确认门（`00-流程总纲.md` §兼容取舍确认门）的拍板人是**业务方**，不是工程侧或 AI：

- **AI MUST NOT 默认兼容**，也 MUST NOT 自行决定不兼容。
- spec 定稿前 MUST 把被改变的既有行为逐条列出（谁受影响、影响多久、三个选项 + 推荐），用业务语言送业务方逐条拍板。
- 拍板结论 MUST 落进 spec 的兼容取舍节；保留项 MUST 带理由与到期日，并登记进替换清单。

## 4. PR 平台动作

合并**方式**由 `merge-gate` 决定；`merge-gate="pr"` 本身要做的事**全部在 `core/` 常驻、与协作面无关**（`core/worktree开发纪律.md` §完成与自动合并门、`core/代码评审纪律.md` §处置），**本文 MUST NOT 复述，连列举都不要**。本节只列**因为有别人**而多出来的事：

- **指派评审人**：PR MUST 指到具体的人（受影响仓 owner 优先），MUST NOT 只开 PR 不指人。
- **合并窗口 SHOULD 提前与 owner 约定**（尤其影响对方对外契约时）；对方未确认时 MUST NOT 单方面推进。
- **人审提出的结论 MUST 回写**到 spec 或 Overview 的"已定决策"表。
- **本次补/改了哪张卡片 SHOULD 在 PR 描述或合并说明里点名**（`engineering-context/cards/<repo>.md` 的哪个域，`core/代码事实纪律.md` §7 第 4 条）。**MUST NOT 因等 owner 复核就把已知有错的卡片留在原样，也 MUST NOT 因此挂起任务**：先就地改正并更新确认时间，再请 owner 事后复核；owner 有异议时改的是卡片内容，不是撤回卡片。

## 5. 多仓合并顺序协商

- 多仓需求全部就绪后 MUST 按依赖顺序合并；**顺序本身**的规则在 `core/`（谁的契约先落地谁先合）。
- **合并顺序 MUST 与各仓 owner 协商确认后再执行**，结果写进 Overview 或 coding plan 的完成清单；跨 owner 的窗口 SHOULD 提前约定，MUST NOT 单方面推进。

## 6. 与其它分册的边界

| 想找的东西 | 在哪 |
|---|---|
| 合并走本地还是 PR | `core/worktree开发纪律.md`（按 `merge-gate`） |
| 代码评审逐轴怎么派、判什么（§四条轴）| `core/代码评审纪律.md` |
| 按边界拆 spec / 垂直切片拆 Issue | `core/00-流程总纲.md` |
| 文档目录、生命周期结算、索引分层 | `core/文档治理.md` |
| 哪个是权威实现、怎么查代码事实、卡片怎么补 | `core/代码事实纪律.md`（无条件常驻）；结构检索探测到代码图谱时走 `capability/graph.md` |

## 一句话

业务方拍兼容、owner 拍跨仓改动、人审拍最终 PR；AI 自查只是地板。
