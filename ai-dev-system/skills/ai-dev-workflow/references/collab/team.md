# 协作面 = team

> 加载条件：存在其他人类协作方时加载。
> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD / MAY。
> 本文只管**因为有别人**才存在的约定：谁拍板、跟谁对齐、结论怎么落。代码事实怎么取、卡片什么时候补与本文无关——那由无条件常驻的 `core/代码事实纪律.md` 定义，人多人少都一样。

## 1. 角色与澄清分工

- **业务目标、规则、边界 → MUST 找业务负责人确认**；**详细程序设计 → 工程侧内部决策与评审**。
- **MUST NOT 要求业务用户理解技术方案后拍板。** 向业务方陈述时用业务语言（`core/用户沟通纪律.md`），把技术取舍翻译成业务影响再问。
- 每个仓库有明确 **owner**；**改动别人仓库前 MUST 先对齐 owner**——对齐内容至少含：要改什么、为什么、对该仓对外契约的影响、合并时机。

## 2. 评审会

- 跨 ≥3 仓的需求，**Step 2 出 Overview 后 MUST 开评审会**。先用"用户确认摘要（业务语言）"跟业务方确认大架构，再由工程侧内部评审详细设计。
- **评审结论 MUST 回写进 Overview 的"已定决策"表**，避免每份 spec 重新吵。
- 跨 <3 仓的需求 MAY 只做异步评审（把 Overview 或 spec 发给相关 owner 确认），但结论同样 MUST 回写。

## 3. 兼容取舍由业务方拍板

兼容取舍确认门（`00-流程总纲.md` 四道门之二）在本协作面下的拍板人是**业务方**，不是工程侧、更不是 AI：

- **AI MUST NOT 默认兼容**，也 MUST NOT 自行决定不兼容。
- spec 定稿前 MUST 把被改变的既有行为逐条列出（谁受影响、影响多久、三个选项 + 推荐），用业务语言送业务方逐条拍板。
- 拍板结论 MUST 落进 spec 的兼容取舍节；保留项 MUST 带理由与到期日，并登记进替换清单。

## 4. PR 平台动作

合并**方式**由标记块的 `merge-gate` 字段决定（见 `core/worktree开发纪律.md`），不由本文决定。

**先划清边界**：`merge-gate="pr"` 本身要做的事**全部在 `core/` 常驻，与协作面无关**——判据见 `core/代码评审纪律.md` §处置 与 `core/worktree开发纪律.md` §完成与自动合并门，**本文 MUST NOT 复述，连列举都不要**（列举一样会漂移）。理由：`merge-gate` 与 `collaboration` 是两个独立字段，一个人的开源项目照样走 PR；把那几条写在只有 `collaboration="team"` 才加载的本文里，solo + pr 的项目就读不到了。

本节只规定**因为有别的人**而额外要做的事：

- **指派评审人**：PR MUST 指到具体的人（受影响仓的 owner 优先），MUST NOT 只开 PR 不指人等着谁来看。
- **合并窗口 SHOULD 提前与 owner 约定**，尤其是会影响对方仓库对外契约的改动；对方未确认时 MUST NOT 单方面按自己的时间表推进。
- **人审提出的结论 MUST 回写**到 spec 或 Overview 的"已定决策"表——口头达成的共识不落文档，等于下一个零上下文 agent 拿不到。
- **本次补了或改了哪张卡片 SHOULD 在 PR 描述 / 合并说明里点名**（`engineering-context/cards/<repo>.md` 的哪个域），让该仓 owner 有机会复核（`core/代码事实纪律.md` §7 第 4 条）。**但 MUST NOT 因为等 owner 复核就把已知有错的卡片留在原样，也 MUST NOT 因此挂起本次任务**——错的卡片比没有卡片更危险：先就地改正并更新确认时间，再请 owner 事后复核；owner 认为写法有问题，改的是卡片内容，不是把卡片撤回。

## 5. 多仓合并顺序协商

- 多仓需求全部就绪后，MUST 按依赖顺序合并——**顺序本身**的推导规则在 `core/`（谁的契约先落地谁先合）。
- 本协作面额外要求：**合并顺序 MUST 与各仓 owner 协商确认后再执行**，并把确认结果写进 Overview 或 coding plan 的完成清单；跨 owner 的合并窗口 SHOULD 提前约定，MUST NOT 单方面按自己的时间表推进。

## 6. 与其它分册的边界

| 想找的东西 | 在哪 |
|---|---|
| 合并走本地非快进合并还是 PR | `core/worktree开发纪律.md`（按 `merge-gate`） |
| 三轴代码评审怎么派、判什么 | `core/代码评审纪律.md` |
| 按边界拆 spec / 垂直切片拆 Issue | `core/00-流程总纲.md` |
| 文档目录、生命周期结算、索引分层 | `core/文档治理.md` |
| 哪个是权威实现、怎么查代码事实、卡片怎么补 | `core/代码事实纪律.md`（无条件常驻）；结构检索在探测到代码图谱时走 `capability/graph.md` |

## 一句话

协作面 = team 意味着**有人要对齐、有人要拍板、有人要审**：业务方拍兼容、owner 拍跨仓改动、人审拍最终 PR，AI 的自查只是这三者之前的地板。
