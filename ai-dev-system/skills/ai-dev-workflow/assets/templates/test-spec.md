# 【repo】_测试方案 — 【功能名】

> 只专注当前代码仓库涉及的部分（功能代码已开发完成）。配合 PRD / Overview / spec / coding plan。
> 输出：`docs/spec/<repo>-<feature>-test-spec.md`。
> **风险驱动，不是模板枚举**：不要机械按"正向/异常/边界/权限"铺用例；先识别高风险点，再设计测试。方案要**可实施**——给到 API 调用模型和数据构造方案，能直接落成测试代码，而不是只写"业务场景+测试意图"。

## 纪律（贯穿全文）

- **输入权威等级**：PRD / PRD 更新说明 > 后端技术文档 / spec > 项目级实施方案（coding plan）> 当前实现事实。实施方案只作"风险增强上下文"，**不得用它覆盖业务规则或接口契约**；冲突时以高等级为准，并把冲突列入 §10。
- **"待确认"防脑补**：后端文档没定义的字段/错误码/鉴权方式/副作用/表结构/唯一键/枚举/清理方式，**一律标"待确认"，禁止自行脑补**。团队版能查 card 的先查（附 cite），查不到的仍标待确认。

## 2. 高风险点分析 + 优先级
先找出最该测的地方，按 影响×可能性 排序，把测试火力对准高风险点（而非平均用力）。**逐条对照下面这份隐蔽缺陷清单**，命中的登进表：

- [ ] PRD 与后端文档不一致
- [ ] 状态流转遗漏 / 非法状态可操作
- [ ] 接口之间数据传递错误
- [ ] 用户/角色/租户/资源归属越权
- [ ] 幂等 / 重复提交 / 重试导致数据重复或状态错乱
- [ ] 并发下库存/余额/额度/次数等竞争
- [ ] 异步任务/回调/消息延迟导致最终状态不一致
- [ ] 删除/取消/撤回/失败/超时后的二次操作
- [ ] 部分成功/部分失败后的补偿或回滚
- [ ] 前端不可见但接口可直接调用的非法路径
- [ ] 历史数据/脏数据/边界配置/开关配置下的异常行为

## 12. CI 门禁分层（团队版，按需）
把测试挂到不同 CI 阶段，快的守 PR、慢的守发布：
| 阶段 | 跑什么 | 阻断条件 |
|---|---|---|
| PR gate | 单元 + 快集成 + lint | 失败即挡合并；P0/P1 用例必过 |
| nightly | 全集成 + 链路 + 慢 NFR | 失败告警，next-day 修 |
| pre-release | 全量 + 模拟链路 + eval 门（含 AI）| 失败阻断发布 |

> **flaky 隔离**：偶发失败的用例先隔离进 quarantine 清单（带责任人+复查日期，只许变短），不许长期一直红/一直被忽略——否则门禁失去意义。
