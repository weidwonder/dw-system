# 升级到 2.2.0（自 2.1.0）

## 结论

**PRD 成稿后、写文件之前，多了一道复核门。** `ai-prd` 现在会派子代理把稿子复核两遍再来找你确认：一遍查这份 PRD **自己跟自己有没有打架**，一遍查它**跟你现有系统有没有冲突**。

此前 PRD 的唯一准出是一份自检清单，它照着模板骨架查"节缺没缺、验收能不能勾验"，**从不拿 PRD 去跟现有系统比**。于是这几类问题一路穿到编码阶段才显形：要做的能力系统里其实已经有了、新规则与某条已生效的业务规则互斥、PRD 依赖的能力其实已废弃、写着"不改 X"但要做的事必然波及 X。而且自检是写稿的那个会话自己做的——现状节本来就是它查的，让它验自己等于没验。

## 需要的动作

**什么都不用做。** 重跑一次安装器升级 skill 即可，没有新配置、没有新问题要回答、没有目录要建。

下次用 `ai-prd` 写 PRD 时，你会在最后的确认环节多看到一段东西：**复核查出、需要你拍板的冲突清单**。每条会写清"系统现在是什么样、PRD 想要什么样、两边各自的业务后果"，由你选，AI 不替你选。

## 代价（说在明处）

成稿会**多一轮往返**（变更 PRD / 整品 PRD 派 2 个子代理，单点小改动的轻量 PRD 只派 1 个）。换掉的是下游返工：需求阶段发现"这功能已经有了"，代价是改一段话；编码阶段发现，代价是整块重做。

这道门**不提供跳过开关**，也不因为"就我一个人开发"而裁剪——恰恰相反，一个人写 PRD 时没有同事会喊出"这个我们早就有了"，子代理是这份稿子唯一的第三方视角。

## 其它变化

- **既有 PRD 不受影响**：复核门只在新的成稿流程里跑，已经落盘的 PRD 不会被回头复核，frontmatter 与文件命名一律不变。
- **组稿步骤编号往后挪了一位**（落盘确认门从第 4 步变第 5 步）。这只影响 skill 内部的交叉引用，你的项目里没有任何东西需要跟着改。
- 4 批提问、三类模板、UI 原型要求、PRD 生命周期与归档、`ai-dev-workflow` 侧的十步流程与四道门，全部无变化。
