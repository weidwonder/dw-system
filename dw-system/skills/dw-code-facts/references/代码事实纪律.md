# 代码事实纪律

> 任何项目、两条路径都适用。各小节什么时候读，见本 skill 的 `SKILL.md`〈读取条件〉。按 RFC 2119 解释 MUST / MUST NOT / SHOULD / MAY。
> 它答「**信哪个**」——同一能力有多处实现时哪一处权威；正交的「**找得到吗**」（检索）由 `graph.md` 负责，**探测到索引才加载**（对照见 §1 表）。
> 资产层完整设计（registry 字段 / 场景蓝图 / 探针集）见 `engineering-context设计.md`，**要动资产结构时才读**；日常补一张卡片只需 §4。

## 0. 一句话规矩

> **要用某个模块的事实，先查卡片；没有卡片就读源码，读完把卡片补上。**

## 1. 卡片是地基，不是升级项

装了本体系的项目**一律**维护 `engineering-context/`——registry（能力→权威实现）+ cards（每仓一张事实卡）；不分项目大小、不分协作面、不由任何探测开关决定。

**初始化只建骨架**（`dw-workflow` 的 `init-初始化.md` 第 5b 步跑 `ctx init`）：只有模板占位、没有真实数据行，**这是正常起步状态**，MUST NOT 因此告警、提示用户、或判定这层不可用；内容按 §4 边干活边补齐。

**MUST NOT 因为 registry 里还没有条目就退回裸 grep 找权威实体**——没有条目只意味着"还没人读过这块代码并固化结论"，处置是读源码 + 补卡（§4）。

**MUST NOT 反过来把它当准入门槛**：卡片没建齐 MUST NOT 阻断流程、降级交付或拒绝干活；缺卡按 §4 当场补，任务照常推进。

| | 本文（代码事实层） | 代码图谱（`graph.md`）|
|---|---|---|
| 答什么 | **信哪个**（消歧） | **找得到吗**（检索） |
| 事实性质 / 载体 | **人工确认的权威口径**，带 cite 与确认时间；`engineering-context/`：registry → cards → scenes → probe-set | **现状代码事实**，随文件变更同步；codegraph 索引 `.codegraph/codegraph.db` |
| 是否可选 | **必备**，缺哪块补哪块 | **可选**，探测到索引才启用，查不了就外包子代理 |

两者 **MUST NOT 互相替代**：图谱列出 v1 与 v2 两处支付实现却不知哪个权威，卡片知道权威却不保证覆盖每个符号与调用边。冲突时**以卡片为准**，并按 §7 第 4 条就地修正卡片。

## 2. 调用方式

| 情况 | 怎么做 |
|---|---|
| 正常 | 安装器已把 `ctx` 链接成全局命令，直接 `ctx <命令>`（下文简写 `ctx`）|
| `ctx` 命令找不到 | **绝不等于这一层不可用**——CLI 本体随本 skill 落盘，MUST 改用 `node <本skill根目录>/scripts/ctx/src/cli.js <命令>`；想恢复全局命令：`cd <本skill根目录>/scripts/ctx && npm link` |
| `<本skill根目录>` 取哪份 | 你加载的这份 `dw-code-facts` 的 `SKILL.md` 所在目录。两份逐字节相同：项目级安装是 Claude Code `.claude/skills/dw-code-facts/`、Codex `.agents/skills/dw-code-facts/`，全局安装是 `~/.claude/skills/dw-code-facts/`、`~/.codex/skills/dw-code-facts/`，任选一份，拿不准先试你自己加载 skill 的那侧；**MUST NOT 写死其中一份**——写死 `.claude/` 那份在 Codex 侧就是错路径 |
| 在哪跑 | MUST 在**项目根**（`ctx` 默认读 `<cwd>/engineering-context`），或用 `--dir <项目根>/engineering-context` 显式指定；子目录里跑会静默返回空且退出码为 0，把"有卡片"误判成"没卡片" |
| 术语说法对不上 | 查 `engineering-context/glossary.md`：glossary 管说法一致、card 管事实权威、registry 管能力落点；"同一实体多种叫法"造成误会时补词条（`engineering-context设计.md` §2.4）|

**任何情况下都 MUST NOT 因为找不到 `ctx` 命令就退回 grep 源码。** 命令清单与输出格式见 `scripts/ctx/README.md`。

## 3. 取事实的固定顺序

凡涉及"这个能力对应哪个仓库/接口""跨服务影响面""哪个是权威实现"的问题，MUST 先用 `ctx`，MUST NOT 直接 grep 旧代码。

**★ 业务全景门限（排序铁律）**：**除非用户明确把任务限定到某一个具体 repo / 服务 / 代码路径**，否则**第一步 MUST 先 `ctx find-scenes <2–5 个高置信关键词：需求名 / 业务入口 / 核心动作>`** 取端到端全景再收窄——跳过全景直钻单个 card，最常见的失败就是漏掉链路上的其它服务。

```bash
ctx find-scenes 作业辅导 错题 重练      # 未限定单仓时先跑：端到端全景
ctx discover "给作业辅导加错题重练入口"  # 意图 → card 清单 + out-of-scope 警告
ctx get-card <repo> [域]                 # 收窄后取某仓 Codebase Card
ctx list-services                        # 已登记仓库/能力
ctx search-semantic "<自然语言>"         # discover 未命中时的兜底
```

**`find-scenes` 无命中不是错误**（起步态 `scenes/` 本就空，必然返回空）：MUST NOT 阻断、MUST NOT 反复重试，改走 `discover` + `get-card`；两者也收不窄时进 §4。本次**确实跨服务**（≥2 个 registry 登记的权威仓库）时 SHOULD 顺手按 `engineering-context设计.md` §2.3 补一张场景蓝图。

> `find-scenes` 返回**场景蓝图指针**（scene 名 + 命中分 + 路径），不直接给"涉及哪些服务"；从蓝图正文读到 / 推断出的服务都是**推断**，MUST 逐个用 `ctx get-card` 核实到权威 card 才能当事实用。
> `discover` 给出的 **out-of-scope 警告**（哪些是废弃/中间产物、别当权威用）MUST 抄进 Step 1〈既有系统清单〉，并在 Step 2 的 A 核查里逐条确认（Lean 的落点：`dw-workflow` 的 `路径-lean.md` §顺序 第 4 行写的那份〈既有系统清单〉；Lean 没有 A 核查）。

## 4. 没有卡片时怎么办（本纪律的核心）

`ctx` 查不到，只意味着**这个模块的卡片还没建**。MUST 按序处置，**三步一次做完，MUST NOT 只做前两步**：

1. **读源码建立事实。** 有代码图谱 → 走 `graph.md`；没有 → 按 `dw-workflow` 的 `上下文卫生.md` 规则 4 把重探索**外包给子代理**，主会话只收结论。**MUST NOT 在主会话裸 grep 全仓**（裸 grep = 没有收窄目标、没有外包、直接把命中内容读进主上下文）。
2. **把读到的权威事实补成卡片**（最小形态见 §4.1），随本次任务分支提交。
3. 补完的卡片即成为后续事实来源；本次任务后续引用它时照常带 cite（§5）。

**补卡是本次任务的一部分，MUST NOT 顺延**——顺延等于成果只留在本次会话里，下一个零上下文 agent 要把同样的路重走一遍。

**MUST NOT 把"读了源码"本身当成交付**：读完不落卡，下次唤起 `ctx` 依然查不到，这条纪律等于没执行过。

### 4.1 补一张卡片的最小形态

卡片有两种，各有一份模板（`assets/context-layer/card-map.md`、`card-domain.md`）：

| 卡 | 路径 | 写什么 |
|---|---|---|
| **仓库地图卡** | `engineering-context/cards/<repo>.md` | 仓库职责一句话 + 〈业务域地图〉（域 → 一句话 → 域卡路径）；跨域陷阱与对外入口总览按需 |
| **业务域卡** | `engineering-context/cards/<repo>/<域>.md` | 一个业务域的权威实现、对外接口、陷阱 |

**新事实先找所属的域**：读地图卡的〈业务域地图〉，有对应的域就写进那张域卡；找不到才新开域，**新开域 MUST 先改地图卡再建域卡文件**。域怎么切只写在地图卡里，并与需求真相源 `docs/requirements/` 的子模块用同一套切法——两套切法并存之后，没人能判断一条事实该往哪找。MUST NOT 按"这次任务做了什么"新开一节：那是变更流水，不是业务域。

域卡最小内容四项，小节名固定、MUST NOT 自造：

| 小节 | 写什么 |
|---|---|
| 职责 | 这个业务域负责什么业务能力，一句话 |
| 权威实现与对外接口 | 本次真正读到并核对过的、**有判断要下**的条目：哪个是权威、哪个入口才是对外承诺、调用它有什么约束；每条带 cite |
| 陷阱项 | 相似但不该用的旧实现；确实没有就写 `无` |
| 确认 | 一行：本次读源码的日期 + 读过的范围 |

可选小节只有〈测试入口〉〈日志与排障〉〈端侧补充〉。同时在 `engineering-context/capability-registry.md` 追加一行（三列即可用）：`Capability` / `权威实现` / `陷阱项（废弃或中间产物）`，每格一句话加指向域卡的指针，展开只在卡里。**第三列 MUST NOT 省**——它是最小 schema 里唯一的防误用装置，省掉就挡不住"改错了那个"。

**只写现状。** MUST NOT 出现带日期的小节、"本次核实"式的累积清单、版本号流水；〈确认〉只有一行，更新时改写，MUST NOT 追加。事故经过去 bug 修复历史，取舍来历去决策记录，对外变化去变更日志。

**〈陷阱项〉只放陷阱。** `ctx` 把本节逐行当成误用警告；"仍在维护""非废弃"这类话写进来会变成假警告。

**MUST NOT 为凑满模板把没核对过的字段填上**：没读到就不写——**看起来权威却已过期的来源比没有来源更危险**（`engineering-context设计.md` §0）。

**MUST NOT 把机器可派生的事实抄进卡片**（逐个方法的签名、调用图、依赖清单、最后修改时间、DB schema 全文）——随时可现查，手抄即制造腐化（`engineering-context设计.md` §4）。卡片只放人工判断。

写完或改完卡片 MUST 跑 `ctx lint-cards`（规则与基线见 `scripts/ctx/README.md` §lint-cards）；新增违规 MUST 当场修掉。

### 4.2 事实不丢，体积有上限

- **事实不丢**：MUST NOT 因为"这次没用上"删除既有卡片里仍成立的事实。
- 既有卡片与源码不符 → **就地修正并更新〈确认〉**，MUST NOT 保留两份互相矛盾的说法，也 MUST NOT 只在本次上下文里绕过它继续干活。
- 卡片记录的实现被本次改动彻底删除 → 移进该域卡的**陷阱项**（写清"已删除"），MUST NOT 直接抹掉——后来的 agent 要知道这名字曾存在、现在不该再用。
- **体积上限**：地图卡 8,000 字节、域卡 16,000 字节、registry 单格 300 字节。超限按 `dw-workflow` 入口〈两条总纲〉的顺序处置：先把来历搬到它的家，再把域拆细（先改地图卡）；"事实不丢"MUST NOT 被读成"卡片可以无限长"。
- **存量的单文件卡片**（一张卡里按 `## <域>` 分段）仍读得出来：`ctx get-card <repo> <域>` 找不到域卡文件时读地图卡里的同名小节。碰到哪个域就把哪个域搬成域卡，MUST NOT 为了搬家而搬家地一次重写整张卡。存量违规由 `ctx lint-cards --init-baseline` 记入基线，只许减不许增。

## 5. cite 纪律

**每条来自卡片的事实（接口名、字段、topic、RPC 签名）MUST 附 cite**（path + anchor + 最近确认时间）；无 cite 的接口/字段一律视为幻觉，MUST 回查。

**卡片里指向源码的 cite 以 `路径#符号` 为主**（如 `export/columns.py#EXPORT_COLUMNS`），行号可附在后面：符号改名比行号漂移少得多。`ctx lint-cards` 校验路径存在、符号在该文件里检索得到、行号不超过文件行数；路径相对项目根，或相对地图卡〈职责〉里 `> 根目录：` 声明的目录，源码不在本项目里的仓库声明 `> 根目录：外部`。

现读源码得到的事实，落盘前 MUST 带 `文件:行`，落盘后按卡片的 cite 引用。**两种出处都算数，MUST NOT 出现第三种"我记得"。**

## 6. 检索纪律

- 查**精确 token**（字段名/接口名/表名）时 MUST 优先用精确匹配（`ctx get-card <repo> <域>`、grep card 正文），不要只靠 `ctx search-semantic`。
- **语义检索结果只作"去哪找"的索引，MUST NOT 当最终事实直接引用**——命中后仍要落到权威 card 段并附 cite。
- 服务级 README 信息（部署、排障、路径）写在域卡的〈日志与排障〉或地图卡的〈对外入口总览〉，没有独立的 README 段。
- `freshness` 列留空时 `ctx` 标注「未声明新鲜度」，此时 **MUST NOT** 假定该条新鲜，按 §8 回查后再当事实用。

## 7. 卡片不够用、必须读真实源码时（clone 决策树）

以下属工程侧内部取证：向用户只说明在核对哪项业务事实及其影响，不报仓库、类、方法等程序细节，除非用户明确要求。

1. **先穷尽文档路径**——接口签名/字段去 card 的"对外接口"段；部署/配置/排障去 card 对应段；跨服务流程去 `ctx find-scenes`。都不够，才真正 clone。
2. **clone 前**：先明确要看哪个仓、为什么要看源码、要核对的具体事实；**没有 repo 地址就向工程 owner / 用户索取，MUST NOT 凭服务名猜 git URL**；用 `git clone --depth=1 <url>` 浅克隆到一次性临时目录，别污染工作区。
3. **clone 后**：**MUST NOT 全仓 grep**——按地图卡的〈业务域地图〉与域卡的〈权威实现与对外接口〉按图索骥（有代码图谱时结构性定位改走 `graph.md`）；读完 MUST 按 §4 把关键发现落成卡片，让后续 agent 不用重新 clone。
4. **卡片有缺漏或与源码不符**（如新增接口没记进去）→ **就地补上 / 改正并更新确认时间**，随本次分支提交。team 协作面 SHOULD 在合并说明里点一句改了哪张卡片，让既有 owner 有机会复核（`dw-workflow` 的 `collab/team.md`）；**但 MUST NOT 因为等 owner 而把卡片留在错误状态**。

## 8. 新鲜度纪律

- 改动**触碰权威面**（canonical 接口签名、废弃标记、路由/配置版本、DB schema、兼容窗口）——哪怕只有 3 行——MUST 触发对应卡片刷新（`engineering-context设计.md` §5）。
- 纯内部实现改动（不碰接口/权威）MAY 不刷卡。
- 刷卡后 MUST 跑 `ctx lint-cards`；评审门的文档轴同样跑它。
- 判断标准是**是否碰权威面**，不是改了多少行。
- **会话开始时先看增量**：`ctx` 读的是本地活文件，没有跨会话的变更推送。开新任务前 SHOULD 先看清"上次到现在 card/registry 变了什么"：

```bash
# 在项目根跑，路径当参数传（engineering-context/ 通常就在项目仓库里）
git log --oneline -20 -- engineering-context/
git diff 'HEAD@{2.weeks.ago}'..HEAD --stat -- engineering-context/cards/ engineering-context/capability-registry.md
```

用时间锚而非"上次的 commit"（本体系不记录上次是哪个 SHA，`<上次>..HEAD` 填不出来）；跨度按你上次碰这个项目的间隔调。reflog 不够长（新 clone）时输出**空 diff 且退出码 0**，只在 stderr 打 `warning: log for 'HEAD' only goes back to …`：**见此 warning 即表示时间锚被截断、diff 不可信，MUST NOT 当作"没变过"**，MUST 改用 `git log --since='2 weeks' -- engineering-context/`。`engineering-context/` 是独立仓库时才用 `git -C engineering-context …`。

## 9. 真相方向铁律

card 事实 **MUST 以合入后的源码为准，MUST NOT 从 PRD 生成**——PRD 是意图，常与已落地事实背离（典型："PRD 说可复用，查代码发现不可复用"）。详见 `engineering-context设计.md` §3。

## 10. 变更感知：CHANGELOG 与依赖声明

多项目之间的变更感知靠两份文件、同一套接口名：**上游在合并前写"我改了什么"**（仓库根 `CHANGELOG.md`），**下游在自己的代码事实层里写"我用了你什么"**（`engineering-context/dependencies/<上游名>.md`）。升级时两边取交集，正常路径**零子代理**；本节不新增任何门；`merge-gate="direct"` 下发版是人的动作，`pr` 下合并即发版（`dw-worktree` 的 `worktree开发纪律.md` §完成与自动合并门）。

### 10.1 上游侧：每次合并写 CHANGELOG

- **载体**：仓库根 `CHANGELOG.md`（MUST 在仓库根，MUST NOT 放 `docs/`——下游要从上游仓库或分发包里直接读到它，而 `docs/` 可能不入库）。顶部固定一个 `## 未发布` 节，其下**五类闭集**、五个小节标题固定存在（空的也留着）：`不兼容` / `新增` / `变更` / `修复` / `内部`。**MUST NOT 自造第六类。**
- **一律写**：每次合并到主分支 **MUST 在 `## 未发布` 下至少写一条**；自认为对外不可见的改动写进 `内部`。**MUST NOT 以"本次无对外变化"为由不写**——我们不知道下游怎么调用我们，这条没有任何声明式豁免（不设标记块字段、不设记号）。
- **`不兼容` 条目的三项必填**：MUST 以**对外接口名**开头（与本仓卡片 §对外接口 里的名字一致；没有卡片时用代码里的导出名 / 路由 / 事件名），并 MUST 含**旧调用方式、新调用方式、迁移步骤**。缺任一项视为条目未写。接口名是下游取交集的唯一键，写成一段自然语言描述就对不上。纯文档 / 流程类仓库（如 skill 分发包）没有代码导出名，用被改变的判据实体名（门名 / 轴名 / 命令名）代替。可照抄的一条：
  `- \`createOrder(payload)\` —— 旧：\`opts.currency\` 可省略、默认 CNY；新：\`payload.currency\` 必填；迁移：调用方把 \`opts.currency\` 提到 \`payload.currency\`，未传得 \`400 order_currency_required\`。`
- **来源是兼容取舍表，不是 diff**：`不兼容` 条目来自 spec §8.1 兼容取舍决策表（Lean：兼容取舍一行）里拍板为"不兼容"或"兼容一段时间"的每一行，**一行一条**；`新增` / `变更` 来自本次的 `FR-###`；bug 类写 `修复`；其余写 `内部`。**MUST NOT 另派子代理去读 diff 生成条目**——那份清单在兼容取舍确认门已经由拍板人逐条过过了。
- **时机是实现阶段、评审门之前**（完整流程 Step 7 内；Lean 在 `dw-workflow` 的 `路径-lean.md` §顺序 第 7 行实现时）：忠实轴跑在评审门，评审门在完成门之前——写在完成门就没有任何一轴看得到它，等于没核。**MUST NOT 推到完成门才写。积压通路 MUST NOT 豁免本条**（它只豁免评审门）。忠实轴的对照义务见 `dw-review-gate` 的 `子代理模板.md` §子代理 prompt 模板 的忠实轴段；完成门只核对条目在（`dw-worktree` 的 `worktree开发纪律.md` §完成与自动合并门），缺条目退回实现阶段补，**MUST NOT 在门内代写**。
- **发版只是规则，不是门**：`direct` 下发版由人做（`pr` 下由完成门兼作发布门，动作在 `dw-worktree` 的 `worktree开发纪律.md` §完成与自动合并门；升位规则与版本节格式以本条为准）——把 `## 未发布` 改名为 `## <版本> — YYYY-MM-DD`，其上新开一个空的 `## 未发布`；版本号按该节内容定：有 `不兼容` 升主版本，否则有 `新增` / `变更` 升次版本，否则升修订号；SHOULD 打 annotated tag `v<版本>`。**`direct` 下 AI MUST NOT 替拍板人定版本号或打 tag。** 发版后的历史节 MUST NOT 再改，改错只能在 `## 未发布` 下补一条 `修复`。
- **仓库根没有 `CHANGELOG.md`** 时在实现阶段按上述形态新建后写条目，随本次分支提交。

### 10.2 下游侧：依赖声明与上游升级

**声明是什么**：每个被本项目调用的上游（SDK、服务、共享库）在 `engineering-context/dependencies/<上游名>.md` **各一份**（一个上游一份，不按模块拆——升级时要看的是"我用了它的哪些接口"这一个问题）。`<上游名>` 取依赖清单文件（`package.json` / `go.mod` / `pom.xml` 一类）里的包名 / 模块名，服务类上游取 registry 里的仓库名；文件名含 `/` 的（npm scoped 包如 `@scope/name`）把 `/` 替换成 `__`，写成 `@scope__name.md`，MUST NOT 造出子目录。模板 `assets/context-layer/dependency.md`，`ctx init` 建目录（既有项目缺目录时首次补声明直接建，MUST NOT 要求重跑 `ctx init`）。

**最小五项**（缺一项等于没写）：

| 项 | 写什么 |
|---|---|
| 上游与当前版本 | 包名或仓库名 @ 当前锁定的版本 |
| 用到的部分 | 对外接口名清单，**与上游 CHANGELOG / 上游卡片里的名字一字不差**（取交集靠它） |
| 调用点 | 每个接口至少一处 `文件:行` |
| 注意事项 | 隐含假设、依赖的默认值、踩过的坑；确实没有写 `无` |
| 确认时间 | 本次读源码的日期 |

**与卡片同一套纪律**：内容 MUST 从**本项目源码**读出（它回答"我怎么用你"，上游文档答不了），MUST NOT 从上游文档或 PRD 抄；本次任务读到或改到了对某个上游的调用、而它还没有声明时，**MUST 在本次任务内补上并随分支提交，MUST NOT 顺延**；只增不减，与源码不符就地修正并更新确认时间。卡片 `## 上下游` 的"下游（我调谁）"行只留一句指针指向本目录，MUST NOT 两处各记一份。

**上游升级的处置顺序**——触发条件：本次任务要把某个上游升到新版本（依赖清单文件里该上游的版本号变化，或服务类上游宣告了新版本）。命中时 MUST 按序：

1. 读本项目对它的声明。**没有声明** → 先按 `dw-workflow` 的 `上下文卫生.md` 规则 4 把"本项目哪里调了它"外包给子代理扫一次，**当场补声明**，再继续；MUST NOT 在主会话裸 grep。
2. 读上游仓库根 `CHANGELOG.md`（SDK 包内随包分发的同一份文件亦可）里**旧版本→新版本之间**的 `不兼容` 条目。**上游没有 CHANGELOG 或缺该版本区间** → 派 **1 个**子代理看上游两个版本之间的 diff，**范围限于声明「用到的部分」列出的接口**，MUST NOT 全量看 diff。
3. 条目与声明的「用到的部分」按接口名字面取交集；上游改了名的按旧名匹配。**匹配不上但拿不准的按"有交集"处理，MUST NOT 按"无交集"处理**，并一句话告知拍板人上游条目不合规。
4. 交集为空 → 一句话告知拍板人后继续；非空 → 每条 MUST 进 spec 的〈既有系统清单〉并带调用点 `文件:行`，随本次改动一并改调用。本步不改分流：是否升级到完整流程仍按 `dw-workflow` 的 `00-流程总纲.md` §Step 0 的判定问题与 §默认倾向 判。
5. 升级完成后更新声明里的版本与确认时间。

正常路径（有声明 + 上游有 CHANGELOG）读两份 markdown、取一次交集，**零子代理**；子代理只在第 1 步（无声明）与第 2 步（上游无 CHANGELOG）各至多一个。

## 一句话

先查卡片，没有就读源码并当场补上；卡片事实不丢、只写现状，每条事实带出处，永远不裸 grep 找权威实体。
