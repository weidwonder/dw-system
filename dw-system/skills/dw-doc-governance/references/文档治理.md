# 文档治理

> 要给新建文档定目录、命名与 frontmatter，要往需求真相源或 TODO 写东西，或要立一条决策记录时读。判文档去留、归档、索引分层与准出归并在 `文档生命周期.md`。

所有项目使用同一套项目级输出目录，与协作面、与项目有哪些代码事实资产都无关。生成文档前先创建所需目录，不得把交付物散落到项目根或 `docs/` 根。

| 文档类型 | 唯一目录 | 示例 |
|---|---|---|
| 需求真相源主文档 | `docs/` 根 | `docs/REQUIREMENTS.md` |
| 需求真相源的一级子模块 | `docs/requirements/` | `docs/requirements/错题重练.md` |
| 还没做的事（唯一出口，见 §TODO 出口）| `docs/` 根 | `docs/TODO.md` |
| 架构真相源 | `docs/` 根 | `docs/ARCHITECTURE.md` |
| 变更 PRD、Overview、Lean Change Spec、技术 Spec、测试 Spec、设计、契约 | `docs/spec/` | `docs/spec/payment-lean-change-spec.md` |
| Coding Plan、实施计划、迁移计划、交接文档（上下文交接） | `docs/plan/` | `docs/plan/payment-coding-plan.md` |
| 执行报告、验证报告、测试报告、审计报告 | `docs/report/` | `docs/report/payment-verification-report.md` |
| Bug 修复历史（**追加式**账本，见下方例外说明；收敛规则在 `文档生命周期.md` §5） | `docs/report/` | `docs/report/bug修复历史.md` |
| 测试场景覆盖度台账（**状态表**，见下方例外说明；收敛规则在 `文档生命周期.md` §5） | `docs/report/` | `docs/report/测试场景覆盖度.md` |
| 测试资产（真实输入样本，**不是文档**） | 项目测试目录，探测优先 | `tests/fixtures/<场景名>/` |
| 决策记录（来历与被否决的方案）| `docs/decisions/` | `docs/decisions/0007-use-outbox-for-mq.md` |

> **本文小节**：[三层真相源](#三层真相源零上下文交接的底线)（零上下文交接的底线 + 可验证判据）· [需求真相源写什么、怎么分层](#需求真相源写什么怎么分层)（只写现状 / 两层承载 / 拆分阈值）· [归属表](#归属表目标项目的产物各放什么) · [决策记录](#决策记录) · [硬规则](#硬规则) · [TODO 出口](#todo-出口还没做的事都去这里)（还没做的事去哪：四类章节 / 准入门槛 / 陈旧提醒）· [默认命名](#默认命名)

## 三层真相源（零上下文交接的底线）

> **为什么要这一节**：项目 MUST 对任何接手者——人或 AI agent——做到**零上下文交接**：需求、架构、实现三层真相源都能从项目自身定位，不依赖任何人口头介绍。层次固定为这三层，**承载形态随项目已有的资产变化**——小项目用 README 的一节就合规，MUST NOT 因为项目小就允许某一层缺失。

| 真相源层 | 回答的问题 | 最小承载形态（三选其一即合规） | 项目长大后 SHOULD 升级为 |
|---|---|---|---|
| **需求** | 现在是什么、为什么做、现在有哪些功能 | README 的一节 **或** `docs/index.md`（二选一即可） | `docs/REQUIREMENTS.md` 主文档（放 `docs/` 根）+ `docs/requirements/` 一级子模块；写什么、何时升级、何时拆，见 ↓ §需求真相源写什么、怎么分层 |
| **架构** | 有哪些模块、各自职责与边界 | README 的一节"架构与边界"：模块划分 / 各自职责一句话 / 对外边界 / 不做什么，**可短至 10 行**；模块路径 MUST 写成反引号代码片段或相对链接（见 ↓ 可验证） | `docs/ARCHITECTURE.md`；存在跨服务场景时再补 `engineering-context/scenes/` |
| **实现** | 某件事落在哪段代码、哪个是权威实现 | `engineering-context/` 的 registry + cards——**必备，不是升级项**：查不到卡片就读源码、读完当场补上（`代码事实纪律.md` §4），事实带 cite | 跨服务场景补 `engineering-context/scenes/`；探测到**代码图谱**时结构性定位走索引（`graph.md`）|

- **可达性（MUST）**：三层真相源都 MUST 能从 README 或 `docs/index.md` 出发、**≤2 跳链接到达**。超过 2 跳等于不存在——接手者找不到就会去猜，猜出来的口径就是下一个错误的起点。
- **缺口只报告、不阻断（MUST）**：唤起或初始化时发现某层缺失或超过 2 跳，MUST 报告为"零上下文交接缺口"并指明补哪一份，MUST NOT 因此中止流程，也 MUST NOT 代用户自动创建——旧项目补齐需要时间，补的时机由用户定。上表的 SHOULD 升级项同理，只提示不代劳。
- **需求 MUST 先写清楚再动代码**，但真相源的**更新**在**准出门**完成（见 `文档生命周期.md` §6）。这是两件事，MUST NOT 混为一谈：开发前定稿的是**意图**（变更 PRD 或整品 PRD 新章节），开发后归并的才是**现状**。**MUST NOT 在实现验收之前把本次口径写进需求真相源**——那会让它描述一件尚未存在、甚至可能中途被推翻的事，而真相源的全部价值就在于"这里写的都已经是真的"。
- **可验证（不因卡片还少而豁免）**：这三层的可达性与"实现真相源可用"都是**机器可判定**的检查，`ctx probe` 有专门的交接题型覆盖它们——`requirement-reachable`（需求真相源 ≤2 跳可达）、`architecture-reachable`（架构真相源 ≤2 跳可达）、`implementation-usable`（架构节列出的模块路径都存在）、`rationale-traceable`（索引现行区各 spec 的 `authority_refs` 非空）。

  **这四道题读的是项目自身文件，不依赖卡片里有多少条目**，所以**卡片还没攒起来的起步态项目同样跑得起来、同样该跑**。骨架里已经有 `engineering-context/probe-set.md`（初始化时 `ctx init` 生成，见 `init-初始化.md` 第 5b 步），任何项目都 SHOULD 至少把这四道题填进去：照 `assets/context-layer/probe-set.md` §零上下文交接检查 里那张标着**「示例（可直接抄进自己项目的探针表）」**的表抄一份（表头是 `| # | 类型 | 输入 | 期望 | severity | weight | status | authority_refs |`，编号 41–44 的那四行），然后 `ctx probe`。
  **MUST NOT 抄错表**：同一文件里另有两张**说明用**的表（`## 题型说明（非探针表）` 的 `| # | 题型 | …`、本节开头的 `| 检查项 | 类型名 | …`），它们的表头都不是解析器认的形状，抄了会解析出 0 道题。
  跑的频次跟着 `probe-set.md` §运行节奏：CI 发布或里程碑节点跑，**MUST NOT 塞进 coding agent 的每轮 loop**。

  两个易错点：**①探针表的表头首列必须是 `#`、次列必须写 `类型` 或 `type`**，写成「题型」整张表不会被解析。症状是 `ctx probe` 打出下面两行并以退出码 1 结束：

  ```
  门禁自检：🛑 失效 — context 层为空（无 registry/cards），无法自检
  🛑 GATE-BROKEN：门禁自检未通过，拒绝出具结论（流水线应红）。
  ```

  **这条报错在卡片还空着的项目上真正的含义是探针表没被解析出来**，MUST 先查表头，**MUST NOT 照它字面去给 registry 现编条目**——registry 的内容按 `代码事实纪律.md` §4 在干活过程中真读了源码才补，为了让自检变绿而填等于制造过期权威；**②架构节里的模块路径 MUST 写成反引号代码片段（`` `src/app.js` ``）或相对链接**才会被 `implementation-usable` 计入——上表说"架构一节可短至 10 行"，但那 10 行里的路径若是散文里的裸文字，抽不到就判失败，而不是放行（零条目算通过就是假门禁）。

### 需求真相源写什么、怎么分层

> **一句话**：只写现在，不写来历。

- **定位（MUST）**：需求真相源只描述 **main 分支上已经实现的现状**，回答"这个项目是什么、为什么做、现在有哪些功能"。**MUST NOT 包含**：项目历史与演进过程、改动前后对比（"原来是 3 次"）、技术选型与实现方案、需求是怎么调整过来的。想知道某条口径当初为什么这么定，去归档索引翻当时那份变更 PRD——**那才是它的去处**。
- **尚未实现的一切 MUST 去 `docs/TODO.md`**（见 §TODO 出口）：在做中/待做的功能、下一步规划、长期形态、待澄清的开放问题、已知风险。**MUST NOT 在需求真相源里留一个"计划中"小节**——它一旦存在，读者就无法再信任"这里写的都是现状"这条前提，整份文档的价值随之归零；读者退回逐条去问人或读代码，等于这份文档不存在。
- **两层承载，MUST NOT 再往下分**：

  | 层 | 文件 | 写什么 |
  |---|---|---|
  | 主文档 | `docs/REQUIREMENTS.md` | **薄**：是什么 / 为什么做 / 有哪些功能（每条一句话 + 链到子模块）/ 用户怎么用 / 明确不做什么 / 服务质量要求 / 子模块划分方式 |
  | 一级子模块 | `docs/requirements/<模块>.md` | 用户可感知的具体行为规则：次数与额度上限、权限范围、状态流转、报错口径、边界条件 |

  **MUST NOT 出现 `docs/requirements/<域>/<模块>.md` 这样的二级目录**——两层是上限不是起点。
- **细节边界（MUST）**：判据是**用户能不能感知**。感知得到的（每天最多 5 次、没权限时看到什么、报错怎么给）写进子模块；感知不到的（缓存策略、内部阈值、数据结构、用了哪个库）**MUST NOT 写**——那是实现真相源（cards）与 spec 的事。PRD 的细节边界与这条线是同一条（`dw-prd` 的 `00-prd生成流程.md`）。
- **何时拆（SHOULD）**：主文档 **<500 行 SHOULD NOT 拆**——没到量就拆只让读者多跳一次；**>800 行 SHOULD 拆**；500–800 行由作者判断。行数只是信号，**MUST NOT 拿它当强制门**去卡住一次本来该过的准出。
- **划分方式 MUST 写在主文档里**：主文档 MUST 有一节说明本项目的子模块**按什么维度切、切成哪几块、各自文件名**。没有这一节，下一个人补功能时就会自己发明一套切法；两套切法并存之后，没人能判断某条规则该往哪找，也没人敢删任何一份。
- **不够用时才升级（MUST）**：真相源承载在 README 一节或 `docs/index.md` 时，**平时 MUST NOT 强制升级**（那是上表"只提示不代劳"的一部分）。只有当**本次准出归并确实有一条用户可感知的规则要写、而现有承载放不下**时，MUST 当场创建 `docs/REQUIREMENTS.md` 把规则写进去，随后更新入口指向它。**`docs/index.md` 一定放不下**——它是索引，每条只有标题与一句话简介，写不下"每天最多 5 次"这种规则；把规则塞进索引会同时毁掉索引与真相源两件东西。

## 归属表（目标项目的产物各放什么）

`dw-workflow` 入口〈两条总纲〉第一条落到目标项目的文档上：每类事实只有一个家，别处写名字加链接。

| 事实类别 | 它的家 | 这里不该放什么 |
|---|---|---|
| 已实现的、用户可感知的行为规则 | 需求真相源（主文档 + 一级子模块）| 来历、改动前后对比、实现方案、还没做的事 |
| 模块划分、职责与边界 | 架构真相源 | 逐个接口的细节 |
| 某能力的权威实现、对外接口、陷阱 | `engineering-context/` 的卡片 | 变更记录、事故经过、逐方法照抄的签名 |
| 本次要做什么、怎么算完成 | `docs/spec/` 下本次的 spec | 还没决定要做的事 |
| 还没做的事 | `docs/TODO.md` | 已完成的事、局部小事 |
| 来历、被否决的方案、取舍的权衡 | `docs/decisions/` | 现行规则的展开 |
| 出过的 bug 与修法 | `docs/report/bug修复历史.md` | — |
| 对下游可见的变化 | 仓库根 `CHANGELOG.md` | 内部推理经过 |
| 有哪些现行文档 | `docs/index.md` | 规则、结论、数字 |

评审门的文档轴查重复的动作：取一句有辨识度的原文全仓检索，命中两处以上 → 留家里那份，其余改成指针。

## 决策记录

规则、spec、卡片、真相源只写现状；**来历与被否决的方案只有这一个去处**。需要它的典型时刻：从规则旁搬走一段"当初怎么定的"、否掉一个以后还会有人想提的方案、做了一个以后可能被反复重议的取舍。日常小决策记进 Overview 的"已定决策"一行表即可。

- 存 `docs/decisions/NNNN-<短标题>.md`，顺序编号；首行之后写一行 `状态：现行 | 已被 NNNN 取代 | 否决` 与决策日期。
- 四节固定：**Context**（为什么要决策）/ **Decision**（定了什么）/ **Alternatives Considered**（考虑过哪些方案、为何否）/ **Consequences**（代价与影响）。
- **现行的记录跟着事实改**：它引用的路径、名字、默认值变了，就地改成现在的；决策本身变了，MUST 另写一篇并把旧篇状态改为"已被 NNNN 取代"，MUST NOT 把旧篇改写成相反的结论。
- **否决的记录只在它还能拦住人时留着**：那个方案已经没有人会再提（前提消失、被别的决策覆盖），整篇删除并修掉指向它的链接。
- 规则旁需要说明来历时，写一个指向对应记录的链接，MUST NOT 把来历抄回规则旁。

## 硬规则

- 文件名必须表达业务主题与文档角色，不得使用生成工具名作为目录或文件名前缀。
- 不得创建 `docs/superpowers/`、`docs/claude/`、`docs/codex/` 等工具专属产物目录。
- 不得把 spec 或 plan 放项目根、仓库根或 `docs/` 根。例外只有三类，都为了一眼可见：需求与架构两层真相源（`REQUIREMENTS.md`、`ARCHITECTURE.md`）、`docs/TODO.md`。**仓库根另有一份 `CHANGELOG.md`**，它不是 spec 也不是 plan，是给下游读的变更日志，MUST 在仓库根（`docs/` 可能不入库）；形态与写法在 `代码事实纪律.md` §10.1，本文不复述。需求真相源的一级子模块住 `docs/requirements/`，**MUST NOT 平铺在 `docs/` 根**——模块一多会把根目录埋掉。
- 同一需求的文档通过正文中的相对链接互相引用；移动文档时必须同步修复引用。
- `docs/index.md` 是发现入口，但不能替代上述目录规则；它**只索引现行口径**，历史文档进归档索引（见 `文档生命周期.md` §2）。
- 报告只有在流程要求形成书面报告时才创建；一旦创建，必须写入 `docs/report/`。
- **例外（两个固定文件名的单一账本）**：不按"每次新建一个 `<feature>-<report-type>-report.md`"的规则拆分。两者形态不同——`bug修复历史.md` 是**追加式**（每条都是发生过的一次性事实），`测试场景覆盖度.md` 是**状态表**（每行描述此刻的覆盖状态，同一场景只有一行）；收敛规则见 `文档生命周期.md` §5——
  - `docs/report/bug修复历史.md`：写入规则见 `bug诊断纪律.md` Phase 3 §归档问题处理历史，供 Phase 0 查重检索。
  - `docs/report/测试场景覆盖度.md`：写入规则见 `测试资产纪律.md` §3，模板 `assets/templates/test-coverage.md`，供批量向用户索要真实素材。
- **两个账本的生命周期归属**：MUST 恒为 `lifecycle: active`、`authority_refs: ['无']`，**MUST NOT 被 `文档生命周期.md` §3 的权威面触发转归档**——它们记录的是发生过的事实与此刻的状态，不冻结任何会过期的权威口径；收敛靠各自的分卷/就地改行规则，不靠归档。
- **测试资产不是文档**：用户提供的真实输入样本落项目**测试目录**（探测既有惯例，兜底 `tests/fixtures/<场景名>/`），MUST NOT 塞进 `docs/`。含凭证的样本进同级 `secrets/` 并 gitignore，脱敏副本 `secrets.example/` 入库。规则见 `测试资产纪律.md` §2。

## TODO 出口（还没做的事都去这里）

> **为什么要这一节**：需求真相源只写已实现的现状（§需求真相源写什么、怎么分层），于是"还没做的"必须有一个固定去处，否则它们会重新渗回真相源，把那条"这里写的都是真的"的前提毁掉。给它一个出口，真相源才守得住。

`docs/TODO.md` 是项目内**还没做的事的唯一出口**，与真相源同放 `docs/` 根。它同样是**快照**——只记此刻仍未做的，做掉的当场删，**MUST NOT 保留"已完成"区**（那是历史，归档索引才是它的去处）。

- **章节按类型分，取值是闭集，MUST NOT 自造第五类**：**想做的功能** / **待澄清的问题** / **已知风险** / **技术欠账**。按类型而不按模块分，是因为读它的人问的是"哪些要拍板、哪些要排期"，而不是"这个模块还欠什么"。
- **每条 MUST 带提出日期**（`YYYY-MM-DD`）。没有日期就无从判断陈旧，陈旧提醒（↓）整条失效。行格式：`- YYYY-MM-DD ｜ <归属模块或"跨模块"> ｜ <一句话>`。
- **准入门槛（MUST）——只收够格的**：

  | 收 | 不收 |
  |---|---|
  | 会改变用户能感知到的行为 | 改个变量名、调整格式 |
  | 会新增或去掉一个功能 | 清掉一行死代码 |
  | 会动某个模块的边界 | 补一个测试、局部重构 |

  **MUST NOT 把 `TODO.md` 当随手记**——把局部小事收进来，清单几周内就长到没人读，届时真正该拍板的那几条会一起被淹掉。局部小事写进代码注释或当场做掉，不进这里。
- **什么时候写**：写需求文档时、写 spec 时、写代码时，只要冒出"这个以后再说"且够格，**当场追加一条**；需求验收时再统一过一遍，把本次做掉的删掉。**MUST NOT 攒到最后一起写**——攒着的必然忘掉一部分。
- **陈旧提醒（SHOULD）**：条目提出日期距今**超过 3 个月**时，SHOULD 提示用户"这条还留着吗"。**AI MUST NOT 自行删除任何条目**——留不留是用户的判断，一条搁置半年的风险项可能正是最该留的那条。3 个月是默认值，项目可在 `TODO.md` 头部声明改写（如 `> 陈旧阈值：6 个月`），声明了就以声明为准。
- **不阻断**：项目没有 `docs/TODO.md` 不是缺陷，第一次有够格条目时才建（与三层真相源"缺口只报告、不阻断"同源）。初始化时 **MUST NOT 代用户创建**。

## 默认命名

- Lean Change Spec：`docs/spec/YYYY-MM-DD-<change-name>-lean-change-spec.md`
- Overview：`docs/spec/YYYY-MM-DD-<project-name>-overview.md`
- 技术 Spec：`docs/spec/YYYY-MM-DD-<repo>-<feature>-eng-spec.md`
- 测试 Spec：`docs/spec/YYYY-MM-DD-<repo>-<feature>-test-spec.md`
- Coding Plan：`docs/plan/YYYY-MM-DD-<feature>-coding-plan.md`
- 交接文档：`docs/plan/YYYY-MM-DD-<feature>-handoff.md`（见 `上下文卫生.md` 规则 2；任务未完成时随任务 worktree 走，合并时若已无用可不带回主分支）
- 报告：`docs/report/YYYY-MM-DD-<feature>-<report-type>-report.md`

**日期前缀（MUST）**：`docs/spec/`、`docs/plan/`、`docs/report/` 下**按次产出**的文档，文件名一律以 `YYYY-MM-DD-` 开头，日期取该文档的**创建日期**。上面七条范式因此写全就是 `docs/spec/YYYY-MM-DD-<change-name>-lean-change-spec.md`、`docs/plan/YYYY-MM-DD-<feature>-coding-plan.md`，以此类推。

- **常青档不加**：需求真相源 `REQUIREMENTS.md`、架构真相源 `ARCHITECTURE.md`、`docs/TODO.md`、两份索引（`docs/index.md` / `docs/index-archive.md`）、两个固定账本（`docs/report/bug修复历史.md` / `docs/report/测试场景覆盖度.md`）、`docs/requirements/` 下的一级子模块——它们是固定名字的长期文档，不属于某一天。
- **目录形态同样适用**：某次产出大到要拆成一个目录时，目录名同样以 `YYYY-MM-DD-` 开头，规则不因形态改变。
- **同一天同主题的第二份属改稿**：改原文件，MUST NOT 新建第二份。同一天不同主题的两份文件名天然不冲突。
- **存量不因新规则改名**：本规则只对新建文档生效。

项目已有更严格的文件名约定时可以沿用，但**目录不可改变**，且 **MUST NOT 用本句豁免掉上面的日期前缀**——项目可以在前缀之上更严格（比如再规定主题词的写法），MUST NOT 把前缀本身豁免掉。
