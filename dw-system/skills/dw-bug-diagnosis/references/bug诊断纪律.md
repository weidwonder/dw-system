# Bug 诊断纪律（core，红回路优先）

> 适用：修 bug、查回归、解释异常行为、处理测试失败——**任何"先要弄清为什么坏"的任务**，在动手改代码之前执行。
> 核心信念：诊断的全部精髓在 Phase 1——先造出一条**能变红的紧反馈回路**，再谈假设。跳过回路直接猜原因，正是本纪律要消灭的失败模式。
> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD。

## 设计缺陷优先原则

诊断过程中若发现根因是**设计本身**有问题（而非局部实现错误），MUST 调整设计，不得继续在其上堆积临时补丁；确认设计没问题时，才按下文流程正常改代码。是设计问题还是实现问题拿不准时，用业务语言向用户说明现象、请用户确认判断，不擅自定性后闷头重构。

## Phase 0：查重复历史（先于红回路）

MUST 在构造红回路之前完成：搜索本仓库 `docs/report/bug修复历史.md`（不存在则跳过本步，视为首次出现）是否有相同或高度相似的问题记录。

**MUST 用关键词检索（grep 或等价检索工具）定位条目，MUST NOT 把整份账本读进上下文**——这份账本按设计会长期增长，全文加载既烧上下文又把无关历史推进注意力窗口。账本已分卷时（`bug修复历史-<年份>.md`），连同各历史卷一起检索。

- 命中 → 读该条目的根因与处理方案，判断这次复发是**方案本身不合理**，还是**回归测试/护栏没拦住**：
  - 方案不合理 → MUST NOT 照抄重放，回到 Phase 1 重新诊断。
  - 方案合理但测试没拦住 → 先定位测试为何失效（测试本身有 bug？场景未覆盖？护栏注释被绕过？），把这一点并入本次假设。
- 同一问题连续复发两次以上，怀疑是承接者理解有偏差时，SHOULD 建议用户更换承接角色（换一个模型/agent 处理），不要让同一盲区再重复一次。

## Phase 1：构造红回路

找到或构造一条**复现命令**，同时满足四个属性：

| 属性 | 含义 | 反例 |
|---|---|---|
| **能变红** | 命令跑完能明确失败（非零退出码 / 断言失败 / 输出与预期 diff） | "跑起来看看日志"——没有失败判据 |
| **确定性** | 重复跑结果一致 | 依赖时序/随机数据、偶发才失败 |
| **快** | 秒级到十秒级，能高频重跑 | 要手工点十步 UI、要等定时任务 |
| **可自跑** | AI/脚本能独立执行并读到结果 | 需要人眼比对截图 |

> 不确定性若来自固定 sleep/setTimeout 等延时等待，改用等待实际状态达成的条件轮询（轮询目标状态是否成立，而非猜测耗时）；确需固定延时时 MUST 写明理由。

构造手段（按成本从低到高选）：已有失败测试 → 新写最小失败单测 → 最小复现脚本 → CLI/curl 命令 + 预期输出断言 → 带断言的日志检查命令。找不到入口时，把系统入口逐层缩小（整条链路 → 单服务 → 单函数），直到某一层能被一条命令打红。

**完成判据**：这条命令已经**真实跑过至少一次**并确认变红。没跑过 = 没有回路。

## 硬门禁

- 红回路存在之前，MUST NOT 提出修复假设、MUST NOT 修改产品代码。
- **发现自己正在"读代码构建理论"而回路还不存在——立即停下**，回去构造回路。先有理论后找证据，是诊断的头号反模式。
- 例外（显式声明后走）：确实无法确定性复现（并发竞争、特定环境、外部依赖抖动）时，本次任务的第一步交付 MUST 改为"缩小复现窗口"——加可观测性（日志/断言/计数）、固定随机种子、录制回放输入——直到回路可造；MUST NOT 以"复现不了"为由直接猜改。
- **同一假设集尝试修复满 3 次仍未解决，且每次修复都在别处暴露新的耦合/新症状**时，MUST NOT 尝试第 4 次修复；MUST 停下并用业务语言向用户说明现象，讨论是否要调整设计/架构（呼应"设计缺陷优先原则"），而不是继续在错误的架构假设上打补丁。

## Phase 2：可证伪假设

1. 基于回路的失败输出与代码事实（跨服务链路先 `ctx find-scenes`/`get-card` 取权威事实并附 cite；卡片查不到就读源码，读完按 `dw-code-facts` 的 `代码事实纪律.md` §4 当场把卡片补上；探测到代码图谱时反向调用链与影响面先查代码图谱；**任何情况下 MUST NOT 全仓裸 grep**，需要大范围探索时按 `dw-workflow` 的 `上下文卫生.md` §2 规则 4 外包给子 agent），列 **3–5 条可证伪假设**，按可能性排序。每条写成"若假设成立，则做 X 观察应看到 Y"。
2. **一次只验一条**：用回路（加日志/断言/最小改动）验证或排除，排除即划掉换下一条。MUST NOT 一次改多处"广撒网"。
3. 全部排除仍红 → 假设集错在更上游，回 Phase 1 缩小回路范围，不凭空追加第 6 条。
4. **模式对比**：代码库内若存在同构的可工作实现，将其与异常路径逐项对比，列出全部差异（不预判"这个不可能有关"）；差异清单本身即可转化为可证伪假设。
5. **反向调用链追溯**：症状出现在调用栈深处时，从捕获错误的地方开始逐层向上问"是谁调用了这里、传入了什么值"，直到定位到值第一次变坏/变空/变错的源头；假设与后续修复都锚定在该源头，而非症状点。
6. **回归先找引入提交**：问题是回归（以前好、现在坏）且找得到一个好的提交时，用 `git bisect run <红回路命令>` 定位引入它的那次提交，把该提交的改动作为假设的锚点。红回路命令就是二分的判据，结论不靠猜。

## Phase 3：修复与防回归

- 修复后红回路 MUST 变绿，且连续重跑两次全绿。
- 复现命令 MUST 固化为回归测试进入测试套件（它已经天然满足四属性）；确实不适合入库的，在归档记录中说明命令与结论，并在覆盖度台账登记为缺口。
- **问题本身 MUST 变成一份测试资产**（按 `dw-workflow` 的 `测试资产纪律.md` §5）：
  1. 触发这个 bug 的**真实输入**——用户发来的文件、报文、日志、失败现场数据，以及用户口头描述的场景——落进 `tests/fixtures/<场景名>/`（目录探测规则见该纪律 §2），场景名即问题的一句话描述；含凭证的进 `secrets/` 并 gitignore，留脱敏副本入库。**MUST NOT 只把数据贴在对话里用一次就丢**：下次复发时它就是唯一能复现的东西。
  2. 该问题跨 §1 判定的长链路（≥3 组件 / 异步多阶段 / 有中间产物）时，回归测试 MUST 是**端到端用例且断言每个环节的中间产物**——只补一个末端断言的单测，下次同类问题仍然定位不到是哪一环坏的。
  3. MUST 在 `docs/report/测试场景覆盖度.md` 登记该场景（状态 ✅，样本与用例位置指向新固化的文件），让台账同时成为"哪些真实故障已经被钉住"的清单。
- 修复触碰权威面（接口/路由/废弃标记）时，MUST 按 `dw-code-facts` 的 `代码事实纪律.md` §8 刷新对应卡片（新鲜度机制的完整设计在 `dw-code-facts` 的 `engineering-context设计.md` §5，日常刷卡不必读它）。
- **纵深防御**：若坏数据/状态本身会跨多层传递，只在源头修一处仍可能被其它路径绕过；SHOULD 在数据流经的每一层都补上校验（入口校验/业务逻辑校验/环境守卫/调试埋点等），让同类问题结构性不可能重现，而不只是点状打上一个补丁。
- **护栏注释固化约束**：若根因牵涉一条必须被后续改动长期遵守的隐性约束，除固化回归测试外，MUST 在相关代码模块顶部补一条简明注释，写清约束内容与相关代码位置，提醒后续改动者不要越过；后续 Agent 若认为该约束不合理，SHOULD 向用户申诉请求重构，而非绕开约束硬改。
- **归档问题处理历史**：修复确认变绿后，MUST 在 `docs/report/bug修复历史.md` 追加一条记录（文件不存在则创建）。条目格式固定如下，MUST NOT 自创结构——全账本格式一致是 Phase 0 关键词检索的前提：

  ```markdown
  ### [YYYY-MM-DD] 问题一句话描述
  - 根因：<简述，无需展开代码复杂关系>
  - 处理方案：<简述方案即可>
  - 修复版本：<修复完成时的版本标识>
  - 回归测试：<测试文件 + 用例名；确实无法创建时写明原因，并注明已获用户确认>
  - 测试样本：<固化后的样本目录，如 tests/fixtures/支付回调迟到/；无真实输入可固化时写"无">
  ```

  「测试样本」行对**新增条目**要求；**存量旧条目不必回改**。

  修复版本取值优先级：项目正式版本文件（`VERSION` / `package.json` / `Cargo.toml` / `CHANGELOG` 顶部条目等）＞最近 Git tag（`git describe --tags`）＞短 commit hash（`git rev-parse --short HEAD`）；项目没有任何正式版本机制时，MUST 至少记 commit hash，不得留空。

  该文件是**追加式的单一账本**，不按 `<feature>-<report-type>-report.md` 规则拆成多个文件——这是 `dw-doc-governance` 的 `文档治理.md` §硬规则 的两个固定文件名例外之一，专供 Phase 0 §查重复历史检索。

- **根因是"改错了实现 / 被旧实现误导"时 MUST 同时把这次消歧结果落进卡片**：把"哪处是权威实现、哪处是不该再用的旧实现"写进对应域卡的〈权威实现与对外接口〉与〈陷阱项〉（`dw-code-facts` 的 `代码事实纪律.md` §4.1 / §4.2），随本次分支提交。这类根因说明项目里已经出现"同一能力有多处实现、分不清信哪个"的实际损失，不补卡下一个 agent 会照样踩。

- **账本收敛**：主文件超过 300 条或 1500 行时分卷、条目引用失效时标注、以及"绝不删条目"的理由，见 `dw-doc-governance` 的 `文档归档与账本收敛.md` §账本收敛 → 追加式账本（要写账本时才读）。

## 与主流程的关系

bug 类需求照常过路由、worktree 隔离门与 Step 0 Triage（多数走 Lean 路径）；本纪律插在"进入实现之前"——Lean 也不豁免。修复完成后同样要过 skill `dw-review-gate` 的评审门（走 Lean 精简版）：诊断期加的临时探针、调试日志、被替换掉的旧分支都归残留轴清理。诊断结论改变影响面判断（如发现跨服务/不可逆）时，按 Triage 规则升级回完整流程。
