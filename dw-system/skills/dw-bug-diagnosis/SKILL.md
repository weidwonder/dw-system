# dw-bug-diagnosis：红回路优先

本 skill 管**"先要弄清为什么坏"的任务在动手改代码之前做什么**。修复本身仍走 `dw-workflow` 的流程（多数是 Lean）：工作区隔离门、兼容取舍确认门、spec 过稿门、代码评审门、完成与自动合并门一道不少；本 skill 只在其中插入红回路门。按 RFC 2119 解释规范词。

核心只有一条：**回路不存在，MUST NOT 提假设，MUST NOT 改代码。** 跳过回路直接猜原因，是本纪律要消灭的失败模式。

## 顺序

| 阶段 | 做什么 | 完成标志 |
|---|---|---|
| Phase 0 | 用关键词检索 `docs/report/bug修复历史.md`，看是不是重复问题 | 有结论：重复 / 相关 / 无 |
| Phase 1 | 构造红回路：一条能稳定变红的复现命令 | 命令真跑过且是红的 |
| Phase 2 | 提可证伪的假设，逐个用回路验证 | 找到让回路变绿的最小改动 |
| Phase 3 | 修复、补回归用例、归档问题处理历史 | 回路变绿且进了测试；历史已追加 |

## 读取条件

| 什么时候 | 读什么 |
|---|---|
| 命中 bug 类任务 | `references/bug诊断纪律.md` 整篇（约一万字节，没有可跳过的分支）：各阶段的判据、硬门禁与"设计缺陷优先"原则 |

## 与相邻 skill 的衔接

- 取代码事实（Phase 2 查权威实现、影响面）加载 `dw-code-facts`；任何文件落盘前过工作区隔离门、修完合并，加载 `dw-worktree`。
- 复现用到的真实输入按 `dw-workflow` 的 `测试资产纪律.md` 固化进测试目录。
- 根因是设计本身有问题时，MUST 调整设计而不是堆补丁；拿不准是设计问题还是实现问题，用业务语言请用户确认（`dw-workflow` 的 `用户沟通纪律.md`）。
- 修复引入的临时探针、调试日志、被替换掉的旧分支，归 `dw-review-gate` 的残留轴核销。
