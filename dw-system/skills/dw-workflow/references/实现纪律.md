# 实现纪律

> 动手写代码那一刻读；完整流程的 Step 7 与 Lean 的第 7–8 步共用。按 RFC 2119 解释规范词。

- **只在任务 worktree 内改**，MUST NOT 回到主工作树直接修改。
- **改在权威实现那一处**：同一逻辑存在多处副本时，先用 `ctx` 核对哪处权威（skill `dw-code-facts`），改在权威那处。
- **边写边删**：实现新逻辑时，被它取代的旧逻辑**当场删除**，MUST NOT 留到"最后统一清理"——留到最后就是留到永远。
- **触碰权威面当场刷卡**；本次删掉的旧实现移进对应卡片的陷阱项（`dw-code-facts` 的 `代码事实纪律.md` §8 与 §4.2）。
- **本阶段内写本次的 CHANGELOG 条目**（`dw-code-facts` 的 `代码事实纪律.md` §10.1）：仓库根 `CHANGELOG.md` 的 `## 未发布` 下至少一条；兼容取舍里拍为"不兼容 / 兼容一段时间"的每一行写一条 `不兼容`（接口名开头 + 旧 / 新调用方式 + 迁移步骤）。MUST NOT 留到完成门才写——评审门的忠实轴要对照它。本次升级了某个上游或改到了对上游的调用，按 `代码事实纪律.md` §10.2 补或更新依赖声明。
- **验证命令每条都真跑**，MUST NOT 靠"应该没问题"；完成后运行项目，确保无基础语法 / 编译错误。
- **MUST NOT 为让测试变绿而削弱、跳过或删除测试**，谁执行都一样；测试本身写错了，作为 plan 与源码不符回报，由主会话定怎么改。
- **卡片不够用、需读其他服务真实源码时**按 `dw-code-facts` 的 `代码事实纪律.md` §7 的 clone 决策树。
- **方案与代码 MUST 守 §设计原则**，评审门的规范轴按它判。
- **向用户汇报只说业务**：完成了哪些业务能力、哪些业务边界保持不变、验证了哪些业务场景、还存在哪些业务风险；文件与代码细节留在 plan / report 里，除非用户明确索要。

## 委派执行

把 coding plan 的任务派给子代理或外部编码工具时（零上下文起步见 `上下文卫生.md` §2 规则 3）：

- **按 checkpoint 分批派**，一批收回、复核完再派下一批。
- **派发说明写明**：本批任务、它独占的文件（并行的两批 MUST NOT 有重叠文件）、验证命令、要回报什么——改了哪些文件、验证输出原文、plan 与源码对不上的地方。
- **收回后主会话 MUST 亲自重跑验证命令并读 diff**，MUST NOT 凭执行者的汇报判定完成：汇报说"已完成"不等于改动真在、测试真绿。

## 设计原则（写方案与写代码都守；本节是这四条在本体系里的唯一定义）

| 原则 | 在这里的含义 | 违反的典型形态 |
|---|---|---|
| **YAGNI** | 只实现本次 spec 的 `FR-###` 要求的东西。没有需求对应的抽象层、开关、配置项、扩展点、"以后可能用到"的参数，MUST NOT 写 | 一个调用方却先抽接口；给单值加成配置项；预留没人调用的钩子 |
| **KISS** | 同一件事能用更直接的写法就不加间接层。每引入一个新概念、新层、新模式，spec 里 MUST 写出它解决的具体问题；写不出就不引入 | 为一次调用建工厂；三行逻辑套成事件总线；把 if 换成策略表却只有一个策略 |
| **DRY** | 同一份知识只有一处权威实现，第二处出现时提取并让两处都调它。DRY 针对的是"同一个知识"：两段碰巧相同、但会各自演化的代码 MUST NOT 为了去重而合并 | 复制一段校验逻辑改两个字；把两个业务上无关的流程硬合成一个带七个开关的函数 |
| **LoD**（最少知识） | 一个模块只和直接协作者说话，MUST NOT 穿过对象链取深层内部（`a.b().c().d()`）；接口只暴露调用方需要的最小面 | 调用方自己遍历依赖的内部结构拿字段；把整个对象传进去只为读一个值 |

四条冲突时按 **YAGNI > KISS > DRY > LoD** 取舍：先不做不需要的，再选最直接的，再消重复，最后收窄接触面。spec 的方案节（`spec写作纪律.md` §7）与代码评审门的规范轴（`dw-review-gate` 的 `评审轴.md`）都按本表判；忠实轴判"镀金"用的也是 YAGNI 这一行。
