# Spec 写作纪律（core）

> **本篇不常驻**：结论行（零上下文可动手、RFC 2119、无占位符）在 `00-流程总纲.md` §移出常驻的三篇，Lean 侧的投影在 `路径-lean.md` §4.2；本篇整篇按 `SKILL.md`〈加载点清单〉「动笔写 spec」与「出现过载信号要交接」那两行的触发点取。要改判据、或遇到结论行没覆盖的情形，取本篇对应小节读全文，MUST NOT 凭那几行推断。
> 一切 spec / plan / 文档的通用纪律。目标：**让一个不熟悉本项目的工程师或 coding agent，不用追问作者就能动手。**

## 1. 零上下文原则

假设读者是"技能不错、但对我们的工具链和问题域几乎一无所知"的工程师，或一个零上下文的 coding agent。文档要自带一切它需要的东西：

- **精确文件路径**，不写"改那个 controller"，写 `src/api/user.controller.ts:42`。
- **完整代码**：凡是让读者写代码的步骤，直接把代码写出来，不写"实现相应逻辑"。
- **精确命令 + 预期输出**：`npm test -- user` → 预期 `3 passing`。
- **每条外部事实带来源**：接口名/字段/topic 来自哪份文档或哪段源码。

## 2. RFC 2119 规范性措辞

在需要约束力的地方用大写关键词，减少歧义。**在文档顶部声明一次**"本文按 RFC 2119 解释下列关键词"，全文统一使用：

- **MUST / REQUIRED / 必须**：违反即错误。
- **MUST NOT / 禁止**：绝对不允许。
- **SHOULD / RECOMMENDED / 应当**：强烈建议，偏离需说明理由。
- **SHOULD NOT / 不应**：强烈不建议，除非有充分理由。
- **MAY / OPTIONAL / 可以**：可选，不影响互操作。
- **Implementation-defined / 实现自定**：契约要求存在，但具体取值/策略交由实现决定——用它区分"没规定"和"故意留给实现"，避免读者把"实现自定"误读成"漏写了"。

## 3. 无占位符（硬规则）

以下是**文档失败**，永远不要写：

- `TBD`、`TODO`、"稍后补充"、"填写细节"。
- "加上适当的错误处理" / "做好校验" / "处理边界情况"——要写清具体处理什么、怎么处理。
- "为上面写测试"——直接给测试代码。
- "同 Task N"——把代码重复写出来（读者可能乱序阅读）。
- 引用了任何任务里都没定义的类型/函数/方法。

> **例外**：把"本期不做、留待将来"的**已知后续工作**列进一个显式标注的"后续 / Out-of-scope 待办"区是允许的——它不是"没写完"，是"划清边界"。禁止的是把 `TODO` 混进**实现步骤**里冒充已完成。二者区别在于：待办区的每条都说明"为什么这期不做"，实现步骤里不许有洞。

## 4. 边界对称

每一条"我们做 X"，强制配一条"我们不做 Y"。Brownfield 项目最常见的失败是集成方**过度归因**新系统的能力。列出"不做 / 不负责 / 维持现状"能消掉大量集成误解。

## 5. 结构 > 篇幅

- 能用表格就别用长段落。
- 决策一旦拍板，记成一行 `决策名 | 方向 | 影响组件`，作为文档的记忆，避免每份 spec 重新吵一遍。
- 开放问题写成"能驱动决策"的具体问句，不写"搞清楚 X"这种含糊句。

## 6. 开放问题的事实门（fact-gate）

登记一条"开放问题（OQ）"之前，先过事实门——**凡是当前能从代码/文档读出来的事实，必须先自己查清、写成证据，绝不能当"待调查"塞进开放问题**。开放问题只留给"读完代码仍需 owner/产品拍板"的残余选择。

把每个待定项先分类：

| 类型 | 处理 |
|---|---|
| **code-fact / doc-fact**（翻代码或文档就能定：接口签名、字段、调用链、哪个是权威实现）| **不是 OQ**。自己查（先用 `ctx` 查卡片，查不到就读源码并按 `代码事实纪律.md` §4 当场补卡；探测到代码图谱时结构性定位查它），写进证据/正文，**带出处**：来自卡片的给 cite，现读源码的给 `文件:行`。 |
| **fact-dependent**（依赖某事实，但该事实可查）| 先把事实查了，多数会消解掉。 |
| **owner-policy**（读完代码仍需业务/技术负责人拍板的取舍）| **这才是 OQ**，登记进开放问题表。 |
| **external-blocked**（受外部依赖/他方阻塞，当前查不了）| 登记为 OQ，写明阻塞原因。 |

> 反模式：把"翻一下代码就能定"的东西全甩进开放问题——这会让评审会浪费在本可自查的问题上，也把"AI 偷懒没查"伪装成"需求不清"。
