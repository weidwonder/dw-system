# 初始化：把协作面写入 CLAUDE.md / AGENTS.md

> 首次在某项目唤起 skill、且两个入口都找不到标记块时执行。**只问一个问题（协作面）+ 一条待拍板的合并方式建议**，之后固化。
> **代码事实层不问**——`engineering-context/` 是必备资产，不是选项：初始化时按第 5b 步直接建骨架，MUST NOT 问用户"要不要建"。
> **代码图谱不问**——项目有没有建代码知识图谱索引由 `SKILL.md` §路由 第 1 步**每次运行探测**得出，MUST NOT 写进标记块：写成配置，项目一长大它就过期。
> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD / MAY。

## 流程

> **第 1–4 步只读文件、只与用户对话，MUST NOT 落盘任何东西。**
> 注入与顶部提示块（第 5、5a 步）、建骨架（第 5b 步）与冲突处置的写盘 MUST 发生在**过完工作区隔离门、进入 worktree 之后**
> （`dw-worktree` 的 `worktree开发纪律.md` §工作区隔离门 第 4 步）。两个原因：
> ① 隔离门要检查主工作树是否干净，在门前写 `CLAUDE.md`/`AGENTS.md` 会把它弄脏，
>    于是**每个项目第一次唤起本 skill 都会被自己的门拦在门外**；
> ② 在主工作树写下的标记块**不会出现在随后新建的 worktree 里**（worktree 是从主分支检出的），
>    配置就此悬在未提交状态，下次唤起读不到块又要重新初始化一遍。
> 落在 worktree 内则随本次任务分支提交、随合并门回到主分支，冲突处置也因此可评审、可回退。
>
> **用户只要求"初始化 / 配一下这个体系"、后面没有别的任务时**：初始化本身就是本次任务，
> 同样建任务分支与 worktree、同样走完合并门，MUST NOT 因为"只是改两个配置文件"就跳过。

1. **检测**：读项目根的 `CLAUDE.md` 与 `AGENTS.md`，查找标记块：
   ```
   <!-- dw-workflow:start -->
   ... collaboration="solo|team" merge-gate="direct|pr" worktree-dir="./.worktrees/" ...
   <!-- dw-workflow:end -->
   ```
   - 任一入口的块内**有 `collaboration`** → **不是初始化**：直接读出字段走路由，把同一标记块幂等同步到另一入口，不再询问。
   - 入口路由表已判为「3.0 之前版本写的块」→ **也不是初始化**：按那一行处置，不进本流程。
   - 两个入口都没有块 → 继续第 2 步。

2. **冲突扫描**：按 `references/环境冲突扫描.md` 的扫描范围扫描，产出冲突清单（可能为空）。扫描是事实收集，自动完成，不问用户。

3. **探测与取证（自动完成，一个都不问用户）**：

   | 探测什么 | 怎么看 | 用途 |
   |---|---|---|
   | **代码图谱** | `.codegraph/codegraph.db` 是否存在 | 只决定要不要加载 `dw-code-facts` 的 `graph.md`。MUST NOT 写进标记块，MUST NOT 据此追问用户 |
   | **代码事实层是否已初始化** | `engineering-context/capability-registry.md` 是否存在 | 只决定第 5b 步要不要建骨架。它是必备资产，**MUST NOT 据此判断"这项目要不要用卡片"**，也 MUST NOT 问用户 |
   | **`merge-gate` 建议** | 有 git 远端（`git remote`）**且**存在 `.github/workflows/` 或等价 CI 配置 → 建议 `pr`；否则建议 `direct` | 只是**建议**，第 4 步交用户拍板；问时 MUST 说明后果：`pr` 是每次合并即发布（合并后打 tag），`direct` 由用户发版。这是初始化时给用户的建议值，**与字段已缺失时的非交互兜底不是同一件事**（后者的唯一权威定义在 `dw-worktree` 的 `worktree开发纪律.md` §完成与自动合并门） |
   | **三层真相源缺口** | 按 `dw-doc-governance` 的 `文档治理.md` §三层真相源 看需求 / 架构 / 实现是否各有其一、能否从 README 或 `docs/index.md` ≤2 跳到达 | 第 6 步**报告**，不阻断 |

4. **询问**（仅当两入口都无块）：一次抛全，不一问一答。

   > 1. **这个项目除你之外，还有其他人一起开发吗？**
   >    - 没有，只有我（我 + AI 也算"只有我"）
   >    - 有其他人（同事 / 外包 / 开源协作者）
   > 2. **做完之后怎么并回主干？** 建议「<按第 3 步探测给出的那一项>」，理由一句话（如"检测到远端仓库和 CI 配置，建议走 PR"）：
   >    - **本地直接合并**：门禁全过后在你本机把任务分支合进主分支。
   >    - **推 PR 走平台**：推分支开 PR，评审与 CI 通过后由平台合并。

   两问都用业务语言问，MUST NOT 把 `solo` / `team` / `direct` / `pr` 这些字段值抛给用户认。
   若第 2 步冲突清单非空，把冲突决断（逐项 移除/修改/保留 + 建议）与上面两问**同一批**抛出。
   用户答复即为**决断已定**，但**处置动作（删除/编辑扫描范围内的文件）与注入一样延后到
   进入 worktree 之后执行**——项目级文件在 worktree 内改，落在主工作树等于绕过隔离门，且不可评审；
   用户级文件与项目级同批处置、同样等进入 worktree 之后：隔离门没过就先动用户目录，初始化中止时会留下一半已改的用户配置（作用方式见 `环境冲突扫描.md` §扫描范围）。

   **MUST NOT 问的四类**：
   - **"要不要建 engineering-context / 要不要维护卡片"**——它是必备资产，不是选项，第 5b 步直接建。
   - 项目有没有代码图谱索引（探测得出，见第 3 步）。
   - `worktree-dir`（有默认值，用户主动要求换位置时才改）。
   - 代码规模或行数（不是任何判据；本体系不按项目大小分档）。

5. **注入**（幂等，**在 worktree 内执行**）：把 `assets/config-snippets/base.md` 的块内内容 + `assets/config-snippets/collab-<collaboration>.md` 的块内内容**按序拼接**，用**一个**标记块包裹，写入 worktree 内项目根的 **两个** 文件：

   - `CLAUDE.md`（Claude Code 自动加载）
   - `AGENTS.md`（Codex 自动加载）

   属性行按下表填实，MUST NOT 留 `solo|team` 这类占位：

   | 字段 | 写什么 |
   |---|---|
   | `collaboration` | 第 4 步问题 1 的答复：`solo` / `team` |
   | `merge-gate` | 第 4 步问题 2 用户拍板的值：`direct` / `pr` |
   | `worktree-dir` | 默认 `./.worktrees/`；用户指定过就写用户给的路径 |

   - **文件**不存在则创建；文件已存在**而其中没有标记块** → 在末尾追加（不动其它内容）；
     已有标记块的一律按下方 §幂等规则 替换块内内容，MUST NOT 再追加一个。
   - **写之前先按下方「入口是软链接时」判断**：任一入口是软链接时，写的对象是链接目标，不是链接本身。

5a. **写顶部提示块**（与第 5 步同一次落盘）：把 `assets/config-snippets/hint.md` 的块内内容，用 `<!-- dw-workflow:hint:start -->` / `<!-- dw-workflow:hint:end -->` 包住，写进入口文件**最前面**（原内容整体下移，MUST NOT 改动原内容的任何一个字）——它只说一句「动手前先加载 `dw-workflow`」，让下一个零上下文 agent 读第一屏就知道要走本流程；判据仍在标记块与各 skill 里，MUST NOT 在提示块里展开规则。写法按下方 §幂等规则。片段读不到时本次不写提示块，不报错、不自拟正文，流程继续。

   **写进哪些入口**，判的是**第 5 步落盘之前**项目根的状态：两个入口文件都在 → 两个都写；只有一个在 → 只写在的那个；两个都不在 → 只写 `AGENTS.md`。MUST NOT 为了写提示块而创建第二个入口文件——被第 5 步顺带创建出来的那个只带标记块。任一入口是软链接时写的是链接目标（见下方 §入口是软链接时），两个入口解析到同一实体文件时**只写一次**。安装器对已有标记块的项目维护同一块（与 `install.mjs` 同一套判据），两边 MUST NOT 各写一套。

5b. **建代码事实层骨架**（幂等，**在 worktree 内执行**）：第 3 步查到项目根下不存在
   `engineering-context/capability-registry.md` 时，在 worktree 内的项目根跑：

   ```bash
   ctx init
   ```

   （`ctx` 命令不可用时改用 `node <skills 根>/dw-code-facts/scripts/ctx/src/cli.js init`，见
   `dw-code-facts` 的 `代码事实纪律.md` §2。）它生成 `capability-registry.md`、`cards/`、`dependencies/`、`scenes/`、
   `probe-set.md`、`glossary.md`、`README.md`、`.gitignore`，已存在的文件一律不覆盖。
   骨架随本次任务分支提交。

   - **MUST NOT 跑 `--minimal`**：卡片目录必须从第一天就在，否则第一次补卡的 agent
     还要先决定目录放哪，同一个项目里就会长出两种放法。
   - **MUST NOT 在这一步通读项目代码去填内容**。骨架里只有模板占位、没有真实数据行，
     这是**正常起步状态**：内容按 `dw-code-facts` 的 `代码事实纪律.md` §4 在后续干活过程中渐进补齐
     （要用哪个模块的事实就补哪个模块的卡片）。一次性铺满卡片既做不准
     （没有具体任务当靶子，写出来的都是泛泛之谈），也会把这次初始化拖成一个大工程。
   - `capability-registry.md` **已存在时跳过整步**，MUST NOT 覆盖用户已有内容，
     也 MUST NOT 因为它"只有占位行"就重建——占位行就是起步态。

6. **报告三层真相源缺口**（报告，不阻断）：把第 3 步查出的缺口一句话说清——缺哪层、补它的**最小形态**是什么（判据与最小形态表见 `dw-doc-governance` 的 `文档治理.md` §三层真相源：需求 = README 一节或 `docs/index.md`；架构 = README 里一节"架构与边界"，短到 10 行也算；实现 = 代码本身 + 子代理外包探索），然后**继续流程**。

   - MUST NOT 替用户创建 `REQUIREMENTS.md` / `ARCHITECTURE.md` / `docs/index.md` / `docs/TODO.md`（后者是「还没做的事」的唯一出口，第一次有够格条目时才建，判据见 `dw-doc-governance` 的 `文档治理.md` §TODO 出口），MUST NOT 为了归档而临时造一个索引（`文档治理.md`）。
   - MUST NOT 把"补齐三层真相源"设成开始开发的前置条件——旧项目补齐需要时间，卡住只会让用户绕开整个流程。
   - 无缺口时一句话带过，不展开。

## 幂等规则（重要）

- **只更新标记块内的内容，绝不重复追加**。重复调用初始化时：
  - 若标记块已存在 → 用新内容**替换块内**，保留块外一切。
  - 若不存在 → 追加一个新块。
- **两个入口必须收敛**：只有 `CLAUDE.md` 或只有 `AGENTS.md` 有标记块时，自动补齐另一文件；两边字段不一致时，以 `CLAUDE.md` 为准并同步到 `AGENTS.md`。
  **只要这次同步会改掉另一入口已有的显式 `collaboration` / `merge-gate` 值，就 MUST 告知**。口径一律以 `CLAUDE.md` 为准（与安装器 `install.mjs` 同一套判据，两边 MUST NOT 各写一套），但 MUST **说一句**被覆盖的是什么：

  > 另外，`AGENTS.md` 里原本写着「<原值的业务语言说法>」，已按 `CLAUDE.md` 的声明统一成上面这两项。如果原来那个才是对的，现在说一声，我改回去。

  这一句 MUST NOT 省——不说的话，用户明确配过的设置被静默改掉，而他不会有任何察觉。
- **顶部提示块同一套口径**：`<!-- dw-workflow:hint:start -->` 与 `<!-- dw-workflow:hint:end -->` 在一份入口文件里各 MUST 只出现一次；已存在则替换块内正文、位置不动，不存在才插到文件最前面。**只写本次写入前就已存在的入口**（落点按 §流程 第 5a 步；本次才被创建的入口只带标记块）。它与标记块是两个独立的块，MUST NOT 把提示块塞进标记块里。
- **块内 MUST NOT 出现第二对标记**：整份 `CLAUDE.md` / `AGENTS.md` 里 `<!-- dw-workflow:start -->` 与 `<!-- dw-workflow:end -->` 各 MUST 只出现一次。块内又出现一对（典型成因：把 `collab-*.md` 连标记一起抄了进来）即视为**块已损坏**，MUST 按"`base.md` 块内内容 + `collab-<collaboration>.md` 块内内容"重建整块（字段值从损坏块里能读到的部分沿用，读不到的按第 4 步重新确认），MUST NOT 只删掉多出来的标记行了事——嵌套一旦发生，块尾那段协作正文可能已在上一次写入时被截断丢失。
- **值非法不猜**：`collaboration` 不是 `solo`/`team`、`merge-gate` 不是 `direct`/`pr` 时，报错中止并列出合法值域，MUST NOT 替用户挑一个。
- 标记用 HTML 注释，对 markdown 渲染无影响，且机器可精确定位。

## 入口是软链接时（重要）

很多项目让 Claude Code 与 Codex **共用一份指导文件**，做法是把 `AGENTS.md` 软链接到 `CLAUDE.md`（反向亦有，也可能两者都链到仓库外的共用文件）。这种链接是用户的刻意配置，**任何写入都必须保留它**。

写 `CLAUDE.md` / `AGENTS.md` 之前，先各判断一次（例如 `ls -l CLAUDE.md AGENTS.md`，或 `readlink CLAUDE.md`（POSIX）/ `Get-Item CLAUDE.md | Select-Object LinkType,Target`（Windows PowerShell），或直接用 harness 的文件工具判断）：

- **不是链接** → 按上面的幂等规则直接写这个文件。
- **是链接** → 逐层解析到实体文件，**把实体文件当作写入对象**，对它照常判断"替换块内"还是"追加新块"。链接本身不删、不改、不替换成普通文件；不要用"先删再建"或整文件覆盖的写法。
- **两个入口解析到同一个实体文件** → 这就是共用一份的情形：**只写一次**，不要把同一标记块注入两遍。此时"两个入口都要有标记块"天然满足，不必再补第二次。
- **断链**（链接目标不存在，或目标所在目录不存在）→ **停下来问用户**，不要新建实体文件把链接顶掉。这通常意味着用户的共用文件被移走了。

## 切换协作面

用户显式要求切换时（如"这个项目现在有其他人一起接手了""以后只有我一个人维护"）：

- 找到标记块，把 `collaboration` 改成新值，并把块内的协作段替换为另一份 `collab-<collaboration>.md` 的**块内内容**（`<!-- dw-workflow:start -->` 与 `<!-- dw-workflow:end -->` 之间的正文，**MUST NOT 把这两行标记一起写进去**——两个 `collab-*.md` 各自带一对完整标记，照抄整份文件会在标记块内部再嵌一对，此后任何"替换首个 start 与首个 end 之间"的写入都会在嵌套的 `end` 处截断，静默丢掉协作段）；`base.md` 那段与其余字段不动。
- **MUST NOT 顺手改 `merge-gate`**——合并方式是独立字段，用户没说就不动；确有必要时单独问一句。
- **切换协作面不影响代码事实层**：卡片照常按 `dw-code-facts` 的 `代码事实纪律.md` §4 边干边补。MUST NOT 借切换的机会重新讨论"要不要用卡片"——那不是可选项。

## 写入示例

见 `assets/config-snippets/base.md` 与 `collab-solo.md` / `collab-team.md`——注入标记块内的原文就是"`base.md` 块内内容 + 对应 `collab-*.md` 块内内容"的拼接。顶部提示块的原文即 `assets/config-snippets/hint.md` 的块内内容。
