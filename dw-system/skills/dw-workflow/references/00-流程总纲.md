# 开发流程总纲（技术栈无关）

> 两条路径共用：流程总览、门的全景、Triage 与默认倾向、不裁剪护栏。完整流程另读本文的步骤索引与按边界拆；Lean 的步骤顺序在 `路径-lean.md`。协作面分册（`collab/solo.md` / `collab/team.md`）只**追加**，MUST NOT 削减本总纲任何一条。
> 全程遵守 `用户沟通纪律.md`（与用户只用业务语言）与 `上下文卫生.md`（方向性决策在聪明区内完成，逼近上限交接而非硬撑）。按 RFC 2119 解释规范词。

## 流程总览

```
路由/初始化（只对话，不落盘）→ 工作区隔离门（独立 worktree；首次唤起在此写标记块）→ Step 0 分流(Triage)
  ├─ 4 项全否 → 读 路径-lean.md：Lean Change Spec → 兼容门 + spec 过稿门（同批）→ 实现 → 评审门
  └─ 任一为是 → 读 步骤-1-7-设计与实现.md：Step 1–5 → 兼容门 → spec 过稿门 → Step 6–7
                 → 评审门 → 读 步骤-8-10-测试.md：Step 8–10
  └─ 两条路径都收尾于：完成与自动合并门 → 主分支
```

## 五道门（贯穿两条路径，Lean 一道也不豁免）

| 门 | 触发时机 | 判据在哪 | 不过门的后果 |
|---|---|---|---|
| **工作区隔离门** | 路由与初始化**对话**完成后、任何文件落盘前（**含初始化自己要写的标记块**）| skill `dw-worktree`（`worktree开发纪律.md` §工作区隔离门）| 改动落进主工作树，与用户未提交的工作纠缠 |
| **兼容取舍确认门** | spec 定稿前（完整流程 Step 5 后 / Lean 开始实现前）| `确认门.md` §兼容取舍确认门 | AI 替用户决定了兼不兼容，留了包袱或造成断裂都没人知情 |
| **spec 过稿门** | spec 定稿后、Step 6 之前（Lean 与兼容取舍同一批抛出）| `确认门.md` §spec 过稿门 | 拍板人从没读过这份 spec 就开工 |
| **代码评审门** | 编码完成、基础验证通过后 | skill `dw-review-gate` | 漏实现、镀金、越界、旧逻辑残留一起进主分支 |
| **完成与自动合并门** | 合并前 | skill `dw-worktree`（`worktree开发纪律.md` §完成与自动合并门）| 未验证的改动进主分支，失败现场也被清掉 |

另有三道**条件触发**的门，不贯穿两条路径，命中才过：

- **红回路门**：bug / 回归 / 异常行为类需求，动手改代码前先过（Lean 也不豁免）。→ skill `dw-bug-diagnosis`
- **不可逆确认门**：Triage **第 3 问命中**（搬迁历史数据 / 不可逆影响）时过，判据与摘要内容见 ↓ §Step 0 第 3 问。它管后果可不可逆，大架构确认门管结构变没变；**两者可同时命中，此时 MUST 合成一份摘要一次抛出，MUST NOT 分两轮问**。
- **大架构确认门**：**改动命中大架构判据**（产品或技术架构的**主干路形状**变了——形状变才算，主干路上的取值变不算；判据与正反例的权威定义在 `用户沟通纪律.md` §1，本文 MUST NOT 复述）时，MUST 先形成**业务语言摘要**交用户确认后才能继续。**触发条件是"改动命中判据"，MUST NOT 写成"Overview 改变了什么"**。落地：完整流程 Step 4 前过（`步骤-1-7-设计与实现.md` §大架构确认门），Lean 在开始实现前与兼容取舍**同一批**抛出（`路径-lean.md` §顺序 第 6 行）。

## Step 0：需求体量与风险分流（Triage）

**先判断体量，再决定走多重的流程。** 没有完整 PRD 的小 Issue / 体验改进，回答 4 个判定问题：

1. 是否改变智能能力给用户的结果或判断方式？
2. 是否改变谁可以做什么、敏感信息保护或使用场景？
3. 是否影响多个业务环节、需要搬迁历史数据或存在不可逆影响？
4. 是否改变经营指标、业务规则或对外承诺？

- **4 项均为「否」** → **默认**走 Lean（先过 ↓ §默认倾向，未命中升级条件再**加载 `路径-lean.md`**），唯一交付物是一页 Lean Change Spec（`assets/templates/lean-change-spec.md`），写入 worktree 内 `docs/spec/YYYY-MM-DD-<change-name>-lean-change-spec.md`；跳过 Step 1–10，五道门一道不少。
  ——**MUST NOT 把本条读成无条件结论**：四问全否**之后**还要过一遍 §默认倾向，命中升级条件即改走完整流程。
- **任意一项为「是」** → 走完整流程：**加载 `步骤-1-7-设计与实现.md`**；涉及 AI/LLM 的，在 Step 4 叠加 AI overlay。

**第 3 问命中时另有一项确认义务（MUST）**：MUST 按 `用户沟通纪律.md` §1 的格式形成**业务语言摘要**交用户确认后才能动手；摘要 MUST 写清**动了哪些历史数据、影响哪些既有业务、出错后能不能退回去、退不回去的部分是什么**。（第 3 问命中本身已经把本次升级到完整流程，这条义务在完整流程里继续成立。）

**4 问 MUST 逐题过一遍，不是"假设"全否**。

### 默认倾向（四问全否之后）

本倾向**无条件适用于所有项目**，MUST NOT 由协作面、项目大小或有没有代码图谱来改变：

> **影响面说不清时，MUST 升级到完整流程出 Overview；说得清才走 Lean。**

**"影响面说不清"的判据（命中任一即算）**，按可评估的时点分两批：

| # | 判据 | 什么时候过 |
|---|---|---|
| 1 | 本次要改的能力在 registry 里跨 ≥2 个权威仓库 | **Triage 当场**，MUST 逐条过 |
| 2 | `ctx discover` 给出了 out-of-scope 警告（命中废弃或中间产物实现）| **Triage 当场**，MUST 逐条过 |
| 3 | 关键事实里有任何一条**给不出出处**（卡片 cite 或 `文件:行`）| **回溯触发**：Step 1 进行中 / Lean 在 `路径-lean.md` §顺序 第 4 行写〈既有系统清单〉时命中即当场升级 |
| 4 | 卡片、`discover`、`search-semantic` 都收不窄，**读完源码仍说不清模块边界** | 同上 |

**判据 3/4 回溯触发，MUST NOT 在 Triage 当场强行判定**。**Lean 没有 Step 1，落点是 `路径-lean.md` §顺序 第 4 行**（写〈既有系统清单〉时）——MUST NOT 因为"我走的是 Lean、没有 Step 1"就认为这两条对自己不适用；在那一步命中即**当场升级回完整流程**（`路径-lean.md` §升级路径）。

**判据 3 MUST NOT 被读成"卡片里查不到就算说不清"**：查不到的正确处置是**读源码 + 当场补卡**（`dw-code-facts` 的 `代码事实纪律.md` §4），补完就有 `文件:行` 出处，判据 3 即不命中。真正命中的是**读了源码也说不出这条事实从哪来**——动态派发、配置化路由、反射调用这类"代码在这儿但决定权不在这儿"。

**判据 4 同理**：卡片没命中不算，**读完源码仍说不清**才算。

**判据 1/2 怎么当场核对**：按 `dw-code-facts` 的 `代码事实纪律.md` §3 的固定顺序取事实（MUST NOT 跳过 find-scenes 直接 discover），拿到端到端全景、命中仓库与 out-of-scope 警告后逐条对照。结果一并进 Step 1 的〈既有系统清单〉，不重复跑。
**registry 还是空的时候，判据 1/2 自然都不命中**——这是正常起步态，MUST NOT 因此判定"说不清"，也 MUST NOT 因此判定"说得清"：此时该看的是判据 3/4 在 Step 1 里的回溯结果。

MUST NOT 用"我感觉不复杂"代替以上任何一条。
**MUST NOT 从"只有我一个人"推出"默认走最短流程"**——一个人维护的十万行遗留系统，默认走 Lean 是危险的；协作面不参与本判据。
**跨仓需求一律升级**，registry 里登没登记那几个仓库不影响本条。
**MUST NOT 从"这项目还没几张卡片"推出"这项目简单"**——卡片少只说明还没人读过这块代码，与代码本身的复杂度无关。

## 七条"不裁剪"护栏

**轻量不等于可省。** 下面七条在任何协作面、有没有代码图谱、任何分流路径下都 MUST NOT 被裁剪，Lean 一条也不豁免。

1. **目录不裁剪。** spec 仍 MUST 写进 `docs/spec/`、plan 仍 MUST 写进 `docs/plan/`、报告仍 MUST 写进 `docs/report/`；MUST NOT 因为"就一份文档"把设计散放在代码注释、聊天记录或仓库其它位置。命名与例外见 `dw-doc-governance` 的 `文档治理.md`。
2. **沟通纪律不裁剪。** 用户只确认业务目标、业务边界和必要的大架构；模块内设计通过业务问题取约束；详细程序设计直接完成，MUST NOT 就它发起技术确认（`用户沟通纪律.md`）。
3. **worktree 与自动合并不裁剪。** 再小的 Lean 改动也 MUST 先进入独立 worktree；验证通过后按 `merge-gate` 合并，失败则保留 worktree，MUST NOT 直接改主工作树（`dw-worktree` 的 `worktree开发纪律.md`）。
4. **代码评审门不裁剪。** MUST NOT 因为"改动很小"就把这道门**免掉**：派几个、跑哪几条轴、够小的改动怎么登记积压延到下一次门，都在 skill `dw-review-gate`，Lean 也不能跳过。**积压是推后不是取消，MUST NOT 读成豁免**，也 MUST NOT 靠拆 commit 把改动压到阈值以下。
5. **兼容取舍不裁剪。** 每次 MUST 走完 `确认门.md` §兼容取舍确认门（逐条列出、交拍板人拍一次、结论落进 spec 的兼容取舍节）；清单为空时也 MUST 显式写一句"本次不改变任何既有可观察行为"，MUST NOT 静默跳过这道门。
6. **测试资产与覆盖度台账不裁剪。** 遇到的真实输入照样 MUST 固化进测试 fixture，长链路照样 MUST 写断言中间结果的端到端用例（`测试资产纪律.md`）。可裁剪的只有**深度**：覆盖度台账 MAY 只记高重要度场景。
7. **补卡不裁剪。** 本次为推进任务而读了源码的模块，MUST 在本次任务内把卡片补上并随分支提交（`dw-code-facts` 的 `代码事实纪律.md` §4）；MUST NOT 因为"改动很小""就查了一个字段""这项目还没建几张卡"就跳过。可裁剪的只有**范围**：只补本次真读过并核对过的那部分，MUST NOT 为了"补全"去写没核对过的字段。

## 按边界拆：spec / Issue / PR 的粒度

**拆分判据是边界，不是人数。**"边界"指代码仓库、独立部署单元、模块或限界上下文。

### 按边界拆 spec

- 需求跨多个边界时 **MUST 按边界划分 spec**，每份明确该边界做什么、不做什么、与上下游的契约。
- **每份 spec 写入对应边界所在仓库的 `docs/spec/`，plan 写同仓 `docs/plan/`，报告写 `docs/report/`。** MUST NOT 把多个边界混成一份大文档，也 MUST NOT 散放到仓库其它位置。
- **出** Overview 时它是这些 spec 的共同上文，MUST 先于它们定稿；其"已定决策"表是各份 spec 之间不重复争论的依据。**要不要出**由 `步骤-1-7-设计与实现.md` §本步必做还是可跳过 的判据表单独决定（跨边界数 × 协作面），本处 MUST NOT 另立一套——跨 2 个边界的 solo 改动同样产出 2 份 spec，把本条读成"有 spec 就必须有 Overview"会与那张表的 MAY 跳过冲突。

### 大 PRD 先做垂直切片，再按边界拆

- 一份 PRD 含多个可独立交付的能力时，**MUST 先按垂直切片拆成一组 feature Issue**（INVEST：独立 / 可协商 / 有价值 / 可估 / 小 / 可测）。每个 Issue 带 Scope 锚点 + 参照的现有实现指针 + 约束护栏 + 测试信号，并标出 Issue 间依赖顺序与显式 out-of-scope。
- 再对每个切片走 Overview → 按边界出 spec。项目若有自己的 PRD 拆解规范，完整拆解方法以其为准。

### PR / 提交粒度

- 一个 coding plan 任务 SHOULD 对应一个小而可 review 的 PR 或提交，约 **3–8 文件**；与人数无关。`merge-gate="pr"` 的平台动作见 `dw-review-gate` 的 `评审处置.md` §处置 与 `dw-worktree` 的 `worktree开发纪律.md` §完成与自动合并门（只认 `merge-gate` 这一个字段）；`collab/team.md` §4 只补"因为有别人"才多做的那几件（指派评审人、与 owner 约合并窗口）。

### 多边界的合并顺序

- 多边界改动 MUST 全部通过完成与自动合并门后再开始合并，并按**依赖顺序**执行：**谁的对外契约先被别人依赖，谁先合**（提供方先于消费方；互不依赖的边界 MAY 任意顺序）。
- 任一步失败立即停止后续合并，并报告已合并与未合并的业务范围（`dw-worktree` 的 `worktree开发纪律.md`）；协作面 = team 时合并顺序还 MUST 与各边界 owner 协商确认后再执行（`collab/team.md` §5）。
