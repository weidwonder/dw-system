# 纯 skill 改动的流程形态

> 对象面（P / K / G）的判据在 `dw-review-gate` 的 `评审门禁.md` §第一步。

## 纯 skill 改动的流程形态

**本次改动范围不含任何可执行代码文件（即只命中 K 面）时：PRD 即 spec，MUST 跳过 Overview、技术 spec（Lean 路径为 Lean Change Spec）与 coding plan，直接改。** 判据是 skill 与 spec 属于**同一种介质**——skill 本身就是真相源，可读性与组织结构俱全，再写一份 spec 描述"要怎么改这份判据文档"是一层纯粹的间接。代码需要 spec 是因为 spec 与代码介质不同、spec 承担翻译；这里没有翻译要做。

- **本节判定发生在动笔之前，那一刻 `git diff` 是空的**——`评审门禁.md` §第一步 那条 `git diff` 口径只对评审门成立，MUST NOT 照搬到这里。动笔前的「改动范围」取**打算改的文件清单**：MUST 在动手前把它逐条列出来（PRD / 改动清单里已列的直接用），按 `评审门禁.md` §第一步 的同一套文件类型判据判面。**清单在实现过程中长出可执行代码文件时 MUST 当场重判**——那一刻起就是 P 面命中，代码那部分补写 spec，MUST NOT 以"当初判的是纯 skill"为由继续跳过。评审门会用真实 diff 再判一次，**两次判定不一致时以评审门那次为准**，且 MUST 把补写 spec 这件事补做完再过门。
- 动手前 MUST 加载伴生 skill `skill-principle` 的**建设路径**作为结构判据：写 description 与触发词、设计渐进披露层次、判断该不该拆分册都照它的原则走。判据以该 skill 当前版本为准，本文 MUST NOT 复述；该 skill 整体不在场时照常推进并记一笔，MUST NOT 因此阻断流程。
- **改动范围一旦含可执行代码文件，代码那部分 MUST 照常写 spec**——B 轴与 C 轴要对照它。
- **跳过的是产物，不是门**：工作区隔离门、兼容取舍确认门、spec 过稿门**一道都不豁免**。无 spec 时兼容取舍结论与过稿结论 MUST 落在 PRD 或改动清单里，**MUST NOT 因为"没有 spec 可写"就不留痕**。
