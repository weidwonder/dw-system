# 两道确认门：兼容取舍确认门与 spec 过稿门

> spec 定稿前后、要请拍板人表态时读；两条路径都适用（Lean 把两道门同一批抛出）。按 RFC 2119 解释规范词。

## 兼容取舍确认门：spec 定稿前，由拍板人拍板

**兼容不是默认项。这是业务取舍不是技术选择，MUST 每次由人拍板，AI 在任何项目形态下都 MUST NOT 自行默认。**

**谁拍板**：solo → 开发者本人（`collab/solo.md` §3）；team → 业务负责人（`collab/team.md` §3）。流程一致，只是"问谁"不同。

1. **先列清单（AI 做）**：逐条列出本次改动会改变的**既有可观察行为**——旧接口请求/响应形状、旧字段与旧枚举值、旧数据在新逻辑下的解读、旧调用方（外部系统、老版本客户端、定时任务、报表）依赖的行为、用户已形成的操作习惯。**清单为空时也要显式写一句"本次不改变任何既有可观察行为，无兼容取舍"**，不许静默跳过。
2. **逐条问拍板人（业务语言）**：每条给三个选项 + 一个推荐 + 一句理由，按 `用户沟通纪律.md` 只讲业务影响（谁受影响、影响多久、代价是什么），不讲实现方案；多条时一次性批量抛出，MUST NOT 一条一条问。

   | 选项 | 含义 | 代价 |
   |---|---|---|
   | **不兼容** | 直接切到新行为，旧行为立刻消失 | 仍在用旧行为的人立即受影响，代码干净无长期包袱 |
   | **兼容一段时间** | 新旧并存到某个到期日，到期后删旧的 | 要维护两套；**MUST 同时定下到期日与到期后的动作** |
   | **永久兼容** | 旧行为长期保留 | 包袱永久化；只有对外契约或不可控调用方才值得 |

3. **结论落盘（MUST）**：写进 eng-spec §8.1 兼容取舍决策表（Lean 写进 lean-change-spec 的兼容取舍一行）。选"兼容一段时间"的，MUST 在替换清单里把对应被取代物登记为**保留例外**，带同一个到期日与到期动作——两处日期不一致就是漏洞。
4. **拍板人未回复不算确认**：MUST NOT 以"先按兼容做，以后再说"推进——那等于替用户选了代价最高的一项。
5. **本门过完 MUST 接着过 ↓ §spec 过稿门**（Lean 是同一批抛出，不分两轮）：本门只覆盖被改变的既有行为，全新能力一条都不在这份清单里，因此拍完 MUST NOT 直接进 Step 6。

## spec 过稿门：spec 定稿后、Coding Plan 之前

**这道门收的是「要做的事对不对」，不是「怎么做对不对」。** spec 是零上下文 coding agent 唯一的输入；它写偏了，后面每一步都照着偏，而下游没有任何一道门会重新去问需求方要什么。

**谁拍板**：solo → 开发者本人（`collab/solo.md` §3）；team → 业务方（`collab/team.md` §3）。流程一致，只是"问谁"不同。

### 摆什么给拍板人

**MUST 摆**（spec 里业务可判定的部分）：§1 范围与"不做什么"、§1.1 功能需求、§8.1 兼容取舍决策、§11 完成定义。

**MUST NOT 请拍板人确认**：§2 数据模型、§3 接口契约、§4 核心逻辑、§7 可观测性，以及任何文件、类、函数、存储、框架的选择——那些是详细程序设计，由 AI 自主完成并自检（`用户沟通纪律.md` §3）。**本门 MUST NOT 被当成把技术选型做成待选项让用户挑的通道**。solo 下拍板人本人愿意通读全份是他的自由，但**你请他表态的参照物 MUST 仍限定在上面那四项**。

### 怎么算过了这道门

1. **逐条落稿（MUST）**：拍板人提的每条意见 MUST 逐条改进 spec，或明确回"不改 + 一句话理由"，**MUST NOT 默默忽略**——沉默的忽略无法与遗漏区分。
2. **改到哪儿要回上一道门（MUST）**：意见改动了 §1.1 功能需求、§11 完成定义或 §8.1 兼容取舍决策时，MUST 先回 §兼容取舍确认门 重过一遍清单再回本门（改需求可能引入新的既有行为变更，而那份清单是照旧版需求列的）；只改技术章节的直接回本门。
3. **怎样算"定稿了"（三条判据，MUST 照此判，MUST NOT 自行解释）**：
   - 拍板人逐点回复，或明确说"就按这个走 / 没问题 / 可以开工"这类整体认可 → **算定稿**。
   - 只回了其中一部分 → **只就未回的那几项再问一次**，已回的不重复问；MUST NOT 因为部分未回就整份重来。
   - **没有回复** → MUST NOT 进入 Step 6，也 MUST NOT 反复追问。一句话告知"等你确认后我再出 Coding Plan"，然后停在这里等——本门与 §兼容取舍确认门 是 spec 阶段之后**仅有的两个**允许因等拍板人而挂起的流程内点；spec 阶段之前的大架构确认门与不可逆确认门（`用户沟通纪律.md` §1）同样 MUST 等（它们都是门，不是对齐开销）。

### 跳过本门只有一条通路

**拍板人在本次对话里显式表态**（"这次不用看 / 直接往下 / 跳过"）才跳过。三条 MUST NOT：

- **MUST NOT 主动提议跳过**——把"要不要省掉这一步"摆到拍板人面前，等于替他把默认值改成跳过。
- **MUST NOT 自行跳过**：改动小、只有我一个人用、上一道门刚问过、spec 是我照着他的话写的——这些都不成立。
- **跳过只对本次流程有效**，MUST NOT 记成项目级默认、MUST NOT 写进标记块、MUST NOT 在下一次流程里沿用。

### 结论 MUST 当场留痕

完整流程写进 eng-spec §13 过稿记录；Lean 写进 lean-change-spec 的过稿记录行。内容为日期 + 三选一结论（定稿 / 拍板人显式跳过本次 / 提了哪些意见及落稿情况）。**不留痕就无法与"漏过了这道门"区分**——那正是代码评审门的文档轴要核对的形态。

### 与相邻两道门的参照物划分（MUST NOT 互相顶替）

| 门 | 参照物 | 时点 |
|---|---|---|
| 大架构确认门 | 本次改动有没有改变主干路**形状** | Step 4 之前（spec 还没写）|
| 兼容取舍确认门 | 被改变的**既有可观察行为**要不要兼容 | spec 定稿前 |
| **spec 过稿门** | **整份 spec 描述的事是不是拍板人要的** | spec 定稿后、Step 6 前 |

大架构确认过 **MUST NOT 被读成"拍板人读过 spec 了"**——那一刻 spec 还不存在。兼容取舍逐条拍过 **MUST NOT 被读成"整份 spec 已被认可"**——那道门只覆盖被改变的既有行为，全新能力一条都不在它的清单里。
