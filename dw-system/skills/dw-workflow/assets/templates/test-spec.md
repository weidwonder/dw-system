# 【repo】_测试方案 — 【功能名】

> 只专注当前代码仓库涉及的部分（功能代码已开发完成）。配合 PRD / Overview / spec / coding plan。
> 输出：`docs/spec/YYYY-MM-DD-<repo>-<feature>-test-spec.md`。
> **风险驱动，不是模板枚举**：不要机械按"正向/异常/边界/权限"铺用例；先识别高风险点，再设计测试。方案要**可实施**——给到 API 调用模型和数据构造方案，能直接落成测试代码，而不是只写"业务场景+测试意图"。

## 纪律（贯穿全文）

- **输入权威等级**：PRD / PRD 更新说明 > 后端技术文档 / spec > 项目级实施方案（coding plan）> 当前实现事实。实施方案只作"风险增强上下文"，**不得用它覆盖业务规则或接口契约**；冲突时以高等级为准，并把冲突列入 §10。
- **"待确认"防脑补**：后端文档没定义的字段/错误码/鉴权方式/副作用/表结构/唯一键/枚举/清理方式，**一律标"待确认"，禁止自行脑补**。MUST 先查 `engineering-context/` 卡片（查到的附 cite）；卡片里没有就读源码核实并当场补卡（`dw-code-facts` 的 `代码事实纪律.md` §4），读了源码仍定不下来的才标待确认。
- **测试反模式（设计与落码都要避开）**：
  - **实现耦合**：断言挂在内部函数/私有结构/调用次序上——实现一重构测试全红，但业务行为没变。测试只挂**稳定缝（seam）**：接口契约、对外可观察行为、落库副作用。
  - **同义反复**：预期值用与被测代码相同的算法现场重算——代码错测试也跟着"通过"。预期值必须来自独立来源：PRD/spec 给的口径、手工推演的具体值、已验证的黄金样本。
  - **水平切片**：先一口气写完全部测试再开始实现——集成风险压到最后才爆。按用例/链路小步走：一个用例红→实现→绿，再下一个（与 coding plan 的 TDD 步骤一致）。
  - **自证替身**：替身替换掉的是被测对象本身，或测试只断言替身返回了它被预设的值——被测对象一行没跑，怎么改都是绿的。替身只替换被测对象的依赖（外部服务、时钟、网络），断言 MUST 落在被测对象产出的结果或副作用上；被测对象对依赖发出的调用（调了哪个依赖、带了什么参数）也是它的副作用，可以断言。
- **测试资产**：真实输入优先于构造数据、长链路必须端到端且断言中间产物、没覆盖的重要场景要挂账——三条规则见 `测试资产纪律.md`，落点分别在 §4 / §8 / §11。

## 2. 高风险点分析 + 优先级
先找出最该测的地方，按 影响×可能性 排序，把测试火力对准高风险点（而非平均用力）。**逐条对照下面这份隐蔽缺陷清单**，命中的登进表：

- [ ] PRD 与后端文档不一致
- [ ] 状态流转遗漏 / 非法状态可操作
- [ ] 接口之间数据传递错误
- [ ] 用户/角色/租户/资源归属越权
- [ ] 幂等 / 重复提交 / 重试导致数据重复或状态错乱
- [ ] 并发下库存/余额/额度/次数等竞争
- [ ] 异步任务/回调/消息延迟导致最终状态不一致
- [ ] 删除/取消/撤回/失败/超时后的二次操作
- [ ] 部分成功/部分失败后的补偿或回滚
- [ ] 前端不可见但接口可直接调用的非法路径
- [ ] 历史数据/脏数据/边界配置/开关配置下的异常行为

## 4. 测试数据构造方案（Fixture）
说明每个高价值用例/链路的入参数据从哪来、怎么准备、怎么传递、怎么清理。**不要写"构造 8 个词""准备有余额用户"这类不可执行描述**，必须落到实体/字段/准备步骤。

**真实样本优先**（见 `测试资产纪律.md` §2）：有真实样本可用的 Fixture，"构造方式"一列直接填**样本文件路径**（如 `tests/fixtures/订单超时自动取消/input-支付回调迟到.json`），不要另写一份构造数据——真实数据的不规整（多余空格、异常编码、超长字段、缺失键）正是构造数据永远想不到的。构造数据只用于真实样本覆盖不到的维度：极值、并发、故意的非法输入。

## 6. 需求 → 用例可追溯矩阵 ★ 最重要产物
保证每条需求/验收点都有用例覆盖，反向也能从用例查到它验证的是哪条需求。

**覆盖状态填 ✅ 的条件**：用例专门为这一条准备了前置状态、触发了它的动作、并断言了它的结果；用例只是途经它、断言落在别处的 MUST NOT 填 ✅，只断言了它一部分结果的填"部分"，没有专门针对它的用例的填"缺"（认定口径见 `测试资产纪律.md` §3）。

**首列的编号 MUST 沿用 spec 那一套原号**：功能需求用 `FR-###`、验收项用 `AC-###`，前缀 + 三位零填充，永不复用、永不重排（编号规则见 `assets/templates/eng-spec.md` §1.1，Lean 见 `lean-change-spec.md`）。**MUST NOT 在本文另编一套**——追溯矩阵的全部价值就在于两侧是同一个号，重编一次，从用例反查需求这个方向就断了。上游 spec 没有编号的存量项目按 `dw-review-gate` 的 `子代理模板.md`〈本轴职责〉忠实轴那段的降级契约走：退回自然语言逐条对照，首列写需求原文并在表上注明"上游 spec 无编号"。

## 8. 端到端链路测试方案

**何时必须有**（命中任意一条即 MUST，见 `测试资产纪律.md` §1）：流程跨 ≥3 个组件/服务/进程；含异步或多阶段环节（队列、定时、回调、重试、多轮模型推理）；有中间产物落盘、落库或传给下一环。

从业务目标出发，覆盖五类链路，重点验证跨接口**状态一致性、数据守恒、异常恢复、并发冲突、异步最终一致性**。每条链路带"数据准备"小节；每步写明调用的 API ID、请求字段、从前序步骤保存的响应字段、本步断言的响应字段与最终状态。

> **每个环节的中间产物 MUST 各写一条断言，不许只断言末端。** 只验末端的链路测试有两个致命问题：中间环节坏了而末端碰巧正确时它是绿的；末端错了它只会告诉你"错了"，不会告诉你**哪一环**开始错。断言挂在环节间的契约（落库记录、消息体、返回结构）上，不挂在内部函数调用次序上；预期值来自独立来源，不用被测代码现场重算。异步环节用条件轮询等待目标状态，不用固定 sleep 猜耗时。

| 链路类型 | 链路# | 数据准备（Fixture ID + 起始状态）| 步骤序列（每步：API ID / 入参 / 用到的前序变量 / **本步中间产物断言** / 最终状态）|
|---|---|---|---|
| 主链路 | L1 | 【FX-XXX；起始状态】 | 【1. API-A → 断言落库 status=pending 且校验和一致，保存 x；2. API-B 用 x → 断言结果条目数=3 且每条含题号；3. …；末端 → 断言列表可见且计数 +1】 |
| 分支链路 | L2 | 【】 | 【】 |
| 异常链路 | L3 | 【】 | 【依赖不可用/超时后的恢复；断言中断点的中间态可恢复】 |
| 并发链路 | L4 | 【】 | 【竞争同一资源，验证守恒/不超卖】 |
| 异步一致性 | L5 | 【】 | 【消息延迟/回调后最终一致；轮询目标状态而非固定等待】 |

## 12. CI 门禁分层（`merge-gate="pr"` 时，按需）
把测试挂到不同 CI 阶段，快的守 PR、慢的守发布：
| 阶段 | 跑什么 | 阻断条件 |
|---|---|---|
| PR gate | 单元 + 快集成 + lint | 失败即挡合并；P0/P1 用例必过 |
| nightly | 全集成 + 链路 + 慢 NFR | 失败告警，next-day 修 |
| pre-release | 全量 + 模拟链路 + eval 门（含 AI）| 失败阻断发布 |

> **flaky 隔离**：偶发失败的用例先隔离进 quarantine 清单（带责任人+复查日期，只许变短），不许长期一直红/一直被忽略——否则门禁失去意义。
