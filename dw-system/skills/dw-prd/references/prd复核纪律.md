# PRD 复核纪律（用户定稿后、落盘前的强制门）

> 适用：本 skill 产出的任何一份 PRD（三类模板都不豁免）。执行时机在 `00-prd生成流程.md` §组稿 第 5 步——跑完 `prd质量清单.md`、**用户在过稿门定稿之后**、**落盘确认门之前**。三者的先后是硬约定：稿子先定型，再交第三方视角查，最后才把要用户拍板的冲突摆给他。
> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD / MAY。
> **本文小节**：[为什么必须交给子代理](#为什么必须交给子代理) · [门禁](#门禁) · [两条轴](#两条轴分开查分开报) · [子代理 prompt 模板](#子代理-prompt-模板) · [严重度与处置](#严重度与处置) · [与其他纪律的关系](#与其他纪律的关系)

## 为什么必须交给子代理

刚写完 PRD 的会话有两处结构性盲区：

1. **它被自己的叙事浸透**。四批提问一路走下来，它记得"我为什么这么写非目标"，于是复核时最容易替自己辩护，看不见目标与非目标已经打架、验收项已经和详细行为节对不上。这与姊妹 skill `<skills 根>/dw-review-gate/SKILL.md` §为什么必须交给子代理 想明白的是同一件事。
2. **现状节是它自己查的**。让同一个会话验"我查得对不对"等于没验——它不会重查一遍卡片，只会重读一遍自己写下的那句话。而且它刚跟用户来回四批，最容易把**用户的口述**当成**系统事实**。

子代理不带这两段记忆：甲轴只拿 PRD，乙轴独立重新取证。附带收益是省主上下文——组稿时上下文已被四批对话装满，再去扫全系统事实必然挤掉正稿。

## 门禁

- 组稿完成、`prd质量清单.md` 自检通过、**且用户已在 `00-prd生成流程.md` §组稿 第 4 步的用户过稿门定稿**后 MUST 执行本门。**未过门 MUST NOT 进入落盘确认门，MUST NOT 把 PRD 或 UI 原型写入 `docs/`。**
- **MUST NOT 在用户读稿之前就派子代理**——哪怕 PRD 和原型刚写完、看着已经完整。复核报告是针对**某一版稿子**的：用户随后提的意见会让它整份作废，而作废的报告最危险的地方不是白花的那点成本，是主会话会带着"这稿已经复核过了"的印象去接受大改，改出来的部分从头到尾没被任何第三方视角看过。**用户尚未表态 MUST NOT 读成"用户没意见"**，判据见 §组稿 第 4 步的三条定稿判据。
- 用户在过稿门定稿后又提出新意见（改稿再定稿）时，MUST 对改后的那一版**重跑受影响的那一轴**，MUST NOT 拿旧版的报告顶替。
- **落盘确认门上用户要求改稿**时同理：改动触及目标 / 非目标 / 现状结论 / 详细业务行为 / 验收项任一处，MUST 重跑受影响的那一轴、再重走一次该门的回述，**MUST NOT 拿改稿前的报告直接落盘**；只改措辞、补错别字的不必重跑。
- `change-prd` / `product-prd` → MUST 派 **2 个并行子代理**，自洽轴 / 冲突轴各一个，各自独立返回报告。
- `lite-issue-prd`（Triage 四项全否的单点改动）→ MUST 派 **1 个子代理**跑两轴精简版，报告仍**分两节**写，MUST NOT 合并成一段总评。
- harness 不支持子代理时：降级为主会话**分轮**执行，一轴一轮、一轮一份报告。MUST NOT 合并成一次"总体看看"——合并会让一轴的显眼问题掩盖另一轴。
- **本门 MUST NOT 因协作面而裁剪**。solo 没有评审会，这道门就是 PRD 唯一的第三方视角（`collab/solo.md` §3 的同一条理由）；team 有评审会，但评审会读的是**这份稿子**，稿子与系统冲突不会因为多几个人读就自己显形。

## 两条轴（分开查、分开报）

两轴的切法沿用姊妹 skill 分轴评审的同一个框架——**每轴盯一个参照物**，因此互不重叠，也不与 `prd质量清单.md`（参照物是模板骨架）重叠：

| 轴 | 参照物 | 只看什么 | 不看什么 | 典型命中 |
|---|---|---|---|---|
| **甲 · 自洽轴** | PRD 自身（含 UI 原型） | 内部有没有互相打架的地方；一个零上下文的下游 agent 拿这份能不能不回头问就动手 | 现状写得对不对（那是乙轴的事） | 目标与非目标打架（目标要做的事被非目标挡住）、验收项与详细行为节对不上、UI 原型声明覆盖的状态与正文不一致、验收项落不到任何一条详细行为上、"做完的标志"与验收标准不是同一件事 |
| **乙 · 冲突轴** | `engineering-context/` 卡片 + 源码 + `docs/REQUIREMENTS.md` + `docs/requirements/` 子模块 + `docs/index.md` 现行区 | PRD 与**现有系统**的功能、约束是否冲突 | PRD 内部写得顺不顺（那是甲轴的事） | 见下表六类 |

**乙轴的六类冲突**（逐类过，MUST NOT 只挑好查的那两类）：

| # | 冲突类型 | 判据 | 为什么它值一条 |
|---|---|---|---|
| 1 | **功能已存在** | 要做的能力在 `capability-registry.md` 里已登记，或卡片里已有等价对外接口，PRD 却当成全新功能提，且没写与既有能力的关系 | 最贵的一类返工：做完才发现系统里已经有一个 |
| 2 | **行为矛盾** | 新规则与某条**已生效**的业务规则互斥（如现有"超时 30 分钟自动取消"，PRD 要"永不取消"），而该规则没有出现在 PRD 的改动范围里 | 实现时必然二选一，此刻不定就是编码阶段 AI 自行猜 |
| 3 | **约束违反** | 撞上系统既有硬约束：鉴权与越权边界、数据保留期与合规口径、对外契约的兼容窗口、字段枚举与唯一键 | 这类冲突到上线才炸，且往往不可逆 |
| 4 | **依赖已废弃** | PRD 假设存在的能力，在 `ctx discover` 的 out-of-scope 提示里、或卡片的废弃标记/陷阱项里 | PRD 建在将死的地基上 |
| 5 | **现状失实** | 独立重新取证后，PRD 现状节的条目与卡片或源码对不上 | 主会话查漏或把用户口述当事实的唯一拦截点 |
| 6 | **非目标挡不住** | PRD 写"不改 X"，但要做的事必然波及 X（共享同一份实现、同一张表、同一个开关） | 最阴的一类：护栏写了，但护栏本身失效，下游会以为有保护 |

## 子代理 prompt 模板

两个子代理共用同一段前置，只换【轴】那一段。**前置里点名加载本 skill 是必须的**——子代理默认不带本流程的纪律，靠关键词自动触发不可靠；同时把 skill 根目录的绝对路径也给它，作为按名字唤起失败时的兜底。派发时 MUST 把每个 `【…】` 占位符替换成真实值（协作面、代码图谱是否可用、项目根、PRD 全文），带着占位符派出去的子代理只会返回一份泛泛而谈的报告。

**为什么 PRD 要内联进 prompt 而不是给路径**：本门在**落盘之前**执行，此刻 PRD 与 UI 原型都还只在对话里，`docs/spec/` 下没有这份文件。不内联的话，子代理会去那个目录找、找不到、然后开始猜。**UI 原型的全文不必内联**（它的 CSS 与脚本对两轴都无意义），内联它的**结构摘要**即可：页面 / 可切换状态 / 关键字段与文案 / **元素上的 `data-anno` 说明与 `data-anno-kind="question"` 待拍板项**（用 `node <skills 根>/dw-prd/scripts/preview.mjs annotations <原型文件>` 取）。甲轴要查的"原型与正文冲突"只可能发生在这一层，而气泡里的说明恰恰是屏幕上看不见、最容易与正文对不上的那部分。

```text
你是 dw-prd 的 PRD 复核子代理，本次只负责【自洽轴 / 冲突轴】其中一轴。

## 前置
先加载 dw-prd skill，读 references/prd复核纪律.md 与 references/prd写作纪律.md。
冲突轴另读 references/00-prd生成流程.md §批 B → 现状怎么取证——取证顺序以那一节为准，
本 prompt 不另立一套。
skill 未能按名字唤起时，直接读这些文件：【skill 根目录绝对路径】/references/…
本项目协作面 =【solo / team】；代码图谱 =【可用 / 无】；项目根 =【绝对路径】。

## 评审对象
下面是待复核的 PRD 全文（用户已定稿、但尚未落盘，`docs/spec/` 下没有这个文件，MUST NOT 去那里找）：

<<<PRD
【PRD 全文】
PRD>>>

UI 原型结构摘要（不涉及 UI 时写"不适用"）：
【页面 / 可切换状态 / 关键字段与文案 / 元素上的 data-anno 说明与 question 待拍板项；原型全文同样尚未落盘】

## 本轴职责
- 自洽轴：只看这份 PRD 内部有没有互相打架的地方，以及一个零上下文的下游 agent 拿着它
  能不能不回头问就动手。逐条比对：目标 ↔ 非目标、验收项 ↔ 详细业务行为节、
  一句话结论的"做完的标志" ↔ 验收标准、UI 原型摘要 ↔ 正文的 UI 描述。
  MUST NOT 评判现状写得对不对（那是冲突轴的事），MUST NOT 重跑 prd质量清单.md 的骨架完备性
  勾验（主会话已经跑过）。
- 冲突轴：只查 PRD 与现有系统的功能、约束冲突，逐条过本纪律 §两条轴 的六类。
  取证按 00-prd生成流程.md §批 B 的顺序：先 ctx find-scenes / discover / get-card，
  卡片没覆盖的模块再读源码（有代码图谱走图谱，没有就把重探索外包给子代理）。
  MUST NOT 评判 PRD 内部写得顺不顺（那是自洽轴的事）。

## 硬要求
- 只报告，MUST NOT 修改或创建任何文件，MUST NOT 写 engineering-context/，
  MUST NOT 把 PRD 落盘——落盘是主会话过完落盘确认门之后的动作。
- 每条问题必须给出 位置(PRD 的节名或原文片段) + 问题描述 + 建议处置 + 严重度，
  不接受"感觉不妥"。
- 冲突轴每条冲突 MUST 带出处：卡片 cite（path#anchor @确认时间）或 `文件:行`。
  **无出处的冲突指控视为幻觉，MUST NOT 提交。**
- **查不到 MUST NOT 报成冲突**。零命中只意味着这个模块的卡片还没建，处置是读源码；
  卡片与源码两条路都取不到证时，写进「未能取证」段并说明缺什么，
  MUST NOT 转成冲突结论，也 MUST NOT 因此判定"这个项目没有可信事实"。
- 判不准的写进「存疑」段并说明缺什么信息，不要为了凑数编问题，
  也不要把拿不准的降级放过。
- 本轴没有问题就明确回答"本轴无发现"，不要为凑数扩到另一轴。

## 返回格式
| # | 严重度 | 位置 | 问题 | 出处 | 建议处置 | 出口 |
「出口」只填【当场改稿】/【回流到批 B】/【回流到批 D】/【需用户拍板】之一，对应本纪律
§严重度与处置 的**三个**出口（中间那个出口按落点细分成批 B / 批 D 两个取值）——这一列
决定主会话把它送去哪里，MUST NOT 留空、MUST NOT 自造别的取值。拿不准填哪个就照实填你
倾向的那个，并在「存疑」段说明。
严重度口径：P0 = 会让下游做出错的东西（与现有系统硬冲突 / 现状失实 / 内部矛盾到无法执行 /
非目标挡不住导致越界）；P1 = 应当修（验收不可判定、功能与既有能力重复却没说明关系、
原型与正文冲突、依赖已废弃未标注）；P2 = 建议考虑。
末尾另起三段（没有就写"无"）：
- 「取证足迹」（**冲突轴 MUST 写，无论本轴有没有发现**）：本轴为取证碰过的每个模块一行，
  三列 `模块 | 取证方式 | 出处`——取证方式只填【卡片命中】/【现读源码】/【未命中】，
  出处对应填 cite / `文件:行` / 留空。主会话只消费【现读源码】那几行去补标注，
  所以**取证方式 MUST NOT 省略**：省了就只能靠有没有 `文件:行` 猜，猜错会给已有卡片的
  模块贴上"尚无 card，待补卡"，把下游引去重复补卡。
- 「未能取证」：**点**级（哪一条现状、哪个冲突猜想证不出来），说明缺什么。
  与「取证足迹」的**模块**级不重叠：足迹回答"碰过哪些模块、怎么碰的"，本段回答
  "哪个具体判断悬着"。
- 「存疑」：判不准的点，说明缺什么信息。
```

## 严重度与处置

- **补交接面（无条件，与有没有发现问题无关）**：冲突轴交上来的「取证足迹」里**取证方式为【现读源码】**的那几行（其余两类不在此列），主会话 MUST 按 `00-prd生成流程.md` §批 B 第 3 步在 PRD 现状节补上模块名、`文件:行` 与规定的标注原文。**MUST NOT 因为"本轴无发现"就跳过这一步**——复核阶段新读到的事实同样是本次取证的产物，不落标注，下游 `dw-workflow` 就不知道该给哪些模块补卡。（补的是 PRD 里的标注，**不是卡片本身**：本 skill 不写 `engineering-context/`，补卡仍是下游的动作。）**补交接面未做 MUST NOT 判为过门**——它不是 P0/P1 里的一条，而是与之并列的过门条件，否则"本轴无发现"时这一步会被整条跳过。
- **P0 与 P1 MUST 全部处理完**才算过门；P2 由主会话决定当场改或写进 PRD 的开放问题清单。
- "处理完"有且只有**三个出口**，MUST 逐条选一个，**MUST NOT 悬空**。分流判据一句话：**事实错了回去补，取舍待定才给用户**。

  | 出口 | 适用 | 动作 |
  |---|---|---|
  | **当场改稿** | AI 自己就能补的：内部矛盾、缺出处、验收表述不可判定、原型与正文不一致 | 直接改稿，改完在报告里标「已修」 |
  | **回流到某一批** | 事实层面错了，不是措辞问题：现状节条目失实（乙轴第 5 类）、验收项落不到任何一条详细行为 | 按 `assets/question-bank.md` §追问触发 的 `[组稿·复核后]` 条目回批 B 重新取证 / 回批 D 补齐，改完重跑受影响的那一轴。**`lite-issue-prd` 没有独立现状节**，回流落点是它的「改动点」表与「场景 → 预期」表（对应关系见 `prd质量清单.md` §完备性 的三类模板矩阵）——**MUST NOT 因为"轻量模板没有那一节"就把这个出口判为不适用** |
  | **进落盘确认门** | 需要用户拍板的：与现有系统的取舍冲突（乙轴第 1–4、6 类基本都是） | 逐条并入落盘确认门的回述清单，用**业务语言**摆出取舍与两边后果 |

  **经「当场改稿」与「回流到某一批」这两条路径处置的每一条，MUST 记进"用户定稿后改了什么"的清单**，由主会话在落盘确认门逐条列给用户（判据在 `00-prd生成流程.md` §组稿 第 6 步）。**MUST NOT 因为"这条不用用户拍板"就不告知**——用户定的是复核前那一版，稿子被改过而他不知道，等于让他确认一份自己没读过的文件。反过来，本门**没有**待拍板条目、也**没有**实质性改稿时，落盘确认门按该步的退化规则收成一句话告知，MUST NOT 再要用户点第二次头。

  **MUST NOT 把"回流到某一批"的条目挪进落盘确认门**——现状写错了是**取证没做到位**，把它摆给用户等于让用户替 AI 校对事实；用户此刻手里没有卡片也没有源码，只能点头。

- **MUST NOT 自己替用户选**。乙轴报出"系统现在是 A，PRD 要 B"时，AI 的职责是把这个取舍连同两边的后果摆清楚，不是挑一个写进 PRD 就算解决。
- **MUST NOT 把需用户拍板的条目悄悄降级成「开放问题」**塞进 PRD 了事——开放问题的结算规则（`collab/solo.md` §2 / `collab/team.md` §2）管的是**提问阶段闭不上的点**，不是复核查出的系统冲突。冲突写成开放问题等于把一个已经查实的矛盾降级成一句"待确认"。
- 改稿后 MUST 重跑**受影响的那一轴**确认（只重跑改动涉及的轴，不必两轴全跑）。
- 子代理判断有误时，主会话 MUST 在回述里写明"不改 + 一句话理由"，MUST NOT 默默忽略——沉默的忽略无法与遗漏区分。
- team 协作面：本门是评审会前的地板，**不替代业务方拍板**；乙轴查出的口径冲突仍按 `collab/team.md` §3 送业务方。
