# 协作面 = solo

> 加载条件：无其他人类协作方时加载。
> 本文按 RFC 2119 解释 MUST / MUST NOT / SHOULD / MAY。
> 本文只管**因为没有别人**才发生变化的约定：谁提需求、谁拍板、开放问题去哪。它裁掉的是**对齐开销**，MUST NOT 被读成"PRD 可以写得糙一点"——没有评审会兜底时，非目标与验收口径反而更容易失守（§3）。

## 1. 需求来源与拍板人都是你

- 需求来自你自己，**MUST NOT 因为"等业务方确认"而挂起**任何一批提问。
- 每批问题照样一次抛全，只是答问的人是你本人。**MUST NOT 退化成一问一答**——批量提问的收益（少轮次、逼你把整批取舍一次想清）与有没有第二个人无关。
- 目标、非目标、边界、验收口径**由你当场拍板**，拍完 MUST 立即落进 PRD 对应章节。口头拍板不落盘 = 下一个会话拿不到，等于没拍。

## 2. 没有评审会，开放问题 MUST 自己逐条闭环

- **MUST NOT 开评审会**这类等待人类到场的动作，也 MUST NOT 把结论留给"评审时再说"。
- 团队场景里，"开放问题"可以挂到评审会上由多方推进；这里没有那个会。因此**开放问题清单 MUST 在成稿前逐条闭环**：要么当场拍板写进正文，要么明确写"本期不解"并给出对应的非目标条目。
- 不允许出现无主的开放问题——挂着没人认领的问题，最后都会在编码阶段变成 AI 自行猜测。

## 3. 四条硬纪律 MUST NOT 因"就我一个人"而裁

**没有评审会替你发现漏洞，这四条就是 PRD 唯一的自检面：**

1. **非目标必须硬**（`prd写作纪律.md` §1）。一个人写需求最容易边写边扩，非目标是唯一的刹车。
2. **验收可判定**（同上 §3）。没有测试同事逐条勾验，验收写成"体验更好"就等于没有验收。
3. **frontmatter 的 `lifecycle` 不裁剪**。个人项目一样会攒下过期 PRD，而且没有同事提醒你哪份已经不作数了。新建 PRD 带 `lifecycle: active`，归并后改 `merged` 并加头注——一行的事，省的是几个月后被自己的旧文档带偏（见 `00-prd生成流程.md` §PRD 生命周期）。
4. **复核门不裁剪，但 MUST 等你先把稿子定下来**（`prd复核纪律.md`；时机见 `00-prd生成流程.md` §组稿 第 4/5 步）。团队里还有别人会替你读这份稿子并喊出"这个我们系统里已经有了"；solo 没有那个人，**双轴子代理就是这份 PRD 唯一的第三方视角**——省掉它等于让"功能其实已存在""新规则与现有规则打架"这类问题一路穿到编码阶段。复核门交上来标着「需用户拍板」的冲突，在落盘确认门由你**当场逐条拍板**（与 §2 的开放问题同理：这里没有会可以挂），拍完 MUST 立即落进 PRD 正文。

> 同理，**批 C 的特殊场景穷举不因协作面精简**：多人同时操作、信息迟到、处理失败、业务过期这些坑与项目有几个人无关，它们只与业务本身有关。

## 4. 业务语言纪律不因"用户就是开发者"而豁免

你既是产品又是技术，但**提问与成稿仍 MUST 用业务语言**（`业务语言纪律.md`）：

- 用技术词向自己提问，会让你直接跳到实现方案，**绕过需求澄清本身**——这正是本 skill 要防的失败模式。
- PRD 正文写死实现，会越权占掉下游 `dw-workflow` 的设计空间；PRD 的细节边界永远是"用户可感知的行为契约与验收口径"。
- 差别只在**取证环节**：你可以直接读自己的代码核实现状，不必像面对业务方那样字斟句酌地翻译来源注记——但写进 PRD 正文的那句话，仍 MUST 是业务事实。

## 5. 详略不由本文决定

写多细（分流选哪个模板、现状要不要逐条带 cite、运营度量写到什么粒度）由**改动形态与项目自身资产**决定：模板分流看 `00-prd生成流程.md` §分流表（单点改动 / brownfield 变更 / 整品），现状取证看 §批 B 的取证顺序（先查卡片、卡片没覆盖再读源码，对任何项目都一样）。**MUST NOT** 从"只有我一个人"推出"默认写最简的那份"——一个人维护的十万行系统，需求写糊了没有任何人会拦住。

## 一句话

协作面 = solo 砍掉的是**对齐动作**（评审会、等业务方拍板），砍不掉的是**自检**——非目标、可判定验收、`lifecycle`、复核门一条不减，因为没有第二个人替你读这份 PRD。
