# dw-prose：把话写全，再把多余的删掉

本 skill 管**一段文字该写什么、该删什么**：规范文本、文档、代码与测试注释、提示词、报错与界面文案。文档放哪、生命周期与归档归 `dw-doc-governance`；skill 的结构与触发归 `skill-principle`；spec 的章节与零上下文要求归 `dw-workflow` 的 `spec写作纪律.md`。本 skill 是判断标准，不是逐条勾选的清单。按 RFC 2119 解释规范词。

## 输入

- MUST 有明确的**范围**（哪些文件或哪段文字）。没有范围就说明缺什么并停下，MUST NOT 自行扩大到全仓。
- **只评不改**还是**动手改**由任务决定：review / 审计类任务只报告；明确要求写、修、精简的任务才落笔。
- 历史文档（已归档的 spec / plan / report、既有迁移指南、变更日志的既有条目）不在范围内：它们记录的是当时的事实，MUST NOT 为了"读起来现代"去改写。
- 生成物（目录表、快照、由脚本产出的清单）不是散文：改它的来源，再重新生成。

## 一、完整命题规则（删改前必做）

动一段文字之前，先把它承载的命题逐条列出来。每条命题由这些成分构成，**成分缺一个就是另一条命题**：

| 成分 | 例 |
|---|---|
| 谁、做什么 | 安装器 / 删除旧 skill 目录 |
| 条件、时机、先后 | 用户确认之后、复制新 skill 之前 |
| 模态 | MUST / MUST NOT / SHOULD / MAY |
| 反向保证与例外 | 旧名字之外的同目录条目不碰；符号链接只删链接 |
| 归属、副作用、失败后果 | 删除失败则中止，项目保持旧安装可用 |

删形容词、删重复、删叙述，**前提是每条命题都还在，且读起来更清楚**。字数变少本身不算改进；为了过体积上限而丢命题是错误，该做的是把内容搬回它的家（`dw-workflow` 入口〈两条总纲〉）。

**就地要有完整的局部规则**：读者在这个位置需要的行为、失败、归属、后果，这里写全；架构、算法、长例子、来历，指向它的家。展开只有一处，关键的一句可以就地重复。

**理由的去留**：省掉它读者可能误用或做出错误的简化——留，写成现在时的反事实（"没有这条，X 会发生"）。只是交代这条规则怎么来的——搬走，见第三节。

## 二、各类文本必须写什么

这不是单向的缩短：代码、类型与结构没表达出来的规则，要**补**。

| 文本 | 必须有 | 不该有 |
|---|---|---|
| 规范文本（skill、纪律、spec） | 触发条件、动作、判据、完成标志、失败处置；防误用的理由 | 来历、评审经过、"为什么当初没这么做" |
| 公开接口注释 | 调用方看得见的返回差异、抛错、副作用、归属、时机、取消与持久性 | 复述签名 |
| 内部注释 | 非局部的结构、不变量、竞态顺序、安全边界、反直觉的失败行为 | 控制流旁白、复述代码 |
| 测试注释 | 非显然的设计：为什么要这个夹具、这条断言、这个平台分支、为什么走真实入口 | 逐步走查、用例清单 |
| README / 卡片 | 使用者面对的规则：配置、语义、失败、限制、扩展点 | 变更记录、逐方法照抄 |
| 操作指南 | 前置条件、必做动作、真实入口、可观察的验证 | 夹具旁白 |
| 决策记录 | 问题、决定、考虑过的方案与否决理由、代价 | 已上线后仍用"应当"口吻的计划 |
| 提示词与可见文案 | 措辞即行为：改它等于改行为，MUST 有对应的行为验证 | — |
| 报错与诊断 | 出错的对象或路径、违反的规则、怎么改 | 内部执行旁白 |

强调只留给改变行为的那半句。通篇加粗等于没有强调。

## 三、只写现状

对每段可疑文字问一句：**一个站在当前 HEAD、看不到任何会话记录与评审串的读者，能不能把这段里的每个引用都找到、每个说法都验证？** 不能——把还成立的事实改写成从仓库视角站得住的话，其余删掉。

| 这类内容 | 去处 |
|---|---|
| 哪一版改的、此前是什么样、改动前后对比 | git 历史；对下游有影响的进变更日志 |
| 出过什么事故、怎么查出来的 | bug 修复历史 |
| 试过哪些方案、为什么否掉、当时的权衡 | 决策记录（`dw-doc-governance`〈决策记录〉） |
| 还没做、以后想做 | `docs/TODO.md` |

分类、检索式、哪些**不算**残留、矫枉过正的几种删法，见 [references/清理推理残留.md](references/清理推理残留.md)——**要成批清理一个目录，或拿不准一处算不算残留时读**。

## 读取条件（到点才读；MUST NOT 预读，MUST NOT 凭记忆代替）

| 什么时候 | 读什么 |
|---|---|
| 要成批清理一个目录，或拿不准一处算不算推理残留 | `references/清理推理残留.md` |
| 拿不准该留多少、删到什么程度 | `references/校准例子.md` |

## 四、工作流

1. 确认范围、只评还是动手改、适用的项目说明。
2. 先读该文字描述的代码或规则本身，再判断这段文字。拿不准尺度时读 [references/校准例子.md](references/校准例子.md)。
3. 看范围内的全部文字，不只看最长的文件。检索与字数只用来找候选，判断靠读。
4. 每个候选归为：留 / 补 / 删 / 还原 / 改结构 / 挂起。MUST NOT 为了凑删除量制造改动。
5. 先改来源，再改派生物；学到一条新尺度后，回头把范围内同类段落一并处理。
6. 跑受影响的检查；改了可见文案的跑行为验证。
7. 汇报：看了哪些、改了什么、刻意留下的、挂起的、实际跑过的检查。

**两难才算两难**：至少两种写法都保住了全部命题、只是在公认的原则之间取舍不同，且本 skill 没给出答案——才算。只有一种写法保得住命题的，不是两难。只评不改时把两难如实列出，MUST NOT 为了推进而削弱命题。用户拍过板的尺度，提炼成不带来历的一组例子补进校准例子，再套用到范围内所有同类段落。

## 案例

**压缩一条规则**。原文："此前两处各列一份权威面清单，确实漂过（一份多了'废弃标记'），所以 MUST NOT 在本节复制那份清单，要看就跳到 §3 第 1 步。"命题两条：本节 MUST NOT 复制清单；清单的家在 §3 第 1 步。理由防误用，留，改现在时；"漂过"的经过搬进决策记录。改后："权威面清单只在 §3 第 1 步；本节 MUST NOT 复制——两处各列一份必然写岔。"

**补一条注释**。函数在删除前把路径解析后核对父目录，代码看得出"做了核对"，看不出"为什么"。补："删除目标由固定父目录加常量拼出；这里再核一次前缀，防止常量表日后被改成含路径分隔符的值。"
