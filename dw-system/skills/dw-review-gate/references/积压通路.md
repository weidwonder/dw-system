# 积压通路：定评审范围，定走哪条通路

> 评审门的第零步。够小的改动 MAY 登记积压、延到下一次门一并评；本篇定基点、判定顺序、积压必做的三件事与结算。按 RFC 2119 解释规范词。

## 第零步：定评审范围，定走哪条通路

**评审范围的基点是可移动的**：存在 `reviewed-through` tag 时取该 tag，否则取目标主分支。范围 = `git diff 【基点】...HEAD`，并入 `git status --porcelain` 里的未提交路径。**tag 不存在是正常状态**（存量项目、刚 clone 的仓库都没有），MUST 退回主分支基点照常执行，**MUST NOT 报错、MUST NOT 阻断本门**；它是**本地**资产，**MUST NOT 要求推送到远端**。tag 指向的 commit 已不可达（分支被重写）时同样退回主分支，并在报告首行注明"基点失效已退回主分支"。

**够小的改动 MAY 不当场跑本门，登记后延到下一次门一并评**——这条通路叫**积压**。按下表**逐条顺序判，命中即定**，MUST NOT 跳着判：

| # | 判定 | 命中时 |
|---|---|---|
| 1 | 本次改动命中 ↓〈禁止积压清单〉 | 当场跑 |
| 2 | **本次任务分支**（`git diff 【目标主分支】...HEAD`）代码 ≥20 行 **或** 文档 ≥40 行 | 当场跑 |
| 3 | **自基点起累计**（`git diff 【基点】...HEAD`）代码 >100 行 **或** 文档 >200 行 **或** 最早一条积压 commit 距今 >14 天 | 当场跑 |
| 4 | `merge-gate="pr"` | 当场跑——每次合并都经 PR，带着未评审的积压开 PR 等于把门禁推给审批人（该门同时是 `pr` 项目的发布门，见 `dw-worktree` 的 `worktree开发纪律.md` §完成与自动合并门） |
| 5 | 以上都不命中 | 积压 |

**第 2 条与第 3 条用的是两个不同的范围，MUST NOT 混为一谈**：第 2 条看**本次任务分支**，第 3 条看**自基点起的全部未结算量**。合一会让累计封顶永远轮不到——第二次积压时累计就已超过单次阈值，那条封顶再也不会命中。**单次阈值按整条任务分支算、MUST NOT 按单个 commit 算**，否则把 25 行拆成两个 13 行的 commit 就绕过去了。

**行数口径**：`git diff 【范围】 --numstat` 每行 added + deleted 之和，按文件分类累加——属**可执行代码文件**（与 `评审门禁.md` §第一步 P 面同一套判据）的计入代码行，其余计入文档行。二进制文件 `--numstat` 输出 `-`，MUST 按代码行计 0 并在告知里**点名该文件**，MUST NOT 当作不存在。

**〈禁止积压清单〉——三类改动无论多小一律 MUST NOT 积压，判定时 MUST NOT 看行数**：

1. **安全与鉴权面**：鉴权、凭证、权限判定、加密、对外暴露面。三行改得起一个漏洞，行数在这里不是风险的度量。
2. **流程与门禁判据本身**：门 / 轴 / 步骤 / 准出项的语义（包括本纪律自己）。**改判据的改动 MUST NOT 用它自己新造的通路给自己开口子。**
3. **对外契约变更**：接口签名、默认值、错误码、CLI 参数、标记块字段。改一个默认值是一行，下游全破。

**积压路径 MUST 做的三件事**：

- 提交时在 commit message 末尾加一行 `Review-Deferred: 代码 N 行 / 文档 M 行 —— 一句话摘要`。这是积压的**唯一**机器可读记录（`git log --grep='^Review-Deferred:'` 即可枚举），**MUST NOT 另立台账文档**——git 本身就是账本，第二份账本只会产生第二份需要同步的真相。
- **一句话告知拍板人**：本次行数、累计行数、基点短 sha。**走不走积压由执行者按上表机械判定，MUST NOT 逐次征求同意**（逐次问就失去了这条通路的全部意义），但 **MUST NOT 不告知**——不告知的跳过与漏跑无法区分。
- 按 `merge-gate` 照常合并，**MUST NOT 移动 `reviewed-through` tag**。不动它正是积压能被下次评到的全部机制；动了它，那批改动就再也不会进入任何一次评审范围。

**积压只豁免本门这一道**：工作区隔离门、兼容取舍确认门、spec 过稿门，以及编码后的**基础验证**（测试跑绿、无编译/语法错），一律 MUST NOT 因积压而跳过。**积压不是"不测也不审"，是"审晚一点"。**

**结算路径**：按本步算出的范围（**含此前全部积压**）跑完整本门——因此 `评审门禁.md` §第一步 的对象面按**整个范围**算，MUST NOT 只按本次任务分支算。报告首行在 `评审门禁.md` §第四步 既有四项之后追加一项 `结算积压：代码 N 行 / 文档 M 行 / 最早 YYYY-MM-DD`，本次无积压时写 `结算积压：无`。**P0/P1 清零且合并成功后 MUST 执行 `git tag -f reviewed-through 【目标主分支 HEAD】`**；合并失败时 MUST NOT 执行它，积压保持未结算。

**积压 MUST NOT 使轴集合为空，也 MUST NOT 使任何一轴被裁剪**——它改的是"**什么时候**跑"，不改"跑**哪几条**轴"。这与 2026-09-03 撤回的那条裁剪准入是两回事：那条改的是派哪几条轴、能把 `{D}` 裁成空集；本条一条轴都不裁，只把整门推后到一个**仍然会到来**的时点，而 `reviewed-through` tag 与 trailer 两项共同保证它一定会到来。

**漏登记 trailer 时的降级**：`git diff 【基点】...HEAD` 非空却取不到任何 `Review-Deferred` trailer，说明此前有人漏登记。MUST 视为时间封顶不命中、按行数两条照常判，并在告知里注明"积压未登记 trailer"，**MUST NOT 因此报错或阻断本门**。
