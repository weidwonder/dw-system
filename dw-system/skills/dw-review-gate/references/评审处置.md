# 评审处置

## 处置

- **P0 与 P1 MUST 全部修完**才算过门；P2 由主会话决定当场修或记入 `docs/report/YYYY-MM-DD-<feature>-review-report.md`。
- **D 轴报告里的文档结算结论 MUST 由主会话当场落盘**，且**不受 P0/P1 口径限制**：整篇失准的完成"改 frontmatter + 插归档头注 + 移出 `index.md` 进 `index-archive.md`"三动作，只有若干行被推翻的**就地更正那几行**并把 `last_confirmed` 更新为当天，仍准确的把 `last_confirmed` 更新为当天（三个出口的判据见 `dw-doc-governance` 的 `文档生命周期.md` §3 第 3 步）。子代理只报告不写文件，落盘没有别的执行者；而"仍准确"不是一条问题，挂在"P0/P1 修完才过门"下它永远轮不到执行（判据见 `文档生命周期.md` §3）。
- 修完后 MUST 重跑**受影响的那一轴**确认（只重跑改动涉及的轴，不必全集重跑）。
- 子代理判断有误时，主会话 MUST 在报告里写明"不改 + 一句话理由"，MUST NOT 默默忽略——沉默的忽略无法与遗漏区分。
- 评审意见要改动拍板人已定的事项（兼容取舍、spec 过稿结论、大架构）时，主会话 MUST NOT 照改，MUST 回到对应那道确认门重过（`dw-workflow` 的 `确认门.md`、`用户沟通纪律.md` §1）——照改等于替拍板人推翻了他的决定。
- **走 PR 合并的项目**（`merge-gate="pr"`，判据由该字段**单独**判定）：
  - **开 PR 前 MUST 先过本门。** 本门是 PR 前的**地板不是天花板**：把 AI 能自查出来的问题挡在 PR 之前，让人审的注意力留给业务正确性与架构取舍，**MUST NOT 用它替代人审**。各轴报告结论 SHOULD 附进 PR 描述。
  - PR 描述 MUST 引用对应 spec / plan 任务号，并附影响范围说明（为什么没扩大）。
  - **MUST NOT 再加"协作面 = team"这一条**——一个人的开源项目照样可能走 PR 与外部审阅。把这几条写进只有 `collaboration="team"` 才加载的分册，等于让 solo + pr 的项目读不到，那是判据解耦了、内容还耦合着。所以它们在本文（判据不随协作面分册加载），不在 `collab/`。
  - `collab/team.md` §4 只补**因为有别人**而额外要做的事（指派评审人、与 owner 约合并窗口），不重复上面这几条。
- **残留轴的卡片核销项命中时，MUST 当场补上再过门**：缺的卡片按 `dw-code-facts` 的 `代码事实纪律.md` §4.1 补齐、被删实现按 §4.2 移进陷阱项，随本次分支提交。它与"该删的旧逻辑没删"同级，MUST NOT 以"下次再补"放过——补卡是本次任务的一部分（`dw-workflow` 的 `00-流程总纲.md` §"不裁剪"护栏 的补卡那一条）。

## 与其他纪律的关系

- 本门产出问题清单，修复动作回 Step 7 执行；改动较大时按 `dw-workflow` 的 `上下文卫生.md` 规则 3 在 checkpoint 处交接。
- 残留轴查出的旧逻辑属于"这次就该删"，不是新需求，MUST NOT 以"超出本次范围"为由推给下次。
- bug 类任务同样过本门（走 Lean 精简版），修复引入的临时探针、调试日志、被替换掉的旧分支都归残留轴。
