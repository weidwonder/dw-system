# 评审走查例子

## 走一遍：一次评审门长什么样

### 例 0：够小，走积压通路

**这是示例不是判据**，各步规则以 `积压通路.md` §第零步 原文为准。改动："修 `docs/index.md` 里两条指向已改名小节的死链接，外加一处错别字。"共动 12 行 markdown、0 行代码。

1. **定基点**：`git rev-parse -q --verify refs/tags/reviewed-through` → 拿到 `a1b2c3d`（上次过门后打的）。范围 = `git diff a1b2c3d...HEAD` 并入未提交路径。
2. **逐条判通路**：①禁止清单——只改 `docs/`，不碰鉴权、不碰门/轴/步骤/准出项的语义、不碰任何对外契约 → 不命中；②本次任务分支 `git diff main...HEAD --numstat` 算出代码 0 行、文档 12 行 → 未达 20/40 → 不命中；③自基点累计算出代码 0 行、文档 31 行（上次还积压过 19 行），最早一条积压 commit 是 6 天前 → 三个封顶都没到 → 不命中；④本项目 `merge-gate` 是 `direct`，不开 PR → 不命中；⑤**走积压**。
3. **登记与告知**：提交时带上 `Review-Deferred: 代码 0 行 / 文档 12 行 —— 修 index.md 两条死链接与一处错别字`；一句话告知拍板人"本次 0 行代码 / 12 行文档，已积压；自基点 `a1b2c3d` 累计 0 / 31 行"。基础验证照跑（`node --test test/*.test.mjs` 全绿）。
4. **合并**：按 `direct` 非快进合并，**`reviewed-through` 一动不动**——它还指着 `a1b2c3d`。
5. **三周后**做一次正常改动（改了 `.ts` 源码 180 行）再过门时：基点仍是 `a1b2c3d`，范围自动含住这 31 行文档积压，对象面按**整个范围**算（于是 D 文档轴也在轴集合里，它正是要看那两条链接改对没有）。报告首行末尾写 `结算积压：代码 0 行 / 文档 31 行 / 最早 2026-08-24`。P0/P1 清零、合并成功后 `git tag -f reviewed-through <主分支新 HEAD>`，积压清零。

**这一例最容易做错的地方**：第 2 步的②与③用的是**两个不同的范围**——②看本次任务分支，③看自基点起的累计。合成一个算，③就永远轮不到（第二次积压时累计必然已越过②的阈值），累计封顶形同虚设。

### 例 1：命中 P 面，当场跑

**这是示例不是判据**，各步规则以 `评审门禁.md` 与 `评审处置.md` 原文为准。改动："优惠券校验从 `couponV1()` 换成 `couponV2()`。"spec 有 `FR-001`–`FR-003`、`AC-001`–`AC-004`，替换清单登记了 `couponV1()` 与配置项 `COUPON_LEGACY`。

1. **判面与派发**：改动范围里有 `.ts` 源码、无 skill 目录树内的 md、不碰 agent 架构、未动 `docs/` → **对象面 = P**，轴集合 = A/B/C/D。上一轮无 P0、未命中大架构门、拍板人没提要求 → **升档条件一条都不命中，全部轴派普通档**。四条轴同属组 1（参照物都是 diff + spec），故**派 1 个子代理跑这一组**（完整流程也 MAY 拆成一轴一个，本例合并）。报告首行写 `本次对象面：P｜轴集合：A/B/C/D｜档位：全部普通档｜各轴 P0 计数：规范 0 / 忠实 0 / 残留 0 / 文档 0`。每个 prompt 的占位符都换成本次真值——`【spec 路径】`、`【改动范围】`、`【本次命中的对象面】` 一个不留。
2. **各轴报回来**（合并派发时是同一份报告的四个分节）：
   - 规范轴：1 条 P2（新函数缺类型标注）。表头不含〈偏离类型〉。
   - 忠实轴：先给覆盖矩阵——`FR-001`/`FR-002` 各有 Task 引用且被 AC 覆盖；`FR-003`（过期券提示文案）**零 Task 引用**。据此报 1 条 P0，偏离类型 `漏做`。另有 1 条 P1，偏离类型 `镀金`：顺手给 `couponV2()` 加了 spec 没要求的缓存。只有本轴的表头多〈偏离类型〉这一列。
   - 残留轴：`COUPON_LEGACY` 引用数已为 0 但**文件还在** → P1；另报 1 条 P1——读过 `pricing-svc` 源码却没补卡。
   - 文档轴：`docs/REQUIREMENTS.md` 的优惠券规则仍写 V1 口径 → 判"若干行被推翻"；另两篇现行 spec 扫过仍准确。
3. **处置**：P0 补 `FR-003` 的实现与验收；两条 P1 分别删掉遗留文件、补卡；镀金那条与用户确认后删掉缓存。P2 当场改。**D 轴结论不等 P0/P1 修完**——主会话当场就地更正 `REQUIREMENTS.md` 那几行，并把三篇的 `last_confirmed` 更新为当天。
4. **重跑**：只重跑忠实轴与残留轴，确认覆盖矩阵无零引用、替换清单两项核销为 0。规范轴那条 P2 已当场改完、就地复核不另起子代理；D 轴的结论由主会话落盘、不是待修问题，也不重跑。

**再走一个纯 K 面的**：改动只动了 `dw-prd/references/UI原型纪律.md` 一份判据文档，没有可执行代码文件，也没动 `docs/`。→ **对象面 = K**，轴集合 = `{S}`。按 `dw-workflow` 的 `纯skill改动.md`，这次**不写 Overview、不写技术 spec、不写 coding plan**，PRD 即 spec，动手前加载 `skill-principle` 的建设路径定结构。评审门派 **1 个**加载 `skill-principle` 的子代理走它的审查路径（轴集合里本来就没有 C/D，替换清单不存在）。主会话汇总时首行写 `本次对象面：K｜轴集合：S｜档位：普通档｜各轴 P0 计数：S=0`。**这一步同时示范了两件事**：跳过的是**产物**（spec / plan），而工作区隔离门、兼容取舍确认门、spec 过稿门一道都没少——它们的结论落在 PRD 或改动清单里。**若这次顺手改了 `docs/REQUIREMENTS.md`**，轴集合就变成 `{S, D}`，多派一个文档轴。

值得注意的是第 2 步的两处：**`FR-003` 零引用是矩阵算出来的，不是读代码读出来的**——没有编号就只能靠自然语言逐条比对，那正是降级路径存在的原因；而**"读过源码没补卡"归残留轴**，它和删遗留文件是同一类账，都属于"这次就该结清"。
