# Worktree 开发与自动合并纪律（core）

> 要建 worktree、`merge-gate` 缺省要取值、或要过完成与自动合并门时读对应小节；隔离门的要点在本 skill 的 `SKILL.md`，本篇是动作细则。

本纪律对所有项目强制执行，不因协作面（solo / team）、项目有哪些代码事实资产、Lean 流程、单人项目、小改动或紧急修复而裁剪。合并**方式**由标记块字段 `merge-gate` 决定（见下方"完成与自动合并门"），合并**要不要做、什么时候做**不由任何字段决定。

## 工作区隔离门

路由与初始化的**对话**做完后，在任何文档或代码向项目落盘前，必须先进入独立 Git worktree。Lean Change Spec 也必须在 worktree 中创建，不得跳过隔离门直接修改主工作树。

**初始化的写盘也在门内，不是例外。** 标记块注入与环境冲突处置改的是项目根的 `CLAUDE.md`/`AGENTS.md` 与用户的 rules/skills/agents，它们与 spec、代码一样 MUST 在 worktree 内落盘（见下方第 4 步）。在门前写会让**每个项目第一次唤起本 skill 都被第 2 步拦下**——那时不干净的正是我们自己刚写的东西。

1. 确认目标是 Git 仓库，并按仓库配置识别默认主分支；优先读取远端默认分支，不得写死为 `main` 或 `master`。
2. 检查主工作树是否干净。此刻本次流程**尚未写过任何文件**（初始化的注入与冲突处置都排在第 4 步），所以不干净只可能是**用户自己的未提交改动**——这正是本条要保护的东西。发现未提交改动时，不得替用户 stash、reset、提交或删除；中止进入开发并用业务语言说明已有工作需要先妥善保存。
3. 从最新主分支创建本次任务分支与独立 worktree。worktree 目录位置读取该仓库 CLAUDE.md（优先）或 AGENTS.md 的 `dw-workflow` 标记块内的设置，未显式覆盖时默认落在仓库根的 `./.worktrees/`；**首次唤起（标记块还没写）时用初始化第 4 步当场定下的值**，没指定就是默认值；每次创建前都从该设置读取，不得沿用上次会话记住的路径或凭空自定义。子目录名包含业务主题，避免与其他任务冲突。若 `.gitignore` 尚未忽略该 worktree 根目录，先幂等追加一行忽略规则，避免其内容污染主工作树的 `git status`。用户显式要求改到其它位置时，更新标记块内的设置后再创建。
4. **进入 worktree 后先结清初始化挂账，再开始本次任务**：
   - **首次唤起**：按 `dw-workflow` 的 `references/init-初始化.md` 第 5 步把标记块注入 worktree 内的 `CLAUDE.md` 与 `AGENTS.md`，并执行用户已决断的环境冲突处置。两者随本次任务分支提交、随合并门回主分支。
   - **项目根下还没有 `engineering-context/capability-registry.md` 时**：按 `dw-workflow` 的 `references/init-初始化.md` 第 5b 步在 worktree 内跑 `ctx init` 建起代码事实层骨架（**MUST NOT 跑 `--minimal`**），随本次任务分支提交。骨架里只有模板占位、没有真实数据行，这是**正常起步状态**，MUST NOT 因此告警或提示用户。
5. 从此刻起，需求文档、spec、plan、report、代码、测试、生成文件、验证和提交全部在该 worktree 内完成。不得中途切回主工作树落盘。
6. 非 Git 仓库无法建立 worktree 时中止开发，不得降级为直接修改当前目录。**初始化同样中止**：它的落盘也要求 worktree。

需求涉及多个仓库时，每个仓库全程使用独立任务分支和独立 worktree。先确认所有仓库都能进入隔离状态，再开始落盘；不得让多个仓库共用一个 worktree。**这条与协作人数无关**——一个人同时改 3 个仓，同样是 3 个任务分支、3 个 worktree；共用一个工作区会让跨仓改动混进同一次提交，任一仓未就绪时无法单独回退。

## 开发期间

- 每个 worktree 只承载一个业务任务，任务改动不得混入其他未完成工作。
- 按 plan 分段提交，确保任务分支可独立验证、可追溯。
- 主分支有新提交时，先把最新主分支合入任务分支并解决冲突，再重新运行受影响验证。
- 不得为了制造“干净状态”而处理主工作树里的用户改动；尤其不得自动 stash、reset、checkout 覆盖或删除未知文件。

## 完成与自动合并门

只有同时满足以下条件，才算“全部完成”：

- 已确认范围内的业务能力、文档和代码全部完成，没有未决业务问题或大架构确认项。
- 计划内测试、构建、静态检查和必要链路验证全部通过，并形成要求的报告。
- 任务分支的改动已提交，worktree 状态干净；不存在调试文件、临时产物或未解释变更。
- **代码评审门已通过，或本次已按判据登记积压**（两条通路，满足其一即可，判据见 `dw-review-gate` 的 `积压通路.md` §第零步）：
  - **已过门**：按 `dw-review-gate` 的 `评审门禁.md` §门禁 算出的**那组轴**逐轴报告齐全（轴集合见评审报告首行），P0 与 P1 已清零。**MUST NOT 按固定的几条轴核对**——轴集合由本次改动触碰的对象面推导，纯 skill 改动只有 skill 原则轴一份报告，照一份写死的轴清单核对会永远过不了门。**命中 P 面时**另需替换清单逐条核销；**D 文档轴在场时**其结论已落盘（判据见 `dw-review-gate` 的 `评审轴.md` §评审轴）。合并成功后 MUST 执行 `git tag -f reviewed-through 【目标主分支 HEAD】`；**合并失败时 MUST NOT 执行它**。
  - **已登记积压**：本次走的是积压通路，改动已带 `Review-Deferred:` trailer、已一句话告知拍板人，且**合并时 MUST NOT 移动 `reviewed-through` tag**。**这条通路只对 `merge-gate="direct"` 成立**——`merge-gate="pr"` 的项目 MUST 在开 PR 之前把积压结清，带着未评审的积压开 PR 等于把未完成的门禁推给审批人。
  - **两条通路都 MUST NOT 省掉基础验证**（测试跑绿、无编译/语法错）。积压推后的只有本门，不是"不测也不审"。
- **兼容取舍已有用户结论**：改变了既有可观察行为的每一条都有用户拍板记录（或显式声明"本次无兼容取舍"）。
- **CHANGELOG 条目已在**（本门**只核对、不生成**，写条目的判据在 `dw-code-facts` 的 `代码事实纪律.md` §10.1）：仓库根 `CHANGELOG.md` 的 `## 未发布` 下有本次分支写的条目（至少一条，`内部` 也算），兼容取舍表里每条"不兼容 / 兼容一段时间"在 `不兼容` 小节都有以对外接口名开头的条目。缺条目 MUST 退回实现阶段补，**MUST NOT 在本门内代写**。另 SHOULD 跑一条检查：自上一个版本 tag（`v*`）以来，目标主分支 first-parent 链上每个提交是否都触碰了 `CHANGELOG.md`——没触碰的逐个列出、一句话告知拍板人，补不补由他定；没有版本 tag 时跳过；**MUST NOT 派子代理去补写**。

  ```bash
  # 先把 【目标主分支】 换成真实分支名（如 main）再执行
  last=$(git describe --tags --abbrev=0 --match 'v*' 【目标主分支】 2>/dev/null) || exit 0
  for c in $(git rev-list --first-parent "$last..【目标主分支】"); do
    git diff --name-only "$c^1" "$c" -- CHANGELOG.md | grep -q . || echo "$c 未写 CHANGELOG"
  done
  ```
- **文档生命周期已结算**（本门**只核对结论，不在此重做盘点**——盘点与逐篇判定由代码评审门的 **D 文档轴**完成，见 `dw-review-gate` 的 `评审轴.md` §评审轴）：
  - **D 文档轴在轴集合内时**：D 轴报告在，其中的 P0/P1 已清零，且判定结果**已落盘**；**D 轴不在轴集合内时**（纯 skill 改动的 `{S}` 等）本项写"不适用（轴集合无 D）"，MUST NOT 因此卡住完成门——失准的已完成"改 frontmatter + 插归档头注 + 移出 `index.md` 进 `index-archive.md`"三个动作，仍准确的已把 `last_confirmed` 更新为当天。**零命中也要有书面结论**（"扫了 N 篇现行文档、0 篇失准"），没有结论无法与"没扫"区分。
  - **本次新建的文档** `lifecycle` 与 `authority_refs` 两个字段齐（只看自己刚建的那几个文件；Step 8–10 新建的 test-spec 等文档在 D 轴之后产生，落在这一项里）。
  - 判据见 `dw-doc-governance` 的 `文档生命周期.md` §3，落地写法见 `dw-doc-governance` 的 `文档归档与账本收敛.md`。
- 已吸收最新主分支并重新验证，没有未解决冲突。
- `merge-gate="pr"` 时，仓库要求的评审、持续集成、owner 或发布门禁全部通过。
- 多仓任务的所有仓库均已达到合并条件；任一仓未就绪时，不提前合并其他仓。

满足完成条件后，无需再次询问用户，自动合并任务分支到识别出的主分支：

**合并方式读标记块字段 `merge-gate`**（`CLAUDE.md` 优先，其次 `AGENTS.md` 的 `dw-workflow` 标记块），只有两个取值：

- **`merge-gate="direct"`（本地直合）**：在主工作树执行非快进合并（`git merge --no-ff`），并运行最小的合并后验证。不开 PR、不等外部门禁。
- **`merge-gate="pr"`（走平台）**：推送任务分支，创建或更新 PR，并在评审与持续集成通过后启用或执行平台自动合并；不得绕过保护分支、审批、CI 或 owner 规则强行写入主分支，也不得在平台未放行时改用本地直合。PR 自身的前置要求（评审门、描述、粒度）与协作面无关，唯一定义在 `dw-review-gate` 的 `评审处置.md` §处置，本文 MUST NOT 复述。**`pr` 下合并即发布，本门兼作发布门**：`pr` 项目不走积压通路，每次进主分支的改动都已过完整评审门，主分支上没有"合了但没发"的中间态。因此 PR MUST 带上发版件（项目的版本号文件按 `CHANGELOG.md` 的分类升位，`## 未发布` 改名为该版本节并在上面新开空的一节），平台放行合并后 MUST 打 `v<版本>` tag 并随即推送；PR 的审批就是拍板人对这次发版的同意，MUST NOT 再另问一次。发版件缺一样，本门不过。

**字段缺失时的判据（本文是唯一权威定义，`SKILL.md` 与 `dw-workflow` 的 `init-初始化.md` 只留指针，MUST NOT 各写一套）**，按顺序取第一个命中的：

1. **仓库现状**——远端主分支受保护、或仓库有 PR 规则 → `pr`。
2. **仍判不出**（无远端、探测失败、本地仓库）→ 由协作面推：`collaboration="team"` → `pr`；`collaboration="solo"` → `direct`。
3. 两步都做完后，MUST 在完成报告里提示补齐该字段。

优先级 MUST 是**现状 > 协作面推断**：现状是可探测的事实，由协作面推只是猜测，且猜错方向危险——在受保护分支上尝试本地直合会失败或违规。**MUST NOT 反过来**（先看协作面、判不出再看现状）：那会让 `collaboration="solo"` 且主分支受保护的项目稳定判成 `direct`，每次合并都撞门禁。

> 与初始化时的建议值不是一回事：`dw-workflow` 的 `init-初始化.md` 用 `git remote` + CI 配置给用户一个**待拍板的建议**，用户可当场改；本节讲的是字段已经缺失时的**非交互兜底**，不询问用户。

多仓任务：全部仓库先通过完成门，再**按依赖顺序合并**：

- 顺序规则是**被依赖方先合**——提供接口、schema、事件或配置契约的一侧先落地，调用方后合，使任一时刻主分支上的组合都能自洽；互相依赖时先合"只加不改"的一侧（新增接口、加可选字段），再合切换调用的一侧。
- 顺序在 Overview 或 coding plan 里预先写死并逐仓核销，不得临场决定；存在其他协作方时，顺序还需与各仓 owner 协商确认后再执行（见 `collab/team.md`）。
- 任何一步失败，立即停止后续合并并报告已合并与未合并的业务范围。

合并与合并后验证成功后，移除任务 worktree，并按仓库规则删除已合并的任务分支。`direct` 下自动合并不等于发布：主分支可以攒几次合并再由拍板人发版（打 tag 是他的动作）；部署与外部通知在两种方式下都仍遵循项目原有授权与门禁。

## 失败与阻塞

测试失败、合并冲突、主工作树出现新改动、权限不足或保护分支门禁未通过时，不得宣称完成，也不得合并。合并失败后保留任务分支和 worktree，不删除现场；用业务语言说明尚未交付的能力、影响和下一步条件。
