# 给 agentic-principle 的三条补充建议

## 这份文档是什么

`ai-dev-system`（AI 辅助开发方法论分发包）已把 **Agentic 应用的架构设计**整体依赖到 `agentic-principle` skill：判定需求为 Agentic 应用时，强制加载它做场景选型、Agent 划分、提示词、注意力与并发预算、步骤级测试，并在代码评审门增派一个加载它的「agent 架构轴」子代理。两个 skill **内容互不搬运、各自独立演进**。

在做这次对接时，我们把双方内容做了一次逐项比对（基线：agentic-principle v0.3.0）。绝大多数是干净互补：它管"Agent 系统怎么设计"，我们管"推理的运行期契约怎么写进 spec"。但有三处，是**在 Agent 语境下真实存在、而 v0.3.0 尚未覆盖**的缺口。

我们这边**已把其中属于"Agentic 建设方法"的部分全部删除**（避免两边重复定义、各自漂移），因此本文档承载它们的完整内容，供你们直接采用或改写。**不采用也没关系**——但那样这三块在两个 skill 里都会是空白，请知悉。

阅读本文档不需要读过 `ai-dev-system`。

---

## 建议 1：工具与动作的自主级别分级 + 审批闸门

**缺口**：v0.3.0 有「工具授权：按职责的最小能力集」（给哪些工具）、有「透明性：关键决策对使用者可见」，但**没有对"这个动作 Agent 能不能自己拍板"分级**。结果是：一个能读文件的 Agent 和一个能删生产数据的 Agent，在设计文档里的授权表述是同一种粒度——都只是"授权了这个工具"。

**为什么需要**：Agent 出事故的典型形态不是"调错了工具"，而是"调对了工具但不该由它自己决定"。最小能力集能防前者，防不了后者。而且这个判断必须在**设计期**做出并写进文档，运行期再补就晚了。

**建议内容**（可直接落进 `agent-construction.md` §三 工具授权，或独立成一节）：

给每个工具/动作标一档自主级别，四选一：

| 级别 | 含义 | 典型 |
|---|---|---|
| `suggestion-only` | 只产出建议，由人或确定性代码决定是否执行 | 给出重构方案、生成待办清单 |
| `assisted-action` | 执行前需人确认单次动作 | 提交前展示 diff 等待确认 |
| `controlled-automation` | 自动执行，但限定在可回滚/可审计的范围内 | 在任务分支上自动改代码并提交 |
| `high-impact-automation` | 自动执行不可逆或高影响的动作 | 发消息给外部、扣款、改权限、删数据、部署 |

三条配套约束：

- **与用户直接交互的 Agent，默认只给前两档**；要给到第三档以上，在设计文档里写明理由。
- **`high-impact-automation` MUST 命名审批闸门**：不是写"需要审批"，而是写清**谁审、在哪一步审、审不过怎么办**。没有具名闸门的高影响自动化，视为设计未完成。
- **闸门是确定性代码，不是提示词纪律**。写在系统提示词里的"执行前请先确认"不算闸门——模型不遵守时没有任何东西拦得住。闸门必须是程序侧的拦截点。

**建议落点**：`agent-construction.md` §三 的最小能力集表增加一列「自主级别」；SKILL.md §各场景必确认项 的通用项增加一条"每个工具的自主级别与高影响动作的审批闸门"；`design-doc-template.md` §一 的批次 2（能力边界）增加对应提问；验证清单增加一条。

## 建议 2：安全管线（注入防护 / 输出检查 / 机器可读判定码）

**缺口**：v0.3.0 的「绝对禁止」覆盖了**凭证不入文档**，`long-artifact.md` 与 `testing.md` 覆盖了产物**质量**校验，但整套 skill 没有涉及**对抗性输入**与**输出安全**：提示词注入、越狱、不可信工具返回内容覆盖系统指令、以及产出内容本身是否安全。

**为什么需要**：Agent 的攻击面比单次 LLM 调用大得多——它读取的每一份外部内容（网页、工具返回、用户上传的文件、子 Agent 的产出）都是潜在的指令注入载体。这在**父子 Agentic** 与**工具密集的单 Agentic** 场景里尤其突出：子 Agent 的返回会被父 Agent 当作事实采纳，一旦被污染，污染沿链路向上传播。

**建议内容**（可独立成 `references/safety.md`，在步骤 2 与步骤 4 引用）：

1. **信任分级**：明确标出每个 Agent 的输入里哪些是**不可信来源**（用户输入、网页、外部 API 返回、他人产出的文件）。不可信内容 MUST 以数据形式传入（明确的分隔与标注），**MUST NOT 拼接进系统指令位置**。
2. **一条不可协商的规则**：不可信内容里的指令性文字**永不改变 Agent 的目标与授权**。系统提示词里显式写死这一条，且工具层做兜底——注入成功时，模型至少不该获得它原本没有的工具权限。
3. **输出侧逐条命名检查**：把"什么算不安全"拆成具名检查项（如泄漏系统提示词、泄漏凭证、输出违禁内容、越权索取个人信息），每项给一个**机器可读的判定码**（如 `safety_prompt_leak`、`safety_injection_detected`）。用码而不是自由文本，日志、指标、测试才能对同一件事对齐。
4. **fail-closed**：安全检查本身出错时 MUST 抑制输出走兜底，**绝不能因为检查逻辑挂了就把未检查的内容放出去**。这是最容易写反的一条——很多实现里 `try/catch` 的 catch 分支直接放行了。
5. **测试侧接住**：`testing.md` 的评测集样本切片增加"注入 / 越狱 / 有害输出"一类，作为回归样本长期保留。

**建议落点**：新增 `references/safety.md`；SKILL.md §基础原则 增加一节指针；§各场景必确认项 通用项增加"不可信输入清单与安全判定码"；验证清单增加一条。

## 建议 3：在既有 Agent 上加能力的增量写法（继承声明 + 平台缺口清单）

**缺口**：v0.3.0 的两条入口是「新建」与「评审」。但真实项目里最高频的第三种场景没有入口——**在一个已经稳定运行的 Agent 平台上加一个 skill / 一个工具 / 一个配套服务，agent loop 本身不动**。按现在的流程，这类需求要么被迫走完整的「新建」（把已经定好的场景选型、编排模式、并发预算重新论证一遍，产出一份大部分内容是复述的设计文档），要么干脆绕过 skill 直接写代码。

**为什么需要**：这类迭代占日常工作的大头。流程太重就会被绕过，绕过之后新增能力的授权、注意力、测试就都没人管了——**恰恰是增量最容易埋雷的地方**。

**建议内容**（可作为 SKILL.md 的第三条入口，配一份精简产出模板）：

新增入口「**在既有 Agent 上加能力**」，判定：目标平台的场景选型、编排模式、agent loop 已定且本次不动，只新增 skill / tool / 服务。走法是「**声明继承 + 只写增量**」：

**① 继承声明（Inheritance Declaration）**：开头一节明确写清从现有平台基线继承了什么、本次不重新论证，逐项列出：场景分类与编排模式、agent loop 与轮次上限、并发上限与上下文上限、既有工具清单与授权基线、既有的测试与评测设施。**继承项只写"继承自哪里（文档/代码位置）"，不复述内容**——复述就会与平台真实状态漂移，而漂移的复述比没有更危险。

**② 只 spec 增量**：设计文档只写本次新增的部分——新增工具/skill 的职责与自主级别、它的输入输出契约、它对既有并发与上下文预算的占用增量、它需要的新测试用例。原有部分一律指向平台基线文档。

**③ 平台缺口清单（Gap Watchlist）**：这是关键的一节。既有平台往往带着已知但没修的缺陷——没有审批闸门、没有轮次上限、工具返回内容未做安全筛查、没有步骤级用例。做增量时**逐条对照本次新增能力是否踩中这些缺口**，踩中的：能在能力层顺手补的就补（例如给新工具单独加一道确认），补不了的**显式登记为风险并标注影响**，而不是默认"平台一直这样，那就这样吧"。

清单形态示例：

| 平台缺口 | 本次新增能力是否踩中 | 处置 |
|---|---|---|
| 无统一审批闸门 | 是——新工具会写生产数据 | 在本能力内加确定性确认步骤 |
| 无 turn 上限 | 否——本次不改 loop | 登记为平台级风险，本次不处理 |
| 工具返回未做安全筛查 | 是——新工具会拉取外部网页 | 在本能力内对返回做注入筛查 |

**建议落点**：SKILL.md §两条入口 扩为三条；新增 `references/incremental.md` 承载三步做法与模板；`design-doc-template.md` 增加一份精简骨架（继承声明 / 增量设计 / 缺口清单 / 测试增量）。

## 备注：我们保留了什么，为什么

有两项在比对中也曾被划入候选，但我们**保留在自己这边**，因为它们对**非 Agent 的 AI 功能**同样必要，移交过去反而会让它们只在 Agent 语境下存在：

- **AI 能力契约的「自主级别」字段**：我们把它作为每个 AI 能力的契约字段（不限于 Agent，比如一个自动批改功能也要标）。**与建议 1 不冲突**——建议 1 是从"工具授权"视角，我们是从"能力契约"视角，两边视角不同、粒度不同，各自定义即可。
- **推理运行期契约**：确定性边界、版本 pin、输出 schema 校验与 re-ask 上限、置信度路由、降级触发器、token/成本预算准入、eval 质量门、结构化可观测字段、数据与训练边界、可审计性。这些是"单次推理怎么被正确执行"，不是"Agent 系统怎么设计"，留在我们的 AI overlay 里。
- 其中**安全**部分我们保留的是**单次推理**视角（输入过滤、输出内容检查、安全失败 fail-closed）。建议 2 要补的是**链路**视角（不可信来源分级、工具返回与子 Agent 产出的注入传播、机器可读判定码）——两者互补，都需要，落点不同。
