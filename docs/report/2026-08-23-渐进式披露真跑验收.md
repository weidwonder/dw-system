## 3. 真跑撞出的三个缺口

**这三个都不是机器闸能发现的。** 撞出它们时 260 项测试全绿，三份文件各自也都自洽——
冲突只在"真按它们说的顺序走一遍、并且把字节数加起来"时才显形。这是 Task 13 存在的
全部理由，**MUST NOT 因为"测试都绿了"就跳过它**。

### 3.1 入口在分流前就加载了完整流程才要的东西

`SKILL.md` 路由第 3 步写「加载常驻六份」，然后才过隔离门、做 Triage；而
`路径-lean.md` 头部写着「MUST NOT 预读常驻篇、MUST NOT 读 `00-流程总纲.md`」，
spec §0 的最窄 Lean 场景写着「全程未加载任何常驻篇」。三处互相打架。

实测 Lean 因此加载 101,923，其中 24,777 是常驻篇的第二份拷贝——自足册本来就是
它们在 Lean 场景上的投影。修正：路由改为分流感知，分流前只取三份，分流后按分支
只补该支要的。见 commit `55e95d7`。

### 3.2 Lean 与自足册的关系被写成了「叠加」

入口清单表下的总括句写「Lean 走到某行时**另加**自足册对应节」，相关行〈适用路径〉
标 `两条`——读起来是两份都读。而自足册对应节写的是二级触发（"要展开时才读原篇"）。

实测后果：**含文档结算的 Lean 加载 133,903，比改造前的 133,545 还多 0.3%**，
`文档治理.md` 被加载两遍。修正：11 行加 `(L§x)` 标记，Lean 取自足册那一节**代替**
原篇。见 commit `2893f20`。

同一轮里判定了**三行 MUST NOT 一刀切成替代**：〈每次唤起〉〈`merge-gate` 缺省〉
〈要建 worktree〉的触发点都在分流前，那一刻自足册还没加载；且自足册 §2 自述
"只补建 worktree 的动作细则与多仓条款"——**它不自足，是补充不是替代**。

### 3.3 两次核算口径错误（本次自身的执行缺陷，记账备查）

- 第一次：测自足册前置节时按 `##` 与 `###` 都切段，触发式节的三级子节被单独切出、
  因自身无标注而被算成前置，得 67,840（正确值 49,678）。
- 第二次：核算 Lean 加载量时**漏算了三道必然触发的门**（18,791），报出 77,420，
  并据此写进了 commit `55e95d7` 的说明。同口径的正确值是 102,712。

两次都是**口径没定清就报数**。教训是：报一个用于下判断的数之前，先把口径写下来
并验一遍边界（这里的边界就是"哪些节算前置""哪些门每次都触发"）。

## 4. 未验证的部分

- 本报告的加载量是**按文档标注静态累加**得出的，不是运行时观测。真实会话里 AI 是否
  严格只读标注允许的那些节，本次没有仪器可测——要测得先有一层加载埋点，那是另一个
  需求，**留作后续版本**。这是本报告最大的不确定性，也是 AC-019/020/021 由「真跑」
  回填为「纸面走查 + 静态核算」的直接理由（spec §11 覆盖自查下的说明）。**这条理由
  此前只写在本节，没有进 AC**——于是三条验收项在字面上承诺了本次没做到的事。
- 完整流程的加载量只算到 `步骤-1-7-设计与实现.md`，未把 Step 8–10 的测试阶段算进去。
- 本仓库自身没有 `engineering-context/`（见 spec §12），所以补卡相关的加载点在本次
  真跑中没有实际触发过。
