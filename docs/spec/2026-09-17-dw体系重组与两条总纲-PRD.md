# dw 体系重组与两条总纲 PRD

> 更新时间：2026-09-17
> 状态：已定稿（2026-09-17 拍板人整体认可）
> 核心目标：把本体系从"越维护越重"改成"有上限、能变轻"，并整体更名为 dw；发布为 3.0.0。

## 一句话结论

1. 立两条总纲，管本体系自身，也管它教给目标项目的写法：**一个事实只有一个家，别处只放链接**；**规范文本有体积上限，超限先搬走、再压缩，最后才抬上限**。
2. 把单体的主流程 skill 按职责拆成七个小 skill，加上产 PRD 的那一个共八个，全部以 `dw-` 开头；体系、仓库、安装命令同步更名为 `dw-system`。
3. 规则正文只留现行规则与防误用的理由；来历、版本戳、被否决的方案搬进决策记录。
4. 代码事实卡按业务域分卡、只写现状、有固定小节与体积上限，并有一条卡片体检命令守住质量。
5. 旧安装重跑安装器即完成升级：旧 skill 目录、旧标记块、旧版本戳、旧忽略规则、旧全局命令链接由安装器自动卸载或改写，使用者不手工改文件。

## 背景

本体系每加一道门、每修一次漂移，规范文本只增不减，已经到了加不动的地步。

- 每个会话必读的仓库说明 116KB，其中"改动时注意"一节 66KB，单段最长一万一千余字符（`CLAUDE.md:204` 起）。
- 注入到每个目标项目说明文件里的标记块 16KB，目标项目的每个会话都要读（`ai-dev-system/skills/ai-dev-workflow/assets/config-snippets/base.md`）。
- 主流程 skill 一个 skill 管七件事，靠入口一张二十余行的加载点清单做内部路由（`ai-dev-system/skills/ai-dev-workflow/SKILL.md:31`）。
- Lean 自足册 122KB，是各原篇在 Lean 场景下的重写副本，靠一条测试保持同步（`references/core/路径-lean.md`、`test/lean-selfcontained.test.mjs`）。
- 代码评审纪律单篇 53KB，待办里已登记要拆（`docs/TODO.md:35`）；常驻前置量距 50,000 字节门槛只剩三百余字节（`docs/TODO.md` 技术欠账、`node --test test/resident-budget.test.mjs`）。
- 同一个量多处各写一份，出事后补闸：已有五条防漂移测试，`test/contract-numbers.mjs:3-7` 记着"栽过三次"。
- `test/wording-redline.test.mjs` 要求每个文件的规范条数不低于历史最大值，精简因此在机制上被堵死。
- 文档治理定义了决策记录目录 `docs/decisions/`（`references/core/文档治理.md:70`），本仓库从未建过；理由与来历于是写进规则正文、测试注释与索引条目，`docs/index.md` 单条长成一整段。
- 用本体系产出的三个项目，卡片质量参差：`aiudit_platform` 整仓一张卡 146KB、33 个域段是按任务先后追加出来的，其中「引用原件预览」与「引用原件预览与定位」两段并存；`myclaws` 的 `claw.md` 71KB，最上面是带日期的小节，「Freshness」一节长成了五十余条带版本号的变更记录，全卡一百二十余个日期戳、只有 12 处 `文件:行`；`agent_fs` 按包分卡最接近可用，但单卡仍到 35KB，接口表逐个方法照抄、废弃段里写着「非废弃且持续维护」（`ctx` 会把它抽成误用警告）。`aiudit_platform` 的 registry 54KB，单元格里装的是整段卡片内容。三张卡三种形态。根因在规则本身：「每仓一张」「只增不减」、没有体积上限、没有域的划分规则（`references/core/代码事实纪律.md` §4.1–4.2、`assets/context-layer/card.md`）。

两条总纲是对照另一个长期维护良好的项目总结出来的：那个项目的根说明文件不到两千词，十二个 skill 每个 6–18KB，靠的就是这两条。

## 目标与非目标

### 产品目标

1. 两条总纲写进体系的总纲位置，每个 skill 与注入块都受它约束，且有机器闸守住体积上限。
2. 任何一个触发点拉进上下文的规范文本，不超过本文〈体积上限〉表的数字。
3. 走 Lean 路径完成一次典型改动，读入的规范文本总量不高于重组前。
4. 规则正文里不再出现版本戳、"此前""实测过"这类来历叙述；每条被搬走的理由在决策记录里找得到。
5. 新写的卡片读起来是同一种东西：打开任何一张域卡，固定位置能找到职责、权威实现、陷阱项、确认日期；卡里没有变更记录；cite 失效能被机器发现。
6. 旧安装（2.x）重跑一次安装器后，目标项目里不残留任何旧名字的 skill、标记块、版本戳、忽略规则，且原有设置（协作面、合并方式、worktree 目录、docs 是否入库）原样保留。

### 非目标

1. 不改任何一道门的判据：工作区隔离门、兼容取舍确认门、spec 过稿门、代码评审门、完成与自动合并门的放行条件不变；Triage 四问与默认倾向不变。
2. 不改 `ctx` 既有命令的名字与语义，只新增；不改 registry 三列的最小形态与 cite 纪律；`engineering-context/` 仍然必备、没有开关。
3. 不改产 PRD 流程与 UI 原型工具的行为，只改名与清理来历叙述。
4. 不引入双语配对、不引入决策记录的冻结清单——那是多人大仓库的做法。
5. 不回改历史文档：`docs/spec/`、`docs/plan/`、`docs/report/` 的存量文档、既有迁移指南、`CHANGELOG.md` 的既有条目里的旧名字原样保留。
6. 不改两个伴生 skill（`agentic-principle`、`skill-principle`）的仓库与安装方式。

## 详细业务行为

### 两条总纲怎么落到日常

- **一个事实只有一个家**：写任何规则、数字、清单前先问"它的家在哪"。家以外的地方只写名字加链接；确需就地知道的关键一句可以重复，但展开只在家里。评审门的文档轴与 skill 原则轴把"同一事实两处展开"报为问题。
- **体积有上限**：超限时按固定顺序处置——① 把不属于这里的内容搬回它的家，留一行链接；② 属于这里但能更短的，压缩；③ 内容确实需要这么多空间，才抬上限，抬上限须拍板人同意并写一句理由。上限是护栏不是削减指标：压缩时每条命题（谁、做什么、什么条件、必须还是可以、反向保证、失败后果）都要留住，字数变少本身不算改进。
- **理由留下，来历搬走**：省略后可能导致误用的理由留在规则旁，用现在时写（"没有这条，X 会发生"）；"哪一版改的""此前出过什么事""试过哪些方案"进决策记录。

### 「一个事实只有一个家」的四样落地约束

1. **归属表指明家**。`dw-workflow` 入口放一张三列表：事实类别 / 它的家 / 这里不该放什么。目标项目一侧沿用已有的输出目录表与三层真相源并补上第三列（需求真相源不放来历，索引不放规则，spec 不放还没做的事，卡片不放变更记录）；体系自身一侧补齐每道门的判据、标记块字段、权威面清单、契约数字各自的家。
2. **引用形态固定**。家以外的地方写「名字 + 指针」，指针用现有交叉引用闸认得的形态，目标不存在即判红。
3. **两条机器闸**。① 规范句重复检测：含 MUST 的句子归一化后出现在两个以上 skill 文件即判红；确需就地重复的关键一句进白名单，每条写明理由。② 权威面重复声明：每份文档的 `authority_refs` 就是它对"家"的声明，同一权威面被两份 `lifecycle: active` 的文档同时声明即判冲突。数字类事实沿用现有的单点定义与防手抄闸。
4. **评审口径**。文档轴与 skill 原则轴的检查动作写明：取一句有辨识度的原文全仓检索，命中两处以上，留家里那份，其余改指针。

### 代码事实卡的质量

| 项 | 规则 |
|---|---|
| 两种卡 | **仓库地图卡** `cards/<仓库或包>.md`：职责一句话、业务域地图（域 → 一句话 → 域卡）、跨域陷阱、对外入口总览。**业务域卡** `cards/<仓库或包>/<域>.md`：一个业务域一张 |
| 域怎么切 | 划分方式写在地图卡里，只此一处：按什么维度切、切成哪几块。与需求真相源 `docs/requirements/` 的子模块用同一套切法；新事实先找所属的域，找不到才新开域，新开域 MUST 先改地图 |
| 域卡固定小节 | 职责（一句话）/ 权威实现与对外接口 / 陷阱项（确实没有写 `无`）/ 测试入口（可省）/ 确认（一行：日期 + 来源）。小节名固定，不自造；前端仓的补充项改为前端域卡模板，不再塞进同一份模板 |
| 只写现状 | 不出现带日期的小节、"本次核实"式的累积清单、版本号流水；「确认」只有一行。事故经过进 bug 修复历史，取舍来历进决策记录，对外变化进变更日志 |
| 只记判断 | 接口表只列"有判断要下"的条目：哪个是权威、哪个是陷阱、约束是什么。逐个方法照抄签名、依赖清单、最后修改时间不进卡 |
| 陷阱项只放陷阱 | "仍在维护""非废弃"这类话不进本节——`ctx` 把本节逐行当成误用警告 |
| cite 形态 | 以 `路径#符号` 为主，行号可附；`ctx` 校验路径存在、符号在该文件里检索得到 |
| registry 保持薄 | 三列每格一句话加指向域卡的指针；展开只在卡里 |
| 体积 | 地图卡 8,000、域卡 16,000、registry 单格 300 字节；超限先搬走来历，再按域拆 |
| 「只增不减」改为「事实不丢」 | 被删除的实现仍要进陷阱项；但卡片超限必须拆，来历必须搬走 |
| 卡片体检 | `ctx` 新增一条体检命令，查：固定小节齐全、体积、带日期的小节名、cite 能否解析、域名近似重复、registry 指针能否解析。新违规判红；存量违规记入基线，只许减不许增。评审门文档轴与刷卡时跑 |

`ctx get-card <仓库> [域]` 用法不变：有域卡文件读域卡，没有则照旧读单文件里的同名小节。

### 升级行为（旧安装重跑安装器）

| 旧残留 | 处置 |
|---|---|

说明文件是软链接、两个入口不一致、只有一个入口有块——沿用现有的幂等规则。

## 核心规则

| 情况 | 处理 |
|---|---|
| 同一事实需要在第二处出现 | 写名字加链接；关键一句可就地重复，展开不可 |
| 某份规范文本超限 | 搬走 → 压缩 → 抬上限，顺序不可跳 |
| 精简让规范条数下降 | 逐条交代去向，闸核对交代齐全才放行 |
| 规则旁想写"为什么" | 防误用的理由留下用现在时；来历进决策记录 |
| 新增一个 skill 或分册 | 同时给出它的触发条件与体积上限；写不出触发条件就不该独立成篇 |
| 目标项目的存量文档、存量索引 | 不因新规则批量回改；被触碰时顺手收敛 |

## 特殊场景与冲突

| 场景 | 处理 |
|---|---|
| 目标项目里旧 skill 目录被用户手改过 | 照删：这些目录历来每次安装都整目录覆盖，从不承诺保留手改 |
| 多人项目只有一个人重跑了安装器，说明文件已入库 | 其他人的旧 skill 读不到旧名字的块，会重新问一次协作面；迁移指南写明"每个人都重跑一次" |
| 用旧的本地检出直接运行 2.x 安装器 | 找不到包内目录而失败；迁移指南写明先更新检出或改用新安装命令 |
| 旧安装命令（旧仓库名） | 依赖托管平台对改名仓库的跳转；旧名字永不另建仓库 |
| 全局 `ctx` 被别的工具占用 | 沿用现有判据：判不出归属一个字节都不动 |
| 存量项目里的超大单卡（如整仓一张 146KB） | 升级不自动拆卡：拆卡要读源码判断域的边界，不是安装器能做的事。首次体检把它记入基线并给出按域拆分的建议清单；之后每次触碰某个域，就把那个域迁成域卡 |
| 同一事实在 registry 与卡片各展开一份 | 卡片是家；registry 那格收成一句话加指针 |
| 重组后某篇仍高于目标上限 | 上限冻结在实测值并登记待办，不为过闸硬删命题 |

## 验收标准

### 流程与规则验收

| 验收项 | 标准 |
|---|---|
| 总纲一处 | 两条总纲的展开只出现在 `dw-workflow` 入口；其它位置只有名字加链接 |
| 八个 skill 可被发现 | 每个 skill 的 description 含做什么、何时用、何时不用；彼此不撞车 |
| 判据不丢 | 重组前各门的每条判据在重组后都找得到住处；去向清单齐全 |
| 体积 | 体积闸全绿；每个高于目标的对象都在待办里有一条 |
| 无来历叙述 | 规则正文检索不到版本戳与来历用语；保留项只剩清单里列明的合法形态 |
| Lean 不变重 | Lean 路径典型改动的读入总量不高于重组前实测值 |
| 门的行为不变 | 既有门禁契约测试在改名与搬家后仍然成立 |
| 家可查 | 归属表覆盖本文列出的事实类别；重复检测闸与权威面重复声明题各有一个植入样本能把它打红 |
| 卡片体检 | 对三类坏样本（带日期小节、cite 指向不存在的符号、两个近似重名的域）各判红一次；对存量超大单卡只记基线不判红 |

### 场景验收

| 场景 | 预期 |
|---|---|
| 全新项目安装 3.0.0 | 只出现 `dw-` 前缀的 skill、新名字的块与戳 |
| 2.17.0 项目重跑安装器 | 〈升级行为〉表逐项完成；协作面、合并方式、worktree 目录、docs 入库决定与升级前一致；打印迁移指南 |

## 风险与兜底

| 风险 | 说明 | 兜底 |
|---|---|---|
| 搬家时丢判据 | 约四十二万字节的规范文本重新分配住处 | 去向清单逐条核对；既有门禁契约测试改路径不改断言；评审门 skill 原则轴全量过一遍 |
