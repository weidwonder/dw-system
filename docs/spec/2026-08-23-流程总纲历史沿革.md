# 流程总纲的历史沿革与立论依据

> **本文不是判据，是判据的来历。** `ai-dev-workflow` 的 `references/core/00-流程总纲.md` 无条件常驻，因此它只留"照着做就不会错"的判据；每条判据"当初为什么这么定"的论证展开搬到这里。
> **读者不读本文也能照总纲把流程走对**——本文只在两种时候要读：想改总纲的某条判据（先看它当初要挡的是什么），或想弄清一条判据为什么长成这个样子。
> 交叉引用的小节名沿用总纲的写法，改总纲小节名时同步改本文。
> 上游 spec：`docs/spec/2026-08-23-渐进式披露与需求追溯-eng-spec.md`（FR-005）。

## 总纲 §四道门 — 大架构确认门为什么绑"改动命中判据"而不绑 Overview

总纲的结论是：大架构确认门的**触发条件是"改动命中大架构判据"，MUST NOT 写成"Overview 改变了什么"**。

论证：Overview 可以被合法跳过（`步骤-1-7` §本步必做还是可跳过），Lean 路径更是从不产出 Overview。把这道门绑在 Overview 上，等于让它在最常见的路径上静默消失——门还写在文档里，但永远不触发。

## 总纲 §Step 0 Triage — 四问分流的意义

总纲的结论是：4 项全否走 Lean，任一为是走完整流程，且 4 问 MUST 逐题过一遍。

论证：这样切分既不给小改动套重流程，也不给有风险的改动（AI 行为、安全、跨服务、对外承诺）走捷径。逐题过而不是"假设全否"，是因为**误把有风险的改动当小改动，才是真正的风险**——分流本身没有回头路，走错时最先丢掉的正是给风险改动准备的那几道功课。

## 总纲 §Step 0 Triage — 第 3 问的确认义务为什么要单列

总纲的结论是：第 3 问命中（搬迁历史数据 / 不可逆影响）时，MUST 先形成业务语言摘要交用户确认；它与大架构确认门各管一件事，同时命中时合成一份摘要一次抛出。

论证：分流只决定**走哪条路径**，它本身不产生任何用户确认动作。而"不可逆"恰恰是最需要人拍板的一类——一次纯历史数据搬迁可以不改变任何主干路形状（大架构确认门不触发）、也不改变任何对外可观察行为（兼容取舍清单为空、无可拍板项），于是在完整流程里也会全程无人拍板。这条确认义务就是补上那个拍板点。它与大架构确认门管的是两件事：那道门管结构变没变，这条管后果可不可逆。

## 总纲 §默认倾向 — 判据 3/4 为什么是回溯触发

总纲的结论是：判据 3/4 MUST NOT 在 Triage 当场强行判定，落点在完整流程 Step 1 进行中 / Lean 第 3 步写〈既有系统清单〉时。

论证：这两条要求关键事实已经开始收集，而 Triage 发生在 Step 1 之前，此时手上还没有"关键事实"这个对象，逐条过只会得到一个编出来的答案。

## 总纲 §默认倾向 — 判据 3 为什么不能读成"卡片里查不到就算说不清"

总纲的结论是：查不到卡片的正确处置是读源码 + 当场补卡，补完就有 `文件:行` 出处，判据 3 即不命中。

论证：把"查不到卡片"读成"说不清"，会让每个刚起步、卡片还没攒起来的项目都被判成说不清，从而无差别升级到完整流程——那条路上的每一步开销都还在，收益却是零，最后的结果是没人再肯照判据走。

## 总纲 §默认倾向 — 为什么 MUST NOT 跳过 find-scenes 直接 discover

总纲的结论是：按 `代码事实纪律.md` §3 的顺序先 `ctx find-scenes` 再 `ctx discover`。

论证：跨服务需求直接钻单个 card，最常见的失败就是漏掉链路上的其它服务——全景没取，后面每一步都在一个被截断的图上做判断。

## 总纲 §兼容取舍确认门 — 为什么兼容不是默认项

总纲的结论是：兼容是业务取舍，不是技术选择，必须每次由人拍板，AI 在任何项目形态下都 MUST NOT 自行默认。

论证：无条件保留旧行为会让包袱永久累积，无条件砍掉又可能打伤还在用旧口径的人。两个方向的代价都落在业务上，而 AI 手里没有判定这个代价的信息。

## 总纲 §代码评审门 — D 文档轴为什么恒跑、子代理 prompt 为什么要点名加载

总纲的结论是：D 文档轴恒跑，MUST NOT 由主会话先判"本次有没有碰文档"再决定派不派；子代理 prompt 必须点名加载 ai-dev-workflow skill。

论证：判断有没有触碰文档本身就是盘点，而盘点正是该轴的第一步——让主会话先判，等于把最容易漏的判断交给最容易漏的人。点名加载则是因为评审者要和实现者守同一套纪律，而靠关键词自动触发不可靠。

## 总纲 §七条"不裁剪"护栏 — 为什么全部写成否定式

总纲的结论是：七条护栏在任何协作面、有没有代码图谱、任何分流路径下都 MUST NOT 被裁剪。

论证：Triage 可以让小改动走得快，协作面可以砍掉对齐开销，代码图谱可以让检索更快——正因为体系里到处都是合法的"可以更轻"，才需要一组写成否定式的兜底。它们要阻断的是同一条推断：**"这次改动很小 / 就我一个人 / 这项目没那么正式，所以可以省"**。

## 总纲 §七条"不裁剪"护栏 第 7 条 — 补卡为什么不能顺延

总纲的结论是：本次为推进任务而读了源码的模块，MUST 在本次任务内把卡片补上并随分支提交。

论证：补卡跳过一次，下一个零上下文 agent 就要把同样的源码重读一遍——代码事实层的价值正是在这里被一次次抵消掉的。顺延即等于没执行，因为下一次任务同样有"这次改动很小"的理由。

## 总纲 §按边界拆 — PR 粒度为什么与人数无关

总纲的结论是：一个 coding plan 任务 SHOULD 对应一个约 3–8 文件的 PR 或提交，这条与人数无关。

论证：agent 单次可产出上千行改动，粒度限制是人类审阅者（以及下一个零上下文 agent）唯一的审查窗口。窗口大小由人的阅读能力决定，不由项目里有几个人决定。
