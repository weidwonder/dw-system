# PRD 复核门（组稿后、落盘确认门前的双轴子代理复核）

- **Issue / 链接**：N/A（对话中提出）
- **Owner**：weidwonder
- **写作进度**：Done
- **Triage 复核**：AI/LLM 行为？否 鉴权/安全/设备？否 跨服务/迁移/不可逆？否 指标/规则/对外承诺？**borderline → 判否**
  - borderline 说明：本次新增一道门，会改变已安装项目的行为契约（`ai-prd` 组稿链路多一步、成稿前多一次子代理开销），第 4 问倾向"是"。判否的理由是它与 `2026-08-10-文档生命周期门控` 同类——**纯 markdown 纪律的新增门，不触碰任何可执行代码、无数据迁移、无不可逆动作**，靠 VERSION bump + migration 指南即可让存量用户知情。这一页 hold 得住；hold 不住的信号是"复核轴需要新的机器判据或新的 CLI 子命令"，那时升级到完整 spec。

## 问题

`ai-prd` 成稿前只有一道 `prd质量清单.md`，它有两个结构性盲区：

1. **参照物只有模板骨架和写作纪律**。78 行清单查的全是"节缺没缺、验收可不可判定、占位符清没清、落位对不对"，**没有任何一项拿 PRD 去跟现有系统比对**。于是这类问题一路穿到下游：要做的能力 registry 里其实已经有了、新规则与已生效的业务规则矛盾却没进改动范围、PRD 假设的依赖其实已废弃、非目标写着"不改 X"而要做的事必然波及 X。它们在 Overview 或编码阶段才显形，那时返工成本已经翻了几倍。

2. **它是主会话自检**。PRD 的现状节是主会话自己查卡片写的，让同一个会话验"我查得对不对"等于没验；而且它刚跟用户来回四批提问，最容易把用户的口述当成系统事实。这与 `ai-dev-workflow` 已经想明白的那件事同构——`代码评审纪律.md` §为什么必须交给子代理：写的人被自己的叙事浸透，会替自己辩护。PRD 侧一直缺这一层。

## 目标

在组稿完成后、落盘确认门之前插入一道**双轴子代理复核门**：一轴查 PRD 内部自洽，一轴查 PRD 与现有系统的功能/约束冲突；结论分三个出口——能自己补的当场改稿，事实层面错了的回流到对应那一批重取证，需要用户拍板的进落盘确认门的回述清单。

## 范围

纯 markdown 纪律改动，不涉及 `ctx` CLI、`install.mjs` 与任何可执行代码。

### A. 两条轴（参照物互斥）

| 轴 | 参照物 | 查什么 |
|---|---|---|
| **甲 · 自洽轴** | PRD 自身（含 UI 原型） | 内部矛盾与不可执行：目标与非目标打架、验收项与详细行为节打架、UI 原型与正文冲突、零上下文下游能不能不回头问就动手 |
| **乙 · 冲突轴** | `engineering-context/` 卡片 + 源码 + `docs/REQUIREMENTS.md` + 现行索引 | 功能已存在 / 行为矛盾 / 约束违反 / 依赖已废弃 / 现状失实 / 非目标其实挡不住 |

切法沿用 `代码评审纪律.md` 三轴的同一个框架——**每轴一个参照物**，所以两轴天然不重叠，也不与 `prd质量清单.md`（参照物是模板骨架）重叠。

### B. 位置：落盘确认门**之前**

插在 `00-prd生成流程.md` §组稿 第 3 步（跑质量清单）与原第 4 步（落盘确认门）之间，原 4–7 步顺延为 5–8。

这是本次设计里最关键的判断，两条理由：

- 落盘确认门要用户拍板，**复核结论必须先到用户手里**——乙轴发现的冲突几乎全是需要用户决策的东西（"系统现在是 A，你要的是 B，那 A 改不改"），先拍板后复核等于让用户在信息不全时确认。
- 落盘之后再查更晚：文件已进 `docs/spec/` 与 `docs/index.md`，下游 `ai-dev-workflow` 可能已经开跑。

### C. 分流与降级（照抄评审门的完整/Lean 分档）

- `change-prd` / `product-prd` → **2 个并行子代理**，各返回一份报告。
- `lite-issue-prd`（Triage 四项全否的单点改动）→ **1 个子代理**跑两轴精简版，报告仍分两节写。
- harness 不支持子代理 → 主会话**分轮**执行，一轴一轮。

### D. 三个出口的处置

复核结论 MUST 分流，这是与代码评审门最大的不同（代码侧的问题 AI 自己就能修，PRD 侧很多修不了）。分流判据一句话：**事实错了回去补，取舍待定才给用户**。

- **当场改稿**（内部矛盾、缺 cite、验收表述不可判定、原型与正文不一致）→ 直接改稿，改完在报告里标已修。
- **回流到某一批**（现状节条目失实、验收项落不到任何一条详细行为）→ 按 `question-bank.md` 的 `[组稿·复核后]` 条目回批 B 重新取证或回批 D 补齐。
- **需要用户拍板的**（与现有系统的取舍冲突）→ MUST 逐条并入落盘确认门的回述清单，**MUST NOT 自己替用户选**，也 MUST NOT 悄悄降级成"开放问题"塞进 PRD 了事。

> **为什么是三个而不是两个**（实现期改判，2026-08-19）：起草时只设了"改稿"与"给用户"两个出口，写 prompt 模板时发现第五类冲突（现状失实）两边都不该去——它不是改措辞能解决的，也不该摆给用户当取舍：用户此刻手里没有卡片也没有源码，只能点头。于是拆出第三个出口，判据落在 `question-bank.md` 的 `[组稿·复核后]` 条目上。

### E. 取证纪律（防止子代理瞎报冲突）

乙轴每条冲突 MUST 带出处（卡片 cite 或 `文件:行`），无出处的冲突指控视为幻觉。反向同样约束：**查不到 MUST NOT 报成冲突**——查不到只意味着这个模块的卡片还没建，处置是读源码；两条路都取不到证时写进「未能取证」段，MUST NOT 转成冲突结论。

## 影响范围 / 不做什么

- 影响：只影响 `ai-prd` 的组稿收尾链路。`ai-dev-workflow` 侧零改动。
- **不做**：
  - 不动 `prd质量清单.md` 的既有勾验项——复核门是**新增**的独立门，不是把清单改造成子代理跑（清单在组稿时给主会话当写作辅助仍然有价值）。

## 验收标准（可判定，含边界/失败用例）

- [ ] 正常路径：对一个 brownfield 变更需求跑 `ai-prd`，组稿后**先**出现两份复核报告（甲/乙各一节），**再**进落盘确认门；报告里的"需用户拍板"条目出现在落盘门的回述清单里。
- [ ] 边界用例：`lite-issue-prd` 分流下只派 1 个子代理，报告仍分两节，MUST NOT 合并成一段总评。
- [ ] 边界用例：项目 `engineering-context/` 只有 `【】` 占位行（正常起步状态）时，乙轴 MUST NOT 报"无法复核"或"资产缺失"，而是走读源码取证；确实取不到证的写进「未能取证」段。
- [ ] 失败用例：子代理报出一条无 cite、无 `文件:行` 的冲突时，该条 MUST 被判为幻觉并剔除，不得进落盘回述清单。
- [ ] 失败用例：harness 不支持子代理时降级为主会话分轮，一轴一轮，MUST NOT 合并成一次"总体看看"。
- [ ] 交叉引用一致：`SKILL.md`、`00-prd生成流程.md`、`prd质量清单.md`、两个 `collab/` 分册对复核门的描述互不矛盾，步骤编号全仓无残留旧号。
