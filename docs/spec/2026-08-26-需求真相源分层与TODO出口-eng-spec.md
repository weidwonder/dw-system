# ai-dev-system_技术 Spec — 需求真相源分层与 TODO 出口

## 0. 阅读导引（MUST，前置）

- **一句话目的**：让需求真相源变成一份**只描述 main 分支当前现状**的薄快照 + 一级子模块细则，并给"还没做的事"一个固定出口 `docs/TODO.md`，使"改了已有功能的行为规则"这类最常见的迭代不再在准出归并时被静默丢弃。

- **端到端场景**：
  1. 迭代把"错题重练每天上限 3 次"改成 5 次。功能清单状态位不动、旅程不变、指标不变。准出归并时，AI 按新的落点映射判定这是"已交付能力的行为契约变更"，到 `docs/requirements/错题重练.md` 就地把 3 改成 5，不留"原为 3 次"的痕迹；变更 PRD 随即转 `merged` 进归档索引。
  2. 项目此前只有 `docs/index.md` 充当需求真相源。本次有一条用户可感知的规则要归并，而目录页装不下。AI 当场创建 `docs/REQUIREMENTS.md`，把规则写进去，并更新 `docs/index.md` 指向它。
  3. 写 spec 时冒出"以后应该支持批量导出"，属模块层面、本次不做。AI 当场往 `docs/TODO.md` 的〈想做的功能〉章节追加一条并记下 2026-08-26。半年后某次准出扫描时提示用户"这条已过 3 个月，还留着吗"，用户不点头就不删。
  4. 迭代只是把一个变量改名、清掉一行死代码。**不进 TODO、不触发任何归并**——它既不改变用户可感知行为，也不动模块边界。

- **核心流程图**：

  ```mermaid
  flowchart TD
    A[需求验收通过，进入准出门] --> B{本次改变了什么}
    B -->|新增/去掉一个功能| C[主文档功能清单增删一行<br/>+ 建或删对应子模块文档]
    B -->|已交付功能的行为规则变了| D[对应子模块文档就地改写<br/>不留前后对比]
    B -->|用户怎么用变了| E[主文档旅程节回填]
    B -->|冒出但本次不做| F{够不够格}
    F -->|影响功能或模块层面| G[写入 docs/TODO.md<br/>记提出日期]
    F -->|局部小事| H[不写]
    B -->|本次做掉了 TODO 里的条目| I[删掉那条]
    C --> J{主文档有无对应承载}
    D --> J
    J -->|真相源只有目录页| K[当场创建 docs/REQUIREMENTS.md]
    J -->|已有主文档| L[完成归并]
    K --> L
  ```

- **决策表**：

  | 本次改动 | 落点 | 主文档动不动 |
  |---|---|---|
  | 新增一个功能 | 主文档清单 + 新建子模块文档 | 动 |
  | 去掉一个功能 | 主文档清单删行 + 删子模块文档 | 动 |
  | 已交付功能的行为规则变了 | 对应子模块文档就地改写 | 不动 |
  | 用户旅程 / 成功指标变了 | 主文档对应节 | 动 |
  | 明确不做什么变了 | 主文档非目标节 | 动 |
  | 服务质量要求变了 | 主文档服务质量节 | 动 |
  | 冒出但本次不做（够格）| `docs/TODO.md` | 不动 |
  | 局部小事（改名、清死代码、补测试）| 无落点 | 不动 |

## 1. 范围

- 本仓库做什么：改 `ai-prd` 与 `ai-dev-workflow` 两个 skill 的判据、模板与机器闸，使需求真相源的**定位、承载形态、更新动作**三者一致；新增 `docs/TODO.md` 这一类文档的约定；并按新规矩改造本仓库自身的文档体系。
- **不做什么**：不改 `ctx` CLI 的任何命令行为（`requirement-reachable` 的判定逻辑不变，仍只验可达性）；不改代码事实层（cards/registry）的任何判据；不为存量项目提供自动迁移脚本。

### 1.1 功能需求（MUST 编号）

| 编号 | 需求 |
|---|---|
| FR-001 | 需求真相源的定位收窄为：只描述 main 分支**已实现**的现状，回答"项目是什么、为什么做"；MUST NOT 包含任何历史记载、前后对比、技术选型、需求调整过程 |
| FR-002 | 需求真相源分两层承载：主文档 `docs/REQUIREMENTS.md` + 一级子模块 `docs/requirements/<模块>.md`；MUST NOT 再往下分层 |
| FR-003 | 子模块的划分方式（按什么切、切成哪几块）MUST 在主文档中显式定义 |
| FR-004 | 拆分阈值：主文档 <500 行时 SHOULD NOT 拆；>800 行时 SHOULD 拆；500–800 行由作者判断 |
| FR-005 | 用户可感知的具体行为规则（次数上限、权限范围、报错口径等）写进子模块文档；主文档只写"有哪些功能"，每条一句话并链到子模块 |
| FR-006 | 新增 `docs/TODO.md` 作为项目内"还没做的事"的唯一出口，章节按类型分：想做的功能 / 待澄清的问题 / 已知风险 / 技术欠账 |
| FR-007 | `TODO.md` 每条 MUST 带提出日期（YYYY-MM-DD） |
| FR-008 | `TODO.md` 的准入门槛：只收会改变用户可感知行为、会新增或去掉一个功能、会动某个模块边界的条目；局部小事 MUST NOT 写入 |
| FR-009 | 陈旧提醒：条目提出日期距今超过 3 个月时 SHOULD 提示用户是否删除；AI MUST NOT 自行删除，删不删由用户决定；3 个月是默认值，项目可在 `TODO.md` 头部声明改写 |
| FR-010 | 准出归并动作从三个写死落点改为按口径类型分派的映射表（见 §0 决策表），并 MUST 声明「功能清单状态位无变化」MUST NOT 被读成「无需归并」 |
| FR-011 | 真相源承载在 `docs/index.md` 或 README 一节、而本次确有用户可感知规则要归并且无处安放时，MUST 当场创建 `docs/REQUIREMENTS.md`；平时 MUST NOT 强制创建 |
| FR-012 | 删除「影响产品范围的变更 MUST 先改需求真相源……最后才是 spec」这条与准出归并互斥的表述，统一为「MUST 先把需求写清楚再动代码，归并在准出门完成」 |
| FR-013 | `product-prd.md` 模板按 FR-001 重写：删除在做/未做状态位、Growth、Vision、开放问题、Risk Mitigation 五节；新增子模块划分声明节 |
| FR-014 | 新增 `assets/templates/requirements-module.md`（子模块文档模板）与 `assets/templates/todo.md`（TODO 模板）两份模板 |
| FR-015 | 本仓库自身 MUST 按 FR-001…FR-012 改造文档体系，取消 `docs/index.md:5` 的「本仓库没有 REQUIREMENTS.md」特例 |
| FR-016 | 新增机器闸 `test/requirements-layering.test.mjs`，覆盖本次的跨文件契约（落点映射表在三处同源出现、目录例外清单一致、两份新模板存在且被加载点清单引用、TODO 章节类型闭集一致） |
| FR-017 | 存量收敛规则：**触碰**定义为本次准出归并确实要**写入**该文件（只读、或被自动检查扫到都 MUST NOT 算触碰）。触碰时 MUST 当场删除该文件里的规划类章节并把内容移入 `docs/TODO.md`；主文档同时超过拆分阈值时 MUST 向用户提出拆分建议并由用户拍板，**MUST NOT 未经确认就自行拆分** |

**编号规则（MUST）**：前缀 + 三位零填充；永不复用、永不重排；删除的条目原地保留编号并改写成「**已撤销** —— 原因」。

## 8. 兼容取舍与替换

### 8.1 兼容取舍（已由用户于 2026-08-26 拍板）

**总口径：下次触碰就必须收敛**（用户选定）。"触碰"= 本次准出归并确实要写入该文件；只读或被自动检查扫到都不算。

| # | 取舍点 | 拍板结果 | 到期日 |
|---|---|---|---|
| 1 | 存量 `REQUIREMENTS.md` 含规划类章节 | 触碰时 MUST 当场删除并把内容移入 `docs/TODO.md` | 随触碰，无固定日期 |
| 2 | 存量项目没有 `TODO.md` | 第 1 条触发移出时 MUST 当场创建；无内容可移则不建 | 同上 |
| 3 | 存量 `REQUIREMENTS-appendix.md` | 触碰时 MUST 拆进 `docs/requirements/`；超阈值的拆分 MUST 先由用户拍板 | 同上 |
| 4 | 版本与迁移指南 | bump 至 2.8.0，**不新增迁移指南** | —— |

**第 4 条的依据**：迁移指南的判据是"升级当时需不需要用户动手"。本次升级当时零动作（重装即可，标记块字段不变、不要求回填存量文档），收敛发生在此后自然触碰的时刻，因此按 `CLAUDE.md` §版本管理「零手动动作的升级 MUST NOT 建迁移文件，更 MUST NOT 为了过闸补一份『需要的动作：无』的空指南」不建。

> **一处纠偏**：`CLAUDE.md` §版本管理 记载"四条既有断言目前无条件要求当前 VERSION 有同名指南、零手动动作的 bump 会让这四条一起判红"。**实测不成立**——这四条在 2.5.0 已各自改成条件式（`installer-migration` 用 `if (existsSync(guide))` 包住，另外三条都指向各自特性的**起始版本**如 `2.1.0.md` 而非当前 VERSION），bump 到 2.8.0 后四份测试 44 项全绿。因此本次**不需要改动这四份测试**，改为一并修正 `CLAUDE.md` 那段过时记载（属 §3 权威面第 8 类「流程与门禁契约」，该记载描述的正是门禁行为）。

**为什么拆分档要用户拍板而删章节档不用**：删规划节 + 移进 TODO 是分钟级动作，且不做的话真相源当场违反 FR-001；而一份上千行的存量主文档拆子模块是小时级工程，会把一个改阈值的小迭代变成文档大重构。两档都 MUST 做，只有拆分那档 MUST 先问。

§7 保留例外与 §8.1 第 1–3 行同为"随触碰生效、无固定日期"，两处口径一致，无冲突。
