## 背景：现在的复核门是怎么工作的

dw-prd 写完 PRD、用户定稿之后，会派评审子代理复核，分两条轴：

- **冲突轴**：拿 PRD 去对照现有系统，查新需求和系统里已有的功能、规则、约束有没有冲突。
- **自洽轴**：只看 PRD 本身，查它内部有没有前后矛盾，以及一个没参与讨论的下游实现者拿到这份 PRD 能不能直接动手、不必回头追问。

自洽轴目前明确要求子代理做的比较只有四项：

1. 目标里要做的事，有没有被非目标挡住。
2. 每条验收标准，能不能在"详细业务行为"里找到对应的行为描述。
3. 一句话结论里写的"做完的标志"，和验收标准说的是不是同一件事。
4. UI 原型里画出来的页面和状态，和正文对界面的描述是否一致。

## 现在的问题

1. **边缘情况没有第三方检查。** 特殊场景只在写 PRD 时由写作者按六个固定类别（多人同时操作、信息迟到、前置条件不满足、处理失败、业务过期、跨阶段继续）逐类填写。写作者对自己写的东西有盲区，而复核子代理并不检查这一块。PRD 自己引入的状态、角色、信息项会带来哪些具体的边缘情况，更没有人去推导。
2. **安全没有第三方检查。** 冲突轴只能发现"违反了系统已有的权限约束"。PRD 自己新定的权限规则是否前后一致、有没有人能借新功能做坏事，没有人检查。全新产品没有既有约束可对照，这类问题就完全落空。
3. **查出缺口后没有正确的去处。** 如果复核发现"某个场景该怎么处理没写"，这是要用户决定的业务问题，应该回到批 C（细节批）去问用户。但现在回流出口只能退回批 B（现状）或批 D（验收），结果要么由 AI 自己替用户定行为，要么被塞进错误的批次。
4. **PRD 的可读性没有要求。** 写作纪律里没有"写清楚"这一条。PRD 可能写满只有作者能解码的缩写，例如"A↔B"、"上述三种"、未定义的简称。读 PRD 的可能是其他人或其他 agent，他们只能猜。
5. **原型可能带出真实个人信息。** 写 PRD 时要求原型使用"真实示例数据"，而原型文件会随 PRD 提交进代码仓库。

## 要达到的效果

总原则：**写 PRD 阶段不新增"请考虑某某情形"的提示。** 边缘情况和安全由自洽轴的评审子代理在复核时找出来，并以**向用户提问**的方式交回，由用户决定怎么处理。

- **FR-001 自洽轴增加六项内部比较。** 子代理除现有四项外，还要检查：
  1. 特殊场景表和核心规则里写的每一种处理方式，验收标准里是否都有对应的验收项。
  2. 某个场景标了"不适用"并给了理由时，这个理由和正文是否矛盾。例如写"不存在多人同时操作，因为只有一个人使用"，正文却描述了多个角色协作。
  3. "不改的现有业务"里承诺不动的东西，详细业务行为里是否又改了它。
  4. 风险的兜底方案是否和非目标冲突，或者引入了详细业务行为里没写的新行为。
  5. 含智能能力时，AI 能力卡写的自主程度和允许行为，是否和详细业务行为一致。例如能力卡写"只给建议"，正文却写它会自动执行。
  6. 信息项里写的"谁能查看、谁能修改"，和原型里各角色能看到的按钮与内容、以及验收标准里的权限场景是否一致。

- **FR-002 自洽轴主动推导 PRD 没覆盖的边缘情况与安全问题，并整理成问题交给用户。** 子代理从 PRD 自己写出来的内容出发去推导，不套固定清单：
  - PRD 新增的每个状态：怎么进入、怎么离开、能不能撤销或回退。
  - PRD 新增的每个信息项：没填、填得超出上限、事后被修改时，系统该怎么办。
  - PRD 里的每个角色：没有权限的人尝试操作时看到什么。
  - 涉及数量的地方：0 个、1 个、达到上限、超过上限时分别怎么处理。
  - 上线那一刻：已经处在流程中途的旧数据怎么处理。
  - 有人故意钻空子：重复提交以多拿好处、冒用他人身份操作、看到不该看的别人的数据、通过导出、通知或分享链接把敏感信息带出去；含智能能力时，用户输入或外部内容里夹带指令，把智能能力带偏。

  **只报下游实现者必须自己猜才能动手的缺口。** 每条写成一个用户能直接回答的业务问题，例如"同一个人连续点两次'领取'，应该领到一份还是两份？"。缺的是关键场景的处理（实现者猜错会做出错误的东西）时算 P1，其余算 P2。PRD 里不涉及的类别（比如没有新状态）直接跳过，不报"不适用"，也不要求写作者补表格。

- **FR-003 增加"回流到批 C"出口。** FR-002 提出的问题，以及任何"处理方式没定、需要用户决定"的缺口，主会话 MUST 带回批 C 向用户提问，按用户的回答补进 PRD，并在落盘确认门里列出"定稿后改了什么"。主会话 MUST NOT 自己替用户定处理方式。子代理报告的"出口"列新增可选值【回流到批 C】。复核门仍然只有三个出口：当场改稿、回流到某一批、进落盘确认门。

- **FR-004 写清轻量 Issue PRD 的"两轴精简版"是什么意思。** 精简的是比较范围：两条轴只对照这份轻量 PRD 实际有的章节（改动点表、场景与预期表等）。FR-002 的推导和提问照做，不精简。

- **FR-005 PRD 写作纪律新增一条，原文采用用户原话，不加举例和解释：**

  > 使用 dw-prd 的时候，我们输出的 PRD 一定要保证 PRD 的每个特征的描述都足够清楚、没有歧义、且不需要额外解释，而且保持简朴精炼。这个原则非常重要，因为读取你 PRD 的并不一定是你，可能是其他人或者 agent。

  自洽轴同步按这一条检查 PRD；发现不符合的描述作为问题报告，出口为"当场改稿"。

- **FR-006 原型示例数据改为"仿真示例数据"。** 原型里的数据要像真实业务，但 MUST NOT 包含真实的个人或客户信息，因为原型文件会提交进代码仓库。质量清单里的 UI 原型那一条同步加上这一点。

- **FR-007 过稿时附一段要点讲解。** 请用户过 PRD 过稿门（dw-prd 组稿第 4 步）和 spec 过稿门（dw-workflow 的确认门）时，除了交出文档全文，还 MUST 用业务语言把文档的重点内容讲一遍；spec 里有技术方案的，把技术方案也讲一遍。目的是用户不想逐字读文档时，凭这段讲解就能直接过稿。spec 过稿门现有的"不请用户确认文件、函数、存储、框架等选择"保持不变：讲技术方案是让用户知道打算怎么做，不是把它摆成选项让用户挑。

## 不做什么

- 不在写 PRD 的四批提问和质量清单里新增"请考虑某某情形"的提示。批 C 现有的六类特殊场景保持原样。
- 不给 PRD 模板新增章节。
- 不改冲突轴。
- 不改 `dw-prd/SKILL.md`。它的体积上限已冻结，而且入口只写到"派子代理跑双轴复核"，具体检查什么本来就写在 `prd复核纪律.md` 里。
