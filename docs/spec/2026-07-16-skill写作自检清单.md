# Skill 写作自检清单（维护本仓库 skill markdown 时使用）

> 适用对象：`ai-dev-system/skills/` 下所有 SKILL.md、references/、assets/ 模板——它们是 skill 的"源码"。
> 来源：吸收 mattpocock/skills 的 writing-great-skills 元方法论，按本仓库约定改造。改任何 skill 文档前后各过一遍。

## 1. 根本德性：可预测性

好 skill 追求**同一过程**，不是同一产出——同样输入下，任何模型应走同样的步骤、查同样的来源、守同样的门禁；产出内容可以随项目不同。自检：这段指令是否描述了"怎么做"的过程，而不是给了一段"照抄进产出"的示例答案？

## 2. 信息层级（三级阶梯）

- **SKILL.md**：入口。只放触发条件、路由逻辑、纪律摘要与指针——读完知道"何时用、先做什么、细节在哪"。
- **references/**：过程与纪律的完整定义。SKILL.md 里的每条摘要必须能在这里找到展开。
- **assets/**：产物骨架（模板/片段）。只放"要生成的东西长什么样"，不放流程指令。

自检：内容放错层了吗？（SKILL.md 里长篇展开 = 该下沉；模板里出现流程指令 = 该上移。）

## 3. 渐进披露

不是每次调用都需要全部内容。判某一节归哪儿有一套固定顺序（**判据分配算法**，权威定义在 `2026-08-23-渐进式披露与需求追溯-eng-spec.md` §4.1）：**路由到分流之间就要用 → 归入口**；**每一步都要用、与走哪条路径哪道门无关 → 归常驻**；**适用于 Lean → 要点进 Lean 自足册**；**有明确触发点 → 进 `SKILL.md` 的〈加载点清单〉**；四步都不成立的小节没有存在理由，MUST 报为设计缺陷、MUST NOT 塞进常驻兜底。

据此的自检：

- **按需加载的分册 MUST 在入口写清加载条件**——`collab/` 协作面看标记块字段，`capability/graph.md` 看运行时探测结果，`core/engineering-context设计.md` 看本次要不要动资产结构，其余分册各自在〈加载点清单〉里占一行（`触发条件` / `加载对象` / `为什么此刻需要` / `适用路径` 四个字段齐全）。**新增 `ai-dev-workflow/references/` 下任何一篇纪律，MUST 同时在〈加载点清单〉加一行**；写不出触发条件就说明它不该独立成篇——没有加载点的分册永远不会被读到，只是死文件。
- **"常驻"MUST NOT 被读成"每次唤起都整篇读"**——常驻说的是"哪几份构成完整流程的基本盘"，不是"什么时候读"。常驻篇内部仍按小节分**前置**与**触发式**（`00-流程总纲.md` 与 `代码事实纪律.md` 每个小节标题下的 `> **何时读本节**` 行）。因此**给一篇常驻文件的某几节标触发式是合规的**，MUST NOT 因为"这篇是常驻的"就判它违规。（本条 2.5.0 改：此前写的是"无条件常驻的 MUST NOT 写成有条件"，那句在按节加载之前成立，之后会把合规的按节标注判成违规。）
- **标加载时机 MUST 用非规范措辞**——给一个原本没有 MUST 的小节添上规范词，等于给它新增一条 Lean 自足册的覆盖义务（覆盖率检查按"小节含 MUST"动态算必覆盖集）。
- 无条件全文粘贴会挤占聪明区（见 `上下文卫生.md`）。

## 4. Leading words：借模型已有的强概念

命名纪律时优先复用模型预训练里语义浓度高的词（红/绿、seam、tracer bullet、聪明区、护栏、门禁），一个准确的词能省一段解释、并把行为锚定到正确联想上。自检：这段冗长的解释能否被一个既有强概念替代？（反向也要防：借来的词若与本仓库既有术语冲突，必须显式定义——遵循 glossary 的"说法一致"原则。）

## 5. 六大失败模式（每次改动后对照扫一遍）

| 失败模式 | 症状 | 自检问题 |
|---|---|---|
| **提前完工** | 模型走完前半流程就认为"够了"，跳过收尾门 | 每个流程是否有显式的"完成判据/准出门"？（如红回路"真实跑过一次"、PRD"质量清单过 gate"） |
| **重复堆叠** | 同一条纪律在多处用不同措辞重复，改一处漏一处 | 新增内容是否与既有条目重复？重复的收敛为一处 + 指针 |
| **沉积** | 历次修补层层叠加，新旧规则并存互相矛盾 | 本次新增是否与旧条款冲突？冲突的删旧，不留"两个版本都在" |
| **蔓延** | 文档越写越长，核心纪律被细节淹没 | 这条内容值得占入口层篇幅吗？能否下沉 references/ 或删除 |
| **空转** | 指令说了"要注意 X"但没给可执行动作 | 每条纪律是否有动词 + 判据？（"注意质量"→失败；"跑 `node --test` 全绿"→合格） |
| **否定依赖** | 只说"不要做 X"，模型仍被 X 吸引 | 每条禁止是否配了正向替代？（"禁止 grep 旧代码"必须跟着"先 `ctx discover`"） |

## 6. 本仓库附加约定

- 中文正文 + 英文术语原形；RFC 2119 关键词大写。
- 新增/改名 `ai-dev-workflow/references/` 下的文件时同步：**`SKILL.md` 的〈加载点清单〉**（新增一篇 MUST 加一行，改名 MUST 同改该行的「加载对象」列）、`00-流程总纲.md` 引用、模板内指针、`CLAUDE.md`（若涉及）。（2.5.0 改：此前这里写的是"`SKILL.md` 目录树与篇数"，那两小节已从 `ai-dev-workflow/SKILL.md` 删除，入口现在只剩工作区隔离门要点 / 路由逻辑 / 加载点清单 / 关键纪律。`ai-prd/SKILL.md` 仍有目录结构小节，改那侧的 references 时同步它。）
- 改小节标题前先查有没有机器闸拿它当锚点（如 `test/lean-selfcontained.test.mjs` 的 `EXCLUDED` 逐字匹配标题），有就同改测试里的映射。
- 模板改动对照设计文档的覆盖度映射（如 change-prd ↔ `2026-07-06-ai-prd-design.md §7`），别丢节。
- 发布前 `./install.mjs <测试目录> --source-dir=. --dry-run` 验证 skill 仍可被安装器发现。
