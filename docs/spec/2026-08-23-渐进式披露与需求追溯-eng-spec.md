## 0. 阅读导引（MUST，前置）

- **一句话目的**：这份 spec 让 `ai-dev-workflow` 从"每次唤起先把七篇纪律全背下来"改成"什么都不预先背，每份判据在它真正要用的那一刻才取、且只取那一节"，同时给 spec 的需求装上能贯通到测试的编号。

- **端到端场景**：
  1. **最窄 Lean**：开发者提一个改三行的需求 → AI **分流前只取三份**（入口含工作区隔离门要点 + `用户沟通纪律.md` + `00-流程总纲.md` §Step 0）→ 建 worktree → Triage 四问全否 → 取 §默认倾向 判未升级 → **分流后**只加载 Lean 自足册前置节 + 协作面分册 + lean spec 模板 → 写带 `FR-###` 编号的一页 spec → 兼容门 → 实现 → 过评审门时才追加 `代码评审纪律.md` 的四节 → 合并。**全程未加载 `代码事实纪律.md`、`上下文卫生.md` 与总纲 §Step 0／§默认倾向 之外的任何常驻内容**——这三处由自足册的投影（§3／§12／其余各节）替代。**走到 §7 清单里带 `(L§x)` 的行时同样是替代不是叠加**：兼容取舍取自足册 §6.1、替换清单取 §4.3、写 spec 与交接取 §4.2、评审门取 §9、完成门取 §11，取了自足册那一节就 **MUST NOT 再取本行原篇**——只有该节自己写明的"要展开／要细则"条件命中才升级去取。
     > **真跑验收（Task 13）修正**：本条原写作「全程未加载任何常驻篇」，与当时的入口实现（路由第 3 步在 Triage **之前**就把常驻六份一次灌完）互相矛盾，实测最窄 Lean 加载 101,923 字节、同一批判据读了两遍。修正后的分两批加载见 §4.1 与 §7 的〈每次唤起（分流前）〉〈Triage 四问全否〉〈Triage 任一为是〉三行。
     > **真跑验收（Task 13）第二次修正**：本条与 §7 清单此前把 Lean 与自足册的关系写成"另加"，于是 Lean 在每个带 `(L§x)` 的行上把同一批判据读两遍——实测**含文档结算的 Lean 反而高于改造前基线**（执行者实测 133,903 vs 133,545，+0.3%）。改正为**替代 + 二级触发**，并补计每次 Lean 必然触发的三道门（自足册 §2 + §9 + §11 = 18,791，上一版 77,420 漏计、偏乐观）。新核算见 §7。
  2. **bug 类 Lean**：同上，但 Triage 后命中红回路门 → 此刻才取**自足册 §3bis**（966 字节）代替 `bug诊断纪律.md`；只有该节写明的"这一步要展开"命中，才再取 `bug诊断纪律.md` 原篇。不命中红回路门的任务永远不为这两份付上下文成本。
  3. **完整流程**：Triage 任一为是 → 在分流前那三份之上补齐常驻余下三份 + 总纲其余前置节，再取 `步骤-1-7` → 写 `eng-spec` 时每条需求编 `FR-###`、每条验收编 `AC-###` → coding-plan 每个任务标 `满足: FR-003, FR-007` → 评审门忠实轴据此产出覆盖矩阵（哪条需求零任务 = 漏做，哪个任务无需求 = 镀金）→ test-spec §6 复用同一套号。
  4. **异常：存量无编号 spec**：忠实轴发现 spec 没有 `FR-###` → 自动退回自然语言逐条对照，并在报告顶部写明"本次未跑覆盖矩阵：spec 无编号" → 不报缺陷、不阻断。

> **FR-014 是实现阶段新增的（2026-08-24，轻量复核的忠实轴按「镀金」报出后登记）**：它不在原 PRD 与本 spec 定稿时的范围内。补它而不是把那批产物划进「不做什么」，判据是**它们已经落盘并改变了本体系的行为契约**——三条闸会拦别人的提交，两条纪律会改别人的派发方式，这种东西 MUST 有编号可追溯，MUST NOT 以"顺手加的"名义游离在追溯体系外。这也正是本次自己引入的 `FR-###` 贯通能力第一次被用在**它自己新增的内容**上：忠实轴的覆盖矩阵抓到"有产物无编号"就报镀金，机制按设计生效了。**MUST NOT 把这条读成"实现阶段可以随意加需求"**——补编号的前件是"已落盘且改变行为契约"，不是"做了就补"。

> **FR-002 的度量对象在代码评审门被改写（2026-08-23，忠实轴发现）**：原文与 AC-003 都写作「常驻 6 篇**合计** ≤ 50,000 字节」，按字面**不成立**——`test/resident-budget.test.mjs` 打印的六份整篇合计一直在 6 万字节以上。**原口径本身不可达**，不是精简没做够：即便执行 §5 错误处理表规定的下一顺位（把 `代码事实纪律.md` 物理拆成常驻要点 + 延后细则，该表预估 −6,550），整篇合计减掉这一刀之后仍 > 50,000。而实现从措辞精简那一轮起用的一直是**前置量**口径——按节加载之下，常驻六份**没有任何一次真实加载会读完整篇**（触发式节要等各自的触发点，多数触发点在单次任务里根本不命中），整篇合计因此不对应任何一次真实的上下文占用，拿它当门槛既高估成本，也会诱导用"删内容"而不是"标对加载时机"去过闸。**改了度量对象却没回填需求文本，是本次唯一一处这样的地方**，此处按实际口径回填，AC-003 与 §7 同改。两条 MUST NOT：**MUST NOT 把实现改回整篇口径**（那是一个已证明不可达的目标值，而 §5 明令 MUST NOT 下调目标值）；**MUST NOT 在任何文档正文里另抄一份手算的前置量**——这个量此前被四份文档各手算一遍、漂成四个互不相同的值（45,260 / 45,286 / 45,290 / 45,292），根因就是各算各的，现在算法只写死在那条闸里，文档一律引用它的输出。

> **FR-006 的范围在代码评审门被收窄（2026-08-23，忠实轴发现）**：原文写作「对本 skill **全部** references 与 assets 做一遍措辞精简」，实测有 11 份 markdown 一次没改——`文档治理.md`、`spec写作纪律.md`、`步骤-8-10-测试.md`、`bug诊断纪律.md`、`测试资产纪律.md`、`AI-LLM-overlay.md`、`engineering-context设计.md`、`环境冲突扫描.md`、`文档归档与账本收敛.md`、`assets/context-layer/` 各模板、`assets/templates/{overview,test-spec,test-coverage}.md`。**处置是收窄范围而不是补做**，判据：这些文件全都**不在常驻集合里**，压它们一个字节也不改善任何一次真实加载量（它们本就按加载点清单在触发时才取，多数触发点单次任务不命中），而措辞精简是有风险的操作——每改一份都要过一遍 §4.2 的红线四条。**留作后续版本**：真要做，判据是"该文件的触发频率高到它的体积开始影响单次任务"，而不是"名单上还剩几份没改"。收窄的代价是 FR-006 覆盖面变小，**MUST NOT 被读成"这些文件的措辞可以随便长"**——它们仍受 §6 Invariant 1/2 的红线闸约束。同时给 FR-006 补一条能判"做没做"的验收项 AC-023：原有的 AC-007 只查红线**不减少**，一个字没改的文件也照样为绿，查不出做没做。


### 4.2 措辞精简算法

对每个被改文件，按下列顺序处理，**顺序不可颠倒**（先删可删的，再压缩，最后核对红线）：

```
1. 删除历史沿革论证（"2.1.0 为何取消分档"这类）→ 移入本仓库 docs/spec/
2. 合并重复表述（同一判据在同一文件里说两遍）
3. 把解释性散文改写成判据表（正反例进表格，附「为什么」列）
4. 删冗长论证从句（保留结论，删"因为…所以…"的展开）
5. 核对红线（§6 Invariant 1/2）：规范条数与判据例子条数不得减少
```

**红线四条**（MUST NOT 触碰）：①任何 MUST / MUST NOT / SHOULD / MAY 结论本身；②判据消歧的正反例；③`MUST NOT 被读成……` 的结论部分（可压其后的论证展开）；④交叉引用的目标文件名与小节名。

**FR-013 一并授权的两组护栏（`installer-migration.test.mjs` 新增）**：把无条件断言改成条件式会丢掉一半防线（"写了指南但写坏了"从此无人拦），因此 FR-013 **MUST** 同时补上这两组，缺一即视为放宽而非改判据形态——①`ai-dev-system/migrations/` 目录里的**每一份**指南都必须是合法版本号命名（`<x.y.z>.md`）、含〈需要的动作〉节、且 ≤45 行（安装器升级时会把它高亮全文打印，超一屏就没人读完）；②`ai-dev-system/VERSION` **MUST NOT 低于**目录里最高的那份指南的版本（写了指南却没 bump 到位，安装器永远不会把它打印给任何人看）。**MUST NOT 为了迎合旧断言补一份「需要的动作：无」的空指南**——安装器会把它高亮全文打印，等于训练用户忽略这块高亮，比没有更糟。
