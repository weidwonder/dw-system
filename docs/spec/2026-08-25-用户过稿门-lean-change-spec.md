## 改什么（现状 → 期望）

**现状**：`00-prd生成流程.md` §组稿 的顺序是「拼装 → 出原型 → 跑质量清单 → 复核门 → 落盘确认门 → 落盘」。PRD 与原型一写完，主会话就直接派双轴子代理跑复核；用户第一次被请求表态，是在复核之后的落盘确认门，而那道门回述的是**关键取舍与复核查出的冲突**，不是"你自己要的东西写对了没有"。

**期望**：在质量清单与复核门之间插一道**用户过稿门**，三门顺序变成 **用户过稿门 → 复核门 → 落盘确认门**。

- **FR-001**：组稿跑完 `prd质量清单.md` 后 MUST 先把 PRD 全文与（涉及 UI 时）原型交给用户读并请他提修改意见；**用户定稿之前 MUST NOT 派复核子代理**。
- **FR-002**：用户的每条意见 MUST 逐条落进稿子，或明确回"不改 + 一句话理由"，MUST NOT 默默忽略；意见改动触碰模板骨架时 MUST 重跑质量清单受影响项，再回本门，直到用户定稿。
- **FR-003**：过稿门的"怎样算定稿了"与落盘确认门的三条确认判据**共用同一套**（逐点回复或整体认可 / 只回一部分 / 没有回复），MUST NOT 另立一套；这两道门是全流程**仅有的两个**允许因等用户而挂起的点。
- **FR-004**：过稿门要用户真的打开原型，因此原型 MUST 以**预览副本**形式落在系统临时目录或用户明确指定的项目外位置，**MUST NOT 因为"用户要看"就提前写进 `docs/`**；正式文件仍在落盘那一步按既有命名重新写出。
- **FR-005**：落盘确认门 MUST 逐条列出**用户定稿之后稿子被改了什么**（复核门的当场改稿与回流改写）——用户定的是复核前那一版。
- **FR-006**：复核门既无「需用户拍板」条目、也无**实质性改稿**（改动了目标 / 非目标 / 现状结论 / 详细业务行为 / 验收项中任何一处即为实质性；只在现状节补出处标注这类纯取证补录不算）时，落盘确认门 MUST 退化为一句话告知并直接落盘，MUST NOT 要用户对同一份稿子点第二次头。
- **FR-007**：过稿门与落盘确认门 MUST NOT 互相顶替——前者的参照物是**用户自己的意图**，后者是**复核门交上来的待拍板冲突与关键取舍**。
- **FR-008**：组稿步骤由 1–8 顺延为 1–9，全仓指向各门的步骤号引用同步；`test/prd-review-gate.test.mjs` 的步骤号断言改为**按门名动态取号**，不再钉死数字。

## 为什么

复核报告是**针对某一版稿子**的。用户还没读过就派子代理，用户随后的意见会让整份报告作废——白跑两个子代理不是最坏的：最坏是主会话带着"这稿已经复核过了"的印象去接受大改，**改出来的那部分从头到尾没有被任何第三方视角看过**，而门禁账面上是"复核已过"。

反过来，复核门也不能挪到落盘确认门之后：那时文件已进 `docs/spec/` 与索引、下游可能已开跑，而冲突轴查出的东西几乎全要用户拍板。所以它的位置是**夹在两道用户门之间，两边都不能挪**。

代价是用户被打断两次。FR-006 的退化规则把这个代价收回去：复核零发现时第二次打断降级成一句话告知。

## 影响范围 / 不做什么

- **不动**双轴的参照物、六类冲突、三个出口的分流判据、取证足迹与补交接面规则——它们与门的位置正交。
- **不动**落盘命名、索引与归档规则、PRD 生命周期。
- **不动** `ai-dev-workflow` 侧的任何门（工程侧四道门与本次无关）。
- **不做**"把过稿门与落盘确认门合并成一道"：两者参照物不同（FR-007），合并会让用户在没看过复核结论时就替它们一起点头。
